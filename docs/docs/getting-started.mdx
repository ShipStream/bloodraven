# Getting Started

This guide walks through installing Bloodraven and creating your first `MysqlFailoverGroup`.

## Prerequisites

- Kubernetes 1.27+
- Helm 3.x
- Two sets of nodes, each labeled for a different site (see [Placement Contract](./placement-contract.mdx))
- [external-dns](https://github.com/kubernetes-sigs/external-dns) installed and configured for your DNS provider (Cloudflare, Route53, Google Cloud DNS, etc.)
- The `DNSEndpoint` CRD (`externaldns.k8s.io/v1alpha1`) installed in the cluster
- (Optional) cert-manager installed if you want automated TLS

## Install the operator

```bash
helm repo add bloodraven https://raw.githubusercontent.com/shipstream/bloodraven/gh-pages
helm install bloodraven bloodraven/bloodraven \
  -n bloodraven \
  --create-namespace
```

This deploys the `bloodraven` operator Deployment, the `MysqlFailoverGroup` CRD, and the necessary RBAC resources.

## Create secrets

### MySQL credentials (recommended: per-role secrets)

Create separate Secrets for each credential role. The operator will create MySQL users with appropriate privileges automatically:

```bash
# Operator credentials (required)
kubectl create secret generic mysql-operator-creds \
  -n default \
  --from-literal=username=bloodraven \
  --from-literal=password=operator-password \
  --from-literal=MYSQL_ROOT_PASSWORD=root-password

# Application credentials (optional)
kubectl create secret generic mysql-app-creds \
  -n default \
  --from-literal=username=app \
  --from-literal=password=app-password
```

### MySQL credentials (legacy: single DSN secret)

Alternatively, create a single Secret containing a MySQL DSN. All components share the same user:

```bash
kubectl create secret generic mysql-credentials \
  -n default \
  --from-literal=dsn='root:yourpassword@tcp(localhost:3306)/'
```

## Label nodes

The operator needs to know which nodes belong to which site. Label at least one node per site:

```bash
# Site: iad
kubectl label node node-iad-1 \
  shipstream.io/failover-group=orders \
  shipstream.io/site=iad

# Site: pdx
kubectl label node node-pdx-1 \
  shipstream.io/failover-group=orders \
  shipstream.io/site=pdx
```

See [Placement Contract](./placement-contract.mdx) for full details on node labeling requirements.

## Create a MysqlFailoverGroup

```yaml
apiVersion: shipstream.io/v1alpha1
kind: MysqlFailoverGroup
metadata:
  name: orders
  namespace: default
spec:
  image: mysql:9.6
  sidecarImage: ghcr.io/shipstream/bloodraven-sidecar:latest

  sites:
    - name: iad
      zone: us-east-1a
      lbIP: 10.0.1.1
      storage:
        storageClassName: fast-ssd
        size: 100Gi
    - name: pdx
      zone: us-west-2a
      lbIP: 10.0.2.1
      storage:
        storageClassName: fast-ssd
        size: 100Gi

  # Option 1: per-role credentials (recommended)
  credentials:
    operatorSecret: mysql-operator-creds
    appSecret: mysql-app-creds

  # Option 2: legacy single secret (mutually exclusive with credentials)
  # secretName: mysql-credentials

  dns:
    hostname: orders.az.example.com
    ttl: 60

  pollInterval: 2s
  failureThreshold: 3
  recoveryThreshold: 2
  failoverCooldown: 5m

  replication:
    maxLagSeconds: 300

  updateStrategy: OrderedUpdate
  cloneTimeout: 3600
```

Apply it:

```bash
kubectl apply -f orders-fg.yaml
```

## Verify

Check the status of the failover group:

```bash
kubectl get mysqlfailovergroups orders -o yaml
```

You should see `status.activeSite` set to one of your sites and both sites reporting their state:

```yaml
status:
  activeSite: iad
  sites:
    - name: iad
      state: writable
      replicating: false
    - name: pdx
      state: read-only
      replicating: true
      secondsBehindSource: 0
  conditions:
    - type: Ready
      status: "True"
    - type: Degraded
      status: "False"
```

You can also query the operator's status API:

```bash
kubectl port-forward -n bloodraven deploy/bloodraven 8082:8082
curl http://localhost:8082/status
```

## ArgoCD integration

By default, ArgoCD does not know how to assess the health of `MysqlFailoverGroup` or `MysqlBackup` custom resources — they will show **Unknown** in the ArgoCD UI. Bloodraven ships lua health check scripts in the chart's `argocd/` directory that teach ArgoCD to map CR status conditions to health states:

| CR | Condition / Field | ArgoCD Health |
|---|---|---|
| `MysqlFailoverGroup` | `Degraded=True`, `RecoveryPending=True`, or `Bootstrapping=True` with `reason=Failed` | **Degraded** |
| `MysqlFailoverGroup` | `Bootstrapping=True` (in progress) or `Updating=True` | **Progressing** |
| `MysqlFailoverGroup` | `Ready=True` | **Healthy** |
| `MysqlBackup` | `phase: Succeeded` | **Healthy** |
| `MysqlBackup` | `phase: Failed` | **Degraded** |
| `MysqlBackup` | `phase: Pending` or `Running` | **Progressing** |

### Option 1: Patch argocd-cm directly

Extract the chart and apply the patch file:

```bash
helm pull bloodraven/bloodraven --untar
kubectl patch configmap argocd-cm -n argocd \
  --patch-file bloodraven/argocd/argocd-cm-patch.yaml
```

Then restart the ArgoCD application controller to pick up the change:

```bash
kubectl rollout restart deployment argocd-application-controller -n argocd
```

### Option 2: ArgoCD Helm chart values

If you deploy ArgoCD via its Helm chart, extract the lua scripts from the Bloodraven chart and merge them into your ArgoCD values file:

```bash
helm pull bloodraven/bloodraven --untar
```

Then copy the contents of `bloodraven/argocd/health-mysqlfailovergroup.lua` and `bloodraven/argocd/health-mysqlbackup.lua` into your ArgoCD values:

```yaml
# argocd-values.yaml
configs:
  cm:
    resource.customizations.health.shipstream.io_MysqlFailoverGroup: |
      # paste contents of bloodraven/argocd/health-mysqlfailovergroup.lua
    resource.customizations.health.shipstream.io_MysqlBackup: |
      # paste contents of bloodraven/argocd/health-mysqlbackup.lua
```

### Option 3: Kustomize overlay

If you manage ArgoCD with Kustomize, extract the patch from the chart and add it as a strategic merge patch:

```bash
helm pull bloodraven/bloodraven --untar
cp bloodraven/argocd/argocd-cm-patch.yaml .
```

```yaml
# kustomization.yaml
patchesStrategicMerge:
  - argocd-cm-patch.yaml
```

### Verifying

After applying, check that ArgoCD recognizes the health checks:

```bash
kubectl get configmap argocd-cm -n argocd -o yaml | grep shipstream
```

Your `MysqlFailoverGroup` and `MysqlBackup` resources should now show proper health status (Healthy/Progressing/Degraded) in the ArgoCD UI instead of Unknown.
