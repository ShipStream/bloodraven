# Placement Contract

Bloodraven uses node labels and taints to control where MySQL pods run and to evict application workloads during failover. This page describes the labeling requirements that cluster administrators must satisfy.

## Why node labeling matters

When the operator performs a failover, it taints nodes at the old active site with `NoExecute` to force Kubernetes to evict application pods that do not tolerate the taint. Taints are scoped per failover group, so a failover in one group does not disrupt pods belonging to another group.

## Required node labels

Every node that participates in a failover group must carry two labels:

| Label | Value | Example |
|---|---|---|
| `shipstream.io/failover-group` | The failover group name | `orders` |
| `shipstream.io/site` | The site name | `iad` |

Apply them with:

```bash
kubectl label node node-iad-1 \
  shipstream.io/failover-group=orders \
  shipstream.io/site=iad

kubectl label node node-pdx-1 \
  shipstream.io/failover-group=orders \
  shipstream.io/site=pdx
```

You can label multiple nodes per site. The operator will taint or untaint all nodes matching the label selector for a given failover group and site.

## Taint behavior

When a site loses its primary role (either through failover or because it becomes unreachable), the operator applies a per-group taint to all nodes at that site:

```
shipstream.io/db-readonly-<group>=true:NoExecute
```

For example, for a failover group named `orders`:

```
shipstream.io/db-readonly-orders=true:NoExecute
```

When a site becomes the active primary, the operator removes this taint from its nodes.

### Effect on pods

The `NoExecute` effect means:

- Pods that **do not** tolerate the taint are immediately evicted
- Pods that **do** tolerate the taint continue running

This gives you two categories of workloads:

| Workload type | Toleration | Behavior on failover |
|---|---|---|
| Write-dependent apps | No toleration for `shipstream.io/db-readonly-<group>:NoExecute` | Evicted from the old site, rescheduled to the new active site |
| Read-only / stateless apps | Tolerates `shipstream.io/db-readonly-<group>:NoExecute` | Continues running at both sites |

## Shared-node support

Because taints are scoped per failover group, multiple groups can share nodes in the same node pool. A failover in `orders` applies `shipstream.io/db-readonly-orders=true:NoExecute`, which only evicts pods that do not tolerate that specific taint. Pods belonging to `inventory` are unaffected — as long as they tolerate the `orders` taint.

### Cross-group tolerations

On shared nodes, application pods must tolerate taint keys from **other** failover groups but **not** their own. This ensures they are only evicted by their own group's failover:

```yaml
# Pod for the "orders" group on nodes shared with "inventory"
spec:
  tolerations:
    # Tolerate other groups' taints so this pod is not evicted by their failovers
    - key: shipstream.io/db-readonly-inventory
      operator: Exists
      effect: NoExecute
    # Do NOT tolerate orders' taint — this pod should be evicted on orders failover
```

A mutating admission webhook or Helm template can automate generating these tolerations across groups.

### Dedicated nodes

If you prefer dedicated nodes per group (the simplest model), no cross-group tolerations are needed. Each node only receives taints for its labeled group, so only that group's pods are affected.

## Scheduling MySQL pods

The operator schedules MySQL pods using the site's `zone` field (via `topology.kubernetes.io/zone` node selector). You do not need to manually configure this placement -- the operator handles it.

The `shipstream.io/failover-group` and `shipstream.io/site` node labels described above are used by the operator to identify which nodes to taint or untaint during failover, not as scheduling constraints for MySQL pods.

## Multiple failover groups

Multiple failover groups can share nodes in the same pool. Each node is labeled with the failover group it serves:

```bash
# Group: orders
kubectl label node node-a shipstream.io/failover-group=orders shipstream.io/site=iad
kubectl label node node-b shipstream.io/failover-group=orders shipstream.io/site=pdx

# Group: inventory
kubectl label node node-c shipstream.io/failover-group=inventory shipstream.io/site=iad
kubectl label node node-d shipstream.io/failover-group=inventory shipstream.io/site=pdx
```

A failover in `orders` taints nodes `node-a`/`node-b` with `shipstream.io/db-readonly-orders=true:NoExecute`. Nodes `node-c`/`node-d` are unaffected because they belong to the `inventory` group's selector.
