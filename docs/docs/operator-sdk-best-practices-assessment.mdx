# Operator SDK Best Practices Assessment

This page records how the Operator SDK best-practices guidance applies to Bloodraven. It is an applicability assessment, not a copy of upstream guidance. The review favors documentation and follow-up decisions over runtime changes because the relevant recommendations touch controller shape, cache scope, multitenancy, security, and operational policy.

## Applicability decisions

| Operator SDK guidance | Source | Bloodraven disposition | Evidence or action |
|---|---|---|---|
| Keep reconciliation idempotent and avoid operator-as-meta-operator designs. | [Operator Best Practices](https://sdk.operatorframework.io/docs/best-practices/best-practices/), [Common recommendations](https://sdk.operatorframework.io/docs/best-practices/common-recommendation/) | Already satisfied. | Bloodraven reconciles declared Kubernetes and MySQL state from custom resources instead of relying on one-shot imperative actions. Operational docs describe status-driven failover and recovery semantics rather than manual hidden state. |
| Prefer clear controller boundaries and one primary kind per controller. | [Operator Best Practices](https://sdk.operatorframework.io/docs/best-practices/best-practices/) | Already satisfied. | The operator has distinct reconcilers for `MysqlFailoverGroup`, `MysqlBackup`, and `MysqlBackupVerification`, with each controller centered on its own custom resource. |
| Avoid hard-coded namespaces and make operator and operand placement configurable. | [Common recommendations](https://sdk.operatorframework.io/docs/best-practices/common-recommendation/) | Partially satisfied; watch namespace scoping is future work. | Install and production docs use example namespaces such as `bloodraven` and `orders`, while manifests and custom resources avoid requiring those exact namespaces. However, the operator manager does not currently expose a configurable watch namespace or cache scope. Future work should evaluate namespace-scoped watches separately from install-time namespace examples. |
| Use structural CustomResourceDefinitions, validation, and meaningful status. | [Common recommendations](https://sdk.operatorframework.io/docs/best-practices/common-recommendation/) | Already satisfied. | CRDs are generated from API types, chart CRD drift is checked in continuous integration, and docs cover status fields for failover, backup, restore, and verification behavior. |
| Set resource requests and hardened security contexts where practical, while preserving user overrides. | [Managing Resources](https://sdk.operatorframework.io/docs/best-practices/managing-resources/), [Pod Security Standards](https://sdk.operatorframework.io/docs/best-practices/pod-security-standards/) | Partially satisfied; default requests need compatibility review. | Bloodraven exposes operand resource override fields such as `resources`, `sidecarResources`, and backup job resources, and backup or restore job paths document hardened pod and container security defaults that merge caller-supplied overrides. The assessment does not claim every operand path has safe default resource requests today; adding defaults everywhere needs a separate compatibility review. |
| Prune completed resources or use time-to-live and retention controls for Jobs and artifacts. | [Resource pruning](https://sdk.operatorframework.io/docs/best-practices/resource-pruning/) | Already satisfied for backup and verification workflows. | Backup profiles expose structured `retentionPolicy`, backup deletion triggers artifact cleanup through a finalizer, point-in-time recovery binlogs are pruned against full-backup retention, and backup verification supports `ttlSecondsAfterFinished`. |
| Make multi-tenant behavior explicit and avoid broad built-in NetworkPolicy assumptions. | [Multi-Tenancy](https://sdk.operatorframework.io/docs/best-practices/multi-tenancy/) | Accepted boundary; no operator-owned NetworkPolicy work planned. | Bloodraven documents NetworkPolicy as an environment responsibility and provides example policies. The chart should not try to own tenant boundaries by default because NetworkPolicy requirements vary by cluster networking, service mesh, and tenant model. |
| Keep watches and caches lean; avoid high-cardinality or unrelated objects where feasible. | [Designing Lean Operators](https://sdk.operatorframework.io/docs/best-practices/designing-lean-operators/) | Accepted tradeoff; no runtime behavior changed in this assessment. | `MysqlFailoverGroupReconciler.SetupWithManager` watches `Secret` objects and maps events through `secretToFailoverGroup` so credential and TLS rotation reconciles affected groups. This is intentional because referenced Secret names can come from multiple failover-group fields and backup or restore paths. The tradeoff is broader than ideal in clusters with many Secrets. Future options include labels for Bloodraven-managed or referenceable Secrets, field indexes, a narrower event predicate, or cache selectors. |
| Provide useful metrics, events, alerts, runbooks, and low-cardinality metric labels. | [Operator Observability Best Practices](https://sdk.operatorframework.io/docs/best-practices/observability-best-practices/) | Already satisfied with future review hooks. | Bloodraven docs cover metrics, Grafana dashboards, Prometheus setup, Events, alert-to-runbook mapping, and log schema. Future metric additions should include documentation, cardinality review, and build validation for dashboard and alert references. |

## Assessment scope and tradeoffs

This review did not change Go code, generated manifests, CustomResourceDefinitions, Role-Based Access Control, or Helm chart behavior. The Operator SDK guidance identifies several operationally important areas, but most are already represented in Bloodraven's design or require careful compatibility work.

The most notable tradeoff is the `Secret` watch. Narrowing that watch could reduce cache and event volume, but an incorrect filter risks missing credential or TLS rotation and leaving MySQL, backup, or restore workflows with stale configuration. The safer near-term action is to document the behavior and evaluate a tested narrowing separately.

## Follow-up candidates

| Area | Candidate follow-up | Tracking disposition | Why it was deferred |
|---|---|---|---|
| Namespace watch/cache scope | Evaluate configurable manager watch namespace and cache scope for namespace-scoped installations. | Future WISHLIST candidate. | Install namespace examples are configurable, but changing manager cache scope affects reconciliation coverage and deployment modes. |
| Secret watch scope | Add a label, index, predicate, or cache-selector design for Secrets referenced by Bloodraven resources. | Future WISHLIST candidate. | The safe shape depends on all Secret reference fields and rotation paths. A runtime change needs controller tests or envtest coverage. |
| Observability review gate | Add a release checklist item for metric documentation, label cardinality, alert mapping, and runbook links. | Future WISHLIST candidate. | Existing docs cover the main surfaces. The next value is a repeatable review process when new metrics or alerts ship. |
| Resource and security defaults | Review all operand pod and job paths for default resource requests, security contexts, and user override fields. | Future WISHLIST candidate. | Existing backup and restore paths are documented; default requests for every operand path need compatibility review before being imposed. |
