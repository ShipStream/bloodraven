# Bloodraven Alert & Event Runbook Matrix

Quick lookup matrix mapping Prometheus alerts and Kubernetes Events to root causes and verified remediation commands.

| Alert / Event | Impact & Severity | Key Diagnostic Checks | Recommended Remediation Action |
|---|---|---|---|
| `BloodravenNoWritableSite` / `NoPrimary` | 🔴 **CRITICAL** (Total write outage) | Check if all sites have `read_only=ON`, network partition, anti-flap cooldown ticking. Every `mysqld` boots `read_only=ON`: on the last active site, `super_read_only=OFF` means a restarted MySQL the operator re-asserts on its next poll (WARN `re-asserting fenced promoted primary`, field `authority`); `super_read_only=ON` with no `status.lastFailoverTarget` is a fence the operator deliberately leaves for a human | If one site is healthy and ahead on GTID: `kubectl bloodraven promote <group> -n <ns> --to=<site> --force` |
| `BloodravenSplitBrainDetected` | 🔴 **CRITICAL** (Multi-primary write divergence) | Multiple sites `read_only=OFF`, app traffic split | 1. Immediately fence loser: `kubectl exec <loser-pod> -c mysql -- mysql -e "SET GLOBAL read_only=ON; SET GLOBAL super_read_only=ON;"`<br>2. Update DNS / routing.<br>3. Inspect GTID diff. |
| `BloodravenDivergentTransactions` / `DivergentTransactionsDetected` | 🔴 **CRITICAL** (Replica cannot replicate due to errant transactions) | Events mention divergent GTIDs, `SecondsBehindSource=null`, replication broken | Run GTID audit. If data on old primary can be discarded: `kubectl bloodraven reclone <group> -n <ns> --target=<divergent-site>` |
| `BloodravenOperatorDown` | 🟠 **HIGH** (Failovers and reconciliations suspended) | Operator deployment down, CrashLoopBackOff, or leader lease contention | `kubectl describe deploy bloodraven -n bloodraven`<br>`kubectl logs -n bloodraven deploy/bloodraven` |
| Sidecar container restarts / `CrashLoopBackOff`, or pod unready during a MySQL stall | 🔴 **CRITICAL** if restarting (no fencing agent on that node between restarts); 🟡 **MEDIUM** if only unready | Sidecar `livenessProbe` path (must be `/peer/ping`, not `/health`); `sidecar-probe.sh ... livez` (`fencingMonitor.secondsSinceProgress`); `safety net:` log lines | Unready with liveness passing is expected while MySQL is down. Upgrade an operator that still renders `/health` liveness. Do not restart the sidecar to re-run the safety net: the monitor re-applies it once MySQL answers. See [playbook 8](./troubleshooting_playbooks.md#8-sidecar-restarting-unready-or-not-fencing-during-a-mysql-stall). |
| `BloodravenReplicationLagging` | 🟡 **MEDIUM** (High RPO on failover, stale reads) | `SecondsBehindSource` > threshold, large transaction or I/O bottleneck | Check `SHOW PROCESSLIST` and replica I/O load. Reduce write bursts or optimize slow queries. |
| `BloodravenKeyringNotSealed` | 🟠 **HIGH** (Tablespace encryption incomplete/unsealed) | Sidecar `/keyring/status`, `status.encryptionAtRest.sites[].phase` | Verify escrow Secret existence and sidecar file permissions. |
| `KeyringEscrowMissing` / `KeyringEscrowCorrupt` | 🔴 **CRITICAL** (Risk of unrecoverable data loss upon restart) | Escrow Secret deleted or digest mismatch on sealed pod | **DO NOT restart the pod**. Extract active keyring from memory/sidecar `/keyring/status` and re-create escrow Secret. |
| `BloodravenDragonflySiteDown` / `DragonflyDegraded` | 🟡 **MEDIUM** (Cache/Session layer degraded) | `status.dragonfly.phase`, Dragonfly pods, endpoints | Verify Dragonfly pod logs, replication link, and auth Secret alignment. |
| `BloodravenBackupStale` | 🟠 **HIGH** (Backup RPO violation) | Latest `MysqlBackup` failed or missing; inspect that run's predecessor/root UID and launch attempt rather than another run's counters | Run on-demand backup: `kubectl bloodraven backup <group> -n <ns>` and check backup Job logs. For a missing configured retry, see [playbook 15](./troubleshooting_playbooks.md#15-scheduled-backup-fails-without-the-expected-retry). |
| `BackupRetryConflict` group event | 🟡 **MEDIUM** (One retry blocked) | The named deterministic successor disagrees with the expected predecessor/root/attempt/group/profile/schedule | Inspect `status.backupSchedules[].retryConflict` and its public lineage fields using [playbook 15](./troubleshooting_playbooks.md#15-scheduled-backup-fails-without-the-expected-retry). Unchanged conflicts do not repeat warnings; other schedules and rollups continue. Do not rewrite lineage to bypass retry limits. |
| `BackupMetadataIncomplete` / `MetadataComplete=False` | 🟡 **MEDIUM** when location is recovered; 🟠 **HIGH** for `DestinationUnavailable` | Read the condition reason and `status.location`; compare with the owned producing Job and check pod-log reachability | Transient log errors retry for ten minutes. A known Job-derived location is usable without optional observations. Unknown destinations keep `Ready=False`; follow [playbook 14](./troubleshooting_playbooks.md#14-backup-completed-with-incomplete-metadata). |
| `BackupFailed` / `RestoreFailed` with MySQL `Access denied` | 🟠 **HIGH** (Backup or recovery blocked) | Confirm the intended credential Secret and Job script version. Older scripts trim MySQL password whitespace and normalize line endings | Use scripts containing the exact-content reader and retry with the existing credentials. See [playbook 12](./troubleshooting_playbooks.md#12-backup-or-restore-reports-access-denied-with-valid-credentials). Do not dump passwords or strip valid Secret contents. |
| `EncryptionAttributionCorrected` event | 🟡 **MEDIUM** (Backup audit record repaired) | A completed backup's encryption status disagreed with its producing Job | Confirm the repaired `status.encrypted` and algorithm match the owned Job's uploader layout and env. Retry affected restore/verification using the corrected backup reference; see the attribution playbook. |
| `S3CredentialsIncomplete` event / `S3CredentialsReady=False` | 🟠 **HIGH** (Every S3 backup, restore and retention cleanup Job fails) | The condition message names each `credentialsSecret` that is missing or lacks non-empty `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`. Jobs no longer fall back to IRSA, Workload Identity or instance-profile credentials, so a Secret that relied on that (for example one holding only `AWS_REGION`) trips this after an upgrade | Add both keys to the named Secret (`kubectl -n <ns> create secret generic <name> --from-literal=AWS_ACCESS_KEY_ID=... --from-literal=AWS_SECRET_ACCESS_KEY=... --dry-run=client -o yaml \| kubectl apply -f -`). The condition clears on the next reconcile. |
| `CredentialReconcileFailed` event mentioning `partial_revokes not confirmed` | 🟡 **MEDIUM** (`app` user can still write the `mysql` grant tables) | The event names the site that could not be confirmed, usually because it is down | Bring the site back; the operator retries every minute. See [playbook 9](./troubleshooting_playbooks.md#9-app-users-mysql-schema-restriction-pending-or-a-replica-stopped-on-a-partial-revoke). |
| `BloodravenBackupVerificationStale` | 🟡 **MEDIUM** (Untested restore integrity) | Latest verification failed; correlate its pinned backup UID/location with its Job snapshot and source inputs | Run on-demand verification: `kubectl bloodraven verify-backup <group> -n <ns>`. A running verification stays bound to its original source; see [playbook 16](./troubleshooting_playbooks.md#16-verification-source-does-not-match-the-expected-backup). |
| `BackupIdentityMismatch` verification event | 🟡 **MEDIUM** (Source identity unprovable; no successful certification) | Status reference or legacy Job inputs disagree, or the Job source snapshot is incomplete/invalid | Preserve evidence and compare immutable source inputs. Create a new verification for the intended source rather than editing the audit record; see [playbook 16](./troubleshooting_playbooks.md#16-verification-source-does-not-match-the-expected-backup). |
| Restore/verification cannot find a Succeeded backup's location | 🟠 **HIGH** (Backup reference unusable; cleanup may miss the artifact) | Compare `status.location` with the producing Job's effective output env; account for kubelet dollar expansion and older underscore encoding | Use the original Job inputs to establish the actual location or take a replacement backup. Preserve legacy producer-reported paths. Follow [playbook 13](./troubleshooting_playbooks.md#13-succeeded-backup-cannot-be-found-at-its-recorded-location); do not guess substitutions in old status. |
| `RestoreBuildFailed` / `RestoreInPlaceBuildFailed` event | 🟠 **HIGH** (Requested restore never started; no Job was created and an in-place restore is terminal `Failed`) | Read the message. `profile "<p>" is missing` or `now stores to <backend>` means the `mysqlBackupRef`'s profile was deleted or moved to another backend after the backup ran; a `decryption` block does not bypass this. `no passphrase is available` means neither `decryption.passphraseSecret` nor the profile's `encryption.passphraseSecret` is set | Restore the profile's original storage block, or point `source.s3` / `source.pvc` at the artifact directly (keep `decryption` for encrypted backups). For in-place, bump `spec.restoreInPlace.confirm` to retry. |
| `BloodravenDNSUpdateFailed` | 🟠 **HIGH** (Clients routing to old/dead site) | `DNSEndpoint` status, `external-dns` controller logs | Check `external-dns` pod logs and cloud DNS provider credentials. |
| `DeploymentLeaseRevoked` / renewal `409 revoked` | HIGH; deployment authority lost, possible partial DDL | Compare grant/current `topologyGeneration`, reason `topology_changed` or `operator_revoked`, deployment DDL boundary | Stop the deployment heartbeat and further DDL. Require manual recovery after DDL; never re-grant to bypass revocation. |
| `PlannedFailoverDeferred` with `DeploymentHold` | Planned maintenance delayed; not an emergency failover block | Inspect message operation/instance, `retryAfter`, `bloodraven_deploy_leases_active` and lease age | Let the holder finish or expire. For approved interruption, coordinate deployment shutdown and use the revoke annotation, not Lease deletion. |
| Deployment renewal `404 not_found` / lease expirations | Deployment coordination expired or released | Operator clock, last renewal, `bloodraven_deploy_lease_expirations_total`, client health | Stop the attempt; do not treat restart or a healthy topology as renewed authority. |
| `spec.leaseDurationSeconds: Invalid value: 0: must be greater than 0` | Lease persistence blocked; planned maintenance can remain deferred past expiry | Housekeeping/reconciler errors and sanitized deployment record state/expiry; not a TLS failure | Use the [invalid Lease duration playbook](./troubleshooting_playbooks.md#invalid-lease-duration-blocks-expiry). Roll out the positive-duration fix with approval; preserve records and review queued maintenance. Do not delete or patch Leases. |
| Deployment API `401` / `403 forbidden` | Deployment preflight blocked | Token audience, TokenReview permission, database `deploymentClients`, group assignment; no token logging | Correct the declared identity or projection through the owning deployment configuration. Do not widen auth or expose plaintext. |
| `TenantPrivilegeRestriction` on a `MysqlDatabase` | 🟡 **MEDIUM** (Independent global access may be denied; a restricted operator account can block apply/delete) | Compare explicit schema rows with `mysql.user.User_attributes` restrictions; the warning identifies a restricted grantor or repair error. Legacy repair is best-effort; normal apply/deletion continues | Use an unrestricted administrator for blocked escaped-name repair. Review real-schema restrictions before lifting them; preserve the intentional `app` restriction on `mysql.*`. See [playbook 10](./troubleshooting_playbooks.md#10-shared-principal-loses-global-access-to-a-tenant-schema). |
| `PartialRevokeLifted` on a `MysqlDatabase` | 🟢 **INFO** (Identifiable legacy artifact repaired) | Event names the account and impossible escaped schema spelling | No action for that artifact. Inspect remaining real-schema restrictions separately; this event does not guarantee full global access was restored. |
| `MysqlDatabase` Pending / Warning `PartialRevokesOff` | 🟡 **MEDIUM** (Tenant changes deferred; existing access preserved) | Read `status.message`; check `@@GLOBAL.partial_revokes` and whether the operator can `SET GLOBAL partial_revokes = ON` on the primary | Restore setting-read access or the operator's `SYSTEM_VARIABLES_ADMIN` privilege; retries resume automatically. Cleanup/deletion is not gated. See [playbook 9](./troubleshooting_playbooks.md#tenant-pending-with-partialrevokesoff-or-ready-with-escaped-grants). |
| `MysqlDatabase` Ready but schema access denied after enabling `partial_revokes` | 🟡 **MEDIUM** (Affected tenant lacks schema access) | Compare literal and legacy escaped schema rows in `mysql.db` on the primary; inspect the Ready condition and applied hash | Upgrade to a Bloodraven release containing the escaped-grant reapplication fix; for later manual mode changes, make a spec edit to reapply. See [playbook 9](./troubleshooting_playbooks.md#tenant-pending-with-partialrevokesoff-or-ready-with-escaped-grants). |
| `MysqlDatabase` Failed: `DatabasePreExists` / `PreExistingOwnerUser` / `PreExistingUser` | 🟡 **MEDIUM** (One tenant parked; no cluster impact) | `status.message` names the first refused `user@host`; compare it against `ownerUser`/`ownerHosts`, `pendingOwnerUser`/`pendingOwnerHosts` and each `appliedUsers[]` `username`/`hosts` and `pendingUsername`/`pendingHosts` — attribution is per `user@host` | Refusal by design: Bloodraven will not adopt a schema or account it did not create. Fix the *spec* (unused `databaseName`, tenant-unique Secret username). See [playbook 7](./troubleshooting_playbooks.md#7-tenant-database-adoption-refused-mysqldatabase). **Never patch `status` to fake attribution.** |
| `MysqlDatabase` Failed: `UserClaimedBySibling` / `DatabaseNameConflict` / `OwnerConflict` | 🟡 **MEDIUM** (One tenant parked) | The message names the peer CR; a `users[]` principal belongs to exactly one `MysqlDatabase` | Share group-level principals through `spec.grants[]` instead of repeating a `users[]` entry, or remove the duplicate CR. |
| `OwnerUserDropSkipped` / `UserDropSkipped` / `OwnerUserReservedSkipped` / `UserReservedSkipped` / `UserTransferred` on delete | 🟢 **INFO** (Account deliberately kept) | Event text names the surviving claim: a sibling's owner/`grants[]`/ledger, a group-level principal, or this CR's own `grants[]` | Not a leak — the account already lost its rights on the dropped database. Remove the remaining claim and drop by hand only if it truly must not outlive the CR. |
