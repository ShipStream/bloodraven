# Bloodraven Alert & Event Runbook Matrix

Quick lookup matrix mapping Prometheus alerts and Kubernetes Events to root causes and verified remediation commands.

| Alert / Event | Impact & Severity | Key Diagnostic Checks | Recommended Remediation Action |
|---|---|---|---|
| `PITRArchiveNotFound` / `PITRArchiveLegacy` / `PITRArchiveDescriptorMissing` / `PITRArchiveIdentityMismatch` / `PITRArchiveEncryptionMismatch` / `PITRArchiveKeyMismatch` / `PITRArchiveVersionUnsupported` / `PITRArchiveObjectInvalid` / `PITRArchiveHistoryReset` / `PITRArchiveListFailed` (restore or verification) | 🟠 **HIGH** (The archive the restore reads was refused before replay) | Status message (token, archive ID, destination); `archiveProfileName`; the descriptor `<prefix>/binlogs/archive.json` (plaintext); the backup's `status.pitrArchiveID` | Wrong profile (`NotFound`); pre-v1.7.0 prefix needs a pre-v1.7.0 image (`Legacy`); wait for replication or restore `archive.json` (`DescriptorMissing`); the backup belongs to another archive (`IdentityMismatch`); fix encryption or passphrase (`EncryptionMismatch` / `KeyMismatch`); a newer format needs the release that wrote it, but a message saying `archive.json is damaged` needs the original object restored (bucket versioning, a copy) or a new prefix (`VersionUnsupported`); `ListFailed` is only a listing refused for permission and names its cause: S3 403 → grant `s3:ListBucket`, PVC permission error → make the archive volume readable by the Job's user (other listing or manifest read failures are retried and, if they persist, fail without a token; a row "retired" during planning is transient: retry); on a replicated copy, any refusal that names a missing or unreadable object can be replication lag: check the copy is complete before applying a permanent remedy; a reset epoch needs a new prefix plus full backup (`HistoryReset`). See playbook 32. |
| `PITRArchiveDestinationShared` / `PITRTargetInvalid` / `PITRBackupFiltered` / `PITRBackupAfterTarget` (`RestoreBuildFailed`) | 🟠 **HIGH** (Restore not started) | `initFromBackup.pointInTime` (`archiveProfileName`, `stopDatetime`), `loadOptions.includeSchemas`/`excludeSchemas`, the backup's `completionTime` | Keep `spec.backup.pitr` on its own prefix; fix the target (whole seconds, no fraction); drop the load filters; use an earlier backup or a later target. See playbook 32. |
| `PITRBackupIdentityUnknown` / `PITRBackupIdentityMismatch` / `PITRBackupInconsistent` / `PITRBackupIncomplete` (`dump-meta`) | 🟠 **HIGH** (The dump cannot be tied to its source and archive) | `dump-meta` termination message; the stamp `<location>.bloodraven-backup.json`; `MysqlBackup.status.failoverGroupUID`, `gtidExecuted` | Take a new full backup (pre-v1.7.0 dumps have no stamp); use the right `mysqlBackupRef`. `IdentityUnknown` saying the dump `is encrypted … but the restore has no decryption passphrase`, `is not encrypted, but the restore decrypts this dump` or `does not decrypt with the configured passphrase` is the restore source's encryption setting: fix it rather than take a new backup. `larger than its bound`: a stamp over 1 MiB or an `@.json`/`@.done.json` over 16 MiB, i.e. a replaced object. A `dump-meta` failure without a token is a transient store error that persisted through its retries. See playbook 32. |
| `PITRTargetNotCovered` / `PITRStopAmbiguous` / `PITRBackupNotOnLineage` / `PITRExcludeIntersectsBackup` / `PITRNoArchivedReplay` / `PITRPlanTooLarge` / `PITRReplayUnsupported` | 🟠 **HIGH** (Requested recovery or verification refused) | Refusal message (it names the target, sets and safe targets); `pitr-download` log `pitr plan` / `download site binlogs` | Flush and wait for archiving (`TargetNotCovered`, `NoArchivedReplay`); choose a target the message offers or exclude the named errant (`StopAmbiguous`); use a backup on the target history (`NotOnLineage`, `ExcludeIntersectsBackup`); `PlanTooLarge`: the message names the limit hit: Job memory (raise the memory limit; for the event-size bound only below its 64 MiB cap, at the cap pick a target whose plan does not read that file), the staging volume (raise `spec.backup.stagingVolumeSizeLimit`) or the node's free ephemeral storage (schedule the Job on a node with more), or use a backup closer to the target; avoid XA in the window (`ReplayUnsupported`). See playbook 32. |
| `PITRArchiveDivergentHistory` / `PITRArchiveSplitBrain` / `PITRArchiveGap` / `PITRArchiveOrderConflict` / `PITRArchiveOrderInversion` / `PITRArchiveNamespaceReuse` | 🟠 **HIGH** (The archive does not prove one history from the backup to the target) | Refusal message and `BLOODRAVEN_PITR_DIVERGENT_SET`; recent failovers; `gtid-audit.sh` divergent rows and promotion records | Copy the printed set into `excludeGtids` when it is history to drop, or use a later backup / earlier target; for gaps and inversions follow the message; reuse needs a new prefix plus full backup. See playbook 40. |
| `PITRCoverageInvalid` / `PITRReplayMismatch` / `BLOODRAVEN_PITR_FAILED` (`restore.py`) | 🟠 **HIGH** (Replay checks or the replay itself failed) | Main container termination message and log (`BLOODRAVEN_PITR_SEGMENT k=`); Job rendered by which operator version | Retry with matching operator versions; preserve `coverage.json` for `ReplayMismatch`; empty a loaded bootstrap target before retrying. See playbook 32. |
| `PITRDivergentHistoryExcluded` / `PITROnHistoryTransactionsExcluded` Warning | 🟡 **MEDIUM** (Restore or verification succeeded with exclusions) | `pointInTime.excludedDivergentTransactionCount`, `onHistoryExclusions` | Confirm the excluded set is what you meant to drop; on-history exclusions are not certified, so check the affected rows. See playbook 40. |
| `PointInTimePartial` Warning | 🟠 **HIGH** (Restore completed at the archive head, before the requested target) | Compare `status.restore.pointInTime.stopTime` with `newestReplayedCommitTime` | Confirm the earlier point is acceptable before routing traffic. See playbook 32. |
| `PITRArchiveReissueRiskDetected` Warning | 🟠 **HIGH** (A site whose manifest holds divergent/quarantined rows was promoted; if it was recloned after a lossy failover it reissues lost GTIDs and every restore from the archive will refuse `PITRArchiveHistoryReset`) | Promoted site's `/archiver/status` `divergentRows`/`quarantinedRows`; whether it was recloned since the lossy failover (`starting bootstrap` with `source=reclone`) | If recloned: new prefix plus full backup, keep the old prefix for earlier targets. See playbook 39. |
| `PITRArchiveUnsafeHistoryDetected` Warning / `PITRArchiveReady=False` reason `ArchiveUnsafeHistory` | 🟠 **HIGH** (The marked site archives nothing more for this prefix, permanently) | `/archiver/status` `historyIntegrity`; live filters, `binlog_format`, `binlog_row_image`, `replica_preserve_commit_order` (the operator refuses these in `spec.mysqlConf`, so the cause is an out-of-band change: `SET GLOBAL`, a hand-edited my.cnf) | Undo the change, then new prefix plus full backup; the marker never clears, and it removes every restore target that needs that site's bytes, including targets before the violation. See playbook 38. |
| `PITRMysqlConfRefused` Warning / `PITRMysqlConfAccepted=False` reason `PITRUnsafeSettingRefused` | 🟡 **MEDIUM** (A `spec.mysqlConf` option that breaks PITR replay was left out of my.cnf; MySQL's safe default applies) | Condition message: `site: <field> sets <key>[=<value>] (<why>)` per refused setting (replication/binlog filter, `binlog_format≠ROW`, `binlog_row_image≠FULL`, `replica_preserve_commit_order`) | Remove the key from `spec.mysqlConf` (group or site), or disable `spec.backup.pitr` if the setting is required. Nothing is archived unsafely meanwhile. See playbook 38. |
| `PITRArchiveRefused` Warning (`MysqlStandbyCluster`) | 🟡 **MEDIUM** (DR standby publishes the dump without a PITR window) | `SourceConfigKnown` reason (`ArchiveLegacy`, `ArchiveDescriptorMissing`, `ArchiveIdentityMismatch`, `ArchiveEncryptionMismatch`, `ArchiveKeyMismatch`, `ArchiveVersionUnsupported`, `ArchiveListFailed`, `ArchiveUnreadable`) and message | `DescriptorMissing` on a replicated copy usually means replication lag; wait or copy `archive.json`. Fix `source.decryption` for encryption/key mismatches. `ListFailed`: grant `s3:ListBucket` to the standby's credentials on a 403, otherwise it is retried. No `MysqlFailoverGroup` or sidecar is involved: work from the standby's condition, `spec.source` and the bucket. See the `MysqlStandbyCluster` section of playbook 37. |
| `BloodravenNoWritableSite` / `NoPrimary` | 🔴 **CRITICAL** (Total write outage) | Check if all sites have `read_only=ON`, network partition, anti-flap cooldown ticking. Every `mysqld` boots `read_only=ON`: on the last active site, `super_read_only=OFF` means a restarted MySQL the operator re-asserts on its next poll (WARN `re-asserting fenced promoted primary`, field `authority`); `super_read_only=ON` with no `status.lastFailoverTarget` is a fence the operator deliberately leaves for a human | If one site is healthy and ahead on GTID: `kubectl bloodraven promote <group> -n <ns> --to=<site> --force` |
| `Ready=Unknown` / `Degraded=Unknown` reason `Initializing` (no `NoPrimaryDetected`; `Degraded` is `True` instead when a replication reason, `DivergentTransactions` or `RestoreReclonePending` applies) | 🟢 **INFO** (Operator startup window, not an outage) | A new operator process (restart, leader change) has not classified every `primary-candidate` yet: the primary answered writable but needs `recoveryThreshold` polls, or a site's first probes failed. `status.activeSite` is empty and the deployment API reports `unstableReason: Initializing` meanwhile. No promotion, fencing or DNS change happens on an unconfirmed answer, and no other site is promoted over it. A second writable answer shows as `SplitBrain` immediately, naming the unconfirmed site | None; it normally clears on the next poll (≈ 2 s), and a site whose probes keep failing becomes `unreachable` after `failureThreshold` polls. A site still unclassified after `failureThreshold` + `recoveryThreshold` probes alternates between answers and errors: the group then reports `NoPrimary` naming it (WARN `site not classified after its probe budget; probes alternate between answers and errors`); check `status.sites[].state` and the site's MySQL connectivity. See "Initializing after an operator start" in `site/content/docs/6.operations/6.failover.md`. |
| `BloodravenSplitBrainDetected` | 🔴 **CRITICAL** (Multi-primary write divergence) | Multiple sites `read_only=OFF`, app traffic split | 1. Immediately fence loser: `kubectl exec <loser-pod> -c mysql -- mysql -e "SET GLOBAL read_only=ON; SET GLOBAL super_read_only=ON;"`<br>2. Update DNS / routing.<br>3. Inspect GTID diff. |
| Planned failover `status.plannedFailover.reason=RecoveryInFlight` | 🟡 **MEDIUM** (Switchover not done; nothing sent to the target. Fix whatever makes that step hang (an unresponsive old primary), then re-annotate, unless the message ends `left fenced` (follow that row instead). |
| `RecoveryPending=True` reason `RecoveryInProgress` that persists | 🟢 **INFO** while a planned failover or ordered update is in flight; 🟡 **MEDIUM** otherwise (a Dragonfly snapshot upgrade defers recovery only intermittently, so it does not explain a persistent stall) | `.status.plannedFailover.phase`, `.status.updatePhase`; `status.sites[].recoveryState`, `replicating` | Expected during a handoff: old-primary recovery, its connection drain and source convergence stand down until it ends, then the drain restarts with a fresh `spec.connectionDrainTimeout` budget. With no handoff in flight, check the site's replication threads and source with `gtid-audit.sh` and [playbook 2](./troubleshooting_playbooks.md#2-divergent-transactions--errant-gtid-on-replica). |
| `BloodravenDivergentTransactions` / `DataLossDetected` (old primary) | 🔴 **CRITICAL** (Old primary holds transactions the new primary never received) | Events mention divergent GTIDs, `status.sites[].divergenceDetectedBy=OldPrimaryRecovery`, old primary fenced and not replicating | Run `gtid-audit.sh`. | `BloodravenDivergentTransactions` / `DivergentReplicaDetected` / `Degraded=DivergentTransactions` (replica audit) | 🔴 **CRITICAL** (A replica, often replicating normally, holds transactions the primary lacks; ordered updates and planned failovers will not promote it, so upgrades stall) | `status.sites[].divergenceDetectedBy=ReplicaAudit`, `divergentGtid`, `divergenceComparedTo`; `gtid-audit.sh` exit 2; `Ready` stays `True` | Preserve the errant events (`mysqlbinlog --include-gtids`), then reclone (`kubectl bloodraven reclone <group> <site> -n <ns>`) or replay them on the primary. Empty transactions on the primary (`SET GTID_NEXT='<uuid>:<n>'; BEGIN; COMMIT;` per GTID) only accept the divergence: the replica keeps rows the primary lacks and becomes promotable again. The audit clears the block within ~30s. See [playbook 33](./troubleshooting_playbooks.md#33-a-healthy-replica-reports-divergent-transactions-or-an-ordered-updateplanned-failover-refuses-a-divergent-target). |
