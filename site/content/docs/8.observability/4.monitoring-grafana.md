The Helm chart ships six dashboards in `charts/bloodraven/dashboards/`. Five need only the operator's metrics. The MySQL Workload dashboard also needs the opt-in `mysqld_exporter`.

| Dashboard | Audience | Purpose |
|---|---|---|
| Overview | On-call, platform | Writable site, unreachable sites, lag, backup freshness, failover activity, paced rollout |
| Failover | On-call | Failover durations, DNS flips, taints, split-brain signals, deployment leases and deferrals |
| Replication | Database owner | Lag, IO/SQL thread state, divergent transactions, reclones |
| Backups | Backup owner | Backup success, duration, size, verification freshness |
| Archiver | Backup owner | PITR archive freshness, backlog, failures |
| MySQL Workload | On-call, application owner | Connection use against the limit, row lock waits, query throughput, replication lag, and role per site. The exporter supplies the workload metrics. |

## Helm sidecar ConfigMaps

Use this path when Grafana has a dashboard sidecar, as in kube-prometheus-stack.

```yaml
grafanaDashboards:
  enabled: true
  namespace: monitoring
  label: grafana_dashboard
  labelValue: "1"
  folder: Bloodraven
```

```bash
helm upgrade --install bloodraven bloodraven/bloodraven \
  --namespace bloodraven \
  --values bloodraven-values.yaml
```

## File provisioning

Copy `charts/bloodraven/dashboards/*.json` into Grafana's provisioning path and configure a provider:

```yaml
apiVersion: 1
providers:
  - name: bloodraven
    folder: Bloodraven
    type: file
    allowUiUpdates: true
    options:
      path: /var/lib/grafana/dashboards/bloodraven
```

## Manual import

In Grafana, open **Dashboards > New > Import**, paste each JSON file, and select the Prometheus datasource.

## MySQL workload dashboard

The MySQL Workload dashboard (`mysql-workload.json`, UID `bloodraven-mysql-workload`) shows connection utilization as a percentage of `max_connections`, current InnoDB row lock waits and new waits per second, and client SQL throughput in queries per second. It also shows each site's role and whether the exporter reached it. **Replication lag by site** uses the operator metric `bloodraven_replication_lag_seconds`, in seconds, and remains available without the exporter. The series ends when a site becomes writable during a handoff. An unreachable site or unknown lag appears as a gap. It links to the Overview dashboard (`bloodraven-overview`), which links back, so you can move from a workload symptom to the HA view without losing the time range. The exporter reads the monitor account from a Secret.

Install it with any of the three paths above; the dashboard is part of the same chart files. Workload measurements appear after you [deploy the exporter and add its scrape job](/docs/observability/monitoring-prometheus#scrape-mysql-workload-metrics). The other five dashboards keep working without it.

Set the Prometheus data source's **Scrape interval** to `30s`, the interval of the example scrape job. A lower value makes `rate()` panels empty at short time ranges. The source queries and units are in the [Monitoring Reference](/docs/observability/monitoring#mysql-workload-series).

The current lock-wait panel shows `0` when MySQL reports no waiting locks and **No exporter data** when the measurement is missing. Historical plots leave gaps for missing values. [Missing data and measured zero](/docs/observability/monitoring#missing-data-and-measured-zero) lists every state.

## Datasource variable

All dashboards use a `datasource` variable. If panels show no data, open dashboard settings, confirm the variable points at the Prometheus datasource scraping Bloodraven, and save the dashboard.

## Troubleshooting

### Paced rollout panels

The Overview dashboard (`bloodraven-overview`) ends with a "Paced rollout" row:

| Panel | Query source | Interpretation |
|---|---|---|
| Groups by rollout phase | `bloodraven_rollout_groups` by phase | All zero when no operator release is being rolled. During a rollout `pending` falls as groups complete and one group is `admitted` or `rolling`. `stalled` above zero with `pending` above zero is a halted rollout. |
| Rollout phase per group | `bloodraven_rollout_group_phase` | One line per group that waits for or holds the slot. A group with nothing to roll, or whose roll completed, has no line. |
| Rollout records not stored | `bloodraven_rollout_record_not_stored` | Above zero: the installed CRD is older than the operator and no group is rolled. |

The first and third panels are fleet-wide and ignore the `ns` and `group`
variables; the second is filtered by both. The panels show no data while
`rollout.pacing=false`. Use
[Paced rollouts](/docs/operations/upgrade-policy#paced-rollouts) for
intervention.

### MySQL workload panels

Run these queries one at a time in Prometheus to check scrape, connection, and collector health.

```promql
up{job="bloodraven-mysql"}
mysql_up{job="bloodraven-mysql"}
mysql_exporter_collector_success{job="bloodraven-mysql"}
```

| Symptom | Cause | Fix |
|---|---|---|
| `up{job="bloodraven-mysql"}` has no series | The job is missing or its relabeled `job` value differs | Add or check the job from `examples/mysqld-exporter-scrape.yaml`, reload Prometheus, and check **Status > Targets**. |
| `up` is `0` | The exporter is not running, its Service has no endpoints, or a NetworkPolicy blocks Prometheus | Run `kubectl get pods -n warehouse -l app.kubernetes.io/name=mysqld-exporter`. Check that the ingress policy names Prometheus's namespace and pod labels. |
| `up` is `1` and `mysql_up` is `0`, and the exporter log says `Access denied` | The Secret's `username` or `password` does not match the monitor account, or the operator has not created the account | Check that `spec.credentials.monitorSecretName` names the Secret the exporter mounts. Restart the exporter after you change the Secret. |
| `mysql_up` is `0`, and the exporter log says `lookup ... no such host` or `i/o timeout` | The target name is wrong, or the egress policy blocks DNS or port `3306` | Use `mysql-<group>-<site>-internal.<namespace>.svc.cluster.local:3306`. Check the exporter's egress policy and the MySQL ingress policy. |
| `mysql_up` is `0`, and the exporter log says `Connections using insecure transport are prohibited` | The group sets `spec.tls` and the exporter does not use TLS | Add `ssl-ca` and `tls-server-name` to the `.cnf` file, and mount `ca.crt`. See [MySQL TLS](/docs/observability/monitoring#mysql-tls). |
| `mysql_up` is `0`, and the exporter log says `certificate is valid for` | The exporter verifies the `-internal` name, which is not in the certificate | Set `tls-server-name` to the `-primary` Service name. |
| `mysql_up` is `1` and `mysql_exporter_collector_success` is `0` or absent | A collector failed or is not enabled | Read the exporter log for `Error from scraper`. Check that the arguments do not disable `global_status` or `global_variables`. |
| `mysql_up` is `0` and the exporter log says `Too many connections` | MySQL reached its connection limit and refused the monitor connection | Compare utilization and open connections before the gap to see how quickly the site reached its limit. |
| One site has data and the other does not | The other target is down or has different labels | Compare the `site` label on `up` for both targets. |
| The **Site role and state** panel has no data | The datasource is missing `bloodraven_site_state` for the selected sites | Check the operator scrape target and compare its `namespace`, `group`, and `site` labels with the dashboard filters. |
| `rate()` panels are empty at short time ranges | The data source's scrape interval is lower than the real `30s` | Set the data source's scrape interval to `30s`. |
| Panels do not change after you edit the Secret or the ConfigMap | The exporter reads both when it starts | Run `kubectl rollout restart deployment/orders-mysqld-exporter -n warehouse`. |

The exporter log is in the exporter pod: `kubectl logs deploy/orders-mysqld-exporter -n warehouse`.

### Deployment coordination panels

The Failover dashboard (`bloodraven-failover`) includes these panels:

| Panel | Query source | Interpretation |
|---|---|---|
| Active deployment leases | `bloodraven_deploy_leases_active` by group/kind | A running deployment normally holds migration and failover-hold leases; release, expiry, or revocation ends their effect. No series can mean no observations yet, not proof of zero activity. |
| Deployment lease revocations per hour | Hourly increase of `bloodraven_deploy_lease_revocations_total` by group/kind/reason | A spike means affected deployments lost authority. Correlate topology changes or administrative revocation with the application's DDL boundary. |
| Planned failover deferrals per hour | Hourly increase of `bloodraven_planned_failovers_deferred_total` by group/reason | `DeploymentHold` is expected during a deployment that overlaps requested maintenance; it does not block emergency failover. |

These panels use the `datasource` and `group` variables. Their source metrics
do not carry namespace/site labels, so the `ns` and `site` variables do not
directly filter them; same-named groups in different namespaces cannot be
separated. No recording rules are needed. Use [deployment coordination operations](/docs/operations/operations#deployment-coordination)
for intervention; do not suppress revocation or fencing signals during maintenance.

| Symptom | Check |
|---|---|
| No data | Prometheus target up, datasource variable, time range |
| Wrong datasource | Dashboard variable default and folder provisioning |
| Sidecar did not import | ConfigMap namespace, `grafana_dashboard` label, sidecar namespace scope |
| Stale dashboards | ConfigMap updated, Grafana sidecar logs, dashboard `uid` stable |
