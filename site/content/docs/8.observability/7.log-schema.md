title: Log schema contract

![log schema infographic](/img/infographics/log-schema.webp)

Bloodraven emits structured JSON logs from both the operator (`bloodraven`) and the per-MySQL sidecar (`bloodraven-sidecar`). This page is the contract that downstream log pipelines key off of: which fields are stable, what the `msg` values are for the events you care about, and what guarantees we make about changing them.

If you only need one rule of thumb: **filter on `msg` for the event vocabulary in the [Event reference](#event-reference) below — those strings are stable. Everything else is best-effort.**

## Streams

Both binaries write to stdout. There are two independent JSON streams; you can tell them apart by the presence of certain keys.

| Stream | Source | Identifies as | What's in it |
|---|---|---|---|
| Operational (`slog`) | Operator and sidecar | Has `time`, `level`, `msg` | Failover, promotion, bootstrap, recovery, fencing, archiver, sidecar startup, divergence detection — every event a human operator or alerting pipeline would care about |
| Controller-runtime (`zap`) | Operator only | Has `ts`, `level`, `msg`, `logger`, `controller`, `controllerKind`, `reconcileID` | Reconcile-loop bookkeeping from controller-runtime: CR fetches, status updates, watch events. Useful for debugging, *not* a stable interface |

The contract on this page applies to the **operational stream**. The controller-runtime stream is emitted as-is by upstream `sigs.k8s.io/controller-runtime` and inherits whatever shape that library produces — we don't redefine it.

To filter to operational logs in most pipelines, key on the presence of the `time` field (slog) or the absence of the `logger` field (zap).

## Common fields

Every record in the operational stream carries:

| Field | Type | Description |
|---|---|---|
| `time` | RFC3339Nano timestamp (string) | Event time, normalized to UTC by the binary's slog handler regardless of pod timezone. Always ends in `Z`. |
| `level` | string | One of `DEBUG`, `INFO`, `WARN`, `ERROR`. |
| `msg` | string | The event identifier. Stable for events listed in the [Event reference](#event-reference); may change for ad-hoc debug logs. |

Records emitted under a specific failover group also carry:

| Field | Type | Description |
|---|---|---|
| `fg` | string | The `MysqlFailoverGroup` namespaced name (`namespace/name`). Present on every operator log scoped to a group. On the sidecar, this is the bare group name passed via `FAILOVER_GROUP`. |

Sidecar records additionally carry:

| Field | Type | Description |
|---|---|---|
| `pod` | string | The pod name (set via `MY_POD_NAME`). Disambiguates per-replica logs when shipping multiple sites' sidecars to one stream. |

## Levels

| Level | When |
|---|---|
| `DEBUG` | Per-poll bookkeeping (status no-ops, transient probe errors, archiver tick events). Off by default — the operator's slog handler is set to `INFO`. |
| `INFO` | State changes the operator deliberately took: failover, promotion, bootstrap, recovery, sidecar lifecycle. **Most of the event vocabulary lives here.** |
| `WARN` | Degraded but not fatal: a single retry, a peer briefly unreachable, a non-critical operation that failed (connection kill, taint patch). The operator continues. |
| `ERROR` | Operator-affecting failure: failover failed, self-fence triggered, status update rejected by the API server, CronJob-pod startup validation failed. **Always paired with an `error` field** (a string carrying either the underlying error or, for validation failures, a description of what was missing). |

`DEBUG` records may appear or disappear without notice. `INFO`/`WARN`/`ERROR` `msg` strings listed below are stable.

## Field naming convention

- Keys are `camelCase`. Common keys: `site`, `fg`, `error`, `peer`, `count`, `source`, `donor`, `recipient`.
- The deployment API's `duration_ms` is an explicit contract exception: a JSON number in milliseconds, not `durationMs`. Its group identity is `group` plus `namespace`, rather than requiring `fg`.
- Site identifiers (`site`, `oldPrimary`, `newPrimary`, `promotedSite`, `donor`, `recipient`, `activeSite`, `authoritativeActiveSite`) all carry the bare site name as defined in `spec.sites[].name`.
- GTID fields (`promotionGtid`, `divergentGtid`, `oldPrimaryGtid`, `newPrimaryGtid`, `followerGtid`, `activeGtid`, `extraGtid`) carry MySQL GTID-set strings exactly as MySQL returns them — never parsed or canonicalised. Computed sets (`divergentGtid`, `extraGtid`) are MySQL-format sets; on the handoff, picker, ordered-update and promotion records they are truncated to 1024 characters with a trailing `…`.
- Counts (`count`, `divergentTransactions`, `extraTransactions`, `attempt`, `maxRetries`) are JSON numbers, not strings.
- Durations (`leaseTimeout`, `pollInterval`, `delay`, `timeout`) are emitted by `slog`'s default `time.Duration` rendering — currently a string like `"30s"`. Treat as opaque if you need to parse, prefer the metric of the same name.

## Event reference

This is the stable vocabulary. `msg` strings here will not change without a deprecation note in the release notes.

### Deployment API

Every `/deploy/v1` request emits one record, including authentication and authorization refusals. Filter on the exact `msg`, not on HTTP paths that can contain caller-provided identifiers.

| Level | `msg` | Fields | Fired when |
|---|---|---|---|
| INFO | `deploy api` | `handler`, `group`, `instance`, `namespace`, `operationId`, `status`, `duration_ms` | A deployment API request completes. |

`handler` identifies the route handler; `group`, `instance`, `namespace`, and `operationId` are strings (empty when not resolved or not applicable). `instance` is the `MysqlDatabase` resource name. `status` is the numeric HTTP status, and `duration_ms` is numeric elapsed milliseconds. No bearer token, lease token, or token hash is logged. Treat unresolved request identifiers as untrusted input, not proof of authorization.

Requests increment `bloodraven_http_requests_total{server="deploy"}`. Lease revocations emit Kubernetes Event `DeploymentLeaseRevoked` on the MFG and increment `bloodraven_deploy_lease_revocations_total{group,kind,reason}` with `TopologyChanged` or `OperatorRevoked`. A planned hold is visible as `Deferred/DeploymentHold`, `PlannedFailoverDeferred`, and `bloodraven_planned_failovers_deferred_total{group,reason}`. See [Deployment API metrics](/docs/configuration/deployment-api#metrics-events-and-logs) for the complete lease metric family.

### Failover

The four events that trace one failover, in order:

| Level | `msg` | Fields | Fired when |
|---|---|---|---|
| INFO | `initiating failover` | `candidate`, `oldPrimary`, `fg` | Operator has chosen a promotion target and is about to run the promotion sequence. DNS flips only after promotion succeeds and the target is verified writable. |
| INFO | `failover complete` | `promotedSite`, `promotionGtid`, `fg` | `Execute` (or the ordered-update `ExecuteHandoff`) finished: candidate is writable. A [planned failover](/docs/operations/planned-failover) emits it too, only once its live confirmation found the target writable and every other site read-only; a planned promotion that ends unconfirmed or held never emits it, and a planned re-run that finds the target already writable and confirms it emits it too. `promotionGtid` is the candidate's `gtid_executed` snapshot taken just before clearing `super_read_only` — the upper bound on data that survived. For a planned re-run that found the target already writable it is the fenced set; for one whose target already held the run's own writes, the set read immediately before the clears (the fenced set plus those writes). |
| INFO | `promotion confirmed: site is writable` | `site`, `fg` | Next poll observes the promoted site is `Writable`. The internal post-failover guard clears here. |
| ERROR | `failover failed` | `error`, `fg`, `retryAt` | The promotion sequence returned an error. The operator re-evaluates the topology at `retryAt` (10s later) even if no site changes state, and earlier if one does. |
| ERROR | `failover picker: refusing candidate whose data regressed` | `site`, `gtid`, `promotionGtid`, `reason`, `fg` | A promotion candidate was excluded because promoting it would replace committed history: its `gtid_executed` is empty in a group known to hold data (a wiped datadir, for example after a failed CLONE), or it does not contain `promotionGtid`, the GTID set recorded at the last promotion. Reclone the site. If no candidate remains, no failover happens and the decision is re-evaluated every 10s. Page on it. |
| WARN | `failover picker: skipping divergent candidate` | `site`, `divergentTransactions`, `divergentGtid`, `selected`, `fg` | Emergency failover preferred `selected`, a candidate without a divergence report, over `site`, which carries one (`recoveryState=RecoveryBlocked`) — even if `site` had a fresher GTID set. Transactions only `site` holds, legitimate ones included, are not on the new primary; `site` keeps its report. |
| ERROR | `failover picker: promoting a divergent candidate; no other candidate remains` | `site`, `divergentTransactions`, `divergentGtid`, `comparedTo`, `fg` | Every remaining candidate carries a divergence report, so emergency failover promotes the freshest of them anyway: divergence never blocks an emergency failover. Its extra transactions become authoritative; once it is the confirmed primary the operator records the `DivergentPromotion` condition. Page on it. |
| ERROR | `promotion succeeded but writable confirmation failed; DNS not flipped` | `site`, `error`, `fg` | `Execute` returned successfully but the promoted site did not report writable within the confirmation window. DNS is **not** flipped and no failover state is recorded — the promotion is treated as unconfirmed and re-evaluated on the next tick. |
| ERROR | `DNS flip failed after successful promotion` | `site`, `error`, `fg` | Promotion **and** writable confirmation both succeeded, so the failover state (cooldown, split-brain target, `promotionGtidExecuted`) and `bloodraven_failovers_total` are already recorded; only the DNS update failed. `bloodraven_dns_flips_total` is left unincremented. The poll loop reconciles DNS against the current active site (see `DNS reconciled to active site` below), so a transient failure such as an RBAC denial self-heals once the write is permitted again — MySQL has already promoted regardless. |
| WARN | `DNS reconcile failed` | `site`, `target`, `hostname`, `error`, `fg` | The poll-driven DNS reconcile tried to point the record at the current active site and the write was rejected. Logged once per failing episode, not once per poll: while the failure persists the retry continues silently (DEBUG `DNS reconcile still failing`) and MySQL is unaffected. |
| INFO | `DNS publication withheld until the initFromBackup restore succeeds` | `site`, `fg` | A new group's `spec.initFromBackup` restore has not succeeded (pending, running, or failed), so the group hostname is not pointed at the writable seed `site`. Logged once per restore; the record is written on the first poll after the restore succeeds. |
| INFO | `DNS reconciled to active site` | `site`, `target`, `hostname`, `fg` | The DNS record diverged from the desired `spec.dns` (target IP, hostname, or TTL) and was repaired — a promotion-time flip that had failed, a hostname rename, a record left stale by an operator restart, or an out-of-band edit. `bloodraven_dns_flips_total{site}` increments here, and only when the A-record target IP actually changed. No promotion is re-run and MySQL is not touched. |

Supporting events emitted inside `Execute`:

| Level | `msg` | Fields |
|---|---|---|
| INFO | `fenced old primary with super_read_only=ON` | `fg` |
| WARN | `failed to fence old primary (may be unreachable)` | `error`, `fg` |
| INFO | `killed app connections on old primary` | `count`, `fg` |
| WARN | `failed to kill app connections on old primary` | `error`, `fg` |
| INFO | `relay log drain complete` | `fg` |
| WARN | `relay log drain did not complete cleanly, proceeding with promotion` | `error`, `fg` |

### Binary log rotation

The operator sends one best-effort `FLUSH BINARY LOGS`, bounded at 1 second (connection setup included) and on a connection of its own, in three places: to the site being promoted, in every promotion (emergency failover, ordered-update handoff, planned failover), after `RESET REPLICA ALL` and before its writes are enabled; to the fenced source of an ordered-update handoff or a planned failover; and to a site before it is recloned while PITR is enabled. Each logs one of two records. The WARN never stops or changes the promotion, handoff or reclone. See [Binary log rotation at promotion](/docs/operations/failover#binary-log-rotation-at-promotion) and [Archiving the tail of an outgoing primary](/docs/backup-and-restore/backup-restore#archiving-the-tail-of-an-outgoing-primary).

| Level | `msg` | Fields | Fired when |
|---|---|---|---|
| INFO | `promotion binlog rotated` | `site`, `durationMs`, `fg` | The rotation of the promotion candidate `site` was acknowledged: what it logged as a replica is in sealed files its sidecar can archive, and its first transaction as the primary starts a new file. `durationMs` is the whole call, connection setup included, so it measures what the rotation added to the promotion. |
| WARN | `promotion binlog rotation failed` | `site`, `durationMs`, `timedOut`, `error`, `fg` | The rotation of the promotion candidate returned an error, or had not answered within 1 second (`timedOut=true`, a JSON boolean; `error` then reads `no answer within 1s; continuing without it`). The promotion continued with the same steps. The site's replica-era binary log stays unsealed until the next rotation, so the PITR archive lags until then; an abandoned rotation may still complete on the server later. MySQL error 1227 in `error` means the operator account lacks `RELOAD`. See playbook 45. |
| INFO | `outgoing primary binlog rotated` | `site`, `durationMs`, `fg`, and `runId` (planned failover) or `candidate` (ordered-update handoff) | The rotation of the fenced source `site` was acknowledged: the last transactions it took as the primary are in a sealed file, which its sidecar archives although the site is now read-only. A planned failover sends it at most once per run and operator process, in the pass that sends the fence and reads it back. |
| WARN | `outgoing primary binlog rotation failed` | `site`, `durationMs`, `timedOut`, `error`, `fg`, and `runId` or `candidate` | The same rotation failed or timed out. The handoff or run continued unchanged; the source's last binary log stays unsealed until its next rotation. See playbook 45. |
| INFO | `pre-reclone binlog rotated` | `site`, `durationMs`, `fg` | The rotation of a reclone's recipient `site` was acknowledged; the operator now waits for the site's sidecar to archive the sealed tail (see [Bootstrap and reclone](#bootstrap-and-reclone)). |
| WARN | `pre-reclone binlog rotation failed` | `site`, `durationMs`, `timedOut`, `error`, `fg` | The same rotation failed or timed out, or it was acknowledged and the name of the file it opened could not be read (`error` says which). It is retried until it is acknowledged, for at most 2 minutes from the start of the wait. See playbook 45. |

`durationMs` is a JSON number of milliseconds on the operator's clock.

### Ordered update handoff

Emitted by `ExecuteHandoff` when an `OrderedUpdate` rollout hands the primary role from the healthy active site to its standby. On success the handoff also emits `failover complete` (see [Failover](#failover)); the emergency-path `Execute` messages above are not emitted. The handoff's two rotations (`outgoing primary binlog rotated` with `candidate`, then `promotion binlog rotated`) are listed under [Binary log rotation](#binary-log-rotation).

| Level | `msg` | Fields | Notes |
|---|---|---|---|
| INFO | `maintenance handoff: fenced source` | `candidate`, `sourceGtid`, `fg` | The active site is fenced with `super_read_only=ON`. `sourceGtid` is its `GTID_EXECUTED` read after the fence, exactly as MySQL returned it — the set the standby must contain. |
| INFO | `maintenance handoff: killed app connections on source` | `candidate`, `count`, `fg` | Application sessions on the fenced active site were evicted. |
| WARN | `maintenance handoff: failed to kill app connections on source` | `candidate`, `error`, `fg` | Best effort; the handoff continues. |
| INFO | `maintenance handoff: candidate caught up to fenced source` | `candidate`, `sourceGtid`, `fg` | The standby's `GTID_EXECUTED` contains `sourceGtid`; promotion starts. |
| WARN | `maintenance handoff refused; source not fenced` | `candidate`, `error`, `fg` | The handoff was refused before the active site was fenced, so no write was paused: the standby did not reach the active site's current set within 30s (the usual case: it is lagging), the active site stopped answering, the active site was read-only, or either site's GTID set could not be read. The update ends with `ordered update failed` and is retried later. |
| WARN | `maintenance handoff refused; candidate has transactions the source lacks` | `candidate`, `extraTransactions`, `extraGtid`, `fg` | Before fencing, the standby's `GTID_EXECUTED` (read first) held transactions the active site's (read second) does not. Promoting it would make that history authoritative (issue #202), so the handoff stops; no write was paused. `extraGtid` is the extra set, truncated to 1024 characters. The update ends with `ordered update failed`; once the replica GTID audit records the divergence the standby is no longer chosen. See playbook 33. |
| WARN | `maintenance handoff aborted; source unfenced` | `candidate`, `error`, `fg` | The standby did not reach the fenced set within the 30s fenced budget, its applier failed, a GTID set could not be read or parsed, the active site stopped answering, the standby's set no longer equalled the fenced set when promotion re-checked it after `STOP REPLICA` or `RESET REPLICA ALL` (missing transactions, or transactions the source lacks: the `error` then says `transactions the source lacks`), or promotion failed before the standby became writable. The active site has `super_read_only` and `read_only` cleared and keeps serving; the standby's replication is restarted (re-created after `RESET REPLICA ALL`); the update ends with `ordered update failed` and is retried later. |
| ERROR | `maintenance handoff: rollback failed: source may be left read-only` | `candidate`, `cause`, `error`, `fg` | The abort could not unfence the active site. Check `@@super_read_only` and `@@read_only` on it. Page on it. |
| ERROR | `maintenance handoff: source left read-only: it restarted during the handoff` | `candidate`, `cause`, `fg` | The abort found the active site with `read_only=ON` and `super_read_only=OFF`: mysqld restarted since the handoff fenced it, so the read-only state is its own and the abort does not lift it. The primary re-assert restores its writes once the update has ended, if its peers hold nothing it lacks. `cause` is why the handoff aborted. |
| ERROR | `maintenance handoff: source left read-only: it no longer holds transactions it held before the handoff` | `candidate`, `cause`, `missingTransactions`, `missingGtid`, `fg` | The abort found the active site read-only and without part of the GTID set the handoff last read from it: it restarted on older data. It is not unfenced; the primary re-assert compares it with its peers and reports it (`own transactions lost`) or restores it. |
| ERROR | `maintenance handoff: source is writable and no longer holds transactions it held before the handoff` | `candidate`, `cause`, `missingTransactions`, `missingGtid`, `fg` | The same finding on an active site that answers `read_only=OFF`: it restarted on older data and came up writable, or something other than the handoff lifted its read-only state. The handoff sends it nothing. It is the group's primary without those transactions, and reuses their GTIDs for what it commits; the standby that holds them is reported by the replica GTID audit (`divergence detected`, and `the primary lacks transactions it issued itself` below). Page on it. |
| ERROR | `maintenance handoff: source not unfenced: it no longer holds transactions it held before the handoff` | `candidate`, `cause`, `error`, `missingTransactions`, `missingGtid`, `fg` | The same finding when the active site's read-only flags could not be read (`error`): the abort does not unfence it and says nothing about whether it is writable. |
| WARN | `maintenance handoff: failed to restart replication on candidate after abort` | `candidate`, `error`, `fg` | Promotion stopped after `STOP REPLICA` (or after `RESET REPLICA ALL`, once the channel was re-created) and the standby's replication threads could not be restarted. The standby is read-only and not replicating; see playbook 23. |
| INFO | `maintenance handoff: restored candidate replication channel` | `candidate`, `host`, `fg` | Promotion stopped after `RESET REPLICA ALL` may have removed the standby's channel; the operator re-created it towards `host` with auto-positioning and restarted replication. |
| WARN | `maintenance handoff: failed to restore candidate replication channel after abort` | `candidate`, `error`, `fg` | The channel could not be re-created after an abort that may have followed `RESET REPLICA ALL`. The standby is read-only with no working channel and nothing re-points it automatically; restore it by hand (playbook 23). |

Emitted by the ordered update itself:

| Level | `msg` | Fields | Notes |
|---|---|---|---|
| WARN | `ordered update: handoff promotion returned an error but the standby is writable; recording the handoff` | `site`, `error`, `fg` | The handoff's final `read_only=OFF` on the standby returned an error after it may have applied, and a probe of the standby's `read_only` (pooled connection, up to 3 tries) found it writable. The handoff is recorded as a promotion (the `status.lastFailover` record, the anti-flap cooldown, DNS) before the error is reported. The source stays fenced and the old active is not rolled; the update ends with `ordered update failed` (`error` contains `failover during update: maintenance handoff: promote <site>: … (source left fenced: the candidate may already accept writes)`). |
| WARN | `ordered update: could not read the standby's read_only after a failed handoff promotion` | `site`, `error`, `fg` | The same failed `read_only=OFF`, but the probe could not read the standby's `read_only`. Nothing is recorded; the source stays fenced, the update ends with `ordered update failed`, and the next topology poll observes the standby. |
| WARN | `ordered update: active-site update stalled; standby is divergent` | `active`, `site`, `divergentTransactions`, `divergentGtid`, `reason`, `fg` | The active site has spec drift, but every otherwise eligible standby carries a divergence report, so none is a handoff target and nothing is fenced. `reason` reads `<site> is divergent (N transactions the primary lacks); reclone or reconcile before the active site can be updated`, the same text the update's error carries. The stall is intended; the update resumes on its own once the audit clears the report. Logged at most every 30s while it lasts. See playbook 33. |
| INFO | `ordered update: deferring follower update; no drifted follower is a healthy direct replica` | `active`, `driftSites`, `fg` | Only non-active sites have spec drift, and none of them is a read-only replica with healthy threads pointed at the active site, so no update attempt could roll one; none is started and the drift stays queued. Typical cause: the drifted site is a returning old primary that old-primary recovery has not rejoined yet (an attempt would also hold that recovery off), or it is unreachable or replicating from the wrong source. The update starts on its own once a drifted follower replicates directly. Logged at most every 30s while it lasts. |
| INFO | `topology manager deferring to its predecessor's ordered update; no failover, recovery or update until it exits` | `fg` | A topology manager restarted (configuration or credential change) while the manager it replaced still had an ordered update running. Until that update exits, the new manager takes no emergency failover, re-assert, old-primary recovery, connection drain, source repoint or update of its own, a new planned failover waits in admission (`admission.waitReason: PredecessorBusy`, nothing fenced), and `status.updatePhase` is empty. The old update's context is cancelled, so this normally lasts seconds. |
| INFO | `predecessor's ordered update exited; topology manager resuming` | `fg`, `heldFor` | The window above ended; `heldFor` is its length. |
| WARN | `ordered update: stalled; site pod not Ready` | `site`, `pod`, `reason`, `error`, `fg` | The update stopped on `site`, whose pod `pod` (empty when there is none yet) is not `Ready`, which here means `Ready` continuously for 30s, measured from the pod's last transition to `Ready` and its newest container start: either the update rolled it and the new pod did not get there within 5 minutes, or the site already runs the new pod template and the update refused to roll another site or hand off the active site while it is not `Ready`. `reason` says why, for example `sidecar not ready: crash looping, last exit code 1 (Error)` (a container that has restarted, in whatever phase of its loop: back-off, running, briefly `Ready` again, or terminated), `pod Ready for less than 30s`, `pod not scheduled: …` or `pod readiness unknown: …` when the API server could not be read. `error` is the full update error. Nothing else is rolled or handed off and the active site keeps serving. Logged on every attempt, at most every 30s while the stall lasts. When the stall stops an attempt that was already running, `ordered update failed` is logged first, its `error` carrying the same text. Mirrored by the `Updating` condition (still `True`, reason `OrderedUpdateStalled`) and the `OrderedUpdateStalled` Warning Event; a retry that finds the same cause rewrites neither. See [Ordered updates](/docs/operations/failover#ordered-updates). |
| INFO | `ordered update: stalled site pod is Ready` | `site`, `fg` | No update attempt was left to clear a stall (the stalled site was the last to roll, or another precondition holds the update), and the operator found the stalled site's pod `Ready` again, continuously for 30s, so a crash-looping pod caught between crashes does not log it. The `Updating` condition returns to `NotUpdating`. |
| ERROR | `ordered update: old active has transactions the new primary lacks; not repointing it` | `site`, `newPrimary`, `divergentTransactions`, `divergentGtid`, `oldPrimaryGtid`, `newPrimaryGtid`, `error`, `fg` | After a successful handoff the rollout updated the old active site, fenced it again with `super_read_only=ON`, and found transactions in its set (`oldPrimaryGtid`) that the new primary's (`newPrimaryGtid`) lacks. The handoff proves the new primary holds the fenced set, so this means a bug or an out-of-band write. The old active is not repointed: it stays fenced with no replication channel, and the update ends with `ordered update failed`. Old-primary recovery then reports the set as `divergentGtid` and blocks (`divergence detected` with `detectedBy=OldPrimaryRecovery`). One exception: if the old active came back on an empty datadir, its set holds only server-init transactions under a new `server_uuid`. Recovery treats such a site as empty and leaves it to auto-clone, so no `divergentGtid` appears. `error` carries the same text as the `ordered update failed` line. Page on it. When the fence or a GTID read fails instead, this record is not logged: the update ends with `ordered update failed` and an `error` containing `before repointing`, and the site is left for old-primary recovery the same way. |

### Paced rollouts

Emitted by the rollout pacer, which admits one failover group at a time to roll a pod change that an operator release causes (see [Paced rollouts](/docs/operations/upgrade-policy#paced-rollouts)). The pacer runs on the leader. The four decision records carry the Kubernetes Event reason in `msg` and are all logged at INFO, also where the Event is a Warning.

| Level | `msg` | Fields | Notes |
|---|---|---|---|
| INFO | `paced rollout: pacer started` | `renderer`, `soak`, `stallAfter`, `startGrace` | Once per leader start. `renderer` is the running release's renderer identity (the value of the `bloodraven.shipstream.io/rendered-by` annotation it writes); the three durations are the effective `rollout.*` chart values. |
| INFO | `paced rollout: RolloutAdmitted` | `fg`, `renderer`, `detail` | The group was given the rollout slot. `detail` is the Event message; it names the `rollout-admit` annotation when that admitted the group. |
| INFO | `paced rollout: RolloutDeferred` | `fg`, `renderer`, `detail` | An admission that had not started was withdrawn after `rollout.startGrace`; the group keeps its pods and waits for the slot again. `detail` says what held it. |
| INFO | `paced rollout: RolloutStalled` | `fg`, `renderer`, `detail` | The group's roll started and has not finished: its ordered update stopped on a pod that is not `Ready`, or `rollout.stallAfter` passed. The group keeps the slot and no other group is rolled. Logged once per stall. Alert on it. |
| INFO | `paced rollout: RolloutCompleted` | `fg`, `renderer`, `detail` | Every workload of the group runs the release's pod template and the group is stable. |
| ERROR | `paced rollout: record not stored` | `fg`, `remedy` | The API server dropped `status.rollout`: the installed `MysqlFailoverGroup` CRD is older than the operator, and no group is rolled until the release's CRDs are applied. Once per group for each operator start. Carries `remedy` and no `error` field. |
| WARN | `paced rollout: pass failed` | `error` | One pass of the pacer (every 5 seconds) could not list the groups or write a decision. The next pass decides again. |
| WARN | `paced rollouts are disabled (BLOODRAVEN_ROLLOUT_PACING): a release-driven pod change rolls every group at once` | (none) | At operator start with `rollout.pacing=false`. |
| ERROR | `invalid paced rollout configuration` | `error` | At operator start: a `rollout.soak`, `rollout.stallAfter` or `rollout.startGrace` value is not a duration, or is zero or negative where that is not allowed. The operator exits. |

### Planned failover

Emitted by a [planned failover](/docs/operations/planned-failover) run. Every record names the run with `runId`, the value of `status.plannedFailover.runID` (and of the hold acknowledgement). Two emitters produce them:

- **Engine** records come from the reconciler that drives the run and are written through the reconciler's logger, so they carry the controller-runtime shape (`ts`, `logger`, `controller`, `reconcileID`) besides the fields below.
- **Topology** records come from the group's topology manager on the operational stream. Their `fg` comes from the manager's logger and is `namespace/name`, as on engine records. (Earlier releases also appended the bare group name as a second `fg` key; none does now.)

Some events are logged by both, as noted. Filter on `msg` and `runId`. A run's two rotations are listed under [Binary log rotation](#binary-log-rotation): `outgoing primary binlog rotated` carries `runId`, `promotion binlog rotated` does not.

| Level | `msg` | Fields | Notes |
|---|---|---|---|
| INFO | `planned failover: claim granted` | `fg`, `runId`, `source`, `target` | The topology manager granted the run its claim after the live evidence probe (topology), and the run's `Fencing` record committed (engine). From here until the claim is released, the topology manager defers cross-site decisions for the group. |
| INFO | `planned failover: claim released` | `fg`, `runId`, `why`; engine also `outcome` | The run's claim was released. `why` is `publishing` (the promotion is confirmed, recorded and published; logged before the `Publishing` write, which needs no claim), `terminal`, `admissionTimeout`, `notCommitted` (the `Fencing` write was proven not to have committed: nothing was fenced), `statusStalled` (a terminal marker ended the run), `managerAbsent`, `zombie` (the uncached block no longer names a live run), `ack` (an automation hold was acknowledged) or `orphanHold` (topology only: an automation hold that no durable record backs any more was released; see `planned failover: released an automation hold no durable record backs`). `outcome` is the terminal outcome, empty for a non-terminal release. |
| INFO | `planned failover: released an automation hold no durable record backs` | `fg`, `runId` | Engine. The group's claim slot held an automation hold, but an uncached read found no `status.plannedFailoverHold`, no `True` `AutomaticFailoverHeld` condition, no `ManualRecoveryRequired` terminal marker and no acknowledgement annotation, so the hold is released (`claim released` with `why=orphanHold`) instead of holding automation with nothing to acknowledge. Typical causes: a run-less `True` condition removed by hand (this releases automation without an operator restart), a group deleted and recreated, or a hold hydrated by a manager start that raced an acknowledgement. `runId` is empty for a hold rebuilt from a run-less condition. |
| INFO | `planned failover: confirming recorded side effect` | `fg`, `runId`, `phase`, `effect` | The pass found a record this process did not write (after an operator restart or a leader change), so it confirms the recorded side effect live before going on. `effect` is `fence`, `drain`, `lagWait`, `dragonflySync`, `dragonflyTakeover`, `promotion` or `rollback`. Logged once per run and phase. |
| INFO | `planned failover: status write ambiguous; settling` | `fg`, `runId`, `revision`, `error` | A status write timed out or failed with a reset connection or a 5xx. The operator re-reads the object and, if `(runId, revision)` did not land, bumps the `planned-failover-status-fence` annotation conditioned on the same `resourceVersion` to prove the write can never commit. The new fence value is always past the stored one (1ns past it when the clock has not moved), and the fence counts as proof only if it moved the object's `resourceVersion`; otherwise the settlement tries again, and reports the write `Unknown` once its attempts are used up. No side effect runs until it is settled. |
| ERROR | `planned failover: cannot settle status write; holding` | `fg`, `runId`, `error` | A run that holds the claim could not settle an ambiguous write (the re-read and the fence both failed). The claim stays held and the pass requeues after 2s; the status-stall deadline bounds how long this lasts. |
| WARN | `planned failover: the target is no longer a primary candidate; not promoting it` | `fg`, `runId`, `site`, `role` | Topology. A promotion attempt found that the target's role in the topology manager's current configuration is not `PrimaryCandidate` (`role` carries the `spec.sites[].role` value, for example `DisasterRecovery` or `ReadOnly`; `spec.sites` changed during the run; the change restarts the topology manager, and the run's claim carries over without a re-proof). Nothing is sent; the run rolls back `TargetNotPromotable`. The pre-write gate repeats the check immediately before clearing `super_read_only`, and every promotion statement repeats it again (the line is logged there too). |
| WARN | `planned failover: pre-write gate refused` | `fg`, `runId`, `reason`, `sites` | Topology. Immediately before clearing `super_read_only` on the target, the gate found a reason not to: `TargetNotPromotable` (the target's role in the topology manager's current configuration is no longer `PrimaryCandidate`), `TargetChanged` or `ExecuteFailed` (the target is not the recorded server, not read-only, has a channel, or does not hold exactly the fenced set), `SourceLost`, `SourceUnfenced`, `AuthorityChanged` (the source holds transactions past the fenced set: its fence was lifted, written through and set again) or `ForeignWritable` (the source), `ForeignWritable` or `PeerUnreadable` (another site). `sites` is the list of sites at fault. Nothing was written to the target by this attempt. A source that does not answer is refused as `SourceLost` only once the 10s source-loss window has expired (counted from the first failed source observation in the drain, lag wait or gate); until then the attempt is retried. The run rolls back or leaves the source fenced; when an earlier attempt may already have written, it ends `ManualRecoveryRequired` (`ForeignWritable`, also for a source with history past the fenced set), or `PromotedUnconfirmed` for `PeerUnreadable` or an unreachable source (`SourceLost`, which names the target). |
| INFO | `planned failover: fenced source binlog not rotated` | `fg`, `runId`, `site`, `reason` | Topology. The run's fence on the source `site` was proven without the pass that sends the fence, reads it back and rotates the source's binary log, so the operator sent no `FLUSH BINARY LOGS` there. `reason` is `fenceReplyLost` (this operator process sent the fence, its reply or read-back was lost, and a later pass found it in place) or `fenceSentByEarlierProcess` (the operator restarted between the fence and its record; whether the earlier process rotated the source is not known). Logged once per run and operator process. The source's last binary log as the primary stays unsealed until its next rotation; to seal it now, run `FLUSH BINARY LOGS` on that site. |
| INFO | `planned failover: named fenced source for re-assert` | `fg`, `runId`, `site` | A run ending `SourceLeftFenced` with its own, attributable fence named the source as the topology manager's last active site, so the primary re-assert can restore it once every site is reachable and read-only (engine and topology). The naming happens after the run's terminal status record (or terminal marker) has committed, before its claim is released. Also logged by a starting topology manager that re-derives the naming from the terminal record or a terminal marker (topology). The fence is the run's own when it was proven applied, or when the durable fence intent names the server (an earlier operator process may have sent it); the name is bound to that server's `@@server_uuid`. A run whose result or marker carries the `FenceNotAttributable` warning is never named, including a run that sent a fence and then ended because authority moved. |
| INFO | `planned failover: could not name the unconfirmed target` | `fg`, `runId`, `error` | A `PromotedUnconfirmed` run could not record the target as the topology manager's last failover target. |
| INFO | `planned failover: a failover was recorded during the run; the unconfirmed target is not named` | `fg`, `runId`, `target` | A `PromotedUnconfirmed` run names its target only while the durable failover record is still the run's baseline (or its own). Another actor's failover was recorded during the run, so the target is not named and that failover's authority stands. |
| INFO / WARN | `planned failover: automation held pending acknowledgement` | `fg`, `runId`, `sites` | A run ended `ManualRecoveryRequired` and its claim became an automation hold (engine at INFO; topology at WARN, also when a starting manager rebuilds the hold from `status.plannedFailoverHold`, a terminal marker or a run-less `True` `AutomaticFailoverHeld` condition, or when the engine installs a hold at runtime). `sites` is a comma-separated string: the hold's ambiguous sites (`status.plannedFailoverHold.ambiguousSites`) when known, empty for a hold rebuilt from a marker or a bare condition. `runId` is empty for a hold from a run-less condition. Automatic cross-site actions stay held until `bloodraven.shipstream.io/acknowledge-planned-failover-hold=<runID>`. Page on it. |
| INFO | `planned failover: hold acknowledged` | `fg`, `runId` | The acknowledgement names the held run; the operator clears `status.plannedFailoverHold` (the `AutomaticFailoverHeld` condition turns `False/PlannedFailoverHoldAcknowledged`), the marker, the hold and then the acknowledgement, in that order. An acknowledgement that names another run, finds no standing hold, or finds the claim slot held for another run emits the `PlannedFailoverHoldAcknowledgmentIgnored` Warning Event instead, and resumes nothing; the annotation is removed when no hold stands. |
| ERROR | `planned failover: status stalled; ended the run with a terminal marker` | `fg`, `runId`, `outcome`, `reason`, `error` | The run's status writes failed for 2 minutes from the durable stall-since time (10 seconds for a run that already released its claim after its promotion was recorded and published: only its `Publishing` write was left); the `planned-failover-terminal` annotation now ends it (`outcome`/`reason` are the marker's). The claim is released, or kept as a hold for `ManualRecoveryRequired`. `error` is usually empty. |
| INFO | `planned failover: status stalled, but the fenced set is too large for a durable out-of-band watermark; keeping the claim` | `fg`, `runId` | The fenced set exceeds 64 KiB, so the stall release is not available: the claim stays held until a status write lands. |
| INFO | `planned failover: promotion already recorded; publishing without the claim` | `fg`, `runId`, `target` | A process that does not hold the run's claim (after a restart or a topology-manager replacement) found a `Promoting` block whose own failover record (its target and fenced set as the watermark, not older than the promotion intent) is the durable record. The confirmed tail had released the claim before the `Publishing` write landed, so the claim is not hydrated back and nothing is deferred: the run writes `Publishing` and `Succeeded` without it, and the topology manager reconciles DNS. Logged once per run and process. |
| INFO | `planned failover: status stalled, but the promotion's failover record is not durable yet; retrying` | `fg`, `runId` | The run's promotion is confirmed but its `Publishing` write has failed for the stall deadline (2 minutes from the durable stall-since time, or 10 seconds when the confirmed tail had already released the claim, in which case the run no longer defers automation), and neither the out-of-band failover annotations nor `status` carry the run's own failover record (its time, target and fenced set as the watermark) yet. The terminal marker would end the run with no durable watermark, so the operator keeps retrying instead; the live `Promoting` block still records the run (and, unless the claim was already released, owns the sites), and a restart re-derives the confirmation from it. Logged once per run. Repeats mean both the status subresource and the annotation write are being rejected. |
| INFO | `planned failover: target replaced before the promotion was recorded; rolling back` | `fg`, `runId`, `target`, `targetServerUUID` | Engine. After `super_read_only=OFF` may have been sent (by this operator process or an earlier one) the target was found replaced: it reads read-only and holds nothing outside the fenced set, and either `@@server_uuid` is not the run's (`targetServerUUID` is the server found) or it lacks part of the fenced set (the run's server on an older copy of its data). Because the run's own failover record is not durable, the source still holds the whole fenced set under the run's fence and every other promotable site answers read-only, the run rolls back (`TargetChanged`) instead of ending `ManualRecoveryRequired`. |
| WARN | `planned failover: a site last seen writable did not answer at the confirmation` | `fg`, `runId`, `sites` | Topology. The confirmation could not read a site (of any role, the source included) whose last answer to this operator process for the run was writable (the source also: holding transactions past the fenced set). It still counts as a second writer: the run ends `ManualRecoveryRequired{ForeignWritable}` with `sites` among the hold's `ambiguousSites`. Logged on every pass until the terminal record lands. |
| WARN | `planned failover: promotion not confirmed; a site this process has not read did not answer` | `fg`, `runId`, `sites` | Topology. The target is writable, but the source or a `PrimaryCandidate` or `DisasterRecovery` peer did not answer the confirmation, and this operator process never read it for the run (it did not pass the pre-write gate itself: it restarted after the clears, or found the target already writable). The run stays `Promoting` and retries every 2s; it confirms once `sites` answer read-only, holds if one answers writable, and ends `PromotedUnconfirmed{PromotionUnconfirmed}` 2 minutes after `promotion.intentTime`. |
| INFO | `planned failover: legacy status refused` | `fg`, `phase` | A non-terminal block written by an older operator (no `runId`, or a removed phase) was refused with reason `LegacyRunRefused`: `NotStarted` for a block that owned nothing (`Pending`, `Validating`, `Admitting`, `Deferred`), `PromotedUnconfirmed` for `Promoting` or `Resuming` (the older operator's promotion may have made the target writable), `SourceLeftFenced` for the other phases. Nothing was hydrated or sent to MySQL. |
| INFO | `planned failover: draining the source failed` | `fg`, `runId`, `sourceReachable`, `error` | A drain query (processlist or `KILL`) failed. The engine probes whether the source still answers (`sourceReachable`); only a source that does not answer counts toward the 10s source-loss window (`SourceLost`). A source that answers is drained up to `drainTimeout` and `drain.remainingConnections` is left unset, with the message `the connections remaining on <site> are unknown (<error>)`. |
| INFO | `planned failover: the fenced GTID set is invalid; rolling back` | `fg`, `runId`, `error` | `status.plannedFailover.fence.gtidSet` does not parse, so no lag probe can ever see the target catch up. The run rolls back with reason `InvalidGTID` at once. |
| INFO | `planned failover: lag probe failed; counting the target as unreachable` | `fg`, `runId`, `error` | The lag probe returned an error; the target counts as unreachable for this pass (the 10s target-loss window, then `TargetLost`). |
| WARN | `planned failover: could not restore the target's super_read_only` | `fg`, `runId`, `site`, `error` | Topology. A rollback (or the `Promoting` re-proof's re-fence) found the target read-only but with `super_read_only=OFF`, and setting it back to `ON` failed or did not read back. The rollback retries with the source still fenced, and ends `SourceLeftFenced` at the rollback deadline if it keeps failing. |
| WARN | `planned failover: rollback found another writable site beside the source` | `fg`, `runId`, `sites` | Topology. The rollback found the source already writable and another site writable too; `sites` is a comma-separated list. When that site is the target and the run may have written to it, the run ends `ManualRecoveryRequired` (`ForeignWritable`) and holds automation; any other writer is left to split-brain handling and the run stays `RolledBack`. |
| ERROR | `planned failover: rollback found the source writable without transactions it held` | `fg`, `runId`, `site`, `lostTransactions`, `lostGtid`, `fenceGtid`, `sourceGtid`, `targetGtid` | Topology. The rollback found the source writable and short of the set it was fenced with (`fenceGtid`), or of transactions it issued itself that the target or another site that answers holds: it restarted on older data and was then made writable. `lostGtid` is what it provably lacks. The run sends nothing to the source, neither creates nor starts the target's channel, and ends `ManualRecoveryRequired` (`SourceUnfenced`) with the automation hold. See [Rollback](/docs/operations/planned-failover#rollback). |
| WARN | `planned failover: the re-proof found the target replaced and cannot prove nothing was written; holding` | `fg`, `runId`, `site`, `targetServerUUID` | Topology. After an operator restart in `Promoting` the target reads read-only with nothing outside the fenced set, but it is not the data directory the run was promoting (another `@@server_uuid`, or part of the fenced set missing), and the evidence for a rollback is incomplete: the run's failover record is durable, the source is not behind the run's fence with the whole fenced set, a site is writable, or a promotable peer does not answer. The run ends `ManualRecoveryRequired`. |
| WARN | `planned failover: the fenced source is not the server the run's fence names; its fence is not lifted` | `fg`, `runId`, `site`, `fenceServerUUID`, `serverUUID` | Topology. The primary re-assert reached a source a planned run left fenced and named, and it answers under another `@@server_uuid` than the run's fence intent names (`serverUUID` is `unreadable` when the identity read failed). | WARN | `planned failover: the group was recreated; its claim slot starts empty` | `fg`, `previousUid`, `uid` | Topology runner. The new object does not inherit that slot, nor the retired manager's failover record. |
| ERROR | `planned failover: pass on an early-returning reconcile failed` | `error` | Engine (controller-runtime stream). ### Divergence and recovery

Fired when the operator inspects a returning old primary (after an emergency failover, or an old active site an ordered update refused to repoint), and by the replica GTID audit, which checks every read-only follower with a replication channel against the confirmed primary about every 30 seconds (and on the first poll after start, after the primary changes or is replaced under the same name, and after a completed promotion, handoff or re-assert; a refused divergent handoff candidate is audited on the next poll), whatever its replication threads report.

| Level | `msg` | Fields | Notes |
|---|---|---|---|
| INFO | `initiating old primary recovery` | `oldPrimary`, `newPrimary`, `fg` | Recovery sequence starting. |
| INFO | `no GTID divergence, auto-recovering old primary as replica` | `site`, `fg` | Old primary's GTID set is a subset of the new primary's, and it holds every transaction it issued itself — safe to attach as replica. |
| WARN | `divergence detected` | `site`, `divergentTransactions`, `divergentGtid`, `oldPrimaryGtid`, `newPrimaryGtid`, `detectedBy`, `primary`, `fg` | `site` holds committed transactions the primary never had. `detectedBy` is `OldPrimaryRecovery` (a returning old primary: `oldPrimaryGtid` is its set, `newPrimaryGtid` the new primary's) or `ReplicaAudit` (a follower, often replicating normally: `oldPrimaryGtid` carries the follower's set, `newPrimaryGtid` the primary's). When the audit re-verifies a block it did not create (an old primary whose replication was reattached by hand), it keeps that block's origin, `OldPrimaryRecovery` or empty for a block restored without provenance; `primary` names the site compared against. The site gets `recoveryState=RecoveryBlocked` and is not promoted by an ordered update or a planned failover. The operator does not auto-recover — the admin must reclone the site or make the primary contain the divergent set (containment then clears it). Emitted when divergence is first detected and again whenever the periodic re-verification finds the set CHANGED — an unchanged report is not re-logged each cycle. Mirrored by the `bloodraven_divergent_transactions` gauge, `Degraded` reason `DivergentTransactions`, and the `DataLossDetected` (old primary) or `DivergentReplicaDetected` (replica audit) Kubernetes Event. See playbook 33 for the replica case. |
| INFO | `divergence cleared: replica holds no transactions the primary lacks` | `site`, `primary`, `fg` | A fresh follower-first audit proved the site's set is contained in the primary's (after a reclone, or after the primary was made to contain the set). The block is dropped and `bloodraven_divergent_transactions{site}` returns to 0. This is the only way a `RecoveryBlocked` follower with a replication channel is cleared; healthy threads alone never clear it. Mirrored by the `DivergenceResolved` Event (replica-audit reports) or `OldPrimaryRecovered` (old-primary reports). |
| WARN | `replica GTID audit unverified` | `site`, `primary`, `error`, `fg` | The audit could not confirm the primary or could not read or parse a GTID set. Nothing changes: an existing block stays and none is invented. Retried on the next audit interval. When the primary could not be confirmed, `site` lists every follower that was due, comma-separated. |
| INFO | `replica GTID audit discarded: a server changed while it was read` | `site`, `primary`, `fg` | `@@server_uuid` of the follower or the primary changed between the audit's reads (a pod replaced by a clone or restore), so the sets do not describe one pair of servers. Retried on the next poll. |
| INFO | `replica GTID audit discarded: authority changed while it ran` | `site`, `primary`, `fg` | A promotion, handoff or update began while the audit was reading. Retried once authority settles. |
| INFO | `old primary recovery complete` | `site`, `source`, `fg` | Old primary is now replicating from the new primary. `source` is the new primary's host. |
| WARN | `own transactions lost` | `site`, `lostTransactions`, `lostGtid`, `comparedTo`, `serverUUIDs`, `detectedBy`, `remedy`, `fg` | `site` lacks transactions it issued itself that `comparedTo` holds: the primary, or a witness (another site that holds transactions the primary lacks, or a peer when no site was writable). With a witness the `remedy` says so: the site keeps replicating, is not recloned automatically, and is not promoted until no other site holds the transactions (the witness is recloned, or they are replayed onto the primary and replicate back). Against the primary, replication cannot return them, so the site is not rejoined by replication and not promoted, and the operator reclones it. For a follower whose channel from the primary runs this is logged only once the deficit cannot be replication lag (see `replica GTID audit: the follower lacks transactions under its own server_uuid …`). `serverUUIDs` are the identities the comparison ran under (the site's current `server_uuid` and the recorded earlier ones, comma-separated). `detectedBy` is `OldPrimaryRecovery` (a site without a channel, a promotion candidate, a refused re-assert) or `ReplicaAudit` (a site with a channel). `remedy` names the manual reclone. Logged on a new or changed set. |
| INFO | `own transactions lost cleared: the site was recloned` | `site`, `fg` | A clone into the site completed; the report is dropped and `bloodraven_own_transactions_lost{site}` returns to 0. |
| INFO | `own transactions lost cleared: the site holds every transaction it issued` | `site`, `comparedTo`, `reason`, `fg` | A report made against the primary `comparedTo` ended: a new comparison with that same primary found nothing lost (the site holds the transactions again). A clean comparison with the primary does not end a report that names another site, or one restored from status that has not been compared yet; see `own transactions lost kept` below. |
| INFO | `own transactions lost kept: the primary does not hold the transactions, the report stands until every other site has been compared` | `site`, `comparedTo`, `heldBy`, `fg` | A comparison with the primary `comparedTo` found nothing lost, but the report does not rest on that primary: it was restored from status after an operator start and names `heldBy` (`another site` when the stored status did not say, or when it named this primary, which is now known not to hold them), or it was made against a site that was the primary before, or while this primary was not the primary yet. ### Replication source convergence

After topology changes, Bloodraven verifies that every follower replicates
directly from the uniquely confirmed active primary. These events cover
candidate, `DisasterRecovery`, and `ReadOnly` followers; they are separate from the
old-primary recovery events above.

| Level | `msg` | Fields | Notes |
|---|---|---|---|
| INFO | `replication source convergence started` | `site`, `activeSite`, `currentSource`, `expectedSource`, `fg` | A follower needs a source or thread-state correction and passed the initial mutation gates. |
| INFO | `replication source convergence complete` | `site`, `source`, `fg` | The canonical source is the active primary and both replication threads are running. |
| WARN | `replication source convergence blocked` | `site`, `activeSite`, `stage`, `followerGtid`, `activeGtid`, `fg` | GTID containment failed before or after stopping replication. No source change is issued. |
| ERROR | `replication source convergence failed` | `site`, `activeSite`, `stage`, `error`, `fg` | A bounded source mutation or verification attempt failed. The next poll can retry safely. |

Stable `stage` values include `pre-stop-gtid`, `post-stop-gtid`, `stop`,
`change-source`, `start`, and `verify`. A follower awaiting its post-restore
reclone (`status.restoreReclones.pending`) is not converged: its status reads
`Pending` with reason `RestorePeerHold` and no convergence event is logged. Use the status
`sourceConvergenceState` and `sourceConvergenceReason` for current state; use
these logs for the detailed failure and GTID evidence.

### Bootstrap and reclone

`starting bootstrap` is the single canonical event for "we are about to clone a replica". The `source` field disambiguates *why*:

| `source` value | Meaning |
|---|---|
| `fresh-deploy` | Initial bootstrap of a new failover group; donor is the seed site. |
| `auto-clone` | Operator detected an empty replica during steady-state and is recovering it without an admin trigger. |
| `reclone` | The `bloodraven.shipstream.io/reclone-site` annotation was set (by an admin, or by the in-place restore's reclone queue), the safety interlock passed, and the operator is wiping the named site. **This is the `reclone-started` event.** |

| Level | `msg` | Fields |
|---|---|---|
| INFO | `starting bootstrap` | `source`, `donor`, `recipient`, `donorHost`, `fg` |
| INFO | `bootstrap deferred: another topology change holds the sites` | `recipient`, `source`, `reason`, `fg` |
| INFO | `cloning from primary` | `donor`, `fg` |
| INFO | `clone completed successfully` | `replica`, `fg` |
| INFO | `setting up replication` | `source`, `fg` |
| INFO | `replication started successfully` | `source`, `fg` |
| INFO | `bootstrap completed successfully` | `source`, `fg` |
| ERROR | `bootstrap failed` | `source`, `error`, `fg` |
| INFO | `clone returned expected connection drop, waiting for restart` | `error`, `fg` |
| INFO | `replica already has primary data (prior clone detected), skipping clone phase` | `fg` |
| INFO | `pre-reclone archive tail wait started` | `site`, `timeout`, `fg` |
| INFO | `pre-reclone archive tail archived` | `site`, `waitedMs`, `rotatedFile`, `fg` |
| WARN | `pre-reclone archive tail not archived` | `site`, `waitedMs`, `rotatedFile`, `reason`, `fg` |
| INFO | `clone recipient server_uuid rotated` | `site`, `previousServerUuid`, `serverUuid`, `fg` |
| WARN | `clone recipient kept its server_uuid` | `site`, `serverUuid`, `fg` |
| INFO / WARN | `clone recipient server_uuid rotation not verified` | `site`, `reason`, `fg` |
| WARN | `could not read the recipient server_uuid before clone` | `site`, `error`, `fg` |
| INFO | `clone restart not confirmed; keeping the recipient's keyring hold` | `recipient`, `source`, `fg` |
| WARN | `could not remove the recorded server_uuid of a clone recipient; will retry` | `site`, `error`, `fg` |
| WARN | `could not record the installed clone in the site's server_uuid history; will retry` | `site`, `fg` |
| WARN | `could not read the recorded server_uuids of clone recipients` | `site` (when one bootstrap asked), `error`, `fg` |
| WARN | `ignoring an undecodable clone server_uuid record` | `fg`, `annotation`, `error` |
| WARN | `could not record the PITRArchiveTailNotArchived event` | `fg`, `site`, `error` |
| WARN | `could not record the CloneServerUUIDNotRotated event` | `fg`, `site`, `error` |

The two `could not record the … event` records mean that the group could not be read when the Warning Event was to be recorded, so the Event is missing. The log line that carries the same finding (`pre-reclone archive tail not archived`, `clone recipient kept its server_uuid`) was written; `error` is the read's error.

A bootstrap is not started while another actor holds the sites (a planned failover, an ordered update, a promotion, an in-place restore, or a replaced topology manager still changing them); it is retried on a later poll. `bootstrap deferred: another topology change holds the sites` appears only when that actor claimed the sites while the bootstrap was being prepared; `reason` names it.

`clone returned expected connection drop, waiting for restart` is not a success signal. The client connection drops both when a clone succeeds (the recipient restarts) and when it is killed or aborted after MySQL has already dropped the recipient's user data. Before configuring replication the operator reads the recipient's `performance_schema.clone_status` and requires a new `Completed` row and a non-empty `gtid_executed`; otherwise it re-fences the recipient and logs `bootstrap failed` with the clone error.

The three `pre-reclone archive tail …` records come before `starting bootstrap` of a reclone (`source="reclone"`), and only while PITR is enabled: `CLONE INSTANCE` wipes the recipient's binary logs, so the operator first rotates them (`pre-reclone binlog rotated`, under [Binary log rotation](#binary-log-rotation)) and waits for the recipient's sidecar to report the sealed tail archived. `pre-reclone archive tail wait started` is logged once per wait; `timeout` is the bound (`2m0s`): the time the sidecar gets after the acknowledged rotation, and the time the rotation is retried from the start of the wait, so a wait lasts at most twice that. `pre-reclone archive tail archived` means the sidecar reported `tail.state: Drained` from a scan that saw the rotation (its `tail.activeFile` is `rotatedFile`, the file the server wrote after the operator's `FLUSH BINARY LOGS`, or a later one); `waitedMs` is how long the reclone waited. `pre-reclone archive tail not archived` means the clone starts without that confirmation: `reason` says why (the sidecar did not answer, it reports no `tail` block, the rotation was not acknowledged or the name of the file it opened could not be read, the sidecar's last scan is from before the rotation or cannot be compared with it, files were still uploading, the archiver cannot archive the tail, a status request or rotation did not return, or the sidecar runs no archiver, which ends the wait at once), and the same text is in the Warning Event `PITRArchiveTailNotArchived`. `rotatedFile` is empty when no rotation was acknowledged. The status requests and the rotation of a wait run off the topology poll, which only picks their results up. A restore whose window needs transactions only that tail held refuses `PITRArchiveGap`. See playbook 46. The fresh-deploy bootstrap and the auto-clone of an empty site do not wait.

The `clone recipient server_uuid …` records follow a clone the operator has confirmed (a new `Completed` row in `clone_status`), before `setting up replication`. Every clone gives its recipient a new `server_uuid`: the mysql container's launcher removes `auto.cnf` on the restart that installs the clone (see [Server identity after a clone](/docs/operations/operations#server-identity-after-a-clone)). The operator reads `@@server_uuid` before `CLONE INSTANCE` and after the restart. `clone recipient server_uuid rotated` carries both values. `clone recipient kept its server_uuid` means they are equal: the launcher did not run in that pod or could not remove the file, the same text is in the Warning Event `CloneServerUUIDNotRotated`, and the bootstrap continues (replication is still set up, and the site stays a failover candidate). `clone recipient server_uuid rotation not verified` means one of the two reads is missing, and `reason` says which: INFO when the value before the clone is unknown (`could not read the recipient server_uuid before clone` precedes it), WARN when the read after the clone failed three times. A clone that failed logs none of them.

The comparison does not need the operator process that issued the clone. The value read before `CLONE INSTANCE` is written to the group (the `bloodraven.shipstream.io/clone-server-uuid` annotation) before the statement is issued; if that write fails the bootstrap ends with `bootstrap failed` and an `error` that starts `clone not started`. A clone that finished after its operator restarted is compared by the next operator, at the start of its next bootstrap of the site (before `replica already has primary data (prior clone detected), skipping clone phase`) or on a poll, with the same `rotated` / `kept` records, once. There `clone recipient server_uuid rotation not verified` (INFO) also covers a record that needs no verdict; `reason` says why: `the clone its server_uuid was recorded for did not begin`, `… failed`, or `the recipient's clone status before the clone is unknown, so its completed clone cannot be told from an earlier one`. `could not remove the recorded server_uuid …` means the verdict was given but the annotation could not be updated; the removal is retried every 15 seconds and the verdict is not repeated by that operator process. `could not record the installed clone in the site's server_uuid history …` means the clone is known to have installed but the clone marker could not be written to `bloodraven.shipstream.io/server-uuid-history`; the record of the clone stays until it is (so a restarted operator marks it too), and until then the site's earlier `server_uuid`s still count as ones it can have lost transactions under, which can only add a report, never hide one.

`clone restart not confirmed; keeping the recipient's keyring hold` ends a bootstrap whose clone may still be copying or waiting for the restart that installs it: the bootstrap failed after `CLONE INSTANCE` was issued, or the operator is stopping. With encryption at rest the site stays `Unsealed`/`Clone` until an operator sees that clone `Completed` or `Failed` (see [Clones and the keyring](/docs/configuration/encryption-at-rest#clones-and-the-keyring)); without it the line has no effect.

The launcher itself logs to the mysql container, not to the operator, in plain text prefixed `bloodraven-launcher:`. It logs one line on a start that finds a clone staged in the data directory and nothing on any other start; the lines are listed under [Server identity after a clone](/docs/operations/operations#server-identity-after-a-clone). They are for a person reading `kubectl logs <pod> -c mysql`, and are not part of this contract.

A reclone-only narrative is therefore: filter `msg="starting bootstrap" AND source="reclone"` for the trigger event, then watch for `bootstrap completed successfully` (`source="reclone"`) or `bootstrap failed` (`source="reclone"`). The `Bootstrapping` condition mirrors them: `True` while the clone runs, then `False` with reason `NotBootstrapping` after `bootstrap completed successfully`, or `False` with reason `BootstrapFailed` after `bootstrap failed`, which also sets `Degraded=True` with reason `BootstrapFailed` until the site replicates or a new clone starts.

`archive descriptor created` is logged once, by the site whose atomic create
wrote `<prefix>/binlogs/archive.json`; a sibling that lost the race verifies
the winner's descriptor silently. `archive descriptor changed` means a
re-verification before a manifest save or retention delete found a different
or missing descriptor; the site stops writing and `lastError` carries the
refusal token. `promotion recorded` follows each saved promotion record
(the first writable observation of an episode); `gtidExecuted` is the
server's set verbatim, and `promotionGtidExecuted` is the record's
[promotion set](/docs/backup-and-restore/backup-restore#promotion-records-and-history-integrity)
in canonical form, empty when the record has none. In that case `promotion
set not recorded` precedes it with the `reason` (no read-only observation
directly before the episode, a server that changed incarnation between that
observation and the episode, a binlog header that could not be read in time,
a server that changed while it was derived); the record is written all the
same. `promotion record confirmed` is logged once per record that carries a
promotion set, when the
first role probe that started at least 10 s after it is saved into it;
`confirmedGtidAdded` is what the server executed in between. The restore
planner reads the promotion set and the confirmation only to refuse a
restore; neither message means that a target in the new primary's first
seconds can be restored (see the
[promotion-record lag window](/docs/get-started/known-limitations)). `uploads wait for the promotion record` is logged on
each scan of a writable site whose current episode has no saved promotion
record yet (the record could not be written, or the role probe is
incomplete); the site uploads nothing until it is saved, and `lastError`
carries the error. `server incarnation reset recorded` follows each saved
incarnation-reset record: the server's `server_uuid` or `server_id`
changed, or its `gtid_executed` no longer contains the site's latest
record's set (a reclone, reset or replaced datadir). `probeInterval` bounds
how long before `observedAt` the change happened. `server incarnation
changed while the sidecar was not running` is logged at sidecar start, before
that record, when the first observation already shows such a change against
the site's latest record (`latestRecordAt`); uploads wait until the record is
saved. `archive history unsafe` is logged once per sidecar
process for the first violation (`violation` is `ReplicationFilter`,
`BinlogFilter`, `BinlogFormat`, `BinlogRowImage` or `CommitOrder`).
`persist history integrity marker` means the marker could not be saved yet;
uploads stay blocked and the save is retried every scan. A violation found
while the archive is not yet verified (or is refused) is held as a pending
marker in the sidecar's pod-lifetime state directory and saved at the first
verified session; `remove pending history integrity marker` means that file
(`path`) could not be deleted after the save. See
[Archive identity](/docs/backup-and-restore/backup-restore#archive-identity).

`archive divergence evidence recorded` is logged when a site's history audit
changes the `divergent` list of its manifest: `rows` is the number of rows
whose transactions the site's server no longer has (0 when the evidence
ended), `missingGtids` those transactions, and `reissuableGtids` the part of
them the server could issue again (the ones under its current
`server_uuid`; empty for a site recloned with a new one). It is information,
not an error. A non-empty `reissuableGtids` is also reported as the
archiver's `lastError` and, on every scan, as WARN `archive binlog` with the
site's name in `file`, like the audit's other failures (a recorded GTID
reuse, an issuance that cannot be verified). See
[Reissue risk](/docs/backup-and-restore/pitr-history-repair#reissue-risk).

`archived binlog tail while read-only` is logged by a site whose server is
read-only when it uploads sealed binlogs of its last writable era (after a
planned failover's flush, or before a reclone): `count` files in this scan,
`through` the last one's name. A read-only site uploads only up to the last
sealed file that holds a transaction its own server originated, never pure
replica copies. `binlog tail not archived while read-only` means such a file
exists but the site could not decide on it or may not upload it; `reason`
says why (for example the site's latest record is an incarnation reset, it
has no promotion record, or a binlog file cannot be read, which includes a file MySQL encrypted that the sidecar [cannot decrypt](/docs/backup-and-restore/backup-restore#encryption-at-rest-and-pitr)) and `pendingFiles`
how many files wait. It is logged once per reason, not on every scan, and
does not set `lastError`: the same `reason` is in the `tail` block of
`/archiver/status`. A failed upload of a tail file is reported like any
other, by `archive binlog` and `lastError`, which stays set (with
`backlogFiles`) until a scan uploads the file or finds nothing left to
upload.

`archive binlog` also reports missing/divergent history and reset guards through
`error`; `/archiver/status.lastError` retains the problem and
`bloodraven_archiver_upload_failures` increases while it persists. The original
message and field keys are unchanged. Audited divergent identities persist in
the manifest and block affected transactions, including discovered aliases and
an otherwise unchecked last row. Bootstrap/clone observations cannot establish
divergence; eligible recovery on a fresh UUID can clear foreign-source flags.
Known same-source loss stays unresolved on numeric return until verified or
explicit canonical recovery. Reuse guards contain verified conflicting issuance;
publication order does not set them. Quarantine or a canonical-backup
acknowledgement provides explicit recovery. Recovery steps are in
[Repair PITR history safely](/docs/backup-and-restore/pitr-history-repair).

`failed to init archive store` is logged once per failed archive store
construction attempt. It used to be a single ERROR line followed by the
sidecar exiting; the sidecar now keeps running and retries with jittered
backoff from 5 s doubling to at most 5 minutes, so the line repeats at
most once per backoff interval. It is ERROR when the `error` text differs
from the previous attempt's (including the first) and WARN while the same
cause repeats. `attempt` counts from 1; `retryIn` is the delay before the
next attempt (a duration). `archive store initialized after retries`
follows the first success after at least one failure; `failingFor` is the
time since the first failed attempt. A first-attempt success logs neither.

The operator's archiver poller emits two lines about the `PITRArchiveReady`
condition. A poller that cannot read the group through the uncached API
reader (when its topology manager starts, or later) leaves the persisted
condition as it is until it can:

| Level | `msg` | Fields | Notes |
|---|---|---|---|
| WARN | `PITR archive condition read failed; leaving the condition as persisted` | `fg`, `error` | Once per episode per topology manager, however long the reads keep failing. `error` also reports a group recreated under the same name (UID mismatch); that condition is not written by this manager. |
| INFO | `PITR archive condition read recovered` | `fg` | The read that ends the episode; the condition is reconciled and written again from the next poll round. |

Per-upload success/failure is also reflected in the `bloodraven_archiver_upload_failures` and `bloodraven_archiver_last_upload_timestamp_seconds` metrics — prefer those for alerting.

`PITRSharedArchivePrefix` was removed with `pointInTime.sites`. The PITR
replay Events (`PITRReplayTruncated`, `PITRDivergentHistoryExcluded`,
`PITROnHistoryTransactionsExcluded`) are listed in
[Monitoring](/docs/observability/monitoring).

`retention deferred` logs `reason="noRetainedBackups"` or
`reason="backupInFlight"` at INFO for normal waits. Bounded backfill with
eligible work remaining also logs `binlogGTIDCoverageUnknown` at INFO while
it schedules the next batch. `archiveIssuanceUnverified` at INFO means
legacy/overlapping issuance checks are pending and new retirements wait.
A failed issuance check logs the same reason at WARN with `error`, naming
site/name/ID and the repair/quarantine remedy. The failure remains in
`/archiver/status.lastError` throughout cooldown until verification succeeds
or that identity is removed/quarantined. All new retirements for that site
can remain deferred; monitor archive capacity. It does not itself schedule
rapid retention retries. Other WARN reasons are
`backupMetadataUnknown` (missing/malformed backup GTIDs or start times),
`backupGTIDCoverageUnknown` (no compatible protocol/proof), and
`binlogGTIDCoverageUnknown` (eligible files lack complete, content-bound
transaction coverage with no immediately eligible backfill). Those coverage
and backup deferrals retain files without themselves indicating an upload
failure. Failed issuance audits do retain lastError and increase the archiver
failure metric as described above.

`retention: coverage unavailable` warns once per failed inspection attempt;
that identity waits the normal retention interval before retry. Healthy
identities can continue in 30-second batches. `fetch retention cutoff` now
logs lookup errors, including HTTP 429, at WARN with the existing `error`
field. Throttling is per transport source IP; it cannot consume another
source's group admission. A 429 has no delete authority and retries after
30 seconds; it is distinct from a successful safe-deferral response.

`retention: delete object` leaves a durable pending record for retry.
`retention: save delete acknowledgements` means successful deletes could
not be acknowledged; the next sweep safely repeats them. `retention sweep
complete` keeps its `cutoff`, `deleted`, and `manifest_pruned` fields.
For a sweep that only finishes older pending deletes without a current
operator proof, `cutoff` is an empty string and `manifest_pruned` is zero.
`deleted` counts successful, idempotent delete calls.

`retention: compact retirement records` means the manifest update that
removes obsolete acknowledged records failed. Their durable records
remain available for later scans; this does not re-upload retired data.
Each site's maintenance can emit retention events while that site is a
replica. Active archive counts exclude retirement records.

|---|---|---|---|
| INFO | `backup stamp written` | `key`, `backup`, `site`, `reused`, `serverID`, `pitrArchiveID`, `serverClockStart` | The init container wrote the stamp before the dump. `reused` is true when a retried pod adopted the stamp an earlier attempt wrote (its earlier `serverClockStart` is kept). `pitrArchiveID` is empty when PITR was off. |
| INFO | `backup stamp finished` | `key`, `backup`, `site`, `serverClockStart`, `serverClockEnd` | `serverClock.end` was added after a successful dump. On encrypted Jobs `backup-encrypt-upload` logs it after the upload, with its own `subcommand` and record fields. |

### PITR archive bindings

Emitted by the `MysqlFailoverGroup` reconciler for the group's
[archive encryption bindings](/docs/backup-and-restore/backup-encryption#archive-encryption-bindings).
`fg` is the group's name. No record carries passphrase bytes, an unkeyed
digest of them, or a `keyCheck`. `keySecretName`
(`mysql-<group>-pitr-key-<h10>`) does end in a truncated keyed digest: `h10`
is an HMAC, under the group's digest key, over the destination and the
passphrase bytes. Without that key it reveals nothing about the passphrase,
but treat it as key-derived rather than key-free (see
[Key snapshots](/docs/backup-and-restore/backup-encryption#key-snapshots)).

| Level | `msg` | Fields | Fired when |
|---|---|---|---|
| INFO | `pitr archive binding changed` | `fg`, `bindingID`, `destination`, `archiveID`, `state`, `reason`, `keySecretName`, `cause` | A binding entry is created, or its `state`, `reason`, `archiveID` or `keySecretName` changes. The last two can change with `state` and `reason` unchanged: a `Pending/Authenticating` check that rejects one candidate key and starts the next logs a line whose `keySecretName` differs and whose `state`/`reason` repeat. Filter on `state`/`reason` yourself if you only want those transitions. `cause` is `proof` (a sidecar report), `check` (a `pitr-archive-check` Job result, including a rejected candidate), `recovery` (rebuilt from a key snapshot's acceptance annotation after a status loss), `integrity` (the snapshot no longer verifies), `c3` (the snapshot is missing: re-created under the same name, or `KeyMaterialLost`) or `input` (any other spec, Secret or snapshot input change; for example a new target's first entry, the identity profile's key Secret or key missing, a `Refused` entry retried after an input change, a check or `Establishing` candidate superseded by an identity change, or an acceptance that could not be recorded). Every line carries a cause. |
| INFO | `pitr archive binding released` | `fg`, `bindingID`, `destination` | A release annotation removed a binding and deleted its snapshots. |
| WARN | `pitr render annotation ignored` | `fg`, `namespace`, `site`, `error` | A site Deployment's `bloodraven.shipstream.io/pitr-render` annotation is malformed or has an unknown `schemaVersion`; it counts as absent. |
| INFO | `pitr render deferred` | `fg`, `namespace`, `sites` | While any site Deployment has no decodable render annotation (and the write binding is not `Bound` or `Establishing`), existing site Deployments and their ConfigMaps are not updated until a check Job authenticates the live key; `sites` lists their sites. A site created meanwhile renders. |

The check Job (`bloodraven pitr-archive-check`) logs INFO `pitr archive check`
(`destination`, `role`, `state`, `reason`, `archiveID`) and writes one
termination line, which the operator parses:

```
BLOODRAVEN_PITR_ARCHIVE_CHECK v=2 state=<Absent|Verified|Refused> reason=<token or empty> archiveID=<id> sourceUID=<uid> sourceNamespace=<ns> sourceName=<name> destinationDigest=<64 hex>
```

`role` is `Writer` or `Reader` (`BLOODRAVEN_PITR_CHECK_ROLE`). Values are
percent-encoded like the PITR verdict. A transient storage error is retried 5
times; the Job then exits non-zero without a line. A verdict that cannot be
written to the termination log exits 4 with ERROR `write the verdict to the
termination log; the check fails` (`path`, `error`); the operator then reports
"check Job `<job>` failed: ..." and retries. The operator likewise retries a
check that exits 0 with a line that does not parse ("check Job `<job>` reported
a verdict line that does not parse: `<parser error>`").

- **Removed messages:** `pitr-download`'s WARN `stop proof scan ended at
  unreadable successor` and WARN `quarantined binlog excluded`, and the
  `anchorReason` texts, which belonged to the removed per-site planner.

  [PITR Job completion and failure metadata](#pitr-job-completion-and-failure-metadata)):

  `BLOODRAVEN_PITR_RESULT v=1` and an optional

- **Removed sentinel and Events:** `BLOODRAVEN_PITR_CROSS_SITE_UNVERIFIED`,
  the `PointInTimeCrossSiteUnverified` Event and reason, and the

- **Added messages:** sidecar `archive descriptor created`, `archive

  `persist history integrity marker`, `remove pending history integrity

## Stability commitments

| What | Stability |
|---|---|
| `msg` strings listed in the [Event reference](#event-reference) | **Stable.** Changes go through a deprecation note in the release notes. |
| Field names listed alongside a stable `msg` | **Stable.** New fields may be added to existing events; existing fields will not be renamed or removed without a deprecation note. |
| Field value shapes (strings, numbers, durations) | **Stable** for the values listed. GTIDs are passed through verbatim from MySQL — their shape is whatever MySQL emits. |
| `time`, `level`, `msg` field names themselves | **Stable.** Tied to `log/slog` defaults. |
| `DEBUG`-level records | **Unstable.** May appear, disappear, or change shape without notice. Disabled by default. |
| Ad-hoc `INFO`/`WARN`/`ERROR` records *not* listed above (e.g. retry warnings, transient probe errors) | **Best-effort.** Field set is intended to be useful but not contractual. Don't build alerts that key on the exact `msg` string. |
| Controller-runtime (`zap`) stream | **Inherited from upstream.** Bloodraven does not redefine this stream's shape. |

## Pipeline integration tips

### Filtering operational vs. controller-runtime

Most aggregators (Loki, Elasticsearch, Vector) let you split streams by JSON shape. A reliable predicate:

```jsonpath
$.time && $.msg   // operational (slog)
$.ts && $.logger  // controller-runtime (zap)
```

### Per-event alerts

Because every key event has a stable `msg`, pipeline alerts can be expressed as exact-match filters rather than fragile regexes. Examples for Loki:

```logql
# Failover started
{app="bloodraven"} | json | msg = "initiating failover"

# Failover failed (escalate)
{app="bloodraven"} | json | level = "ERROR" and msg = "failover failed"

# Divergence requires manual reclone
{app="bloodraven"} | json | msg = "divergence detected"

# Reclone triggered (track who/what asked for it via fg + recipient)
{app="bloodraven"} | json | msg = "starting bootstrap" and source = "reclone"

# Sidecar self-fenced — page on this
{app="bloodraven-sidecar"} | json | msg =~ "^SELF-FENCING:"

# Planned failover held automatic failover — page on this
{app="bloodraven"} | json | msg = "planned failover: automation held pending acknowledgement"
```

### Correlating with metrics and Kubernetes Events

Several stable log events are mirrored by other observable signals — when one fires, the others fire too:

| Log event | Metric | Kubernetes Event |
|---|---|---|
| `failover complete` | `bloodraven_failovers_total{target_site}` | `FailoverExecuted` |
| `divergence detected` | `bloodraven_divergent_transactions{site}` &gt; 0 | `DataLossDetected` (old primary) or `DivergentReplicaDetected` (replica audit) |
| `divergence cleared: replica holds no transactions the primary lacks` | `bloodraven_divergent_transactions{site}` returns to 0 | `DivergenceResolved` or `OldPrimaryRecovered` |
| `divergent site promoted; its extra transactions are now part of the primary's history` | (none) | `DivergentSitePromoted` |
| `old primary recovery complete` | `bloodraven_divergent_transactions{site}` returns to 0 | `OldPrimaryRecovered` |
| `own transactions lost` | `bloodraven_own_transactions_lost{site}` &gt; 0 | `OwnTransactionsLost` |
| `own transactions lost cleared: …` | `bloodraven_own_transactions_lost{site}` returns to 0 | `OwnTransactionsLostResolved` |
| `promotion refused: candidate lacks transactions it issued itself and would issue their GTIDs again` | (none) | `PromotionRefusedOwnTransactionsLost` |
| `ordered update: stalled; site pod not Ready` | (none; the `Updating` condition carries it) | `OrderedUpdateStalled`, once per stall |
| `paced rollout: RolloutStalled` | `bloodraven_rollout_stalls_total{reason}`; `bloodraven_rollout_group_phase{phase="stalled"}` is `1` until the roll completes | `RolloutStalled` |
| `paced rollout: RolloutAdmitted` / `RolloutDeferred` / `RolloutCompleted` | `bloodraven_rollout_admissions_total{reason}` / `bloodraven_rollout_deferrals_total` / `bloodraven_rollout_completions_total` | `RolloutAdmitted` / `RolloutDeferred` / `RolloutCompleted` |

| `failed to start topology manager` | (none) | `TopologyManagerStartFailed`, rate-limited: at once when a running manager was torn down, otherwise after one 30s retry, then at most every 5 minutes |
| `planned failover: automation held pending acknowledgement` | (none; `status.plannedFailoverHold` carries it, summarised by the `AutomaticFailoverHeld` condition) | `PlannedFailoverManualRecoveryRequired`, then `PlannedFailoverHoldPersisted` every 10 minutes |
| `planned failover: status stalled; ended the run with a terminal marker` | `bloodraven_planned_failovers_total{result}` | `PlannedFailoverStatusStalled` |

Prefer metrics for alert thresholds and Kubernetes Events for human notification routing; logs are richest for forensics and timeline reconstruction.

### Useful structured fields to index

If your pipeline supports indexing specific fields, the high-value ones are:

- `fg` — partitions everything by failover group
- `site` (and `oldPrimary` / `newPrimary` / `promotedSite` / `donor` / `recipient`) — for per-site timelines
- `level` — for severity routing
- `source` — for bootstrap/reclone disambiguation
- `error` — full error string from the operator's `error` chain

## PITR Job completion and failure metadata

PITR restore and verification Jobs run `dump-meta`, `pitr-download`,
optionally `decrypt-download`, and then `restore.py` (see
[The restore Job](/docs/backup-and-restore/backup-restore#the-restore-job)).
The init containers log JSON records. `dump-meta` records also carry
`subcommand="dump-meta"`.

| Level | `msg` | Fields | Notes |
|---|---|---|---|
| INFO | `dump metadata` | `location`, `backupUID`, `sourceUID`, `pitrArchiveID`, `site`, `dumpEnd` | `dump-meta` read and accepted the dump's `@.json`, `@.done.json` and stamp, and wrote `dump.json`. `dumpEnd` is µs RFC 3339 UTC; `pitrArchiveID` is empty when the backup was taken with PITR off. |
| ERROR | `read dump metadata` | `error` | `dump-meta` refused the dump (`error` starts with its token), or could not read it from the store. |
| INFO | `pitr plan` | `archiveID`, `mode`, `outcome`, `witness`, `groundTruth`, `segments`, `files`, `sites`, `replayed`, `divergent`, `onHistoryExcluded`, `downloaded`, `indexedTransactions`, `memoryPeakBytes`, `spilledPeakBytes`, `spillDiskPeakBytes` | `pitr-download` found a plan and staged it. `witness` is the witness GTID and `groundTruth` is `Origin` or `Anchored` (both empty without a witness); `sites` is a comma-separated list; `replayed` is the replayed transaction count; `divergent` and `onHistoryExcluded` are GTID counts; `downloaded` (archived files fetched) and `indexedTransactions` size the planning work. `memoryPeakBytes` is the peak of the planner's memory budget charge; `spilledPeakBytes` is the peak of the planning data spilled to the staging volume and `spillDiskPeakBytes` the peak disk space its files held (both 0 when the plan fit in memory). |
| WARN | `pitr loss report incomplete` | `rows`, `count`, `error` | Latest mode only. `coverage.json`'s `lost` list may lack excluded transactions: `pitr-download` could not read `count` archived files it needed only for that list (`rows`: comma-separated `<site>/<file>`, up to 4 KiB; `error`: why the first one was not read, up to 1 KiB). The plan, or the refusal, is the same as with the files readable, and the restore goes on. |
| ERROR | `download site binlogs` | `error` | Kept. `pitr-download` refused (`error` starts with its token) or failed to plan or stage. |

Configuration and setup failures log, also with `error`: `missing required
env`, `invalid dump-meta config`, `resolve dump storage`, `init dump store`
and `write dump metadata` (`dump-meta`); `invalid pitr-download config`,
`invalid archive config` and `init archive store` (`pitr-download`).

`dump-meta` and `pitr-download` write the same refusal, stable token first
and bounded to about 3 KiB, to their termination messages, and the operator
copies it into restore and verification status. The tokens and their order
are in [Restore refusals](/docs/backup-and-restore/backup-restore#restore-refusals).
A timestamp-mode `PITRArchiveDivergentHistory` names the transactions to
exclude, up to 1 KiB, and `pitr-download` prints the whole set to its log as
`BLOODRAVEN_PITR_DIVERGENT_SET gtids=<set, up to 64 KiB>`; it prints the same
line on success when the plan excluded divergent transactions. `coverage.json`
in the staging directory records the full plan, refusals included.

`restore.py` prints these text sentinels to its log:

| Sentinel | When |
|---|---|
| `BLOODRAVEN_PITR_TARGET_LOCAL gtids=<set, up to 64 KiB>` | Before the load, when the target already holds its own transactions (image initialization, first-boot users); they are kept and are part of the certified executed set. |
| `BLOODRAVEN_PITR_START mode=<mode> stop=<target or none> segments=<n> transactions=<n>` | Before the first segment. |
| `BLOODRAVEN_PITR_SEGMENT k=<index> file=<site>/<name> gtids=<count> transactions=<n>` | Before each segment (`file` is percent-encoded). |
| `BLOODRAVEN_PITR_COMPLETE segments=<n>` | After the replay; `segments=0` when the backup already is the target state. |
| `BLOODRAVEN_PITR_FAILED: mysqlbinlog exit=<rc> segment=<k>` / `BLOODRAVEN_PITR_FAILED: mysql exit=<rc> segment=<k> (…)` | A replay process failed; on a `mysqlbinlog` failure `mysql` is killed first. The `mysql` form's parenthesised note says `<k>` is where the failure was detected (the failing statement may be from an earlier segment, since `mysql` reads ahead) and appends a pipe or read error; a `mysql` still running then is killed (`exit=-9`). Also written to the termination message. |
| `BLOODRAVEN_PITR_FAILED: cannot open a session to …` / `BLOODRAVEN_PITR_FAILED: cannot read the replayed gtid_executed to prove the replay (R6): …` | The fresh session for the baseline proof (R2) or the replay proof (R6) could not be opened or read: an operational failure, not a mismatch. |
| `BLOODRAVEN_PITR_PARTIAL requested=<target> newest=<time or none>` | Outcome `Partial`. |
| `BLOODRAVEN_PITR_DIVERGENT count=<n>` and `BLOODRAVEN_PITR_DIVERGENT_SET gtids=<set, up to 64 KiB>` | The replay excluded transactions outside the target history. A set cut at 64 KiB ends with `...`. |
| `BLOODRAVEN_PITR_ON_HISTORY_EXCLUSIONS gtids=<set, up to 64 KiB>` | An excluded transaction on the target history precedes a replayed one. A set cut at 64 KiB ends with `...`. |
| `BLOODRAVEN_PITR_RESULT v=1 executed=<set>` or `BLOODRAVEN_PITR_RESULT v=1 executedSha256=<hex>` | The proven post-replay `@@global.gtid_executed`; only its digest when the set is longer than 2 KiB. |

A PITR Job's outcome comes from its main container's termination message, not
its log. On success `restore.py` (through `verify.sh` on a verification)
writes, as its last action:

```text
BLOODRAVEN_PITR_VERDICT v=2 mode= stop= outcome= archive= encryptionMode= sourceUID= sourceNamespace= sourceName= segments= files= transactions= lastFile=<site>/<name> newest= divergent=<n> onHistoryExcluded=<n> executedSha256= sites=
BLOODRAVEN_PITR_RESULT v=1 executed=<set>
BLOODRAVEN_PITR_ON_HISTORY_EXCLUSIONS gtids=<set>
```

- Line 1, the verdict, is at most 1024 bytes. `mode` is `timestamp` or
  `latest`; `stop` is the µs UTC target (empty in latest mode); `outcome` is
  `TargetCovered`, `Partial` or `ArchiveHead`; `archive` and `encryptionMode`
  identify the archive and `source*` its source group; `files` counts the
  distinct files the segments read; `transactions` the replayed transactions;
  `divergent` and `onHistoryExcluded` are GTID counts; `executedSha256` is the
  hex SHA-256 of the post-replay `gtid_executed`; `sites` lists at most eight
  staged sites plus a `+N` count. `stop`, `source*`, `lastFile`, `newest` and
  `sites` are percent-encoded.
- Line 2 carries the post-replay `gtid_executed`, or only
  `executedSha256=<hex>` when it is longer than 2 KiB.
- Line 3 is present only when the on-history exclusions are non-empty and
  short enough to fit; otherwise status records only their count.
- The message fits the main container's share of the kubelet's termination
  messages (12 KiB split among the pod's containers, at most 4 KiB each),
  which the operator renders as `BLOODRAVEN_TERMINATION_MESSAGE_LIMIT`
  (default 3072): line 3 is dropped first, then line 2 gives way to
  `executedSha256=<hex>`. No line is ever cut; `verify.sh` refuses
  `PITRCoverageInvalid: restore.py's verdict is N bytes, over …` rather
  than publish one that does not fit.

The operator accepts the verdict only from a Succeeded pod the Job owns, exit
code 0, matching the rendered mode, target, encryption and source group,
with a line 2 whose set hashes to `executedSha256`; anything else reports
`PITRCoverageInvalid`. It fills `pointInTime` in status from it. `restore.py`
and `verify.sh` write their own refusals there too (`PITRCoverageInvalid: …`,
`PITRArchiveIdentityMismatch: …`, `PITRExcludeIntersectsBackup: …`,
`PITRNoArchivedReplay: …`, `PITRReplayMismatch: …`,
`PITRReplayUnsupported: …`, `BLOODRAVEN_PITR_FAILED: …`,
`SanityCheckFailed: …`, `SanityCheckTimeout: …`). Other failures fall back
to the log tail. The failure detail recorded in status is the earliest
failing container's message. The served reason for `BLOODRAVEN_PITR_FAILED`
is `PITRReplayFailed`; the message keeps the sentinel.

The Python restore Job's text sentinel `BLOODRAVEN_RESTORE_COMPLETE` carries
only the source and target GTID and binlog coordinates, which the operator
reads best-effort; the `pitr*` keys are gone. These Job messages are not in
the Event reference contract above.

## Artifact cleanup Job

The finalizer's cleanup Job runs `bloodraven artifact-cleanup`. It logs
`artifact cleanup complete` (`objects`) or `artifact cleanup failed`
(`exitCode`, `error`), with `subcommand`, `backup`, `storageType` and
`location` on every record. These Job messages are best-effort, not part of
the Event reference contract. The operator reads the outcome from the
container's termination message instead:
`BLOODRAVEN_CLEANUP_COMPLETE objects=<n>` on success, or
`BLOODRAVEN_CLEANUP_FAILED: <reason>` on failure, with exit code 64 for a
refusal or configuration error and 75 for a transient storage error. An
abandoned (never-succeeded) backup's cleanup that finds no stamp but objects at
the location deletes nothing, exits 0 with
`BLOODRAVEN_CLEANUP_SKIPPED: <reason>` and logs WARN `artifact cleanup skipped`
(`reason`), with the same common fields.
