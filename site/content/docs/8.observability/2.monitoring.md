## Minimum alert set

| Signal | Why it matters | Runbook |
|---|---|---|
| Operator down | Reconciliation and DNS updates stop | [Operator unavailable](/docs/operations/runbooks#operator-unavailable) |
| No writable site | Application writes are unavailable | [Emergency manual promotion](/docs/operations/runbooks#emergency-manual-promotion) |
| Split-brain detected | More than one site may accept writes | [Split-brain recovery](/docs/operations/runbooks#split-brain-recovery) |
| Replication lag high | RPO risk is increasing | [Replication lag high](/docs/operations/troubleshooting#replication-lag-high) |
| Divergent transactions | A site holds transactions the primary lacks: an old primary cannot safely rejoin, or a replica (often replicating normally) is excluded from ordered updates and planned failovers | [Divergent recovery](/docs/operations/runbooks#divergent-old-primary-recovery), [Divergent replicas](/docs/operations/failover#divergent-replicas) |
| Backup stale | Recovery point is aging | [Failed backup](/docs/operations/runbooks#failed-backup) |
| Verification stale | Backups are not proven restorable | [Backup Verification](/docs/backup-and-restore/backup-verification) |
| PITR archive lagging | PITR RPO target may be missed | [Backup And Restore](/docs/backup-and-restore/backup-restore) |
| Dragonfly degraded | Cache/session continuity may be unavailable during planned failover | [Playground Dragonfly co-management](/docs/get-started/playground#dragonfly-co-management) |

## Operator health

Check these before debugging individual failover groups:

```bash
kubectl rollout status deployment/bloodraven -n bloodraven
kubectl logs -n bloodraven deploy/bloodraven
kubectl port-forward -n bloodraven deploy/bloodraven 8080:8080
curl http://localhost:8080/metrics | grep '^bloodraven_'
```

## Prometheus metrics

Metrics are served on `:8080/metrics` in standard Prometheus exposition format.

### Available metrics

Deployment lease metrics are listed in the [Deployment API metric reference](/docs/configuration/deployment-api#metrics-events-and-logs).
Active lease counts are dimensionless; age is seconds; grants, expirations,
revocations, and deferrals are event counts. The bounded labels are `kind`
(`migration`, `failover-hold`), grant `result` (four values), and revocation
`reason` (`TopologyChanged`, `OperatorRevoked`). `group` scales with managed
group names; `operationId`, `instance`, and token material are never metric
labels. Per group, active/age/expiry families have at most two kind series,
grants have at most eight kind/result series, and revocations have at most
four kind/reason series. The deferral counter uses a bounded controller
reason such as `DeploymentHold`. These families have no namespace label;
same-named groups in different namespaces cannot be distinguished by them.

| Metric | Type | Labels | Description |
|---|---|---|---|
| `bloodraven_poll_latency_seconds` | Histogram | `site` | Duration of each MySQL probe. A site in probe backoff records nothing on the polls that skip it. |
| `bloodraven_state_transitions_total` | Counter | `site`, `from`, `to` | Count of state transitions per site. `from` and `to` are kebab-case site states, as on `bloodraven_site_state`. |
| `bloodraven_taint_operations_total` | Counter | `site`, `action` | Count of node taint/untaint operations |
| `bloodraven_dns_flips_total` | Counter | `site` | Count of DNSEndpoint updates (DNS record flips) |
| `bloodraven_failovers_total` | Counter | `target_site` | Total number of failovers executed. Incremented after successful MySQL promotion. |
| `bloodraven_keyring_promotions_blocked_total` | Counter | `namespace`, `group`, `site`, `outcome` | Promotion decisions that skipped or refused a site because it is mid-keyring-rotation. `outcome` is `skipped` or `refused`. Incremented once per decision, not per Event reminder. |
| `bloodraven_primary_reassert_total` | Counter | `site` | Times the operator restored writability on the promoted primary after finding it fenced with no writable site remaining (typically the target's own sidecar re-fenced it with a stale lease right after a promotion, or the primary's MySQL restarted and came back with the `read_only=ON` every `mysqld` boots with). A steadily increasing counter means something keeps fencing the primary — check the sidecars' connectivity to the operator's auxiliary Service. |
| `bloodraven_websocket_connected_clients` | Gauge | -- | Number of currently connected WebSocket clients |
| `bloodraven_replication_lag_seconds` | Gauge | `namespace`, `group`, `site`, `role` | Replication lag in seconds on a follower site. `-1` if lag is NULL (not replicating). Only present for replica sites. `role` is the kebab-case of `spec.sites[].role`: `primary-candidate`, `disaster-recovery`, or `read-only`. |
| `bloodraven_replication_running` | Gauge | `namespace`, `group`, `site`, `role`, `thread` | Whether a replication thread is running (`1`=yes, `0`=no). Thread is `io` or `sql`. Only present for replica sites. |
| `bloodraven_restore_reclone_pending` | Gauge | `namespace`, `group`, `site`, `phase` | `1` for each site a full-instance in-place restore has not recloned yet (`status.restoreReclones.pending`); `phase` is the kebab-case of the queue phase (`armed`, `draining`, `held`). Such a site's replication receiver is stopped by design until its reclone, so exclude it from replication alerts (see `BloodravenReplicationDown`). The series is removed when the site leaves the queue. |
| `bloodraven_replication_source_state` | Gauge | `namespace`, `group`, `site`, `state` | Direct-source convergence state set for each follower, scoped by failover group. `state` is one of `converged`, `pending`, or `blocked`; one series is `1` and the others are `0`. Cleared for the active primary. |
| `bloodraven_site_state` | Gauge | `namespace`, `group`, `site`, `role`, `state` | Current site state as a state-set: `1` for the current state, `0` for others. `state` is the kebab-case of `status.sites[].state`: `writable`, `read-only`, `unreachable`, or `unknown`. `role` is the kebab-case of `spec.sites[].role`. |
| `bloodraven_divergent_transactions` | Gauge | `site` | Number of transactions on a site that the primary lacks: a returning old primary after emergency failover, or a replica found by the replica GTID audit (which runs whatever the replication threads report). `0` when healthy. Non-zero means the site is `RecoveryBlocked`: it is not promoted by an ordered update or planned failover, and `Degraded` is `True` with reason `DivergentTransactions`. |
| `bloodraven_own_transactions_lost` | Gauge | `site` | Number of transactions a site issued itself, under a `server_uuid` it has had, that another site holds and the site lacks (`status.sites[].lostGtid`). `0` when healthy. Non-zero means the site is not replicated and not promoted until it is recloned, which the operator does itself (`recoveryState: RecloneRequired`); a value that stays non-zero means the automatic reclone cannot run (the `RecoveryPending` condition says why). |
| `bloodraven_archiver_upload_failures` | Gauge | `namespace`, `group`, `site` | Cumulative PITR archiver upload failures reported by the per-site sidecar, including one per failed archive store construction attempt. Monotonic except across sidecar restarts — use `increase()` / `rate()` in dashboards. |
| `bloodraven_archiver_last_upload_timestamp_seconds` | Gauge | `namespace`, `group`, `site` | Unix timestamp of the last successful PITR binlog archive per site. `0` if nothing archived yet. A read-only site's value advances when it uploads the [tail of its last writable era](/docs/backup-and-restore/backup-restore#archiving-the-tail-of-an-outgoing-primary), for example after a planned failover or before a reclone; a site that has only ever been a replica stays at `0`. |
| `bloodraven_archiver_backlog_files` | Gauge | `namespace`, `group`, `site` | Sealed binlogs present in the MySQL index but missing from the archiver manifest at the end of the last scan. `>0` means archival is falling behind. On a read-only site it counts only the sealed binlogs of its writable-era tail, while they are uploading or failing to upload; it is `0` when the site has no tail, and also when the site may not upload its tail (`tail.state: Blocked` in `/archiver/status`, with the reason). |
| `bloodraven_backup_verified_timestamp_seconds` | Gauge | `group`, `profile` | Unix timestamp of the last `Succeeded` `MysqlBackupVerification` per profile. Anchor staleness alerts on this gauge &mdash; a fresh `bloodraven_backup_last_success_timestamp_seconds` without a fresh verification means nobody has *proven* the backup can be restored. |
| `bloodraven_backup_verification_last_attempt_timestamp_seconds` | Gauge | `group`, `profile` | Unix timestamp of the last terminal verification attempt, regardless of result. Distinguishes "verification never ran" from "verification ran but failed". |
| `bloodraven_backup_verification_runs_total` | Counter | `group`, `profile`, `result` | Terminal verification attempts labelled `success` or `failure`. |
| `bloodraven_backup_verification_duration_seconds` | Histogram | `group`, `profile` | Wall-clock duration of a verification run. |
| `bloodraven_backup_verification_replay_lag_seconds` | Gauge | `group`, `profile` | For successful `mode: Latest` PITR verifications only: `completionTime − pointInTime.newestReplayedCommitTime`. Timestamp drills never set it, because their newest replayed event is a historical target. A rising value means archived binlogs trail the live primary &mdash; alert below your RPO target. |
| `bloodraven_restore_duration_seconds` | Histogram | `namespace`, `group`, `restore_kind`, `target_site` | Data-plane duration of successful restore Jobs. `restore_kind` is `init_from_backup` or `in_place`; duration starts at Job `status.startTime` when available and ends when the operator observes terminal success. |
| `bloodraven_restore_last_success_timestamp_seconds` | Gauge | `namespace`, `group`, `restore_kind`, `target_site` | Unix timestamp of the last successful restore Job observation. |
| `bloodraven_restore_last_source_size_bytes` | Gauge | `namespace`, `group`, `restore_kind`, `target_site` | Source backup artifact size in bytes for the most recent successful restore when known from `MysqlBackup.status.sizeBytes`. Direct S3/PVC restores and unknown sizes clear/omit this series so an older known size is not reported as current. |
| `bloodraven_dragonfly_site_up` | Gauge | `group`, `site` | Dragonfly site reachability from the operator's latest `INFO replication` poll (`1` reachable, `0` unreachable). |
| `bloodraven_dragonfly_promotions_total` | Counter | `group`, `target_site`, `result` | Dragonfly promotion attempts labelled `success`, `failed`, `skipped`, or `sessions_lost`. `success` is a `REPLTAKEOVER` that preserved continuity. `sessions_lost` is a successful `REPLICAOF NO ONE` fallback — the target is writable but session continuity is not guaranteed. `failed` means the target was not promoted. |
| `bloodraven_dragonfly_manager_panics_total` | Counter | `namespace`, `name` | Panics recovered inside the Dragonfly manager polling loop. Any increase should be investigated. |
| `bloodraven_license_info` | Gauge | `namespace`, `group`, `organization`, `edition`, `valid` | Constant-1 info series for the license observed on a failover group. `edition` is `community`, `production`, or `organization`. `valid` is the string `true` or `false`. No license is `edition="community"`, `valid="true"`. An invalid token is `edition="community"`, `valid="false"`. An ended update period stays `valid="true"`. One series per group. |
| `bloodraven_license_updates_expiry_timestamp_seconds` | Gauge | `namespace`, `group`, `organization`, `edition` | Unix timestamp when the paid update period ends. Absent for community and invalid licenses. A past value is the supported perpetual state. Alert with `(bloodraven_license_updates_expiry_timestamp_seconds - time()) / 86400 < 30`. |

Dragonfly replica full-resync state is exposed on the CR as
`status.dragonfly.sites[].syncInProgress`, with companion fields
`linkStatus`, `lastIOSecondsAgo`, and `ready`. `syncInProgress` and
`lastIOSecondsAgo` are absent when Dragonfly's `INFO replication` did not
report them. If you export custom-resource
status with kube-state-metrics or another CRD status adapter, alert when
`syncInProgress` remains true for longer than the expected warm-up window or
when it toggles repeatedly outside planned failovers and Dragonfly image
rollouts. Frequent full resyncs can spike master latency and reduce planned
failover session-preservation confidence.

### Scrape configuration

Add a scrape job for the operator:

```yaml
# prometheus.yml
scrape_configs:
  - job_name: bloodraven
    kubernetes_sd_configs:
      - role: pod
        namespaces:
          names: [bloodraven]
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_label_app_kubernetes_io_name]
        regex: bloodraven
        action: keep
      - source_labels: [__meta_kubernetes_pod_container_port_number]
        regex: "8080"
        action: keep
```

Or if using the Prometheus Operator, create a `PodMonitor`:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: bloodraven
  namespace: bloodraven
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: bloodraven
  podMetricsEndpoints:
    - port: metrics
      interval: 15s
```

### Alerting rules

Recommended alerts:

```yaml
groups:
  - name: bloodraven
    rules:
      # Site has no healthy primary
      - alert: BloodravenNoPrimary
        expr: |
          count by (site) (
            bloodraven_state_transitions_total{to="writable"}
          ) == 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Site {{ $labels.site }} has no writable primary"

      # High poll latency may indicate network issues
      - alert: BloodravenHighPollLatency
        expr: |
          histogram_quantile(0.99, rate(bloodraven_poll_latency_seconds_bucket[5m])) > 1
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Poll latency to {{ $labels.site }} exceeds 1 second (p99)"

      # Failover occurred
      - alert: BloodravenFailoverOccurred
        expr: increase(bloodraven_failovers_total[5m]) > 0
        labels:
          severity: warning
        annotations:
          summary: "Failover occurred: {{ $labels.target_site }} promoted as new primary"

      # Replication lag exceeds threshold on a data-bearing replica.
      # role=~"primary-candidate|disaster-recovery" pages RPO risk and stays
      # silent on role="read-only" readers, whose lag is designed (they are shed
      # from mysql-<group>-replicas). For promotable replicas only, use
      # role="primary-candidate".
      - alert: BloodravenReplicationLagging
        expr: bloodraven_replication_lag_seconds{role=~"primary-candidate|disaster-recovery"} > 300
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "Replication lag on {{ $labels.group }}/{{ $labels.site }} ({{ $labels.role }}) is {{ $value }}s"

      # A site holds transactions the primary lacks (old primary after an
      # emergency failover, or a replica found by the GTID audit)
      - alert: BloodravenDivergentTransactions
        expr: bloodraven_divergent_transactions > 0
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.site }} has {{ $value }} transactions the primary lacks — reclone it or make the primary contain them; ordered updates and planned failovers will not promote it"

      # Replication thread down on a data-bearing replica. Sites awaiting
      # their post-restore reclone have their receiver stopped by design.
      - alert: BloodravenReplicationDown
        expr: |
          bloodraven_replication_running{role=~"primary-candidate|disaster-recovery"} == 0
          unless on(namespace, group, site) bloodraven_restore_reclone_pending == 1
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Replication {{ $labels.thread }} thread stopped on {{ $labels.group }}/{{ $labels.site }} ({{ $labels.role }})"

      # A failed full-instance restore left peers held with their
      # replication stopped; an administrator must decide what to keep.
      - alert: BloodravenRestoreReclonesHeld
        expr: bloodraven_restore_reclone_pending{phase="held"} == 1
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.group }}/{{ $labels.site }} is held after a failed in-place restore: no replication, not promotable"

      # No writable site in a failover group
      - alert: BloodravenNoWritableSite
        expr: |
          max by (namespace, group) (bloodraven_site_state{state="writable"}) == 0
        for: 30s
        labels:
          severity: critical
        annotations:
          summary: "No site is currently writable in {{ $labels.namespace }}/{{ $labels.group }}"

      # Dragonfly site unavailable; MySQL remains authoritative, but planned
      # session/cache continuity is at risk.
      - alert: BloodravenDragonflySiteDown
        expr: bloodraven_dragonfly_site_up == 0
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "Dragonfly site {{ $labels.site }} is unreachable for {{ $labels.group }}"

      # Failed Dragonfly promotion means the MySQL failover may have succeeded
      # with cache unavailable.
      - alert: BloodravenDragonflyPromotionFailed
        expr: increase(bloodraven_dragonfly_promotions_total{result="failed"}[5m]) > 0
        labels:
          severity: warning
        annotations:
          summary: "Dragonfly promotion failed for {{ $labels.group }} target {{ $labels.target_site }}"

      # Empty-master fallback: target is writable but REPLTAKEOVER did not run.
      - alert: BloodravenDragonflySessionsLost
        expr: increase(bloodraven_dragonfly_promotions_total{result="sessions_lost"}[5m]) > 0
        labels:
          severity: warning
        annotations:
          summary: "Dragonfly promoted {{ $labels.target_site }} via REPLICAOF NO ONE for {{ $labels.group }}; session continuity is not guaranteed"

      # A recovered panic keeps the manager alive, but it is still a bug signal.
      - alert: BloodravenDragonflyManagerPanic
        expr: increase(bloodraven_dragonfly_manager_panics_total[5m]) > 0
        labels:
          severity: critical
        annotations:
          summary: "Dragonfly manager recovered a panic for {{ $labels.namespace }}/{{ $labels.name }}"
```

## Grafana dashboards

Bloodraven ships five ready-to-use Grafana dashboards covering every metric the operator publishes. They live in the chart at [`charts/bloodraven/dashboards/`](https://github.com/ShipStream/bloodraven/tree/main/charts/bloodraven/dashboards) and are also installable as ConfigMaps via the Helm chart.

| Dashboard | UID | What it's for |
|---|---|---|
| **Overview** | `bloodraven-overview` | Health at a glance: writable sites, state timeline, failover activity, replication lag, backup/archiver freshness. Start here. |
| **Failover & Topology** | `bloodraven-failover` | Auto and planned failovers, durations, lag-wait histograms, state transitions, DNS flips, node taints, split-brain resolves. |
| **Replication & Recovery** | `bloodraven-replication` | Replication lag per site, IO/SQL thread up/down, divergent transactions, reclone ops, poll latency. |
| **Backups & Verification** | `bloodraven-backups` | Backup run/failure counts, duration, size, last-success age, verification runs, PITR replay lag. |
| **PITR Archiver** | `bloodraven-archiver` | Per-site archiver upload age, backlog files, upload failures. |

All five dashboards share a `datasource` variable and cross-link in the top-left corner, so you can roam between them without losing the time range.

### Setup — three paths

Pick whichever matches your Grafana install. All three use the same JSON files.

#### 1. Helm chart + kube-prometheus-stack (zero-config)

If your Grafana is deployed by [kube-prometheus-stack](https://github.com/prometheus-community/helm-charts/tree/main/charts/kube-prometheus-stack) or the upstream [grafana/grafana](https://github.com/grafana/helm-charts/tree/main/charts/grafana) chart, its dashboard-sidecar watches for ConfigMaps labelled `grafana_dashboard: "1"` by default. Just enable the flag:

```bash
helm upgrade --install bloodraven bloodraven/bloodraven \
  --namespace bloodraven --create-namespace \
  --set grafanaDashboards.enabled=true
```

The chart renders one ConfigMap per dashboard, the sidecar picks them up within ~30s, and the dashboards appear in a "Bloodraven" folder in Grafana. No restart, no re-login.

Common tweaks in `values.yaml`:

```yaml
grafanaDashboards:
  enabled: true
  # Sidecar is often scoped to the monitoring namespace
  namespace: monitoring
  # Change folder name
  folder: MySQL / Bloodraven
  # If your sidecar watches a non-default label
  label: grafana_dashboard
  labelValue: "1"
```

#### 2. Grafana file-based provisioning

If you provision Grafana from disk, copy the JSON files into your provisioning directory and point a provider at them:

```bash
# One-time copy (re-run on upgrade to get dashboard updates)
kubectl -n monitoring cp -c grafana \
  bloodraven/charts/bloodraven/dashboards \
  grafana-pod:/var/lib/grafana/dashboards/bloodraven
```

```yaml
# /etc/grafana/provisioning/dashboards/bloodraven.yaml
apiVersion: 1
providers:
  - name: bloodraven
    folder: Bloodraven
    type: file
    disableDeletion: false
    updateIntervalSeconds: 30
    allowUiUpdates: true
    options:
      path: /var/lib/grafana/dashboards/bloodraven
```

#### 3. Manual UI import

For one-off installs:

1. In Grafana, click **Dashboards → New → Import**.
2. Paste the contents of any file in [`charts/bloodraven/dashboards/`](https://github.com/ShipStream/bloodraven/tree/main/charts/bloodraven/dashboards).
3. Pick your Prometheus datasource when prompted.
4. Repeat for each dashboard you want.

Cross-dashboard links use the dashboard UID (`bloodraven-overview`, etc.) so they keep working as long as you don't edit the UID on import.

### Prerequisites

- Your Prometheus must be scraping the operator — either the ServiceMonitor the chart ships (`--set metrics.serviceMonitor.enabled=true`) or an equivalent scrape job.
- The dashboards use standard Prometheus histograms/gauges, so no recording rules are required. Alerts in the next section can sit alongside them.

## Kubernetes Events

Bloodraven records standard Kubernetes Events on all five of its kinds: `MysqlFailoverGroup`, `MysqlBackup`, `MysqlBackupVerification`, `MysqlDatabase` and `MysqlStandbyCluster`. These events can be forwarded to Slack, PagerDuty, or any webhook endpoint using tools like [Kubewatch](https://github.com/robusta-dev/kubewatch), [Argo Events](https://argoproj.github.io/argo-events/), or [Event Router](https://github.com/heptiolabs/eventrouter).

The tables below list every Event reason the operator records, with the one type (`Normal` or `Warning`) it is always recorded with. They are generated from the reason registry in `api/v1alpha1/events.go`. Reasons are named `<Subject><PastTenseVerb>`, optionally followed by a qualifier that names the cause: `Succeeded` and `Failed` for an operation, `Rejected` for a request that is not admitted, `Refused` for an automatic action blocked for safety. An Event that accompanies a status condition and repeats that condition's reason (a condition mirror) keeps the condition's reason instead.

### Topology and failover

Recorded on `MysqlFailoverGroup`.

| Reason | Type | Description |
|---|---|---|
| `FailoverExecuted` | Normal | A failover completed and a new primary was promoted. |
| `DataLossDetected` | Warning | Divergent transactions found on old primary after emergency failover. |
| `DivergentReplicaDetected` | Warning | The replica GTID audit found a replica holding transactions the primary lacks; emitted on first detection and when the count changes. |
| `DivergenceResolved` | Normal | A replica's divergence report was cleared by a fresh containment proof (after a reclone, or after the primary was made to contain the set). |
| `DivergentSitePromoted` | Warning | A site carrying a divergence report became the primary (an emergency failover with no clean candidate); its extra transactions are now authoritative. Also recorded as the `DivergentPromotion` condition. Repeats the condition reason. |
| `OldPrimaryRecovered` | Normal | The old primary recovered after a failover and is now replicating from the new primary. |
| `OwnTransactionsLost` | Warning | A site lacks transactions it issued itself under a `server_uuid` it has had, and the primary holds them: its volume came back older, or a crash lost them. Replication cannot bring them back, because the site's receiver drops events that carry its own `server_id`, and a promoted site would issue the same GTIDs again. The message names the site, the set (`status.sites[].lostGtid`) and the primary it was compared with. The operator does not start the site's replication, does not promote it and reclones it (`recoveryState: RecloneRequired`); a site that also holds transactions the primary lacks stays `RecoveryBlocked` for an administrator. When the holder is not the primary but another site that holds transactions the primary lacks, the message says so: the site keeps replicating and is not recloned, and it is not promoted until that other site is repaired. Emitted on detection and when the set changes; once more after an operator restart when the installed CRD does not store `lostGtid`. See [A returning site that lost its own transactions](/docs/operations/failover#a-returning-site-that-lost-its-own-transactions). Repeats the condition reason. |
| `OwnTransactionsLostResolved` | Normal | A site's `OwnTransactionsLost` report ended. The message gives the cause: the site was recloned; a new comparison found it holds every transaction it issued that the primary holds; the report had been made against another site and the current primary never held those transactions (nothing was repaired); or the witness that held them no longer does. |
| `OwnTransactionsLostRecloneFailing` | Warning | The automatic reclone of a site that lacks transactions it issued itself has failed three or more times in a row. The operator keeps asking, with a wait that doubles from 5 minutes to at most 2 hours; every failed clone made the primary send its whole data set. The message gives the count and the next attempt; the clone's error is in the `BootstrapFailed` Degraded condition. Emitted for the third and every later failure. |
| `PromotionRefusedOwnTransactionsLost` | Warning | Automatic promotion refused: the remaining candidates lack transactions they issued themselves (`recoveryState: RecloneRequired`) and would issue those GTIDs again. The group stays without a writable primary until the primary returns (the sites are then recloned from it) or an administrator promotes one by hand. |
| `OwnTransactionsLostSitePromoted` | Warning | A site carrying an `OwnTransactionsLost` report became the primary without a reclone (an administrator made it writable). Unless its `server_uuid` was changed first, it issues the lost GTIDs again: the same GTID then names two transactions, replicas that hold the first skip the second, and the PITR archive of the group cannot be trusted across them. The message names the site and the set. |
| `SplitBrainDetected` | Warning | Both sites are writable (split brain). Also emitted when a second site answers writable before the debounce confirms it; the message names the unconfirmed sites, and fencing waits for the confirmation. |
| `NoPrimaryDetected` | Warning | Both sites are read-only (no primary). Not emitted when the cause is a mid-rotation or pending-reclone promotion refusal (that is `KeyringPromotionRefused` or `PromotionRefusedReclonePending`), or while the group is `Initializing` after an operator start. |
| `TotalLossDetected` | Warning | Both sites are unreachable. |
| `SiteRecovered` | Normal | Degraded condition cleared, topology is healthy. Not emitted when the group leaves `Initializing`, which is not a degraded state. |
| `PromotionRefusedReclonePending` | Warning | Automatic promotion refused: the remaining candidates have not been recloned since a full-instance in-place restore and still hold pre-restore data (`status.restoreReclones.pending`). ### Refused workloads and metadata

Recorded on `MysqlFailoverGroup` and `MysqlBackupVerification`.

The operator refuses to act on something until a human fixes it, and does not retry in a loop. Each Event repeats the condition reason it sets and is recorded once per finding.

| Reason | Type | Description |
|---|---|---|
| `WorkloadSelectorMismatch` | Warning | A site's Deployment or Dragonfly StatefulSet has a selector other than the one the operator renders (for example an object left from an older release with other label keys). Delete it so the operator re-creates it (a MySQL site keeps its PVC). Repeats the condition reason. |
| `MetadataVersionUnsupported` | Warning | An internal annotation payload carries a `schemaVersion` this operator does not know (a newer operator wrote it, or it was edited). ### PITR archiving

Recorded on `MysqlFailoverGroup`.

The archive identity reasons are refusals, not transient errors: they do not clear by themselves. They are listed in [Archive identity](/docs/backup-and-restore/backup-restore#archive-identity).

Divergent rows in a site's manifest (archived transactions its server no longer has, for example the tail an old primary archived before it was recloned) are evidence for restores, not an archiver error. They fire no Event and leave the condition `True`; its message lists them, for example `Every site reports a running archiver with a ready store and no error; iad: 1 divergent row (...)`. Only a server that could issue those GTIDs again is an error: its sidecar reports `reissuableGtids`, and the condition turns `False` with reason `ArchiverError` ([Reissue risk](/docs/backup-and-restore/pitr-history-repair#reissue-risk)).

A `PITRArchiveNotReady` → `PITRArchiveRecovered` pair is expected, not an incident, when:

- A pod takes more than 60 s to come back during a rollout or node move (`SidecarUnreachable`), for example while an RWO volume detaches and reattaches.
- A new group's pods, or a bootstrapped site, take more than 5 minutes to start answering (`SidecarUnreachable`).
- PITR is enabled with `updateStrategy.type: Recreate`, or a pod does not roll onto the PITR configuration through the ordered update (`ArchiverDisabled`). With the default ordered update, sites waiting for it report `Unknown`/`AwaitingRollout` with no Event, for up to 30 minutes; a rollout still pending after that is `ArchiverDisabled`, as is a PITR spec whose `profileName` renders no archiver.
- MySQL takes more than about a minute to accept connections after a pod start, for example during a long InnoDB crash recovery (`ArchiverError`, `role check: ...`).

Two failed archiver scans in a row (about 2 minutes at the default 60 s scan interval) also produce a pair if the third scan succeeds. Alert on a `PITRArchiveNotReady` without a following `PITRArchiveRecovered` within, say, 10 minutes, or on the condition itself.

| Reason | Type | Description |
|---|---|---|
| `PITRArchiveNotReady` | Warning | The `PITRArchiveReady` condition entered `False` (from absent, `Unknown` or `True`). The message reads "PITRArchiveReady is False (<reason>): <message>", with the reason (`ArchiveStoreInitFailed`, an archive identity refusal such as `ArchiveLegacy`, `ArchiveForeign`, `ArchiveCopy`, `ArchiveDescriptorMissing`, `ArchiveEncryptionMismatch`, `ArchiveKeyMismatch`, `ArchiveVersionUnsupported`, `ArchiveStoreUnsupported` or `ArchiveUnsafeHistory`, then `ArchiverError`, `SidecarOutdated`, `ArchiverDisabled`, `SidecarUnreachable`) and every affected site. Not repeated while the condition stays `False`, even if the reason changes, and not re-fired by an operator restart. |
| `PITRArchiveRecovered` | Normal | The `PITRArchiveReady` condition returned from `False` to `True` after 2 clean poll rounds: "PITRArchiveReady is True again: every site reports a running archiver with a ready store and no error". |
| `PITRArchiveUnsafeHistoryDetected` | Warning | Edge-triggered on entering `PITRArchiveReady=False` / `ArchiveUnsafeHistory`: a site persisted its history-integrity marker after an out-of-band change (`SET GLOBAL`, a hand-edited my.cnf): such options in `spec.mysqlConf` are refused instead (`PITRMysqlConfRefused`). Fires in addition to `PITRArchiveNotReady`. The marker removes every restore target that needs that site's bytes, including targets before the violation. Remedy: undo the change, new prefix plus full backup ([Unsafe history marker](/docs/backup-and-restore/pitr-history-repair#unsafe-history-marker)). |
| `PITRArchiveReissueRiskDetected` | Warning | The active site changed to a site whose server could reissue GTIDs its archive already holds: its manifest has divergent or quarantined rows with transactions the server no longer has, issued under the `server_uuid` it still has (a data directory restored or reset without a clone, or a clone by a release that kept the recipient's `server_uuid`). The message lists them; a sidecar that has not reported that verdict warns on the row counts instead. Its new writes reuse those GTIDs: start a new archive prefix and take a full backup ([Reissue risk](/docs/backup-and-restore/pitr-history-repair#reissue-risk)). |
| `PITRArchiveTailNotArchived` | Warning | A reclone started although the recipient's binary log tail was not confirmed archived: before CLONE wipes a site's binary logs the operator rotates them and waits up to 2 minutes for the site's sidecar to archive the sealed tail. The message names the site and why the wait ended (the sidecar did not answer, the rotation was not acknowledged, the archiver was still uploading or could not upload). A point-in-time restore whose window needs transactions only that tail held refuses `PITRArchiveGap`. Not emitted when PITR is not enabled. |
| `PITRMysqlConfRefused` | Warning | While PITR is enabled, group or site `spec.mysqlConf` sets an option that breaks PITR replay (a replication or binlog filter, `binlog_format≠ROW`, `binlog_row_image≠FULL`). The option is left out of the rendered my.cnf and `PITRMysqlConfAccepted` is `False` / `PITRUnsafeSettingRefused`; fires once per refused set. Remove the option from `spec.mysqlConf`. |

Emitted on deletion under `deletionPolicy: Delete`, and on an owner rotation or host removal, where the account still loses its rights on this database unless this CR's own `spec.grants[]` declares it. |
| `OwnerUserReservedSkipped` | Warning | An owner account this CR recorded has since become a group-level principal, so it is never dropped. Emitted on deletion under `deletionPolicy: Delete`, and on an owner rotation or host removal, where its rights on this database are still revoked. |
| `UserRotated` | Normal | The username in a `spec.users[]` Secret changed: the new principal was created and granted, then the previous one was revoked and dropped. Also emitted when an abandoned rotation target is dropped before rotating to a newer username. |
| `UserHostsRemoved` | Normal | Hosts were removed from a `spec.users[]` entry's `hosts`; that principal was revoked and dropped on exactly those hosts. |
| `UserRemoved` | Normal | A `spec.users[]` entry was removed; its principal was revoked and dropped on the hosts recorded for it. |
| `UserTransferred` | Normal | A `spec.users[]` entry was removed, but its principal is now declared by another surface of this CR (another `users[]` entry, the owner or `spec.grants[]`), so the account is kept and no `UserRemoved` follows. |
| `UserDropSkipped` | Warning | A `users[]` principal was not dropped because this CR's own `spec.grants[]` declares it or another live `MysqlDatabase` still claims it. Emitted on deletion under `deletionPolicy: Delete`, and on a rotation, entry removal or host removal, where the principal still loses its rights on this database unless this CR's own `spec.grants[]` declares it. |
| `UserReservedSkipped` | Warning | A `users[]` principal this CR recorded has since become a group-level principal, so it is never dropped. Emitted on deletion under `deletionPolicy: Delete`, and on a rotation, entry removal or host removal, where its rights on this database are still revoked. |
| `PartialRevokeLifted` | Normal | The operator removed a restriction on an impossible legacy escaped spelling of the database name from an account this CR recorded; such restrictions were left by older operator builds. |
| `TenantPrivilegeRestriction` | Warning | The best-effort repair of legacy escaped-schema restrictions found something it will not or could not fix: the operator account is restricted on the database (repairs on that spelling are skipped for every account), a recorded tenant account has a restriction on the real schema that needs review by the privilege owner, or a repair step failed. Normal tenant reconciliation continues; see the privilege restriction recovery playbook. |
| `InvalidSpec` | Warning | The spec failed validation at reconcile time (for example an identifier or a username from a Secret that does not match the allowed pattern, or a MySQL system schema as `databaseName`). The CR is `Failed` with `Ready=False/InvalidSpec` and no SQL runs. Repeats the condition reason. |
| `MySQLError` | Warning | MySQL refused a statement with a non-transient error while applying the database, its accounts or grants, or while revoking or dropping a retired account. The CR is `Failed` with `Ready=False/MySQLError` and the message carries the error; retried every minute. Repeats the condition reason. |
| `DatabaseNameConflict` | Warning | An older `MysqlDatabase` on the same group already declares this `databaseName`. This CR is `Failed` with `Ready=False/DatabaseNameConflict` before any SQL runs, and re-checked every minute. Repeats the condition reason. |
| `DatabasePreExists` | Warning | The schema already exists and `status.databaseCreated` does not say this CR created it, so adoption is refused. The CR is `Failed` with `Ready=False/DatabasePreExists`; re-checked every minute. Repeats the condition reason. |
| `OwnerConflict` | Warning | An older `MysqlDatabase` on the same group shares this CR's owner Secret or owner MySQL user. This CR is `Failed` with `Ready=False/OwnerConflict` before any SQL runs; give each `MysqlDatabase` a distinct owner. Repeats the condition reason. |
| `OwnerUserReserved` | Warning | The owner Secret names a group-level principal (`root`, `replicator`, a MySQL system account or a `spec.credentials` user). The CR is `Failed` with `Ready=False/OwnerUserReserved` and no SQL runs; use a tenant-specific username. Repeats the condition reason. |
| `PreExistingOwnerUser` | Warning | An owner account `user@host` already exists and no record of this CR names that user on that host, so adoption is refused. The CR is `Failed` with `Ready=False/PreExistingOwnerUser`; re-checked every minute. Repeats the condition reason. |
| `PreExistingUser` | Warning | A `spec.users[]` account `user@host` already exists and no record of this CR names it on that host, so adoption is refused. The CR is `Failed` with `Ready=False/PreExistingUser`; re-checked every minute. Repeats the condition reason. |
| `UserClaimedBySibling` | Warning | A `spec.users[]` username is already claimed by another `MysqlDatabase` on the group (as its owner, in its `spec.grants[]`, or in its `users[]` ledger). The CR is `Failed` with `Ready=False/UserClaimedBySibling` before any SQL runs; share a group-level principal through `spec.grants[]` instead. Repeats the condition reason. |
| `UserReserved` | Warning | A `spec.users[]` Secret names a group-level principal (`root`, `replicator`, a MySQL system account or a `spec.credentials` user). The CR is `Failed` with `Ready=False/UserReserved` and no SQL runs. Repeats the condition reason. |
| `GrantUserMissing` | Warning | A `spec.grants[]` user does not exist at host `%`; the operator never creates it. The CR is `Failed` with `Ready=False/GrantUserMissing`; create the principal at the group level and the CR goes `Ready` on its own (re-checked every minute). Repeats the condition reason. |
| `PartialRevokesOff` | Warning | The operator cannot confirm or enable `partial_revokes=ON` on the primary, so tenant changes are deferred. The CR is `Pending` with `Ready=False/PartialRevokesOff` and retries; existing accounts and grants are left intact. Repeats the condition reason. |

### MysqlStandbyCluster

Recorded on `MysqlStandbyCluster`.

| Reason | Type | Description |
|---|---|---|
| `BucketScanned` | Normal | A discovery scan changed `status.discovered` (the newest dump, the archive identity or its binlog window). The message gives the dump and the manifest and binlog counts. Rescans that find nothing new emit nothing. |
| `ManifestParseFailed` | Warning | A binlog manifest under the source prefix could not be read or parsed. The source archive is refused: `SourceConfigKnown=False` with the archive reason (for example `ArchiveLegacy`, `ArchiveVersionUnsupported` or `ArchiveUnreadable`), and `latestDump` is published without `binlogArchive`. |
| `MetadataParseFailed` | Warning | The newest dump's `@.json` metadata is unreadable or malformed. `SourceConfigKnown` is `False` with reason `MetadataUnreadable`; the bucket itself stays readable. |
| `PITRArchiveRefused` | Warning | On a `MysqlStandbyCluster`: the source archive was refused (`SourceConfigKnown=False` with an archive reason); emitted when the reason changes. |
| `AuthFailed` | Warning | The archive store for the source bucket could not be constructed (for example bad credentials or an unusable endpoint). `BucketReadable` and `SourceConfigKnown` are `False` with reason `AuthFailed`; discovery retries every discovery interval and the Event repeats on each failed attempt. Repeats the condition reason. |
| `ConfigError` | Warning | The standby's storage backend could not be resolved: an invalid `spec.source.s3` bucket, prefix or endpoint (a prefix must name more than the bucket root), an unreadable `credentialsSecretName` Secret, or a `spec.source.decryption.passphraseSecretKeyRef` Secret or key that is missing or empty. `BucketReadable` and `SourceConfigKnown` are `False` with reason `ConfigError`; retried every discovery interval. Repeats the condition reason. |
| `ListFailed` | Warning | Listing the source bucket prefix failed. `BucketReadable` is `False` with reason `ListFailed` and `status.discovered` keeps the last successful scan; retried every discovery interval. Repeats the condition reason. |

### Forwarding events with Kubewatch

[Kubewatch](https://github.com/robusta-dev/kubewatch) can watch for Kubernetes Events and forward them to Slack, PagerDuty, webhooks, and more. Example configuration to forward all Bloodraven events to Slack:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: kubewatch
data:
  .kubewatch.yaml: |
    handler:
      slack:
        channel: "#mysql-alerts"
    resource:
      event: true
    namespaces:
      - bloodraven
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kubewatch
spec:
  template:
    spec:
      containers:
        - name: kubewatch
          env:
            - name: KW_SLACK_TOKEN
              valueFrom:
                secretKeyRef:
                  name: kubewatch-secrets
                  key: slack-token
```

::note

Store credentials in a Kubernetes Secret, not in the ConfigMap. The `KW_SLACK_TOKEN` environment variable is read by Kubewatch at startup.
::
[Argo Events](https://argoproj.github.io/argo-events/) and [Event Router](https://github.com/heptiolabs/eventrouter) are alternatives that offer richer filtering and routing capabilities.

## Status API

The operator serves a JSON status API on `:8082`.

### `GET /status`

Returns the current state of all failover groups:

```bash
curl http://localhost:8082/status
```

```json
{
  "default/orders": {
    "activeSite": "iad",
    "sites": [
      {
        "name": "iad",
        "role": "PrimaryCandidate",
        "state": "Writable"
      },
      {
        "name": "pdx",
        "role": "PrimaryCandidate",
        "state": "ReadOnly"
      }
    ],
    "pollTime": "2025-01-01T00:00:00Z"
  }
}
```

### `GET /active-site`

Returns the active (writable) site for a specific failover group. Used by the sidecar's startup safety net.

```bash
curl "http://localhost:8082/active-site?namespace=default&group=orders"
```

```json
{
  "namespace": "default",
  "group": "orders",
  "activeSite": "iad"
}
```

| Status | Meaning |
|---|---|
| `200` | Failover group found. `activeSite` may be `""` if no single writable site exists (first boot, split-brain). |
| `400` | Missing `namespace` or `group` query parameter. |
| `404` | Failover group not found on this operator instance. |
| `503` | Operator has no active topology managers (startup race or non-leader replica). |

### `GET /ws/status`

WebSocket endpoint that streams the full topology of each failover group in
real time. A message is sent at the end of every operator poll cycle, not only
on state transitions, so dashboards can render live counters and health
indicators. The cadence is every 2 seconds per group (`pollInterval`), including
during a site outage: probe backoff is per site, so a site that stays down is
re-probed less often, but the poll loop and this stream keep the base cadence.

Each message is a JSON object with camelCase keys:

```json
{
  "namespace": "default",
  "group": "orders",
  "activeSite": "iad",
  "sites": [
    {
      "name": "iad",
      "role": "PrimaryCandidate",
      "state": "Writable",
      "lastSeenTime": "2026-04-10T00:00:00Z",
      "replication": "NotApplicable"
    },
    {
      "name": "pdx",
      "role": "PrimaryCandidate",
      "state": "ReadOnly",
      "lastSeenTime": "2026-04-10T00:00:00Z",
      "replication": "Healthy",
      "secondsBehindSource": 0,
      "gtidExecuted": "3e11fa47-71ca-11e1-9e33-c80aa9429562:1-45839"
    }
  ],
  "lastFailover": {
    "time": "2026-04-09T22:10:00Z",
    "target": "iad",
    "promotionGtidExecuted": "3e11fa47-71ca-11e1-9e33-c80aa9429562:1-45839"
  },
  "pollTime": "2026-04-10T00:00:00Z"
}
```

The top level carries `namespace`, `group`, `activeSite`, `sites`,
`lastFailover`, `alert`, `updatePhase` and `pollTime`. `lastFailover` has the
shape of the CR's `status.lastFailover` (`time` in RFC 3339, `target`,
`promotionGtidExecuted`) and is omitted when the group has no failover record.
Each site entry carries `name`, `role`, `state`, `lastSeenTime`,
`replication`, `secondsBehindSource`, `gtidExecuted`, `recoveryState`,
`divergentGtid` and `divergentTransactionCount`.

`sites[].replication` is the CR's `status.sites[].replication` value
(`Healthy`, `Lagging`, `Broken`, `Unknown` or `NotApplicable`), debounced the
same way: `Healthy` or `Lagging` only after both replication threads have run
with a source set for consecutive polls, and `NotApplicable` on the writable
primary. It is not a per-poll reading of the replication threads. The former
boolean `replicating` field (the raw per-poll `IO and SQL thread running`
flag) and the top-level `lastFailoverTarget` and `promotionGtidExecuted`
fields are gone; `lastSeen` is now `lastSeenTime`.

When a site holds transactions the primary lacks (an old primary after an emergency failover, or a replica found by the replica GTID audit), the site entry includes recovery fields:

```json
{
  "name": "pdx",
  "role": "PrimaryCandidate",
  "state": "ReadOnly",
  "lastSeenTime": "2026-04-10T00:00:00Z",
  "replication": "Broken",
  "recoveryState": "RecoveryBlocked",
  "divergentGtid": "a1b2c3d4-0000-0000-0000-000000000000:11-15",
  "divergentTransactionCount": 5
}
```

The stream does not say which check found the divergence. `GET /status` and
the CR's `status.sites[]` carry `divergenceDetectedBy` (`OldPrimaryRecovery`
or `ReplicaAudit`) and `divergenceComparedTo`; a replica-audit entry usually
has `replication: Healthy`.

```javascript
const ws = new WebSocket("ws://localhost:8082/ws/status");
ws.onmessage = (event) => {
  const msg = JSON.parse(event.data);
  console.log(`${msg.group}: active=${msg.activeSite}`);
};
```

Both the REST and WebSocket endpoints use camelCase JSON keys, so the same
field names work for either consumer.

## Troubleshooting

### Common conditions

| Symptom | Likely cause | Investigation |
|---|---|---|
| `Ready=False` (reason `NoWritablePrimary` or `ReplicationUnhealthy`), `Degraded=True` | A site is unreachable (`SiteUnhealthy`) or replication is broken | Check `status.sites[].state` and MySQL pod logs |
| `Degraded=True`, reason `BootstrapFailed`; `Bootstrapping=False`, reason `BootstrapFailed` | A clone into a site failed and the site does not replicate yet. Deployment leases are refused while it holds | Read the condition message for the target and the error, fix the cause (often replication credentials or the donor), then clone again with `kubectl bloodraven reclone <group> <site> --cold`. It clears once the site replicates or a new clone starts |
| `Ready=Unknown`, `Degraded=Unknown`, reason `Initializing` | The operator just started and has not classified every `PrimaryCandidate` site yet (a writable answer needs `recoveryThreshold` polls) | Normally clears on the next poll. It lasts at most `failureThreshold` + `recoveryThreshold` probes of a site; a site still unclassified then alternates between answers and errors, and the group reports `NoPrimary` naming it. Check `status.sites[].state` and the operator logs. See [Failover: Initializing after an operator start](/docs/operations/failover#initializing-after-an-operator-start) |
| `Ready=False`, reason `InitFromBackupInProgress` | A new group's `spec.initFromBackup` restore has not succeeded yet. The seed is writable and `status.activeSite`, but applications are kept off it: no DNS record, no `-primary`/`-replicas`/per-site Service endpoints, no clones | Watch `status.restore`. See [Backup and restore: Applications wait for the restore](/docs/backup-and-restore/backup-restore#applications-wait-for-the-restore) |
| `Ready=False`, reason `InitFromBackupFailed` | The `initFromBackup` restore failed; the seed may hold partial data. The group stays out of service and nothing is cloned | Follow the condition message: read the restore Job log; if the load had started, empty the target (delete and recreate the group, or delete the group's MySQL pods and PVCs together and wait until the re-created claims are `Bound` and the pods `Running`), then delete the Job. See [Backup and restore: A failed bootstrap restore](/docs/backup-and-restore/backup-restore#a-failed-bootstrap-restore) |
| `Ready=False`, both sites `ReadOnly` | No primary exists (may follow a failed failover) | See [Operations: Manual promotion](/docs/operations/operations#manual-promotion-fallback-operator-unreachable) |
| `Ready=False`, both sites `Writable` | Split brain | See [Operations: Split brain recovery](/docs/operations/operations#split-brain-recovery) |
| `RecoveryPending=True`, reason `RecoveryInProgress` | Old primary is being reconfigured as a replica | Wait for the condition to clear. If it stays true, check operator logs and `status.sites[].replication`. See [Failover: Old primary recovery](/docs/operations/failover#old-primary-recovery). |
| `RecoveryPending=True`, reason `DivergentTransactions` | Old primary returned with divergent transactions | Check `status.sites[].divergentGtid`, then trigger a reclone: `kubectl bloodraven reclone <group> <site>` (it fills in the required `divergentGtid` prefix). See [Failover: Old primary recovery](/docs/operations/failover#old-primary-recovery). |
| `Degraded=True`, reason `DivergentTransactions`, `Ready=True` | A site holds transactions the primary lacks; a replica can be replicating normally. Ordered updates and planned failovers will not promote it | Check `status.sites[].divergentGtid` and `divergenceDetectedBy`, preserve the errant binlog events, then reclone the site or make the primary contain the set. See [Failover: Divergent replicas](/docs/operations/failover#divergent-replicas). |
| `Updating=True`, reason `OrderedUpdateStalled` | An ordered update rolled a site whose new pod does not become `Ready` and stay `Ready` for 30s (often a sidecar that cannot start or crash-loops), or a site already on the new template is not `Ready` by that rule. The update rolls nothing else and the active site keeps serving | Read the condition message for the site, pod and cause, then `kubectl describe pod` and the container logs (`--previous` for a crash loop). Fix the cause or the spec; the update retries every 30s. See [Failover: Ordered updates](/docs/operations/failover#ordered-updates). |
| `DivergentPromotion=True` | A divergent site was promoted; its extra transactions are now authoritative | Review the set in the condition message, then remove the condition. See [Failover: Failover sequence](/docs/operations/failover#failover-sequence). |
| Repeated failovers | Flapping network or unstable MySQL | Check `bloodraven_state_transitions_total` and consider increasing `failureThreshold` or `failoverCooldown` |
| High replication lag | Slow network, heavy write load, or undersized replica | Check `bloodraven_replication_lag_seconds` and MySQL performance metrics |

### Operator logs

The operator logs structured JSON. Key fields to filter on:

```bash
kubectl logs -n bloodraven deploy/bloodraven | jq 'select(.msg == "failover")'
kubectl logs -n bloodraven deploy/bloodraven | jq 'select(.level == "ERROR")'
```

### Sidecar logs

Check the sidecar container for self-fencing events:

```bash
IAD_POD=$(kubectl get pod -n orders \
  -l app.kubernetes.io/name=mysql,bloodraven.shipstream.io/failover-group=orders,bloodraven.shipstream.io/site=iad \
  -o jsonpath='{.items[0].metadata.name}')
kubectl logs -n orders "$IAD_POD" -c sidecar | jq 'select(.msg | contains("self-fence"))'
```
