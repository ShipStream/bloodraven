## Operations decision table

| Task | Use when | Do not use when | Verify with |
|---|---|---|---|
| Planned failover | Healthy target and scheduled maintenance | Split-brain or target lagging | `status.plannedFailover`, DNS, app writes |
| Manual promotion | Operator unavailable and old primary fenced | Operator is healthy | active site, GTIDs, DNS |
| Split-brain recovery | Multiple writable sites | Only DNS is stale | writable state and GTID comparison |
| Reclone old primary | Divergence accepted or no data to recover | Data owner has not reviewed divergence | replication running and lag low |
| Backup restore | Production recovery or drill | Source artifact unverified | MySQL smoke test and app validation |

## Deployment coordination

The optional [Deployment API](/docs/configuration/deployment-api) persists `migration` and `failover-hold` coordination in Kubernetes Leases. Restarting Bloodraven does not clear them. A live hold defers planned failover (`Deferred`, reason `DeploymentHold`), ordered update, and restore-in-place. It never blocks emergency promotion, returning-primary fencing, or primary reassertion.

For a delayed planned operation, inspect `status.plannedFailover.message` and `admission.retryTime`, the API's lease summaries, and `status.topologyGeneration`. The message names the blocking operation and instance. Prefer letting the deployment finish and release its hold; if its client died, expiry ends the hold without manual deletion. Continuing renewal can move the deadline, so use the live lease observation rather than an old status snapshot.

To revoke deployment authority deliberately:

1. Identify every affected deployment in the group, record its operation ID and DDL boundary, and obtain approval to interrupt it. Revocation does not roll back schema changes or kill a client process.
2. Stop or fence the deployment clients through their deployment system so they cannot start another operation. Preserve their failure and schema evidence; post-DDL uncertainty requires manual recovery.
3. Annotate the group with an explicit revocation request:

```bash
kubectl annotate mysqlfailovergroup orders -n bloodraven \
  bloodraven.shipstream.io/revoke-deployment-leases=true --overwrite
```

4. Verify `DeploymentLeaseRevoked` events and `bloodraven_deploy_lease_revocations_total{reason="OperatorRevoked"}`. Renewals must return `409 revoked` with `OperatorRevoked`; the topology generation need not change for administrative revocation. Check that deferred maintenance proceeds only after normal preflight succeeds.

Do not delete coordination Leases, modify their token hashes, or reset `status.topologyGeneration` as a recovery shortcut. In particular, never delete the operator's leader-election Lease to clear a deployment hold. A new deployment attempt after revocation requires the application's own recovery checks; a healthy primary alone does not prove a partially applied migration is safe.

### Deferred operation with invalid Lease duration

If a plan remains `Deferred/DeploymentHold` past the hold's expiry and operator logs report `spec.leaseDurationSeconds: Invalid value: 0: must be greater than 0`, the operator has a deployment Lease persistence bug. It rounds remaining lifetime down to zero, so Kubernetes rejects expiry writes, release or revocation in the final fractional second, and archival of old revocations. The stored record remains unchanged; housekeeping and planned-hold checks keep failing. This is separate from deployment client TLS trust failures.

1. Preserve sanitized lease state, expiry, operation ID, and operator errors. Coordinate with deployment owners and stop clients whose confirmed authority has expired; require manual schema verification if DDL may have started.
2. Upgrade or rebuild and roll out an operator containing the positive-duration persistence fix. Restarting the same affected binary or requesting revocation is not a workaround for the rejected write. Do not patch Lease durations or delete deployment records, which can erase revocation fencing.
3. Verify the validation errors stop, expired records leave the active lease list, and planned maintenance resumes normal preflight after all holds end. The fixed operator processes existing records without a data reset; rollout can therefore unblock queued maintenance. Review pending maintenance before rollout. A completed revocation remains terminal even after its original expiry.

## Planned failover (graceful switchover)

To promote a replica during planned maintenance, annotate the `MysqlFailoverGroup` with the target site name. The operator drains writes on the current primary, waits for the target to catch up, and promotes it atomically -- no `kubectl exec` required.

```bash
kubectl annotate mysqlfailovergroup orders \
  bloodraven.shipstream.io/planned-failover=pdx
```

Optional per-request override (otherwise the `spec.plannedFailover` defaults apply):

```bash
kubectl annotate mysqlfailovergroup orders \
  bloodraven.shipstream.io/planned-failover=pdx:maxLagWait=30s
```

Watch progress on the CR:

```bash
kubectl get mysqlfailovergroup orders \
  -o jsonpath='{.status.plannedFailover}{"\n"}'
```

The run advances through `Admitting → Fencing → Draining → WaitingForLag → Promoting → Publishing → Succeeded` (with the two Dragonfly phases before `Promoting` when Dragonfly is enabled), emitting Kubernetes Events (`PlannedFailoverStarted`, `PlannedFailoverClaimGranted`, `PlannedFailoverDrainStarted`, `PlannedFailoverTargetCaughtUp`, `PlannedFailoverSucceeded`) along the way. A run that does not succeed ends `Failed` with `status.plannedFailover.result.outcome` saying what the cluster was left in. See [Planned failover](/docs/operations/planned-failover) for the full lifecycle, rollback behaviour, and RPO guarantees.

Unlike the legacy `kubectl exec` dance below, this path:

- **Respects the anti-flap cooldown.** A planned failover cannot run within `spec.failoverCooldown` of the last failover (planned *or* emergency).
- **Guarantees zero RPO on success.** Promotion only proceeds when the target's `GTID_EXECUTED` equals the fenced source's set, with every other `PrimaryCandidate` and `DisasterRecovery` site answering read-only. A down DR site therefore blocks planned failovers until it is back (a site cannot be removed from `spec.sites`; see [Replacing a site](#replacing-a-site)).
- **Rolls back on timeout.** If the target does not catch up within `maxLagWait`, the operator clears the fence on the source and reports `status.plannedFailover.phase: Failed` with `result.outcome: RolledBack` and `result.reason: LagTimeout`.
- **Holds automation when it cannot explain a possible write.** A run that ends `ManualRecoveryRequired` sets `AutomaticFailoverHeld=True` until an administrator acknowledges it; see the [hold runbook](/docs/operations/runbooks#planned-failover-automation-hold).
- **Leaves an audit trail.** Every run is recorded on the CR, and every attempt in the `bloodraven_planned_failovers_total{result=...}` counter. A request refused without a run (an invalid value, a standing automation hold, a request beside a running run or an earlier run's unhealed fenced source) is recorded as a `PlannedFailoverRejected` Event.

### Manual promotion (fallback, operator unreachable)

If the operator is unreachable and you must promote a site by hand, the legacy three-step dance still works. Use this only as a break-glass procedure; prefer the annotation API above whenever the operator is healthy.

**Step 1: Fence the current primary**

```bash
SOURCE_POD=$(kubectl get pod -n orders \
  -l app.kubernetes.io/name=mysql,bloodraven.shipstream.io/failover-group=orders,bloodraven.shipstream.io/site=iad \
  -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n orders "$SOURCE_POD" -c mysql -- \
  mysql -u root -p -e "SET GLOBAL super_read_only=ON;"
```

**Step 2: Stop and reset replication on the target**

```bash
TARGET_POD=$(kubectl get pod -n orders \
  -l app.kubernetes.io/name=mysql,bloodraven.shipstream.io/failover-group=orders,bloodraven.shipstream.io/site=pdx \
  -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n orders "$TARGET_POD" -c mysql -- \
  mysql -u root -p -e "STOP REPLICA; RESET REPLICA ALL;"
```

**Step 3: Promote the target**

```bash
TARGET_POD=$(kubectl get pod -n orders \
  -l app.kubernetes.io/name=mysql,bloodraven.shipstream.io/failover-group=orders,bloodraven.shipstream.io/site=pdx \
  -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n orders "$TARGET_POD" -c mysql -- \
  mysql -u root -p -e "SET GLOBAL read_only=0;"
```

When the operator returns it will observe the new topology on its next poll cycle and update Services, DNS, and taints accordingly. No operator restart is required.

::warning

Manual promotion **bypasses** the anti-flap cooldown and the zero-lag gate. Ensure you understand the current replication state before promoting a site -- data loss is possible if the target has not finished applying relay logs. The planned-failover API above is safer; reach for this only when the operator is genuinely unavailable.
::
## Split-brain recovery

If both sites report `Writable` (split brain), the operator will **not** take automatic action. You must resolve this manually:

1. **Identify the authoritative site** -- determine which site has the most recent data by comparing GTID sets:

   ```bash
   IAD_POD=$(kubectl get pod -n orders \
     -l app.kubernetes.io/name=mysql,bloodraven.shipstream.io/failover-group=orders,bloodraven.shipstream.io/site=iad \
     -o jsonpath='{.items[0].metadata.name}')
   PDX_POD=$(kubectl get pod -n orders \
     -l app.kubernetes.io/name=mysql,bloodraven.shipstream.io/failover-group=orders,bloodraven.shipstream.io/site=pdx \
     -o jsonpath='{.items[0].metadata.name}')

   kubectl exec -n orders "$IAD_POD" -c mysql -- \
     mysql -u root -p -e "SELECT @@gtid_executed;"

   kubectl exec -n orders "$PDX_POD" -c mysql -- \
     mysql -u root -p -e "SELECT @@gtid_executed;"
   ```

2. **Fence the non-authoritative site**:

   ```bash
   PDX_POD=$(kubectl get pod -n orders \
     -l app.kubernetes.io/name=mysql,bloodraven.shipstream.io/failover-group=orders,bloodraven.shipstream.io/site=pdx \
     -o jsonpath='{.items[0].metadata.name}')
   kubectl exec -n orders "$PDX_POD" -c mysql -- \
     mysql -u root -p -e "SET GLOBAL super_read_only=ON;"
   ```

3. **Re-establish replication** from the authoritative site to the fenced site:

   ```bash
   PDX_POD=$(kubectl get pod -n orders \
     -l app.kubernetes.io/name=mysql,bloodraven.shipstream.io/failover-group=orders,bloodraven.shipstream.io/site=pdx \
     -o jsonpath='{.items[0].metadata.name}')
   kubectl exec -n orders "$PDX_POD" -c mysql -- \
     mysql -u root -p -e "
       STOP REPLICA;
       RESET REPLICA ALL;
       CHANGE REPLICATION SOURCE TO
          SOURCE_HOST='mysql-orders-iad-internal.orders.svc.cluster.local',
         SOURCE_USER='replicator',
         SOURCE_PASSWORD='<replicator-password>',
         SOURCE_AUTO_POSITION=1;
       START REPLICA;
     "
   ```

   Read the replicator password from the failover group's credentials Secret.
   If the group enforces TLS for replication, include the corresponding
   `SOURCE_SSL_*` options from your MySQL TLS setup as well.

4. The operator will detect the corrected topology and resume normal operation.

::caution

Split brain means both sites accepted writes independently. You may need to reconcile conflicting data manually before re-establishing replication. Replication will break if conflicting transactions exist on both sides.
::
## Recovering a divergent old primary

After an emergency failover, the old primary may come back with transactions that never replicated. If GTID sets match, the operator sets `RecoveryPending=True` with reason `RecoveryInProgress`, reconfigures the old primary as a replica, and clears the condition after replication is healthy. If the old primary has divergent transactions, the operator fences the site and sets `RecoveryPending=True` with reason `DivergentTransactions`. A replica that is still replicating can be divergent too; the operator's replica GTID audit reports it the same way, with `divergenceDetectedBy=ReplicaAudit` (see [Divergent replicas](/docs/operations/failover#divergent-replicas)).

Check the divergence details:

```bash
kubectl get mysqlfailovergroup orders -o jsonpath='{range .status.sites[*]}{.name}: recoveryState={.recoveryState} divergentTxns={.divergentTransactionCount} divergentGtid={.divergentGtid}{"\n"}{end}'
```

To recover the site, investigate the lost transactions and then trigger a reclone:

**Step 1: Investigate the lost transactions**

Review the divergent GTID set to understand what data was lost. These transactions were committed on the old primary but never reached the replica before failover.

**Step 2: Trigger a reclone**

Use the reclone annotation to have the operator run `CLONE INSTANCE` on the divergent site, replacing all its data with a fresh copy from the current primary. The annotation value names the group and its uid, so a request written for an earlier group of the same name never applies, and must include a prefix (8 or more characters) of the source UUID of the observed `divergentGtid` — this **confirmation interlock** prevents a fat-fingered site name from destroying the wrong replica. `kubectl bloodraven reclone orders iad` builds the value; by hand:

```bash
# Read the divergent GTID and the group's uid first:
DG=$(kubectl get mysqlfailovergroup orders -o jsonpath='{.status.sites[?(@.name=="iad")].divergentGtid}')
echo "$DG"
# a1b2c3d4-0000-0000-0000-000000000000:11-15
GROUP_UID=$(kubectl get mysqlfailovergroup orders -o jsonpath='{.metadata.uid}')

# Annotate with <site>:confirm=<group>:uid=<uid>:gtidPrefix=<first 8+ chars of the UUID>
kubectl annotate mysqlfailovergroup orders \
  bloodraven.shipstream.io/reclone-site="iad:confirm=orders:uid=${GROUP_UID}:gtidPrefix=a1b2c3d4"
```

A value cannot contain `:`, so the prefix stops before the GTID's `:11-15` interval. If the prefix doesn't match the observed `divergentGtid` (wrong site, stale copy of the GTID, typo), or the name or uid is not this group's, the operator emits a `RecloneRejected` Warning Event and clears the annotation — no clone is started. Re-read `status.sites[].divergentGtid` and try again.

A `RecloneRequested` Normal Event marks the start. The site will temporarily appear unreachable during the MySQL restart that follows the clone. Progress is reported in the `Bootstrapping` condition: `True` while the clone runs, then `False` with reason `NotBootstrapping` once it finished, or `BootstrapFailed` (with `Degraded=True`, reason `BootstrapFailed`) when it failed.

With PITR enabled, the clone starts up to 2 minutes after the site's binary log was rotated for it, which is normally at the request and at most 4 minutes after it. `CLONE INSTANCE` wipes the site's binary logs, and the site is often an old primary whose last transactions are not archived yet, so the operator first rotates the site's binary log and waits until its sidecar reports the sealed tail archived. `Bootstrapping` turns `True` only when the clone starts; a site with nothing left to upload is confirmed once its sidecar has scanned the rotated log, which the rotation itself triggers. If the tail is not confirmed within 2 minutes of the rotation, the clone starts anyway and a Warning Event `PITRArchiveTailNotArchived` names the site and the cause: a point-in-time restore whose window needs transactions only that tail held then refuses `PITRArchiveGap`. See [Archiving the tail of an outgoing primary](/docs/backup-and-restore/backup-restore#archiving-the-tail-of-an-outgoing-primary).

### Server identity after a clone

Every clone gives its recipient a new `server_uuid`. `CLONE INSTANCE` does
not copy `auto.cnf`, so on its own MySQL brings the recipient back with the
identity it had before, on the donor's data. For a recloned old primary that
is a hazard. Its next own transaction would take the next free number under
its old UUID, and after a lossy failover that is the GTID of a transaction it
committed before the failover and the donor never received. A PITR archive, a
backup or a replica that still holds the lost transaction would then know two
different transactions by one GTID.

The mysql container therefore starts through a launcher that the operator
renders into every pod (the container's `command`; it ends by running the
image's own entrypoint). On the start that installs a finished clone it
removes `auto.cnf` from the data directory, mysqld generates a new
`server_uuid`, and the recipient's first own transaction is `<new uuid>:1`.
This covers a reclone, the fresh-deploy bootstrap, the auto-clone of an empty
site and the reclones that follow an in-place restore, and a `CLONE INSTANCE`
you run by hand.

| Start of the mysql container | `server_uuid` | Line in the mysql container's log |
|---|---|---|
| Installs a finished clone | New | `bloodraven-launcher: a finished clone is staged in /var/lib/mysql/#clone; removed auto.cnf so mysqld generates a new server_uuid (previous: <uuid>)` |
| Ordinary restart, pod replacement, first boot of an empty volume | Unchanged | none |
| Rolls back a clone that was interrupted (mysqld killed during the copy) | Unchanged | `bloodraven-launcher: an interrupted clone is staged in …; mysqld rolls it back and server_uuid stays <uuid>` |
| Installs a finished clone while the keyring is sealed and the binary log is encrypted ([encryption at rest](/docs/configuration/encryption-at-rest#clones-and-the-keyring)) | Unchanged | `bloodraven-launcher: WARNING: … the keyring … is read-only (the site is sealed) …; server_uuid is NOT rotated` |
| Installs a finished clone, but `auto.cnf` cannot be removed or `#clone` cannot be read | Unchanged | `bloodraven-launcher: WARNING: …; server_uuid is NOT rotated` |

A clone that failed or was killed leaves the recipient without data. The
operator reports it as `BootstrapFailed`, never promotes it, and the clone
that completes later rotates the identity.

The operator checks the result of every clone it runs. It reads the
recipient's `server_uuid` before `CLONE INSTANCE` and after the restart, and
logs `clone recipient server_uuid rotated` with both values. A recipient that
came back with the same one gets the log line `clone recipient kept its
server_uuid` and a Warning Event `CloneServerUUIDNotRotated` naming the site.
The Event reports and nothing more: the site replicates and stays a failover
candidate, because refusing it would turn a risk to the archive into an
outage of a two-site group.

The check does not depend on the operator process that started the clone. A
clone runs in mysqld, and it can finish after the operator restarted or
lost leadership. Before it issues `CLONE INSTANCE`, the operator therefore
writes the recipient's `server_uuid` to the group, in the
`bloodraven.shipstream.io/clone-server-uuid` annotation, and it does not
start the clone if that write fails. Whichever operator next looks at the
site (at the start of its next bootstrap, including one that finds the
cloned data in place and only sets up replication, and on every poll)
reads the site's `performance_schema.clone_status`: a completed clone newer
than the record is compared and reported as above, once, and the record is
removed. A clone that never began or that failed removes the record with
no verdict (`clone recipient server_uuid rotation not verified`). An
operator that stops between the Event and the removal of the record
reports the same clone again after its restart; a report is never lost
that way.

When you see the Event:

1. Check that the pod runs the launcher:
   `kubectl get pod <pod> -o jsonpath='{.spec.containers[?(@.name=="mysql")].command[0]}'`
   prints `/bin/bash`. A pod created before the operator release that
   introduced the launcher has no `command`; it rolls with the group's
   pending update (`Updating=True`).
2. Read the launcher's line: `kubectl logs <pod> -c mysql | grep bloodraven-launcher`.
3. Reclone the site once the cause is gone. Until then, if the site lost
   transactions as a primary, do not promote it: its sidecar reports them in
   `reissuableGtids`
   ([Reissue risk](/docs/backup-and-restore/pitr-history-repair#reissue-risk)).

Read a site's `server_uuid` after a clone, not before: monitoring that keys
on it sees a new server, and the site's PITR archive manifest records the
change as a reset record. Replication with `SOURCE_AUTO_POSITION` does not
depend on the replica's `server_uuid`. The `gtidPrefix` of a reclone request
is the source UUID of the recorded divergent GTID set, not the site's current
`server_uuid`.

A custom `spec.image` must ship `/bin/bash` and its entrypoint at one of the
paths the launcher looks for; see
[Implementation prerequisites](/docs/operations/upgrade-policy#implementation-prerequisites).

### Recloning a `ReadOnly` site

A reader is a valid clone recipient but never a donor. If a reader has lost
its PVC or source convergence is blocked and its data can be discarded, use
the plugin's destructive cold-reclone confirmation:

```bash
kubectl bloodraven reclone <group> <reader-site> --cold
```

For example:

```bash
kubectl bloodraven reclone orders reader --cold
```

The operator validates a uniquely writable `PrimaryCandidate` donor before
starting `CLONE INSTANCE`. The reader client Service has no healthy endpoint
while clone, catch-up, or direct-source convergence is incomplete. Clone
reads from the active primary at full speed and is not throttled.

### Troubleshooting blocked source convergence

Inspect the generic source fields independently of old-primary recovery:

```bash
kubectl get mysqlfailovergroup orders \
  -o jsonpath='{range .status.sites[*]}{.name}: source={.sourceHost} state={.sourceConvergenceState} reason={.sourceConvergenceReason}{"\n"}{end}'
```

- `Pending/SourceMismatch` means the observed source is not the confirmed
  primary and convergence has not completed.
- `Pending/ProbeFailed` or `Pending/MutationFailed` means a probe or bounded
  `STOP REPLICA` / `CHANGE REPLICATION SOURCE TO` / `START REPLICA` attempt
  failed. Check the four stable convergence log events and their `stage`.
- `Pending/RestorePeerHold` means the site awaits its reclone after a
  full-instance in-place restore (`status.restoreReclones.pending`). Its
  replication receiver is stopped on purpose so the restore's `DROP`
  statements cannot reach it; only its reclone (or removing the queue)
  restarts replication.
- `Blocked/GTIDDiverged` means the active primary does not contain the
  follower's executed GTID set. Bloodraven intentionally leaves the channel
  unchanged, or stopped if the second containment check failed after STOP.
  Do not reset replication metadata to force a rejoin. Review the GTIDs and
  preserve any required data before recloning.

Convergence is also deliberately paused during bootstrap, ordered updates,
restore, topology freeze, pending promotion, planned failover, and split
brain. Resolve or allow that operation to finish before treating `Pending`
as a source fault.

## PVC loss recovery runbook

Use this when one site's MySQL data PVC is irrecoverable: cloud volume
deleted, local disk lost, filesystem corrupted beyond repair, or a
failed clone left the data directory unusable.

::caution
**Data loss boundary**


If the lost PVC belonged to a primary that accepted writes not yet
replicated elsewhere, those transactions are unrecoverable from
Bloodraven. PITR can only replay binlog files that survived long enough
to be archived; a lost primary PVC takes its unarchived binlog tail with
it. See [Durability and RPO](/docs/architecture/durability-and-rpo#pitr-and-the-rpo-window).
::
### 1. Identify the failed site and current primary

```bash
kubectl get mysqlfailovergroup orders \
  -o jsonpath='{.status.activeSite}{"\n"}{range .status.sites[*]}{.name}: state={.state} recovery={.recoveryState} divergent={.divergentGtid}{"\n"}{end}'
```

Do not wipe the active primary unless you are deliberately restoring
from backup. If the damaged site is the active primary, first let the
operator fail over or run a planned failover to a healthy
PrimaryCandidate site.

### 2. Confirm the target has no recoverable divergent data

For normal old-primary divergence, use the GTID-prefix reclone flow
above. For PVC loss, the target has no usable data to preserve, so the
operator accepts a cold reclone with an explicit destructive confirmation:

```bash
kubectl bloodraven reclone orders iad --cold
```

The operator emits `RecloneRequested` and drives the same clone path used
for automatic bootstrap. It will not reclone the current active primary.
If you will also delete the claim (step 3) and it was expanded beyond
`spec.sites[].storage.size`, do step 3 first.

### 3. If the PVC object itself is bad, delete it

If Kubernetes is still binding the pod to a corrupted claim, delete the
site pod and PVC so the operator can recreate storage from the CR spec.
The operator recreates it at `spec.sites[].storage.size`. If the claim had
been expanded beyond that size, follow
[Recreating an expanded claim](#recreating-an-expanded-claim) instead of
the commands below, and request the reclone (step 2) after it:

```bash
IAD_POD=$(kubectl get pod -n orders \
  -l app.kubernetes.io/name=mysql,bloodraven.shipstream.io/failover-group=orders,bloodraven.shipstream.io/site=iad \
  -o jsonpath='{.items[0].metadata.name}')
kubectl delete pod -n orders "$IAD_POD"
kubectl delete pvc -n orders mysql-orders-iad-data
```

If your cluster uses local-path storage, clear any `db-readonly` taint
from the node before deleting the PVC; otherwise the provisioner's helper
pod may be evicted and the replacement claim can stay `Pending`.

### 4. Watch bootstrap and clone progress

```bash
kubectl describe mysqlfailovergroup orders
kubectl get pods -l bloodraven.shipstream.io/failover-group=orders -w
```

Expected condition flow:

| Phase | What you should see |
|---|---|
| Requested | `RecloneRequested` Event on the `MysqlFailoverGroup`. |
| Archiving the tail (PITR enabled only) | Nothing changes on the group for up to 2 minutes (4 when the rotation is acknowledged late) while the operator rotates the site's binary log and waits for its sidecar to archive the sealed tail; the operator log shows `pre-reclone archive tail wait started`. A Warning `PITRArchiveTailNotArchived` Event means the clone started without that confirmation. |
| Bootstrapping | `Bootstrapping=True`; the target site pod may restart while `CLONE INSTANCE` replaces the data directory. |
| Recovering | The cloned site comes back read-only and replication is configured from the active primary. |
| Healthy | `Bootstrapping=False` with reason `NotBootstrapping` and a `lastTransitionTime` after the request, `RecoveryPending=False`, target `state=ReadOnly`, `recoveryState` empty, replication running, and `divergentGtid` empty. |
| Failed | `Bootstrapping=False` with reason `BootstrapFailed`, and `Degraded=True` with reason `BootstrapFailed` naming the target and the annotation that clones it again. Deployment leases are refused until the site replicates or a new clone starts. |

Clone time is proportional to dataset size and storage throughput. Small
playground datasets finish in minutes; production datasets can take much
longer.

### 5. Verify the site rejoined safely

```bash
kubectl get mysqlfailovergroup orders \
  -o jsonpath='{range .status.sites[*]}{.name}: state={.state} replication={.replication} lag={.secondsBehindSource} recovery={.recoveryState}{"\n"}{end}'
```

The recovered site should be read-only, replicating from the current
primary (`replication=Healthy`), and below your `spec.replication.maxLagSeconds` threshold before
you consider the incident closed.

::warning

If the old primary came back with no divergence (GTID sets match), the operator automatically reconfigures it as a replica — no manual intervention is needed. The `RecoveryPending` condition only appears when divergent transactions exist.
::
## Total loss recovery

If both sites are `Unreachable`, the operator cannot take any action. Recovery steps:

1. Investigate infrastructure (nodes, network, storage) at both sites
2. Bring at least one MySQL instance back online
3. The operator will detect the recovered site and begin normal operation
4. Once the second site is back, re-establish replication if it does not resume automatically

## Scaling storage

`spec.sites[].storage.size` and `storageClassName` are applied only when
the site's PVC (`mysql-<group>-<site>-data`) is created, and admission
refuses a change to either after that: the operator does not resize or
move a site's volume. A size is compared by value, so rewriting `100Gi`
as `102400Mi` is not a change.

To grow a site's volume, expand the PVC itself, if its StorageClass
allows it (`allowVolumeExpansion: true`):

```bash
kubectl -n orders patch pvc mysql-orders-iad-data --type merge \
  -p '{"spec":{"resources":{"requests":{"storage":"200Gi"}}}}'
```

The operator never changes an existing claim, so the expansion stays. The
underlying volume expansion behavior depends on your storage provider;
some require a pod restart. `spec.sites[].storage.size` keeps recording
the size the claim was created with. To move a site to another
StorageClass or zone, or to fix a wrong class, zone or size in a group
that never held data, see [Replacing a site](#replacing-a-site).

### Recreating an expanded claim

The operator creates a missing claim at `spec.sites[].storage.size`. It
keeps an existing claim of that name as it is: on an existing claim it sets
only the owner reference and the labels, never the size or class. So a
claim deleted after an expansion (for a [PVC loss recovery](#pvc-loss-recovery-runbook))
comes back at the original size, and the clone of a dataset that outgrew it
fails. Create the replacement claim yourself, at the expanded size, before
the operator does. The operator recreates a deleted claim within seconds,
so stop it for the swap. The site's Deployment would also recreate its pod,
which keeps the old claim in use, so scale it to zero too. While the
operator is stopped, no group it manages fails over; keep the window short.
The site must not be the active primary.

1. Record the operator's replica count, then stop it:

   ```bash
   kubectl -n bloodraven get deployment bloodraven -o jsonpath='{.spec.replicas}'
   kubectl -n bloodraven scale deployment bloodraven --replicas=0
   ```

2. Wait until the operator's pods are gone, scale the site's Deployment
   (`mysql-<group>-<site>`) to zero and wait for its pod to go, then delete
   the claim and wait until it is gone:

   ```bash
   kubectl -n bloodraven wait --for=delete pod -l app.kubernetes.io/name=bloodraven --timeout=2m
   kubectl -n orders scale deployment mysql-orders-iad --replicas=0
   kubectl -n orders wait --for=delete pod -l bloodraven.shipstream.io/failover-group=orders,bloodraven.shipstream.io/site=iad,app.kubernetes.io/name=mysql --timeout=5m
   kubectl -n orders delete pvc mysql-orders-iad-data
   kubectl -n orders wait --for=delete pvc/mysql-orders-iad-data --timeout=5m
   ```

3. Create the claim with the name, labels, access mode and class the
   operator would use, and the expanded size:

   ```yaml
   apiVersion: v1
   kind: PersistentVolumeClaim
   metadata:
     name: mysql-orders-iad-data
     namespace: orders
     labels:
       app.kubernetes.io/name: mysql
       app.kubernetes.io/instance: orders
       app.kubernetes.io/managed-by: bloodraven
       bloodraven.shipstream.io/failover-group: orders
       bloodraven.shipstream.io/site: iad
   spec:
     accessModes: [ReadWriteOnce]
     storageClassName: fast-ssd   # the site's spec.sites[].storage.storageClassName
     resources:
       requests:
         storage: 200Gi           # the expanded size
   ```

4. Scale the operator back to the recorded count, then scale the site's
   Deployment back to one replica yourself: under the default
   `OrderedUpdate` strategy the operator does not re-render an existing
   Deployment that has no configuration change, so it stays at zero.

   ```bash
   kubectl -n bloodraven scale deployment bloodraven --replicas=<recorded count>
   kubectl -n orders scale deployment mysql-orders-iad --replicas=1
   kubectl -n orders wait --for=condition=Ready pod -l bloodraven.shipstream.io/failover-group=orders,bloodraven.shipstream.io/site=iad,app.kubernetes.io/name=mysql --timeout=10m
   ```

   The operator takes the claim as its own and leaves its size alone. Then
   request the reclone
   (`kubectl bloodraven reclone orders iad --cold`).

## Replacing a site

Sites cannot be removed or renamed, and a site's `zone`, `storage`
and `serverID` cannot change: a site's name is part of its Deployment,
PVC, Service, archive and keyring names, and its volume is bound to its
zone. Admission refuses removing or renaming a site with this message:

```text
spec.sites cannot be removed or renamed; see the site-replacement procedure (Operations > Replacing a site)
```

A change to a site's `zone`, `serverID`, `storage.storageClassName` or
`storage.size` is refused with that field's own message, which also points
to the site-replacement procedure. Adding a site is allowed.

To drop, rename or move a site, replace the group. How depends on whether
the group holds data. A typo in a new group is the common case and has the
short path, but only when you can show that the group never held data.

### Does the group hold data?

`status.activeSite` does not answer this. It names the site that is the
unique writable primary now. It is empty whenever no site or more than one
site is writable, which also happens on a group that holds data.

A group never held data only when every one of these checks passes:

1. **Every site can be inspected.** Each site's MySQL pod is `Running`
   and answers a query, or the site's claim has never been bound to a
   volume, so the site never had storage to write to:
   `kubectl -n orders get pvc mysql-orders-iad-data -o jsonpath='{.spec.volumeName}'`
   prints nothing. Any other site, one you cannot query, may hold data.
2. **No site holds a schema.** On every running site's MySQL,
   `SHOW DATABASES` lists only `mysql`, `information_schema`,
   `performance_schema` and `sys`.
3. **No site has a client.** On every running site's MySQL,
   `SHOW PROCESSLIST` shows no client other than the operator, the sidecar
   and replication.
4. **No tenant database.** No `MysqlDatabase` names the group in
   `spec.failoverGroupRef`:
   `kubectl -n orders get mydb -o custom-columns=NAME:.metadata.name,GROUP:.spec.failoverGroupRef.name`.
5. **No restore succeeded.** `spec.initFromBackup` is absent, or
   `status.restore.phase` is not `Succeeded`.
6. **No failover happened.** `status.lastFailover` is absent:
   `kubectl -n orders get mfg orders -o jsonpath='{.status.lastFailover}'`.

If any check fails, a site cannot be inspected, or you are unsure, the
group holds data: use [A group that holds data](#a-group-that-holds-data).

A group whose `spec.initFromBackup` restore failed has the schemas of its
partial load, so check 2 fails. Nothing could write to it, because the
group publishes no endpoints until the restore succeeds. Follow
[A failed bootstrap restore](/docs/backup-and-restore/backup-restore#a-failed-bootstrap-restore)
for it instead.

### A group that never held data

A mistake caught before the group was used (a `storageClassName` that does
not exist, so the site's PVC stays `Pending`; a `zone` no node carries, so
the pods stay `Pending`; a wrong `size`, `serverID` or site name) is fixed
by deleting the group and creating it again, under the same name, from the
corrected manifest. Do this only when every check in
[Does the group hold data?](#does-the-group-hold-data) passes.

1. **Save the manifest and correct it.** Look at every backup and PITR
   prefix the group's profiles use: the S3 prefix
   (`aws s3 ls s3://<bucket>/<prefix>/ --recursive | head`), or the
   `subPath` on a claim you created (`claimName`). If a prefix holds any
   object, give that profile a new prefix in the corrected manifest. The
   old prefix can hold the deleted group's archive descriptor, which the
   new group (a new UID) refuses with `ArchiveForeign`.
2. **Delete the group** as described in
   [Deleting a group without losing backups](#deleting-a-group-without-losing-backups).
3. **Apply the corrected manifest.**

### A group that holds data

Build a new group from a final backup of the old one and move the
applications to it. Writes stop before that backup and stay stopped until
the applications use the new group, so every committed transaction is in
the backup.

**Downtime.** Applications cannot write from step 3 until step 8: the
final backup, the new group's provisioning and restore (the load takes
roughly as long as the step-2 rehearsal took), its verification and the
cut-over. A new group created without `spec.initFromBackup` (step 1) is
loaded schema by schema at step 6, and those loads set the downtime. Reads may keep using the old group, whose data no longer changes.

1. **Write the new group's manifest under a new name.** The old group
   still exists in the same namespace, so the new one cannot reuse its
   name. Write all of it now except `spec.initFromBackup.source`, which
   step 4 adds:
   - The site list you want, each site with its own `serverID`.
   - Its own `spec.dns.hostname`: two groups publishing one record
     conflict.
   - **Fresh backup and PITR prefixes**, never the old group's: the new
     group starts a new archive and needs a new baseline backup.
   - **Placement.** Both groups run side by side until step 9. The old
     group keeps a read-only taint (`NoExecute`, with a key that names the
     old group) on the nodes its read-only `PrimaryCandidate` site's
     `taintNodeSelector` selects, and a failover moves that taint to the
     other candidate's nodes. The new group's pods tolerate only the new
     group's taint. A MySQL pod is placed by its site's `zone` alone, so a new
     pod can land on any node of that zone, including the old group's
     writable node, and the old group's next failover taints that node and
     evicts it. The same holds the other way: an old pod can land on any node of its
     zone, so the new group's failover can taint it. Each new site's `zone`
     must therefore be a zone that contains none of the old group's nodes:
     give the new group's nodes zone labels of their own.
     Spare nodes in a shared zone are not enough, and a rehearsal that
     passes does not prove the isolation, because no failover happens
     during it. Each new `taintNodeSelector` must select only the new
     group's nodes: a selector that matches a node of the old group puts
     the new group's taint on it, and the old group's pods on that node are
     evicted. Scenario 37 in
     [`playground/chaos-scenarios.md`](https://github.com/ShipStream/bloodraven/blob/main/playground/chaos-scenarios.md#37-pitr-planned-failback-no-reclone)
     shows the selector side: the restored group's selector names a label
     no node of the source group carries.
   - **`spec.initFromBackup.loadOptions`.** `spec.initFromBackup` is fixed
     at creation, so decide the load filter now. A `MysqlDatabase` refuses
     to adopt a schema it did not create, so the tenant schemas are loaded
     at step 6 instead. List the schemas the old group's `MysqlDatabase`
     objects manage
     (`kubectl -n orders get mydb -o custom-columns=NAME:.metadata.name,GROUP:.spec.failoverGroupRef.name,SCHEMA:.spec.databaseName`)
     in `loadOptions.excludeSchemas`. Both `excludeSchemas` and
     `includeSchemas` hold at most 256 names: with more than 256 tenant
     schemas, list the schemas that are not tenant schemas in
     `loadOptions.includeSchemas` instead. An empty `includeSchemas`
     restricts nothing and loads every schema: when every application
     schema is a tenant schema, leave `spec.initFromBackup` out, create the
     new group empty, and load every schema at step 6. The choice is final
     once the group is applied.
2. **Rehearse in a scratch group** before writes stop. Restore an earlier
   backup of the old group into a scratch group made from the step-1
   manifest, with its own name, DNS hostname and prefixes and no backup
   schedules, and with the same sites, placement and `loadOptions`. Wait
   until every scratch site's MySQL pod is `Running`,
   `status.restore.phase` is `Succeeded` and the group is `Ready=True`, and
   note how long the restore took. A step-1 manifest without
   `spec.initFromBackup` has no restore: wait for `Ready=True`, then run
   step 6 on the scratch group for a few schemas and extrapolate the time
   to all of them. A site that stays `Pending` here would
   stall step 5 while writes are stopped: fix the placement and rehearse
   again. Then delete the scratch group:
   `kubectl -n orders delete mfg <scratch> --cascade=foreground`.
3. **Stop writes to the old group.** Stop or scale to zero every writer:
   the applications, workers, cron jobs and migration tools. Do not edit the
   group's `MysqlDatabase` objects or credential Secrets until step 8: the
   operator applies those to MySQL. On the old primary, `SHOW PROCESSLIST`
   must show no application session, and `SELECT @@GLOBAL.gtid_executed`
   read twice, a minute apart, must return the same set. Record that set.
4. **Take the final backup** and wait for it to succeed:
   `kubectl -n orders get mysqlbackup <backup> -o jsonpath='{.status.phase}'`
   is `Succeeded`. Its `status.gtidExecuted` must be the set recorded in
   step 3; if it is smaller, the backup ran on a replica that had not
   caught up: take another. Unless the new group leaves out
   `spec.initFromBackup` (step 1), set `spec.initFromBackup.source.backupRef` in
   the new manifest to this backup, or build `source.s3` / `source.pvc`
   from its `status.artifactStorage`
   (`kubectl -n orders get mysqlbackup <backup> -o jsonpath='{.status.artifactStorage}'`).
   With `source.backupRef` and an S3 backup, the new group must define a
   profile with the backup's `spec.profileName` that stores to S3: the
   restore reads the dump at the recorded `status.artifactStorage` with
   that profile's credentials (its prefix may be new). Without it the
   restore fails with `RestoreBuildFailed` (`profile "<name>" is missing
   from spec.backup.profiles`), and the new group has to be deleted and
   created again with such a profile or with `source.s3`.
5. **Apply the new manifest and wait for the restore**:
   `status.restore.phase` is `Succeeded` and the group is `Ready=True`.
   A group created without `spec.initFromBackup` (every application schema
   is a tenant schema) has no restore: wait for `Ready=True`.
6. **Recreate the tenant databases and accounts.** A `MysqlDatabase`'s
   `spec.failoverGroupRef` cannot change: for each of the old group's,
   create one for the new group under a new name (same `databaseName`),
   wait for `Ready`, then load its schema from the final backup with a
   per-schema `spec.restoreInPlace` (`loadOptions.includeSchemas` naming
   that schema, a new `confirm` for each run; see
   [Per-schema in-place restore](/docs/backup-and-restore/backup-restore#per-schema-in-place-restore)).
   Restores do not load users: recreate the MySQL accounts that neither the
   group's credentials nor a `MysqlDatabase` create.
7. **Verify the new group before any client uses it.** Row counts and
   `CHECKSUM TABLE` of the application's tables match the old group (its
   data is frozen, so they must be equal). This is the check for every
   restore source. Do not compare GTID sets: a restore without
   `pointInTime` does not install the dump's GTID set, so the new
   primary's `@@GLOBAL.gtid_executed` holds only its own transactions.
   Take a baseline backup of the new group and, when PITR is on, wait for
   `PITRArchiveReady=True`. Verify it with a `MysqlBackupVerification`.
8. **Cut over.** Every name derived from the group name changes:
   `mysql-<new>-primary` and `mysql-<new>-replicas`, the per-site Services
   and the Dragonfly Services. Point the clients (or the CNAME they use) at
   the new endpoints, then start the writers. Until a writer has written to
   the new group, the unchanged old group is the way back; after that,
   going back loses those writes.
9. **Retire the old group** once the applications run against the new one.
   Delete the old group's `MysqlDatabase` objects (the default
   `deletionPolicy: Retain` leaves MySQL untouched), then delete the group
   as described in
   [Deleting a group without losing backups](#deleting-a-group-without-losing-backups).
   The final backup is one of its backups: keep it as that section
   describes if your recovery policy needs it.

### Deleting a group without losing backups

Deleting a group deletes what it owns: its Deployments, PVCs and
Services, its `MysqlBackup` and `MysqlBackupVerification` objects, and the
claim `mysql-<group>-backup-<profile>` of each profile with
`pvc.provisioned`. `spec.deletionPolicy: Retain` on a `MysqlBackup` only
stops the cleanup Job from deleting its artifact. It does not keep an owned
backup claim: the claim is deleted with the group, and under the usual
`Delete` reclaim policy its volume goes too, with every backup and PITR
archive on it. Do not remove the claim's owner reference by hand: the
operator sets it again on its next reconcile. Keep what you need on storage
the group does not own, in this order:

1. **Stop new backups and verifications.** Set `suspend: true` on every
   entry of `spec.backup.schedules` and on every profile's `verification`.
   A suspended schedule's failed backup is not retried either.
   Wait until no backup or verification Job of the group is running:
   `kubectl -n orders get jobs -l bloodraven.shipstream.io/failover-group=orders`.
2. **List the group's backups and where each artifact is:**

   ```bash
   kubectl -n orders get mysqlbackup -l bloodraven.shipstream.io/failover-group=orders \
     -o custom-columns=NAME:.metadata.name,PHASE:.status.phase,POLICY:.spec.deletionPolicy,BUCKET:.status.artifactStorage.bucket,CLAIM:.status.artifactStorage.claimName,LOCATION:.status.artifactStorage.location
   ```

3. **Copy what you keep off the group's own claims.** An artifact in S3 or
   on a claim you created (`claimName`) stays where it is. An artifact on
   `mysql-<group>-backup-<profile>` does not: copy it to S3 or to a claim
   you created, for example from a pod that mounts the claim, and check the
   copy (every file present, with the same size and checksum). An encrypted
   backup also needs the key that decrypts it. The backup records its
   dump-key snapshot Secret in `status.artifactStorage.passphraseSecretKeyRef`,
   that Secret can be the only copy of the key, and step 4 deletes it with
   the backup. Copy its data into a Secret you own, under a new name and
   without the operator's labels. Copy the base64 value as it is: decoding
   the key through a shell variable can change its bytes.

   ```bash
   set -eu
   src=$(kubectl -n orders get mysqlbackup <backup> -o jsonpath='{.status.artifactStorage.passphraseSecretKeyRef.name}')
   key=$(kubectl -n orders get mysqlbackup <backup> -o jsonpath='{.status.artifactStorage.passphraseSecretKeyRef.key}')
   key=${key:-passphrase}
   b64=$(kubectl -n orders get secret "$src" -o "jsonpath={.data.$key}")
   test -n "$b64"
   kubectl -n orders apply -f - <<EOF
   apiVersion: v1
   kind: Secret
   metadata:
     name: orders-final-dump-key
   type: Opaque
   data:
     passphrase: $b64
   EOF
   test "$(kubectl -n orders get secret orders-final-dump-key -o jsonpath='{.data.passphrase}')" = "$b64"
   ```

   A copy is restored with `spec.initFromBackup.source.s3` or
   `source.pvc`, and `spec.initFromBackup.decryption.passphraseSecretKeyRef`
   naming `orders-final-dump-key`. The last command proves the Secret holds
   the same bytes; to prove the copied artifact too, restore it into a
   scratch group with that `decryption` before step 4.
4. **Delete the group's backups while their storage still exists.** Set
   `spec.deletionPolicy: Retain` on each backup whose artifact you keep in
   S3 or on a `claimName` claim. Leave `Delete` on the others, including
   those whose artifact you copied off an owned claim. Then delete them
   and wait until none is left:

   ```bash
   kubectl -n orders delete mysqlbackup -l bloodraven.shipstream.io/failover-group=orders
   kubectl -n orders get mysqlbackup -l bloodraven.shipstream.io/failover-group=orders
   ```

   A `Delete` backup runs its cleanup Job now, while its storage still
   exists, and then deletes its dump-key snapshot Secret. A `Retain`
   backup is released and its artifact and dump-key snapshot stay. A backup
   left for the group deletion can wait on a cleanup Job that mounts a
   claim the same deletion removes, and hold the group's deletion.
5. **Delete the group in the foreground**, and wait until it and
   everything it owns are gone:

   ```bash
   kubectl -n orders delete mfg orders --cascade=foreground
   kubectl -n orders get pvc,mysqlbackup,mysqlbackupverification -l bloodraven.shipstream.io/failover-group=orders
   ```

   The second command must return nothing before you apply a group with
   the same name. A background delete returns while the old PVCs are still
   terminating, and a new group of the same name would meet them.

## Updating MySQL version

Change `spec.image` to the new version:

```yaml
spec:
  image: mysql:9.7
```

If `updateStrategy.type` is `OrderedUpdate`, the rollout follows the [ordered update sequence](/docs/operations/failover#ordered-updates) with zero downtime. Otherwise, both sites are updated simultaneously.

See the [Upgrade and version-skew policy](/docs/operations/upgrade-policy) for the supported MySQL baseline and the cross-site and sidecar ↔ operator skew contract.

## Updating the sidecar

A group that leaves `spec.sidecar.image` unset runs the sidecar image the
operator release ships with (the chart's `sidecar.image.repository` and
`sidecar.image.tag`, default the chart's `appVersion`), so upgrading the
operator updates its sidecars: the new image changes the pod spec and the
group rolls. The operator rolls such a change one group at a time
([Paced rollouts](/docs/operations/upgrade-policy#paced-rollouts)), and a
change of the chart values below is paced the same way. To mirror the image into a private registry, set the chart
values rather than pinning every group:

```bash
helm upgrade bloodraven bloodraven/bloodraven --reuse-values \
  --set sidecar.image.repository=registry.example.com/mirror/bloodraven-sidecar
```

To pin one group to a specific image instead, set `spec.sidecar.image`:

```yaml
spec:
  sidecar:
    image: ghcr.io/shipstream/bloodraven-sidecar:v2.0.0
```

A pin stays until you change or remove it, and a pin tagged with another
release than the operator gets a `SidecarVersionSkew` Warning. Either change
follows the same update strategy as MySQL image changes. A pin holds the
sidecar image only: an operator release that changes the pod spec in another
way rolls a pinned group too.

## Rotating MySQL credentials

Rotation of the per-role credential Secrets is fully automated:

1. Update the `password` value in the relevant Kubernetes Secret (e.g. `mysql-operator-creds`)
2. The operator detects the change, connects to the primary, and runs `ALTER USER` to update the MySQL password
3. Pods are rolling-restarted to pick up the new credentials from the updated Secret

No manual MySQL commands or operator restarts are needed.

## DNS provider configuration

DNS provider credentials and settings are managed entirely by external-dns, not by Bloodraven. To change your DNS provider or rotate provider credentials, update your external-dns deployment configuration. Bloodraven only manages the `DNSEndpoint` CR; external-dns handles syncing it to the actual DNS provider.

## Maintenance mode

To prevent automatic failovers during maintenance (e.g., network changes), you can temporarily increase the failover cooldown:

```bash
kubectl patch mysqlfailovergroup orders --type merge -p '
  {"spec": {"failoverCooldown": "24h"}}'
```

Restore it after maintenance:

```bash
kubectl patch mysqlfailovergroup orders --type merge -p '
  {"spec": {"failoverCooldown": "30m"}}'
```

## Deleting a failover group

The operator uses a finalizer to ensure graceful cleanup when a `MysqlFailoverGroup` is deleted:

1. Node taints are removed from all sites
2. The `DNSEndpoint` CR is automatically garbage-collected via its owner reference to the `MysqlFailoverGroup`
3. MySQL pods, Services, PVCs, and the PodDisruptionBudget are deleted
4. The finalizer is removed and the CR is deleted

To delete:

```bash
kubectl delete mysqlfailovergroup orders
```

::warning

PVCs are deleted as part of cleanup. If you need to preserve data, back up the MySQL instances before deleting the failover group.

The group's `MysqlBackup` objects and the backup claims it provisioned (`pvc.provisioned`) are deleted with it. `deletionPolicy: Retain` does not keep a backup stored on such a claim. To keep backups, follow [Deleting a group without losing backups](#deleting-a-group-without-losing-backups).
::
