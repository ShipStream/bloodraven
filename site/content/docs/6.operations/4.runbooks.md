![runbooks infographic](/img/infographics/runbooks.webp)

Every runbook starts with the same incident header. Fill it in before making changes.

| Field | Value |
|---|---|
| Severity | Set from paging policy |
| Expected impact | Read/write outage, degraded failover, backup risk, or no user impact |
| Data loss risk | None, possible async lag loss, or unknown |
| Prerequisites | `kubectl`, namespace access, MySQL credentials if SQL is needed |
| Required permissions | Read CRs/Events/logs; write CR annotations only when runbook says so |
| Estimated time | Record expected and actual time |
| Rollback path | Document before action |
| Verification command | Always include active site, DNS, and app write check when relevant |

If `spec.dragonfly.enabled=true`, include `status.dragonfly.phase`, active Dragonfly Service endpoints, and a Redis-compatible cache/session read/write check in the same incident record.

## Planned failover

Use [Planned Failover](/docs/operations/planned-failover) for controlled maintenance. Do not use during split-brain or when the target replica is unhealthy.

```bash
kubectl annotate mysqlfailovergroup orders -n orders \
  bloodraven.shipstream.io/planned-failover=pdx --overwrite
kubectl get mysqlfailovergroup orders -n orders -o wide
```

Every `PrimaryCandidate` and `DisasterRecovery` site must be up and answering: a planned failover waits (`admission.waitReason: PeerUnreadable`) and then ends `NotStarted` with `AdmissionTimeout` while one is down. Bring the site back first (a site cannot be removed from `spec.sites`; to drop one, see [Replacing a site](/docs/operations/operations#replacing-a-site)).

Wait for the run to finish, then check its outcome, not only the phase:

```bash
kubectl get mysqlfailovergroup orders -n orders \
  -o jsonpath='{.status.plannedFailover.phase}{" "}{.status.plannedFailover.result.outcome}{" "}{.status.plannedFailover.result.reason}{" "}{.status.plannedFailover.result.warnings}{"\n"}'
```

`kubectl bloodraven promote orders pdx --wait` does the same and also reports a run the operator ended with the `bloodraven.shipstream.io/planned-failover-terminal` annotation while status writes were failing (status may still read `Promoting`); `kubectl bloodraven status orders` prints `Ended by terminal marker: <outcome>:<reason>` for it. Treat the marker's outcome like `result.outcome` below.

Verify DNS and application writes before starting maintenance on the old active site.

If Dragonfly is enabled, also verify `status.plannedFailover.dragonfly.sessions` (`Preserved` or `Lost`) and confirm the active Dragonfly Service points at the new site.

```bash
kubectl get mysqlfailovergroup orders -n orders \
  -o jsonpath='{.status.plannedFailover.dragonfly}{"\n"}'
kubectl get endpoints orders-dragonfly -n orders
```

If the run did not succeed, `result.outcome` decides what to do:

| Outcome | Action |
| --- | --- |
| `NotStarted`, `RolledBack` | Nothing was written to the target and the source is writable. Fix `result.reason` and re-annotate. If `result.warnings` includes `TargetReplicationNotRestored` (with `SourceReplaced`, say), the target was left without a running channel: restore it by hand or reclone the target first. If it includes `TargetSuperReadOnlyNotRestored`, first run `SET GLOBAL super_read_only = ON` on the target and confirm `SELECT @@super_read_only` reads 1: until then privileged sessions can write to it beside the source. |
| `SourceLeftFenced` | Follow [Planned failover left the source fenced](#planned-failover-left-the-source-fenced). |
| `PromotedUnconfirmed` | Follow [Promoted but unconfirmed](/docs/operations/planned-failover#promoted-but-unconfirmed). |
| `ManualRecoveryRequired` | Follow [Planned failover automation hold](#planned-failover-automation-hold). |

## Planned failover left the source fenced

Use when `status.plannedFailover.result.outcome` is `SourceLeftFenced`. Nothing was written to the target, and the run did not make the source writable again. Usually the source is read-only behind the run's fence; when the message says `source "<site>" left as it is`, the run did not prove its fence (it says whether it sent one), so read the source's flags first.

1. Read the reason, the warnings and the message:

   ```bash
   kubectl get mysqlfailovergroup orders -n orders \
     -o jsonpath='{.status.plannedFailover.result}{"\n"}{.status.plannedFailover.message}{"\n"}{.status.lastFailover.target}{"\n"}'
   ```

2. Check every site's state: `SELECT @@GLOBAL.read_only, @@GLOBAL.super_read_only, @@GLOBAL.gtid_executed;`.
3. If another site is writable, that site is the primary. Do not unfence the source; old-primary recovery repoints it as a replica.
4. If no site is writable, decide by the [healing table](/docs/operations/planned-failover#healing-a-fenced-source):
   - `SourceLost`, or a peer unreachable: emergency failover decides. Restore connectivity. If nothing failed over and the source comes back read-only, the next item applies.
   - An attributable fence (no `FenceNotAttributable` warning; reasons such as `StatusStalled`, `ManagerUnavailable`, `SourceLost` or a rollback that could not confirm the unfence), every site reachable, and `status.lastFailover.target` empty or the source: the topology manager re-asserts the source on its own within `failoverCooldown` (WARN `re-asserting fenced promoted primary`). Wait for it. It does not lift a fence from a source that came back as another server (WARN `planned failover: the fenced source is not the server the run's fence names; its fence is not lifted`) or without transactions a peer holds (`recoveryState: RecloneRequired`): both are manual, and a source that lost transactions is recloned, not unfenced.
   - `FenceNotAttributable` (also on a run that sent its fence and then ended because authority moved), `LegacyRunRefused`, `UnknownSite` (the source or target was removed from `spec.sites` mid-run, so nothing was named), `AuthorityChanged` before the fence was applied, or `status.lastFailover.target` naming another site: manual. A `FenceNotAttributable` or `LegacyRunRefused` message ends with this advice (`check which site is writable; if none is, unfence the site with the most complete GTID set by hand (confirm no other site is writable first); re-annotate only once a site is writable`). Pick the site with the most complete GTID set, confirm no other site is writable, and unfence it (`SET GLOBAL super_read_only=OFF; SET GLOBAL read_only=OFF;`). Do not re-annotate a planned failover instead: with no writable site, admission waits (`AuthorityUnsettled`) and ends `NotStarted{AdmissionTimeout}` after 2 minutes, and writes stay refused all along. Request a planned failover only after one site is writable.
5. Verify `status.activeSite`, DNS and an application write.

While the run's own attributable fence has not healed (the source is not yet observed writable and no failover was recorded since the run started), a new planned-failover request is refused with a `PlannedFailoverRejected` Warning (`... left source "<site>" fenced and the fence has not healed yet; ...`) and `status.plannedFailover` keeps the fenced run: let the re-assert finish, or unfence by hand, then re-annotate.

## Planned failover automation hold

Use when the `AutomaticFailoverHeld` condition is `True` (`status.plannedFailoverHold` is set), you see `PlannedFailoverManualRecoveryRequired` or `PlannedFailoverHoldPersisted` Events, or a bootstrap, reclone or keyring rotation is refused with `automatic failover is held after planned failover <runID>; resolve the split brain, then annotate bloodraven.shipstream.io/acknowledge-planned-failover-hold=<runID>` (a rotation adds `; retrying after the acknowledgement`). A planned failover may have written to its target and ended `ManualRecoveryRequired`. Emergency failover, split-brain resolution, the re-assert, ordered updates, rotations, recovery and DNS reconciliation are held for the group until you acknowledge the hold. Dragonfly is held as well: a failed Dragonfly master is not replaced, replicas are not re-attached, and Dragonfly rollouts and snapshot upgrades do not promote, so a Dragonfly failure during the hold is an outage of the cache until you acknowledge. Writes continue on whichever site is writable, and backups, backup schedules, verification and keyring work keep running.

| Field | Value |
|---|---|
| Severity | High: automatic failover is off for this group |
| Data loss risk | Unknown until the sites are compared; the hold exists so that automation does not discard writes |
| Required permissions | SQL on every site; annotate the `MysqlFailoverGroup` |
| Rollback path | None needed: acknowledging only resumes automation |

1. Read the held run and the sites it names:

   ```bash
   kubectl get mysqlfailovergroup orders -n orders \
     -o jsonpath='{.status.plannedFailoverHold}{"\n"}{.status.plannedFailover.runID}{" "}{.status.plannedFailover.result}{"\n"}{.metadata.annotations.bloodraven\.shipstream\.io/planned-failover-terminal}{"\n"}'
   ```

   `status.plannedFailoverHold` names the run (`runID`), its `reason`, `sourceSite`, `targetSite` and the `ambiguousSites`: the target, the source, and every site the failing step found writable or could not read. A hold rebuilt from the terminal marker by a process that did not see the run lists every site in `spec.sites`. When status writes had stalled, a terminal-marker annotation `{"schemaVersion":1,"runID":"<runID>","outcome":"ManualRecoveryRequired","reason":"<reason>"}` (optionally with a `warnings` array) carries the same hold instead.
2. On every site read `@@GLOBAL.read_only`, `@@GLOBAL.super_read_only`, `@@GLOBAL.gtid_executed` and `SHOW REPLICA STATUS`. Compare the source and the target with `GTID_SUBTRACT` both ways.
3. Resolve the split brain by hand. Decide which site is the primary from the data, not from history: the site holding the transactions you must keep. Fence every other site (`SET GLOBAL super_read_only=ON;`). If both sites took writes, preserve the losing site's extra transactions (`mysqlbinlog --include-gtids=<extra set>`) before anything reclones it.

   With `reason: SourceUnfenced` the hold is for a source that lost transactions (the message starts `the rollback found source "<site>" writable without transactions it held before (<gtid set>)`; see [A source that lost transactions](/docs/operations/planned-failover#a-source-that-lost-transactions)). The source restarted on older data and is serving writes, and it issues the lost GTIDs again for other transactions, so `GTID_SUBTRACT` stops showing the difference once it has issued as many as it lost: go by the message, not by a later comparison. The target, or another site, holds the only copies of the lost transactions. Stop replication on any site that still replicates from the source and holds them (`STOP REPLICA;`), save them (`mysqlbinlog --include-gtids='<gtid set>'` against that site's binary logs), and only then decide: keep the source's history, re-apply what still matters by hand and reclone the sites that hold the old transactions; or fence the source, make the target the primary and reclone the source.
4. Make sure exactly one `PrimaryCandidate` is writable and DNS points at it. The topology manager does not move DNS while the hold stands.
5. Acknowledge the hold with the run's id. The plugin reads it from the group:

   ```bash
   kubectl bloodraven ack-planned-failover-hold orders -n orders
   # or, by hand:
   kubectl annotate mysqlfailovergroup orders -n orders \
     bloodraven.shipstream.io/acknowledge-planned-failover-hold=<runID>
   ```

6. Verify: `status.plannedFailoverHold` disappears, the condition turns `False` with reason `PlannedFailoverHoldAcknowledged`, the annotation is removed by the operator, the Normal Event `PlannedFailoverHoldAcknowledged` is emitted, and the log shows `planned failover: hold acknowledged` then `planned failover: claim released` with `why=ack`. Automation then resumes from the state you left: old-primary recovery repoints the fenced site, or reports divergence for you to reclone.

An acknowledgement naming another run is ignored (`PlannedFailoverHoldAcknowledgmentIgnored`); correct the value. One that finds no standing hold, or the claim held for another run, is ignored the same way and removed; nothing is resumed. A `True` condition without `status.plannedFailoverHold` (a hand-edited status, or a CRD rolled back across the planned-failover claim release, which prunes the hold record but keeps the condition) names no run and cannot be acknowledged: after resolving the split brain, remove the condition by hand (`kubectl patch mysqlfailovergroup orders -n orders --subresource=status --type=json -p '[{"op":"remove","path":"/status/conditions/<index>"}]'`). The operator then releases the hold on its next pass, without a restart: the log shows `planned failover: released an automation hold no durable record backs` and `planned failover: claim released` with `why=orphanHold`. Until then such a refusal reads `automatic failover is held by a True AutomaticFailoverHeld condition that names no run; resolve the split brain, then remove the condition`. Do not acknowledge before step 4: the next poll would act on whatever state the sites are in.

## Dragonfly degraded

Use when `status.dragonfly.phase=Degraded`, `bloodraven_dragonfly_site_up==0`, Dragonfly promotion failed, `status.dragonfly.replTakeoverSupported=false`, or you see `DragonflySessionsLost` / `DragonflyReplTakeoverUnsupported`. MySQL is still authoritative; this runbook protects cache/session continuity.

1. Confirm MySQL `status.activeSite` and application writes are healthy.
2. Inspect `status.dragonfly.replTakeoverSupported` and `replTakeoverProbeMessage`. A false value means the running image does not advertise `REPLTAKEOVER` — pin `v1.38.0+` (or a private build that has the command) and roll the StatefulSets.
3. Inspect `status.dragonfly.sites[]` for sites whose `role` is `Unreachable` or `StaleMaster`, and for syncing or link-down sites.
4. Check the active Dragonfly Service endpoints and pod role/traffic labels.
5. Restart or reschedule only the affected Dragonfly pod if the stale site has not accepted writes.
6. If a stale master may have accepted writes, keep it out of the active Service and decide whether cache/session data can be discarded.

```bash
kubectl get mysqlfailovergroup orders -n orders \
  -o jsonpath='{.status.dragonfly}{"\n"}'
kubectl get pod -n orders -l app.kubernetes.io/name=dragonfly --show-labels
kubectl get endpoints orders-dragonfly -n orders
```

## Emergency manual promotion

Use only when automation cannot complete and you have confirmed the old primary cannot accept writes.

1. Preserve Events and logs.
2. Confirm old primary is unreachable or fenced.
3. Confirm candidate has the best GTID/replication position available.
4. Promote using your approved MySQL operational procedure.
5. Update or unblock Bloodraven reconciliation only after state is consistent.

Verification:

```bash
kubectl get mysqlfailovergroup orders -n orders -o yaml
dig orders.az.example.com
```

## Split-brain recovery

Use when more than one site can accept writes.

1. Stop application writes if possible.
2. Identify all writable sites.
3. Choose the authoritative site using business ownership and GTID evidence.
4. Fence losing sites by ensuring `super_read_only=ON` and blocking application traffic.
5. Preserve divergent data for manual reconciliation.
6. Reclone losing sites only after data owners approve.

Do not skip GTIDs to make replication look green.

## Divergent old primary recovery

Use when the old primary contains transactions absent from the promoted site.

1. Export evidence from the old primary.
2. Ask the data owner whether divergent rows must be recovered manually.
3. Keep the old primary fenced.
4. Reclone from the active primary when approved.
5. Verify replication returns to healthy.

```bash
kubectl describe mysqlfailovergroup orders -n orders
kubectl get events -n orders --sort-by=.lastTimestamp | grep -i divergent
```

## Divergent replica

Use when `Degraded=True` with reason `DivergentTransactions` names a site with
`divergenceDetectedBy=ReplicaAudit`, or an ordered update or planned failover
refuses a divergent target. The replica is usually replicating normally; its
extra transactions are history the primary never had.

1. Read the set: `kubectl get mysqlfailovergroup orders -n orders -o jsonpath='{.status.sites[?(@.name=="<site>")].divergentGtid}'`.
2. Decode and keep the errant events on the replica:
   `mysqlbinlog --include-gtids='<divergentGtid>' <binlog files> > errant.sql`.
3. Ask the data owner whether the transactions must be kept.
4. Discard them with `kubectl bloodraven reclone orders <site> -n orders`, or
   keep them by replaying the decoded transactions on the primary. To accept
   the replica's divergence instead, commit an empty transaction per GTID on
   the primary (`SET GTID_NEXT='<uuid>:<n>'; BEGIN; COMMIT;`, then
   `SET GTID_NEXT='AUTOMATIC';`). That makes the GTID sets agree without
   moving rows: the replica keeps rows the primary lacks, becomes promotable
   again once the audit clears, and a later promotion makes those rows
   authoritative with no `DivergentPromotion` record. Use it only when the
   transactions' effects are absent, harmless, or already reconciled.
5. Within about 30s the audit logs `divergence cleared: replica holds no
   transactions the primary lacks`, `Degraded` clears, and a stalled ordered
   update resumes on its own.

See [Divergent replicas](/docs/operations/failover#divergent-replicas).

## PVC loss recovery

Use when a MySQL data PVC is deleted or corrupted.

1. Confirm whether the affected site is active.
2. If active, stop application writes and follow emergency recovery policy.
3. If standby, reclone from the active primary.
4. If both sites are lost, restore from backup.

See [Backup And Restore](/docs/backup-and-restore/backup-restore) for restore workflows.

## Total site loss

Use when all nodes/storage/network for a site are gone.

1. Confirm surviving site is writable and healthy.
2. Confirm DNS points to the surviving site.
3. Disable app scheduling to the lost site.
4. Rebuild site infrastructure.
5. Rejoin via clone or restore.

Expected impact is bounded by failover detection, relay-log drain, DNS TTL, and application reconnect behavior.

## Keyring not sealed

Use when `bloodraven_keyring_phase{phase="sealed"}` is 0 for a site, or
`status.conditions[type=EncryptionAtRestReady]` is `False`.

A site that is not sealed is running with a **writable keyring**. Its
data is still encrypted, but the operator cannot yet prove the key is
durably escrowed.

1. Find out what it is waiting for — `message` carries the reason:

   ```bash
   kubectl get mysqlfailovergroup orders -n orders \
     -o jsonpath='{range .status.encryptionAtRest.sites[*]}{.name}{"\t"}{.phase}{"\t"}{.message}{"\n"}{end}'
   ```

2. `Unsealed` with `unsealReason: Clone` or `Bootstrap` is normal and
   transient. Wait for the clone to finish.
3. `Unsealed` with "waiting for the sidecar to escrow" — check the
   sidecar can reach the operator:

   ```bash
   kubectl exec -n orders deploy/mysql-orders-iad -c sidecar -- \
     wget -qO- localhost:8080/keyring/status
   ```

   `lastError` on that payload names the failure. Common causes: the
   operator's auxiliary Service is unreachable, or the escrow token
   Secret was deleted (the operator re-mints it on the next reconcile,
   but the pod needs to roll to pick it up).
4. `Escrowed` that never becomes `Sealed` — the pod has not rolled onto
   the sealed rendering. Check for a stuck ordered update
   (`status.updatePhase`).
5. `Failed` — read the message and follow
   [Keyring escrow lost](#keyring-escrow-lost) if it names a missing or
   corrupt Secret.

Full background: [Data-at-rest encryption](/docs/configuration/encryption-at-rest).

## Keyring escrow lost

Use on a `KeyringEscrowMissing` or `KeyringEscrowCorrupt` Event.

::caution
**Do not restart the affected pod**


A sealed site's escrow Secret is its **only** durable copy of the keys.
If the Secret is gone but the pod is still running, the keyring is alive
on the pod's tmpfs. Deleting, evicting, or draining that pod destroys it
and makes that site's data unrecoverable.
::
1. Confirm the pod is still running:

   ```bash
   kubectl get pod -n orders -l bloodraven.shipstream.io/site=iad
   ```

2. If it is running, recreate the exact missing Secret from the keyring
   still mounted in the running pod. Do not force an unseal or rollout:
   that would destroy the only surviving in-memory copy before it was
   durable again.

   ```bash
   set -o pipefail
   # The site's MySQL pod, selected as its Deployment selects it (Dragonfly
   # and backup pods share the site label). Expect exactly one name.
   POD=$(kubectl get pod -n orders \
     -l app.kubernetes.io/name=mysql,app.kubernetes.io/instance=orders,bloodraven.shipstream.io/site=iad \
     --field-selector=status.phase=Running -o jsonpath='{.items[*].metadata.name}')
   [[ "$POD" != *" "* && -n "$POD" ]] || { echo "expected one MySQL pod, got: '$POD'" >&2; exit 1; }
   PHASE=$(kubectl get mysqlfailovergroup orders -n orders \
     -o jsonpath='{.status.encryptionAtRest.sites[?(@.name=="iad")].phase}|{.status.encryptionAtRest.sites[?(@.name=="iad")].unsealReason}')
   # Only a sealed site whose escrow was lost: a rotation, bootstrap or
   # clone in progress owns its Secret.
   [[ "$PHASE" == "Failed|" || "$PHASE" == "Sealed|" ]] || { echo "site is $PHASE; not an escrow loss" >&2; exit 1; }
   SECRET=$(kubectl get mysqlfailovergroup orders -n orders \
     -o jsonpath='{.status.encryptionAtRest.sites[?(@.name=="iad")].keyringSecret}')
   VERSION=$(kubectl get mysqlfailovergroup orders -n orders \
     -o jsonpath='{.status.encryptionAtRest.sites[?(@.name=="iad")].keyringVersion}')
   DIGEST=$(kubectl get mysqlfailovergroup orders -n orders \
     -o jsonpath='{.status.encryptionAtRest.sites[?(@.name=="iad")].keyringDigest}')
   KEYRING_DIR=$(kubectl get mysqlfailovergroup orders -n orders \
     -o jsonpath='{.spec.encryptionAtRest.keyring.dataFileDir}')
   KEYRING_DIR=${KEYRING_DIR:-/run/mysql-keyring}
   FG_UID=$(kubectl get mysqlfailovergroup orders -n orders -o jsonpath='{.metadata.uid}')

   if kubectl get secret "$SECRET" -n orders -o name >/dev/null 2>&1; then
     echo "Secret $SECRET exists (KeyringEscrowCorrupt?): not touching it; see below" >&2
     exit 1
   fi
   KEYRING_FILE=$(mktemp)
   kubectl exec -n orders "$POD" -c mysql -- cat "$KEYRING_DIR/keyring" >"$KEYRING_FILE" || exit 1
   ACTUAL_DIGEST="sha256:$(sha256sum "$KEYRING_FILE" | cut -d' ' -f1)"  # macOS: shasum -a 256
   if [[ "$ACTUAL_DIGEST" != "$DIGEST" ]]; then
     echo "the running keyring does not match status; nothing was written" >&2
     exit 1
   fi
   kubectl create secret generic "$SECRET" -n orders --from-file=keyring="$KEYRING_FILE" || exit 1
   rm -f "$KEYRING_FILE"
   kubectl label secret "$SECRET" -n orders \
     app.kubernetes.io/name=mysql-keyring \
     app.kubernetes.io/managed-by=bloodraven \
     bloodraven.shipstream.io/failover-group=orders bloodraven.shipstream.io/site=iad \
     bloodraven.shipstream.io/keyring-version="$VERSION"
   kubectl annotate secret "$SECRET" -n orders bloodraven.shipstream.io/keyring-digest="$DIGEST"
   kubectl patch secret "$SECRET" -n orders --type=merge -p="{
     \"metadata\":{\"ownerReferences\":[{
       \"apiVersion\":\"shipstream.io/v1alpha1\",\"kind\":\"MysqlFailoverGroup\",
       \"name\":\"orders\",\"uid\":\"${FG_UID}\",\"controller\":true,\"blockOwnerDeletion\":true
     }]},\"immutable\":true
   }"
   ```

   Do not set the phase back to `Sealed` by hand. The operator does it
   once the Secret hashes to the recorded digest and MySQL confirms it is
   running that keyring (Event `KeyringRecovered`); a hand-written status
   could overwrite a rotation started meanwhile. Verify that the site
   returns to `Sealed` without restarting the pod.

   The doctor helper
   `.agents/skills/bloodraven-doctor/scripts/keyring-escrow-recover.sh -n orders orders iad`
   does the same and also stops if the site's state changes while it runs.

   The block checks the running keyring against the recorded digest before
   it writes anything and never deletes a Secret. On `KeyringEscrowCorrupt`
   the Secret still exists, so it refuses. Replacing it is a deliberate,
   separate step: back the existing Secret up
   (`kubectl get secret "$SECRET" -n orders -o yaml > escrow-backup.yaml`),
   delete exactly that Secret, and run the block again; it re-verifies the
   running keyring first.
3. If the pod is already gone, that site's data is unrecoverable.
   Delete the unreadable PVC, then re-clone it from a healthy peer. The
   confirmation token is mandatory because this permanently discards the
   target site's local data:

   ```bash
   kubectl delete pvc mysql-orders-iad-data -n orders
   kubectl bloodraven reclone orders iad --cold -n orders
   # or by hand, with the group's uid:
   kubectl annotate mysqlfailovergroup orders -n orders \
     bloodraven.shipstream.io/reclone-site="iad:confirm=orders:uid=$(kubectl get mfg orders -n orders -o jsonpath='{.metadata.uid}')"
   ```

4. If **every** site lost its escrow, restore from backup. Backup
   artifacts are logical dumps protected by a separate key, so they do
   not depend on any site's keyring.

## Network partition diagnosis

Use [Network Partitions](/docs/operations/network-partitions). Prioritize preventing two writable sites.

```bash
kubectl get mysqlfailovergroup orders -n orders -o yaml
kubectl get endpoints,networkpolicy -n orders
kubectl get events -n orders --sort-by=.lastTimestamp
```

## Failed backup

1. Keep the last successful backup.
2. Inspect `MysqlBackup` status and Job logs.
3. Fix credentials, storage, or MySQL source health.
4. Trigger a manual backup.
5. Verify the new backup.

```bash
kubectl get mysqlbackup -n orders
kubectl describe mysqlbackup -n orders <backup-name>
```

## Failed restore

1. Confirm this is a recovery environment or approved destructive action.
2. Inspect restore Job logs.
3. Validate source path and decryption Secret.
4. Recreate the recovery failover group if bootstrap partially initialized MySQL.

## Paced rollout halted

Use when `BloodravenRolloutStalled` fires, a group shows
`status.rollout.phase: Stalled`, or other groups show `Pending` /
`RolloutHalted` after an operator upgrade.

One group started rolling to the operator release's pod template and has
not finished. It keeps the rollout slot, so every other group keeps the
pods it had. The other groups are not affected; the stalled group is the
one to look at. Background:
[Paced rollouts](/docs/operations/upgrade-policy#paced-rollouts).

1. Find the stalled group and the reason:

   ```bash
   kubectl get mysqlfailovergroup -A -o jsonpath='{range .items[?(@.status.rollout.phase=="Stalled")]}{.metadata.namespace}/{.metadata.name}{"\t"}{.status.rollout.reason}{"\t"}{.status.rollout.message}{"\n"}{end}'
   ```

2. Check that the group still serves: `status.activeSite` is set and that
   site is `Writable`. Under `OrderedUpdate` a stalled roll leaves the
   active site serving. Under `Recreate` every site restarted together;
   if none is writable, treat it as an outage first
   ([Emergency manual promotion](#emergency-manual-promotion)).

   ```bash
   kubectl bloodraven status orders -n orders
   kubectl get pods -n orders -l bloodraven.shipstream.io/failover-group=orders
   ```

3. Read why the roll does not finish.
   - `OrderedUpdateStalled`: a rolled pod is not `Ready`. The message
     names the site, the pod and the cause (for example `mysql not ready:
     crash looping, last exit code 127` for a `spec.image` the launcher
     cannot start; see
     [Implementation prerequisites](/docs/operations/upgrade-policy#implementation-prerequisites)).
     Read that pod's `mysql` and `sidecar` container logs.
   - `StallTimeout`: the roll has taken longer than `rollout.stallAfter`.
     The message lists what is outstanding: workloads not rolled yet,
     rollouts not finished, or the reason the group is not stable (for
     example a divergent replica that the handoff refuses; see
     [Divergent replica](#divergent-replica)).
4. Decide whether the cause is the group or the release.
   - **The group** (its image, its nodes, its data): fix it. The stalled
     group is admitted, so a spec change that repairs it is not held.
     When the roll completes the record becomes `Complete` and the next
     group is admitted after the soak.
   - **The release** (the same failure would hit the next group): roll
     the operator back to the release that ran before. Waiting groups
     then have nothing to roll; the groups already rolled are rolled
     back one at a time, the stalled one first.
5. If the cause is the group, it cannot be fixed soon and the other
   groups should not wait, let the rollout continue past it:

   ```bash
   kubectl annotate mysqlfailovergroup orders -n orders \
     bloodraven.shipstream.io/rollout-release-slot=true
   ```

   The group's own roll continues and its record stays `Stalled`, so the
   alert keeps firing for it. Remove the annotation
   (`bloodraven.shipstream.io/rollout-release-slot-`) when the group has
   completed. Do not do this while the cause is unknown: if it is the
   release, the next group stalls too.
6. Verify: the group's `status.rollout.phase` is `Complete`, and
   `bloodraven_rollout_groups{phase="stalled"}` is `0`.

Rollback path: rolling the operator back (step 4). The operator never
rolls a stalled site back on its own.

## Paced rollout not progressing

Use when `BloodravenRolloutPendingTooLong` fires: groups have waited for
the rollout slot for 30 minutes and no group is rolling or stalled. The
waiting groups run their old pods and are otherwise unaffected, but spec
changes that restart their pods wait as well.

1. Rule out a CRD that is older than the operator:

   ```bash
   kubectl get events -A --field-selector reason=RolloutRecordNotStored
   ```

   Any such Event, or `bloodraven_rollout_record_not_stored` above `0`:
   follow [Rollout record not stored](#rollout-record-not-stored).
2. List the waiting groups and why each waits:

   ```bash
   kubectl get mysqlfailovergroup -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{"\t"}{.status.rollout.phase}{"\t"}{.status.rollout.reason}{"\t"}{.status.rollout.message}{"\n"}{end}'
   ```

3. `Pending` / `GroupNotStable`: the group is passed over until it is
   stable. The message gives the reason (not `Ready`, a restore, a
   planned failover, a recovery that is pending, the
   `AutomaticFailoverHeld` hold). Resolve that with the group's own
   runbook; the group is admitted once it is stable. A group that is
   never stable is never admitted on its own.
4. `Pending` / `NotStarted`, with `RolloutDeferred` Events: the group was
   admitted and did not start within `rollout.startGrace`. The message
   says what held it. If every group is deferred in turn, read the
   operator log for `paced rollout:` lines and for errors of the group
   reconcile.
5. To roll one waiting group now, whatever holds it:

   ```bash
   kubectl annotate mysqlfailovergroup billing -n billing \
     bloodraven.shipstream.io/rollout-admit=true
   ```

   This skips the stability check. Do it only when you have looked at the
   group and rolling its pods is safe: an `OrderedUpdate` group still
   refuses a handoff it cannot prove, a `Recreate` group restarts every
   site. Remove the annotation (`bloodraven.shipstream.io/rollout-admit-`)
   when the roll has completed; while it is set, every later release
   rolls this group without waiting.
6. Verify: `bloodraven_rollout_groups{phase="pending"}` falls to `0`.

## Rollout record not stored

Use when `BloodravenRolloutRecordNotStored` fires, a group has a
`RolloutRecordNotStored` Warning Event, or no pod rolled after an
operator upgrade and no group has a `status.rollout`.

The installed `MysqlFailoverGroup` CRD is older than the operator, so the
API server drops `status.rollout`. The operator rolls no group without a
stored record. Nothing is restarted and no data is at risk; the groups
stay on the pods of the previous release, and spec changes that restart
pods wait.

1. Confirm:

   ```bash
   kubectl get crd mysqlfailovergroups.shipstream.io -o yaml | grep -c 'rollout:'
   kubectl logs -n bloodraven deploy/bloodraven | grep 'paced rollout: record not stored'
   ```

   A count of `0` from the first command means the CRD has no
   `status.rollout`.
2. Apply the CRDs of the release the operator runs, with server-side
   apply (Helm does not upgrade a chart's `crds/`). See
   [Production install](/docs/get-started/install-production) for the
   command, and
   [Upgrading from v1.6.0 to v1.7.0](/docs/operations/upgrade-policy#upgrading-from-v160-to-v170)
   before you apply CRDs to a cluster that still runs v1.6.0.
3. Verify within a minute, without restarting the operator: one group
   shows `status.rollout.phase` `Admitted` or `Rolling`, the others
   `Pending`, and `bloodraven_rollout_record_not_stored` is `0`.

## Operator unavailable

Use [Operator Availability](/docs/architecture/operator-availability). Sidecar self-fencing is part of the safety model; do not disable it during diagnosis.

```bash
kubectl rollout status deployment/bloodraven -n bloodraven
kubectl logs -n bloodraven deploy/bloodraven
kubectl get lease -A | grep bloodraven
```

## DNS failover stuck

1. Confirm `status.activeSite` changed.
2. Inspect `DNSEndpoint` and external-dns logs.
3. Confirm provider record and TTL.
4. If applications still write old site, fence the old site and restart affected clients.

```bash
kubectl get dnsendpoint -A | grep orders
kubectl logs -n external-dns deploy/external-dns
dig orders.az.example.com
```
