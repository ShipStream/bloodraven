---
title: kubectl bloodraven plugin
---

`kubectl-bloodraven` is the operator's day-2 sidekick: a single static
binary that wraps the annotation grammars and on-demand CR shapes
the operator already understands. It is the recommended way to drive
a planned failover, kick off an ad-hoc backup or verification, or
peek at the current health of a `MysqlFailoverGroup` without
reaching for raw `kubectl annotate` / `kubectl apply` incantations.

The plugin only touches API objects — it never talks to MySQL
directly. Any operator-side validation (cooldown, site role, divergent
GTID prefix match, profile existence) still applies, so the safety
properties documented under [Failover](/docs/operations/failover),
[Planned failover](/docs/operations/planned-failover), and the backup pages are
preserved.

## Install

The plugin follows the [`kubectl` plugin
convention](https://kubernetes.io/docs/tasks/extend-kubectl/kubectl-plugins/):
any executable named `kubectl-<name>` on `$PATH` is callable as
`kubectl <name>`.

```bash
make build-kubectl-plugin       # produces bin/kubectl-bloodraven
make install-kubectl-plugin     # copies it into ~/.local/bin (preferred)
# or
sudo install -m 0755 bin/kubectl-bloodraven /usr/local/bin/

kubectl bloodraven version
```

Pinning a release tag at build time:

```bash
make build-kubectl-plugin KUBECTL_PLUGIN_VERSION=v0.2.0
```

The plugin reuses your existing kubeconfig (`$KUBECONFIG` /
`~/.kube/config`), honours `--context` / `--namespace` (`-n`), and
inherits the RBAC of the user invoking it — exactly the same surface
you'd hit with raw `kubectl get/annotate/create`.

## Commands

| Command | What it does | Equivalent without the plugin |
|---|---|---|
| `status [group]` | One-shot health view for one group or every group in the namespace | `kubectl get mysqlfailovergroup -o wide` + `kubectl describe` |
| `promote <group> <site>` | Apply the `planned-failover` annotation with optional `--max-lag-wait` override | `kubectl annotate mysqlfailovergroup <group> bloodraven.shipstream.io/planned-failover=<site>:maxLagWait=...` |
| `reclone <group> <site>` | Re-clone a divergent follower, or cold-reclone a candidate, DR site, or reader with `--cold`; auto-fills the GTID prefix when present | `kubectl annotate mysqlfailovergroup <group> bloodraven.shipstream.io/reclone-site=<site>:confirm=<group>:uid=<uid>[:gtidPrefix=<prefix>]` |
| `ack-planned-failover-hold <group>` | Acknowledge a planned-failover automation hold for the held run, read from `status.plannedFailoverHold.runID` (optional `--run-id`) | `kubectl annotate mysqlfailovergroup <group> bloodraven.shipstream.io/acknowledge-planned-failover-hold=<runID>` |
| `backup <group> --profile <name>` | Create a `MysqlBackup` CR; optional `--source-site`, `--wait` | `kubectl create -f mysqlbackup.yaml` |
| `verify-backup <group> --profile <name>` | Create a `MysqlBackupVerification` CR; optional `--backup`, `--wait` | `kubectl create -f mysqlbackupverification.yaml` |

Global flags accepted by every command:

```
--kubeconfig string   Path to kubeconfig (defaults to $KUBECONFIG or ~/.kube/config)
--context string      Kubeconfig context to use
--namespace, -n       Namespace (defaults to the kubeconfig context's namespace, or "default")
--output, -o string   "table" (default), "wide", "json", "yaml" — for commands that print data
```

Flags may come before, between or after the positional arguments (`kubectl bloodraven reclone orders iad -n orders` and `kubectl bloodraven reclone -n orders orders iad` are the same command). A `--` ends flag parsing.

### status

Per-group health, including site state, replication, recovery progress,
planned-failover phase, in-flight restores, backup schedules, and PITR
window.

```bash
# Detailed report for one group.
kubectl bloodraven status orders -n orders

# Whole-namespace table.
kubectl bloodraven status -n orders

# Wide table with planned-failover and recovery columns.
kubectl bloodraven status -n orders -o wide

# All namespaces.
kubectl bloodraven status --all-namespaces

# JSON/YAML for piping into other tools.
kubectl bloodraven status orders -o json | jq '.status.activeSite'
```

Below the site table, the detailed report lists every site that carries a
recovery report under "Site reports": the transactions a `RecoveryBlocked`
site holds that the primary lacks (`status.sites[].divergentGtid`, and the
site it was compared with), and the transactions a `RecloneRequired` site
issued itself and lacks (`status.sites[].lostGtid`), with the site that
holds them (`lostComparedTo`: the primary, or another site). For the latter it also
prints the whole message of the `OwnTransactionsLost` condition, which the
conditions table cuts at 80 characters: it names the site that holds the
transactions and says whether the operator is recloning the site or what the
automatic reclone waits for.

```text
Site reports:
  pdx lacks 10 transactions it issued itself, which the primary iad holds: 22222222-0000-11f1-8000-0000000000b2:91-100
  Own transactions lost: pdx lacks 10 transactions it issued itself that iad holds (...); automatic reclone waiting: another clone is running (by hand: kubectl bloodraven reclone orders pdx --cold). ...
```

### promote (planned failover)

```bash
# Same effect as `kubectl annotate ... planned-failover=pdx`.
kubectl bloodraven promote orders pdx -n orders

# With per-request override and synchronous wait.
kubectl bloodraven promote orders pdx \
  --max-lag-wait 30s \
  --wait --timeout 5m
```

The only per-request annotation override the operator recognises is
`maxLagWait`. `drainTimeout` is read from
`spec.plannedFailover.drainTimeout` on the CR — set it there if you
need a non-default value.

`--wait` polls `.status.plannedFailover.phase` and prints one line per
phase transition until the run reaches `Succeeded`, `Failed`,
or `Deferred`. On `Failed` it prints the run's `result.outcome` and
`result.reason`. **Exit code is 0 only on `Succeeded`** (or when the
operator skips the request because the site is already the active
primary, including a run that ends `Failed{NotStarted, AlreadyActive}`
because the site became the active primary before the run started:
`Planned failover skipped: site "<site>" became the active primary before
the run started.`). `Failed`, `Deferred`, a refusal and wait timeout all
return non-zero.

The annotation is written with an optimistic lock on the
`resourceVersion` the command validated. If the group changed in between,
the plugin re-reads it, validates again and retries, up to 5 times.

The wait follows only this request's run. It records
`status.plannedFailover.runID` before writing the annotation and ignores
that run, and its terminal marker, until a new run appears, so a previous
run's `Succeeded` is never reported as this request's result, and neither
is the result of a run for another site that a concurrent request
started. Two pending runs absorb the request, and the wait follows them
and says so: an `Admitting` run to the same site, and a `Deferred` run to
any site, which the operator retargets to the new annotation when it
resumes (`The request replaces the target of deferred planned failover
<runID> (was "<old>"); it runs for "<site>" when it resumes.`). If a
followed run ends while the annotation is still set, the wait keeps
going until the operator takes the request, and reports a new run if one
starts; a timeout then reads `planned failover <runID> ended but the
operator has not taken the request (the annotation is still set)`. If
status shows a different run before the adopted run's result was read,
the error says `planned failover <runID> was replaced in status before its
result was read`.

Some refusals write no run at all (an invalid value, a standing automation
hold, a request beside a running run or beside an earlier run's unhealed
fenced source): the operator removes the annotation and records a
`PlannedFailoverRejected` Event, which `--wait` prints as the error.
`--wait` therefore also needs `list` on `events` in the group's
namespace. If no Event is found, the error says the operator removed the
request without starting a run, names a run for another site that took
its place (`planned failover <runID> runs for site "<other>", from another
request`), and, when the Events could not be listed (an RBAC `Forbidden`,
say), ends `and its refusal Event could not be read: <error>`. A timeout
before the operator admits the request says so (is the operator
running?).

Upgrade the operator before the plugin where you can; the plugin
tolerates the skew. Against an operator that writes
`status.plannedFailover` without a `runID` (one from before the
planned-failover claim release), `--wait` prints `warning: the operator
wrote status.plannedFailover without a runID: it is older than this
plugin; following the run it started by its start time` to stderr and
reports that run's `Succeeded`, `Failed` or `Deferred` result. `Deferred` means the
operator has accepted the request but the anti-flap cooldown is still
ticking — the operator will retry once the cooldown expires, but the
promotion has *not* taken effect yet, so scripts that chain commands
on success will get the right answer.

See [Planned failover](/docs/operations/planned-failover) for the full lifecycle,
rollback rules, and what happens when the target is unhealthy / the
anti-flap cooldown is active.

### reclone

```bash
# Divergent-GTID case: plugin auto-fills the prefix from
# status.sites[iad].divergentGtid.
kubectl bloodraven reclone orders iad -n orders

# Cold reclone (no divergent GTID recorded). CLONE INSTANCE wipes the
# datadir, so the operator requires an explicit confirm token —
# `--cold` generates it for you from the group name.
kubectl bloodraven reclone orders iad -n orders --cold

# Explicit override (matching the documented 8-char minimum).
kubectl bloodraven reclone orders iad -n orders --gtid-prefix=a1b2c3d4
```

Readers use the same destructive cold-reclone workflow. The exact generic
form is:

```bash
kubectl bloodraven reclone <group> <reader-site> --cold
```

`--cold` is mandatory when no divergent GTID confirmation is available. It
generates the group-name confirmation token, and the operator still rejects
the active primary or an invalid target. A successful request wipes the
reader datadir, clones from the uniquely confirmed active primary, and then
waits for direct replication to converge. Clone traffic is unthrottled and
runs against the primary, so plan capacity before rebuilding a large reader.

With PITR enabled, any reclone starts up to 2 minutes after the request (4
when the rotation is acknowledged late): the
operator first rotates the site's binary log and waits for its sidecar to
archive the sealed tail that `CLONE INSTANCE` would wipe. A Warning Event
`PITRArchiveTailNotArchived` on the group means the clone started without
that confirmation. See
[Archiving the tail of an outgoing primary](/docs/backup-and-restore/backup-restore#archiving-the-tail-of-an-outgoing-primary).

### ack-planned-failover-hold

```bash
# After resolving the split brain by hand (see the hold runbook).
kubectl bloodraven ack-planned-failover-hold orders -n orders

# Name the run explicitly; refused unless it is the held run.
kubectl bloodraven ack-planned-failover-hold orders -n orders \
  --run-id 6f1c2a4e-4b7d-4a1f-9a0e-2d5b8c3f7e10
```

The plugin reads the held run's id from `status.plannedFailoverHold.runID`,
or from the `planned-failover-terminal` marker when status writes stalled,
and writes `bloodraven.shipstream.io/acknowledge-planned-failover-hold=<runID>`.
It refuses when the group has no hold, and when the hold names no run (a
`True` `AutomaticFailoverHeld` condition without `status.plannedFailoverHold`,
which a hand-edited status or a CRD rollback across the planned-failover
claim release produces; remove that condition by hand once the sites are
resolved, and the operator releases the hold without a restart). It does
not check the sites:
acknowledge only after the
[hold runbook](/docs/operations/runbooks#planned-failover-automation-hold)
steps are done.

### backup

```bash
# Ad-hoc backup against the configured "nightly" profile.
kubectl bloodraven backup orders --profile nightly -n orders

# Pin the source site, e.g. for taking a dump from the new replica
# right after a planned failover.
kubectl bloodraven backup orders --profile ondemand --source-site iad -n orders

# Block until done.
kubectl bloodraven backup orders --profile nightly --wait --timeout 1h -n orders
```

The plugin validates that the profile exists in
`spec.backup.profiles` and that any `--source-site` is in
`spec.sites` before posting the CR — so a typo fails immediately
instead of being deferred to the operator's reconcile loop.
The operator additionally rejects `ReadOnly` sites as backup sources;
readers are ineligible both for automatic selection and explicit overrides.

### verify-backup

```bash
# Verify the latest Succeeded MysqlBackup for the nightly profile.
kubectl bloodraven verify-backup orders --profile nightly -n orders

# Verify a specific backup with a blocking wait.
kubectl bloodraven verify-backup orders --profile nightly \
  --backup orders-nightly-abcde --wait --timeout 30m -n orders
```

When the profile carries a `verification` block with PITR /
sanity-check options, those settings are copied onto the manual CR
verbatim, so a manual run reproduces what the scheduled CronJob would
do.

## Why a plugin instead of raw `kubectl`?

Three motivations:

1. **Discoverability.** `kubectl bloodraven --help` lists every Bloodraven
   capability without an admin having to grep CRD YAML.
2. **Safety nets.** Pre-flight validation refuses obviously-broken
   inputs (wrong site, wrong profile, missing CR) so the operator's
   event log isn't polluted with `Failed{UnknownSite}` from typos.
3. **Streaming `--wait`.** Long-running operations (planned failover,
   backup, verification) emit one progress line per phase transition,
   which makes CI/CD pipelines and runbooks dramatically easier than
   polling `kubectl get -w` and parsing JSONPath.

The plugin is intentionally thin: it never replaces the operator's
authority over MySQL, never bypasses the cooldown, and never holds
state of its own. Treat it as a typing aid that prints a useful
summary at the end.

## Troubleshooting

* `error: MysqlFailoverGroup ... not found` — check `--namespace` (or
  `--context`) and run `kubectl get mysqlfailovergroups -A` to confirm
  the CR exists.
* `error: site "..." is not defined in spec.sites` — list the sites
  with `kubectl bloodraven status <group>`; spelling is case-sensitive.
* `Planned failover failed: outcome=NotStarted reason=CooldownActive` — the
  anti-flap cooldown is still ticking. Wait for the time in the message, or
  set `spec.plannedFailover.onCooldown: Defer` to queue the request.
* `Planned failover failed: outcome=NotStarted reason=AdmissionTimeout` — the
  claim was not granted within 2 minutes; the message names the last wait
  reason (for example `PeerUnreadable`: a `PrimaryCandidate` or `DisasterRecovery`
  site did not answer).
* `outcome=ManualRecoveryRequired` — automation is held for the group; see
  the [hold runbook](/docs/operations/runbooks#planned-failover-automation-hold).
  The `status` summary shows `+held` while the hold stands.
* `timed out after Xs waiting for ...` — the operation is still in
  progress on the server side; re-run `kubectl bloodraven status` to
  inspect the current phase. `--wait --timeout` is the polling budget,
  not the operator's budget.
* A site with `sourceConvergenceState: Blocked` and
  `sourceConvergenceReason: GTIDDiverged` cannot be safely repointed. Compare
  the follower and active-primary GTID sets, preserve any data that needs
  review, then use the divergent-prefix reclone flow or the explicit reader
  cold-reclone command above.
