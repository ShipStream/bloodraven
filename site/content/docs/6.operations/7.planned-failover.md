title: Planned failover
---

![planned failover infographic](/img/infographics/planned-failover.webp)

Planned failover is the admin-triggered graceful switchover path. It is the operational-hygiene counterpart to [emergency failover](/docs/operations/failover): use it for maintenance windows, rolling kernel upgrades on the active site's nodes, or any time you want to move the primary role to a specific replica **without** relying on the operator's automatic detection.

## TL;DR

```bash
kubectl annotate mysqlfailovergroup orders \
  bloodraven.shipstream.io/planned-failover=pdx
```

The operator claims the group's sites, fences the current primary, waits for `pdx` to apply the fenced source's whole GTID set, promotes it, publishes DNS, and records the failover. When `spec.dragonfly.enabled=true`, the same request also waits for the target Dragonfly replica to catch up and promotes it before the MySQL promotion. A successful run ends with `.status.plannedFailover.phase: Succeeded` and `.status.plannedFailover.result.outcome: Succeeded`.

Only `primary-candidate` sites are valid targets. `dr-only` and `read-only`
followers are never promoted, used for active DNS, or involved in node-taint
handoff. Readers remain direct followers and application read pools after the
switchover.

## Why not `kubectl exec`?

Manual promotion via three `kubectl exec ... SET GLOBAL ...` commands (see [Operations](/docs/operations/operations#manual-promotion-fallback-operator-unreachable)) works but has four real problems:

1. **No atomicity** — a dropped connection or typo mid-sequence leaves the cluster fenced-on-both-sides or promoting a replica that has not drained its relay logs.
2. **No lag gate** — nothing mechanical checks that the target is caught up before you flip `read_only=0`.
3. **No audit trail** — `bloodraven_failovers_total` does not increment, no Event fires, no CR status reflects what you did.
4. **Bypasses the anti-flap cooldown** — a switchover immediately before a real emergency exposes the cluster to a window where the operator refuses to take automatic action.

The annotation API closes all four.

## Strict by design

A planned failover is optional, so it is strict. It moves the primary role only when it can prove that doing so is safe. Otherwise it waits (before anything is fenced) or stops, and it never writes to the target on a guess:

- **Positive read-only evidence.** When the claim is granted, when the source is fenced, and again immediately before the target's `super_read_only` is cleared, every other `primary-candidate` and every `dr-only` site must answer, and answer read-only. A site that does not answer is treated as a site that might be writable: the sidecar does not self-fence on lease expiry while it can still reach a peer, so a site the operator cannot reach may still be accepting writes. An unreadable `read-only` reader does not block the run; it is recorded as the warning `UnreachablePeers`. A writable reader blocks it like any other writable site.
- **A down DR site blocks planned failovers.** This follows from the rule above and is the deliberate availability cost. While a `primary-candidate` or `dr-only` site is down, a request waits in admission with `waitReason: PeerUnreadable` and ends `NotStarted` with `reason: AdmissionTimeout` after 2 minutes. Bring the site back, or remove it from `spec.sites`, then re-annotate. Emergency failover is not affected.
- **No guessing after a possible write.** Once `super_read_only=OFF` may have reached the target, a run that cannot explain what it finds does not let automatic split-brain resolution pick a winner. It ends `ManualRecoveryRequired` and holds automation until a human acknowledges it (see [The automation hold](#the-automation-hold)).
- **A run never ends `Succeeded` while a foreign writable site exists.**

## Lifecycle

```
            ┌──── Deferred (owns nothing; annotation kept) ────┐
 annotate ──┤                                                  ▼
            └──► Admitting (owns nothing) ──claim granted──► Fencing ──► Draining ──► WaitingForLag
                     │                                         │                         │
                     ▼ reject / deadline                       │            ┌────────────┴─────────────┐
               Failed{NotStarted}                              │            ▼ Dragonfly enabled        │
                                                               │   WaitingForDragonflySync             │
                                                               │            ▼                          │
                                                               │   PromotingDragonfly ─────────────────┤
                                                               │                                       ▼
                                                               │                                   Promoting
                                                               │                                       │ confirmed
                                                               ▼ nothing written to the target         ▼
                                                          RollingBack ──► Failed{RolledBack |      Publishing ──► Succeeded
                                                                          SourceLeftFenced}        (claim released)
              Promoting ── a write may have been sent; target lost or unconfirmable ──► Failed{PromotedUnconfirmed}
              Promoting ── a foreign writer, foreign transactions, or a writable target with a channel ──► Failed{ManualRecoveryRequired} + hold
```

`WaitingForDragonflySync` and `PromotingDragonfly` are skipped when Dragonfly was not enabled when the request was accepted.

| Phase | What the operator is doing |
| --- | --- |
| `Admitting` | The request was given a `runID`. The run owns nothing yet. Its annotation is removed once validation accepts the request; a request admitted into a wait before its validation (`AuthorityUnsettled`, or a refused deployment admission reservation) keeps the annotation until validation decides, and any `NotStarted` end removes it. Each pass re-validates the request against an uncached read, taken again once the deployment admission reservation is held, and asks the topology manager for the claim. While the claim is not granted, `admission.waitReason` says why (see [Admission](#admission)). The run ends `Failed{NotStarted, AdmissionTimeout}` at `admission.deadlineTime`, 2 minutes after it entered `Admitting`. |
| `Deferred` | Cooldown with `onCooldown: Defer`, or an unexpired deployment `failover-hold` (`admission.deferReason: DeploymentHold`). The run owns nothing and the annotation is kept; admission is retried at `admission.retryTime`, and the run enters `Admitting` with a fresh 2-minute deadline. A failover in flight also moves it to `Admitting`, waiting with `AuthorityUnsettled` (see [Admission](#admission)). While the deployment admission reservation is refused (an ordered update or in-place restore holds the sites, or a topology change is not persisted yet) the run stays `Deferred` and records `admission.waitReason` with the message `deferred; admission waiting (<reason>): <detail>`. A deferral that switches from `DeploymentHold` to `CooldownActive` emits `PlannedFailoverDeferred` again. |
| `Fencing` | The claim is granted. `sourceSite`, `claimTime`, `claimBaseline` and the fence intent (`fence.state: Intended` with the source's `sourceServerUUID`) are durable before anything is sent. On one pinned session the operator re-checks that the source is the same server and writable, sets `super_read_only=ON`, reads it back, snapshots `GTID_EXECUTED`, and re-probes every peer. The source's `role=primary` pod label is stripped, so the `-primary` Service sheds it. |
| `Draining` | The fence is proven (`fence.state: Applied`, `fence.gtidSet` is the fenced set; an empty set is valid for a source that never binlogged a transaction). `KillAppConnections` runs on the source every second until no application session is left or `settings.drainTimeout` (measured from `drain.startTime`) passes. A drain query that fails on a source that still answers does not count as a lost source: the drain proceeds at `drainTimeout` with `drain.remainingConnections` left unset and the message `... the connections remaining on "<site>" are unknown (<error>) ...` (log `planned failover: draining the source failed`). |
| `WaitingForLag` | Polling the target until its `GTID_EXECUTED` contains `fence.gtidSet`, bounded by `settings.maxLagWait` from `lagWait.startTime`. A target holding any transaction outside that set rolls the run back with `DivergentTarget`: the source is fenced, so such a transaction is history the source never had. A `fence.gtidSet` that cannot be parsed rolls back at once with `InvalidGTID`. A target whose identity read (`@@server_uuid`, pinned before `Promoting`) keeps failing counts as unreachable even while the lag probe answers, and rolls back `TargetLost` after the 10-second loss window. |
| `WaitingForDragonflySync` | Captures the source Dragonfly replication offset and polls the target replica until it reaches it, bounded by `settings.dragonfly.maxSyncWait`. |
| `PromotingDragonfly` | Strips the source Dragonfly traffic label, then promotes the target with `REPLTAKEOVER` (recorded first as `dragonfly.takeover.state: Intended`). If the target already reports `role:master` on a re-run, no second `REPLTAKEOVER` is sent, and the takeover counts only with evidence that the run made it master; a lost `REPLTAKEOVER` reply is resolved by reading the target's role, and a Dragonfly master that is neither the source nor the target is not taken over (see [Dragonfly during failover](/docs/operations/failover#dragonfly-during-failover)). The takeover's result gets its own write while the phase still reads `PromotingDragonfly`. Both role changes run only under the run's claim, re-checked immediately before the label strip and again before `REPLTAKEOVER`; after an operator restart the run re-proves its MySQL authority first, so Dragonfly never moves to the target after MySQL authority moved elsewhere. The phase is bounded from `takeover.intentTime` (see [Deadlines](#deadlines-and-worst-case-write-outage)): past that deadline no new takeover is started, and the run applies `onSyncTimeout` as for a failed takeover, except that a target an earlier attempt already promoted is finished instead. A run that sent a `REPLTAKEOVER`, or whose target reports master, waits for a busy Dragonfly gate up to one more gate allowance (about 40 seconds) past the deadline before it fails the takeover. |
| `Promoting` | The promotion intent (`promotion.state: Intended` with the target's `targetServerUUID`) is durable. On one pinned target session the operator runs `STOP REPLICA` and `RESET REPLICA ALL`, then the pre-write gate, then clears `super_read_only` and `read_only`, then confirms with live reads. The gate requires the target to still be a `primary-candidate` in the current `spec.sites` (a role change during the run rolls it back `TargetNotPromotable`; the role is also checked before `STOP REPLICA`), the recorded server, read-only, without a channel and holding exactly the fenced set; the source to be the fenced server, still read-only, with no transactions past the fenced set (transactions the target wrote that replicated back to it do not count); and every other `primary-candidate` and `dr-only` site to answer read-only. A source the gate cannot read is retried until the 10-second source-loss window expires (counted from the first failed source observation in the drain, the lag wait or the gate; the run stays `Promoting`), then rolls back `SourceLost`. A re-run classifies how far an interrupted promotion got from MySQL state and `@@server_uuid` before it sends anything. |
| `Publishing` | The promotion is confirmed (`promotion.state: Confirmed`), recorded in the topology manager, and published to DNS (`dns.state`). The claim was released right after the record and DNS, before this write: only status bookkeeping remains, so a stalled `Publishing` write never keeps automation (a split-brain fence of a site an external writer made writable, say) blocked. `promotion.warnings` carries the run's warnings, so a terminal record written by another process keeps them. |
| `RollingBack` | A failure while nothing was written to the target. The rollback intent (`rollback.reason`) is durable, then every step is decided live (see [Rollback](#rollback)). |
| `Succeeded` | Terminal success, written together with `status.lastFailover`, `status.lastFailoverTarget` and `status.promotionGtidExecuted`. |
| `Failed` | Terminal failure. `result.outcome` says what the cluster was left in and `result.reason` says why (see [Outcomes](#outcomes-and-reasons)). |

Every transition is one durable status write, conditioned on the `resourceVersion` of an uncached read, and every side effect runs only after the record that announces it has committed. An operator restart therefore always lands on a record whose side effect is either done or provably not started, and the next pass confirms it live before going on: it logs `planned failover: confirming recorded side effect`. The block is retained until a new annotation replaces it; a new annotation replaces only a terminal block.

## The claim

The claim is what a planned failover owns while it runs. It is held in one slot per group in the operator process, shared by every topology-manager generation, and granted by the topology manager against the other actors that can change the sites. While a run holds the claim (from `Fencing` until its promotion is confirmed, recorded and published, or a terminal record is durable), the topology manager defers:

- emergency failover, split-brain resolution and the primary re-assert (`cross-site action deferred: planned failover in progress`);
- ordered updates, keyring rotations and bootstraps;
- old-primary recovery, its connection drain and replication-source convergence;
- DNS reconciliation (the run publishes DNS itself before it releases);
- Dragonfly emergency and rollout promotions.

Application writes on whichever site is writable continue, and writable `dr-only` or `read-only` sites are still fenced. A request that is only waiting (`Admitting` without a grant, or `Deferred`) owns nothing and defers nothing.

The claim is released only by the run that owns it, and only after one of: a promotion confirmed live, recorded in the topology manager, published to DNS and marked in the annotation `bloodraven.shipstream.io/planned-failover-confirmed: <runID>:since=<confirmation time>` (the `Publishing` write follows without the claim; if the annotation cannot be written, the claim is kept and the tail retries, logging `planned failover: could not record the promotion's confirmation; keeping the claim`), a durable terminal record, a status write proven not to have committed, or a durable [terminal marker](#status-stalls-and-the-terminal-marker). An operator restart (or topology-manager replacement) before the `Publishing` write lands first looks at the run's `planned-failover-confirmed` annotation and the durable failover record. If the annotation names the run, or the record is the run's own, recognised by content (target, the fenced set as its watermark, and a time not before the promotion intent, all taken from the record the operator would restore), the promotion was confirmed and recorded and the claim had been released: it is not hydrated back, the run writes `Publishing` without it (`planned failover: promotion already recorded; publishing without the claim`), and the topology manager reconciles DNS. The annotation counts even after a later emergency failover replaced the run's failover record, and the new topology manager applies it as the run's promotion record (a newer record wins). Otherwise (the record was not durable yet) the restart hydrates the claim from the `Promoting` block, re-derives the confirmation from the live target, records the promotion, and releases again. Once the claim is released, Dragonfly emergency follow-ups, rollouts and snapshot upgrades no longer treat the run as the owner although `status.plannedFailover.phase` still reads `Promoting`: the claim slot decides, not the phase. Before the topology manager is registered after a restart, the status form decides instead: a run that still needs the claim, or a durable hold, owns Dragonfly. A released run whose `Publishing` write keeps failing is ended by the terminal marker after 10 seconds rather than 2 minutes, so a later failover that replaces the run's record cannot leave a restart holding the group for a run that already succeeded. A `ManualRecoveryRequired` run does not release it: the claim becomes an [automation hold](#the-automation-hold). The release is logged as `planned failover: claim released` with a `why` field.

After an operator restart the claim is hydrated from an uncached read when the topology manager starts, and the run re-proves its authority before its next side effect: the durable failover record still matches `claimBaseline` (an invalid copy, such as a malformed annotation or a target no longer in `spec.sites`, beside an unchanged valid copy is not a change; with no valid copy left the check fails closed), the fence is still the run's own, and no other site is writable. Within one process the claim and the leader election are re-checked immediately before every statement that changes a role, including the `super_read_only=OFF` right after the pre-write gate's probes. A source read that fails during the re-proof is a loss-window sample like any other (10 seconds before `SourceLost`), and an unreadable `read-only` site is no lack of evidence. If the run's source or target is removed from `spec.sites` while it runs, the run ends at once without MySQL access (`SourceLeftFenced{UnknownSite}`, or `PromotedUnconfirmed` from `Promoting`) and releases the claim.

### Admission

An `Admitting` pass first re-validates the request (a failure ends it `NotStarted` with that reason): the target is a known `primary-candidate`, is not already active, is not mid-keyring-rotation (`KeyringRotation`), is a healthy read-only replica without a divergence report (`DivergentTarget`, `TargetUnhealthy`), is not awaiting its post-restore reclone (`TargetUnhealthy`), no in-place restore or ordered update is in progress (`ConcurrentOperation`), the cooldown has passed (`CooldownActive`) and the durable failover record is readable (`InvalidFailoverState`). A cooldown found by an `Admitting` run ends it `CooldownActive`, with one exception: a request that waited in `Admitting` before its first validation (`AuthorityUnsettled`, or a refused deployment admission reservation) and still carries its annotation becomes `Deferred` with `CooldownActive` under `onCooldown: Defer`, its annotation kept for the retry.

Validation is skipped while a failover is in flight, because the status it reads is not yet meaningful: a target that emergency failover is promoting has stopped replicating, and validating it would end the run `TargetUnhealthy` seconds before it becomes the primary. Authority is unsettled while `status.activeSite` is empty, or while the durable failover record is newer than the run's `startTime` (for a new request with no run yet, recorded within the last 2 minutes) and names a site other than `status.activeSite`. Meanwhile an `Admitting` run waits with `admission.waitReason: AuthorityUnsettled`, a `Deferred` run moves to `Admitting` with that wait reason and a fresh 2-minute deadline, and a new request whose validation refusal depends on status (anything but `InvalidAnnotation`, `UnknownSite` or `TargetNotPromotable`) is admitted into the same wait. A new request that arrives while the deployment admission reservation is refused is handled the same way: a request-only refusal ends it `NotStarted` at once, and anything else is admitted into `Admitting` with `waitReason` `UpdateInFlight`, `RestoreInFlight`, `AuthorityUnsettled` or `ClaimHeld`, a `PlannedFailoverAdmissionDelayed` Event and the 2-minute deadline. Once authority settles the run is validated: a run whose target was just promoted ends `NotStarted{AlreadyActive}`, and one aimed elsewhere proceeds or is refused against the new primary. If authority does not settle within the deadline the run ends `AdmissionTimeout`.

Then it asks for the claim. The grant probes every site live: the source must answer writable with a readable `@@server_uuid`; the target must answer read-only with both replication threads running, no applier error, and replicating from the source; every other `primary-candidate` and `dr-only` site must answer read-only, and no site may be writable beside the source. Transient conditions wait; the latest is `admission.waitReason`, written (with a `PlannedFailoverAdmissionDelayed` Event) only when it or its detail changes (another claimant, say):

| `waitReason` | Waiting for |
| --- | --- |
| `ManagerAbsent`, `ManagerNotReady`, `ManagerRetiring` | No topology manager is running for the group, it has not completed a poll, or it is being replaced. |
| `PredecessorBusy` | A replaced topology manager is still changing the sites (its ordered update has not exited). |
| `AuthorityUnsettled` | A failover is in flight (`status.activeSite` is empty, or a failover record newer than the run is not yet published), the topology manager names no unique writable primary, the source reads read-only, the target or another site reads writable, or authority moved while the claim was being decided. |
| `PeerUnreadable` | The source, or a `primary-candidate` or `dr-only` peer, did not answer (see [Strict by design](#strict-by-design)). |
| `TargetNotReady` | The target did not answer, has no channel, its threads are not both running, its applier reports an error, or it replicates from a site other than the source. |
| `PromotionInFlight`, `UpdateInFlight`, `RestoreInFlight`, `BootstrapInFlight` | Another topology change holds the sites. |
| `RecoveryInFlight` | A recovery, connection-drain or source-convergence step is still running on the sites. Each such step is bounded (about 40s at most). |
| `KeyringRotation` | A keyring rotation of the target is being admitted. |
| `DragonflyUpgradeInFlight` | A Dragonfly snapshot upgrade is in flight. |
| `ClaimHeld` | Another run holds the claim. |
| `StatusUnsettled` | Reserved; not written by this release. |

A reason that cannot pass by waiting rejects the run at once instead: `UnknownSite`, `TargetNotPromotable`, `AlreadyActive`, `KeyringRotation` (the target is mid-rotation), `DivergentTarget`, `TargetUnhealthy` (a reclone-pending target), and `ManualRecoveryPending` (an [automation hold](#the-automation-hold) stands). A planned failover is not an override for a site awaiting its post-restore reclone.

While the latest run ended `SourceLeftFenced` with its own attributable fence and that fence has not healed (the source is not observed writable, and no failover was recorded after the run started), a new request is refused with a `PlannedFailoverRejected` Warning only: `planned failover refused: planned failover <runID> left source "<site>" fenced and the fence has not healed yet; the topology manager re-asserts it, or unfence it by hand, then re-annotate`. The annotation is removed and `status.plannedFailover` keeps the old run, because a restarted operator names the source for the re-assert from that block.

## Spec-level defaults

A [deployment hold](/docs/configuration/deployment-api#durability-and-fencing) defers admission regardless of `onCooldown`. `admission.deferReason: DeploymentHold` names the operation and instance in the message, and `admission.retryTime` is the earliest hold expiry. Renewal can extend the wait. A hold found while a run is already `Admitting` (normally impossible: a hold lease is refused while a run is active) ends it `NotStarted` with `ConcurrentOperation`. Ordered update and restore-in-place honor the same holds, while emergency failover and fencing never consult them. A hold does not relax any normal admission requirement when it expires. Use the [explicit revocation procedure](/docs/operations/operations#deployment-coordination), not Lease deletion, when approved maintenance must interrupt a deployment.

Cluster-wide knobs live on the CR so common overrides don't have to be spelled into every `kubectl annotate`:

```yaml
spec:
  plannedFailover:
    maxLagWait: 5m     # max time to wait for the target to catch up before rolling back
    drainTimeout: 30s  # upper bound on KillAppConnections polling after super_read_only=ON
    onCooldown: Reject # one of: Reject (default) or Defer
  dragonfly:
    plannedFailover:
      maxSyncWait: 30s      # Dragonfly target sync / REPLTAKEOVER budget
      onSyncTimeout: Proceed # one of: Proceed (default) or Fail
```

All fields are optional; omitting `plannedFailover` is equivalent to `{maxLagWait: 5m, drainTimeout: 30s, onCooldown: Reject}`. Omitting `dragonfly.plannedFailover` is equivalent to `{maxSyncWait: 30s, onSyncTimeout: Proceed}` when Dragonfly is enabled. The effective values are snapshotted into `status.plannedFailover.settings` when the request is accepted (again when a `Deferred` run resumes), so a spec edit does not change a running switchover.

- **`maxLagWait`** — how long `WaitingForLag` polls the target before rolling back. Set shorter than the default when you know the cluster is caught up and want to fail fast.
- **`drainTimeout`** — upper bound on the `Draining` phase's `KillAppConnections` loop. After `super_read_only=ON`, the operator kills stragglers every second until the count reaches zero or the budget expires; advancing to `WaitingForLag` happens either way (`drain.remainingConnections` records what was left) so a stuck client cannot block the switchover. Surviving clients cannot write: they get `ER_OPTION_PREVENTS_STATEMENT`.
- **`onCooldown`** — what happens when admission finds the anti-flap cooldown active:
  - `Reject` (default): stamp `Failed{NotStarted, CooldownActive}` and clear the annotation. The admin must re-annotate after the cooldown expires.
  - `Defer`: stamp `Deferred`, keep the annotation in place, and retry admission automatically at `admission.retryTime`. Useful when you want to queue a switchover immediately after an emergency event without manually waiting out the cooldown. Removing the annotation while `Deferred` ends the run `NotStarted` with `Canceled`.
- **`dragonfly.plannedFailover.maxSyncWait`** — how long `WaitingForDragonflySync` waits for the target Dragonfly replica to reach the source offset. The same duration is used as the `REPLTAKEOVER` timeout. Dragonfly takes that timeout in whole seconds, so it is rounded up to the next second (minimum 1s). The operator waits up to 12s beyond it for the reply, because the target Dragonfly allows its master 10s past the budget.
- **`dragonfly.plannedFailover.onSyncTimeout`** — what happens when Dragonfly sync or promotion cannot prove session preservation (including a source offset that could not be captured, `dragonfly.sourceOffsetState: Unavailable`):
  - `Proceed` (default): continue to the MySQL promotion and record `status.plannedFailover.dragonfly.sessions: Lost` with `dragonfly.reason` `DragonflySyncTimeout` or `DragonflyPromotionFailed`.
  - `Fail`: roll back before the MySQL promotion (`rollback.reason` `DragonflySyncTimeout` or `DragonflyPromotionFailed`), release the MySQL fence, and leave `status.activeSite` unchanged.

### Per-request override

The annotation value may carry a `maxLagWait` override. The value follows the one grammar of Bloodraven's one-shot action annotations, `<subject>(:<key>=<value>)*`: the subject is the target site, each pair splits at its first `=`, values use only `A-Za-z0-9._/+-` (so a value never contains `:` or `=`), and each key appears once:

```bash
kubectl annotate mysqlfailovergroup orders \
  bloodraven.shipstream.io/planned-failover=pdx:maxLagWait=30s
```

Useful when you know the target is caught up and want to fail fast rather than wait five minutes for the default timeout. An unparseable value (an unknown or repeated key, an empty pair, a value outside the charset, whitespace inside the value, or overrides with no site such as `:maxLagWait=5s`) is rejected with a `PlannedFailoverRejected` Event and removed; no status block is written for it. An annotation for the already-active site is removed with a `PlannedFailoverSkipped` Event. While a run is live (`Admitting` or later), a leftover copy of its own request (the same target, with the same or no `maxLagWait`) is removed silently, and any other request is removed with a `PlannedFailoverRejected` Event (`planned-failover annotation ignored: a previous planned failover is still running`). A `Deferred` run instead takes a new request as its target when it resumes. The operator removes only the annotation value it evaluated: a request written in the meantime is left for the next pass.

```bash
kubectl get mysqlfailovergroup orders \
  -o jsonpath='{.status.plannedFailover}{"\n"}'
kubectl bloodraven status orders
```

The duration is `result.completionTime - startTime` (`kubectl bloodraven status` prints it). Nothing is lost by construction: the gate promotes only a target that holds exactly the fenced set.

## Outcomes and reasons

`result.outcome` says what the cluster was left in:

| Outcome | Meaning | What to do |
| --- | --- | --- |
| `Succeeded` | The promotion completed, was confirmed with positive evidence, recorded and published. | Nothing; check `result.warnings`. |
| `NotStarted` | No fence intent was ever durable: nothing was sent to any site. | Fix the reason and re-annotate. |
| `RolledBack` | A fence intent was durable, nothing was written to the target, and the source is writable at the end. | Fix the reason and re-annotate. |
| `SourceLeftFenced` | Nothing was written to the target, and the source stays read-only: a writable peer, an unattributable fence, an unconfirmed unfence, a lost source, a status stall, no manager, or a source or target removed from `spec.sites`. | See [Healing a fenced source](#healing-a-fenced-source): most cases heal on their own, some are manual. |
| `PromotedUnconfirmed` | `super_read_only=OFF` may have been sent to the target, and the target could not be confirmed or was lost. | See [Promoted but unconfirmed](#promoted-but-unconfirmed). |
| `ManualRecoveryRequired` | The run may have written to the target and the result cannot be explained: a foreign writable site, transactions on the target outside the fenced set, a writable target with a replication channel, a replaced server after a possible write (or after the run's failover record became durable). **Automation is held.** | Follow the [hold runbook](/docs/operations/runbooks#planned-failover-automation-hold). |

`result.reason` says why:

| Reason | Outcome(s) | Meaning |
| --- | --- | --- |
| `InvalidAnnotation`, `UnknownSite`, `TargetNotPromotable`, `AlreadyActive`, `TargetUnhealthy`, `KeyringRotation`, `CooldownActive`, `ConcurrentOperation`, `InvalidFailoverState`, `Canceled` | NotStarted | Admission refused the request (see [Admission](#admission)). `TargetNotPromotable` also ends a run in `Promoting` whose target's role changed in `spec.sites` during the run: nothing is written to it and the run rolls back (RolledBack or SourceLeftFenced). |
| `UnknownSite` | SourceLeftFenced, PromotedUnconfirmed | The run's source or target was removed from `spec.sites` while the run held the claim. The run ended at once without MySQL access, like a manager absence, and named nothing: check the remaining sites by hand. |
| `DivergentTarget` | NotStarted; RolledBack or SourceLeftFenced | The target has a divergence report (refused before fencing), or held transactions outside the fenced set during the lag wait (rolled back). Reclone the target or make the primary contain the set, then re-annotate. See [Divergent replicas](/docs/operations/failover#divergent-replicas). |
| `ManualRecoveryPending` | NotStarted | A new request was refused because an [automation hold](#the-automation-hold) stands. |
| `AdmissionTimeout` | NotStarted | The claim was not granted within 2 minutes; the message names the last wait reason. |
| `AuthorityChanged` | NotStarted, RolledBack, SourceLeftFenced, ManualRecoveryRequired | Authority moved: the source was replaced or turned read-only before the fence was sent, the source's `super_read_only=ON` is not this run's, the source holds transactions past the fenced set before a write (its fence was lifted, written through and set again; the rollback lets the target catch up), the claim could not be re-established, or the failover record changed after a possible write. |
| `LegacyRunRefused` | NotStarted, SourceLeftFenced, PromotedUnconfirmed | The block was written by an older operator (see [Upgrading across this release](#upgrading-across-this-release)). |
| `FenceFailed` | RolledBack, SourceLeftFenced | The fence could not be applied and proven within 30 seconds (this includes a peer that stayed unreadable). |
| `SourceLost` | SourceLeftFenced (RolledBack if the source answers writable again); PromotedUnconfirmed | The source did not answer for 10 seconds; emergency failover takes over after the release. Once the target holds the run's own writes, an unreachable source at the pre-write gate ends `PromotedUnconfirmed` at once and names the target. |
| `SourceUnfenced` | RolledBack, SourceLeftFenced | The source's fence disappeared (for example mysqld restarted to its boot state) before the promotion. |
| `TargetLost` | RolledBack, SourceLeftFenced, PromotedUnconfirmed | The target did not answer for 10 seconds. |
| `ForeignWritable` | SourceLeftFenced (before a write), ManualRecoveryRequired (after a possible write) | Another site answered writable, the source holds transactions past the fenced set after a possible write, or the rollback found the target writable beside an already-writable source. |
| `PeerUnreadable` | RolledBack or SourceLeftFenced; PromotedUnconfirmed | A `primary-candidate` or `dr-only` peer did not answer at the pre-write gate. |
| `LagTimeout` | RolledBack, SourceLeftFenced | The target did not apply the fenced set within `maxLagWait`. |
| `InvalidGTID` | RolledBack, SourceLeftFenced | The fenced set could not be parsed. |
| `DragonflySyncTimeout`, `DragonflyPromotionFailed` | RolledBack, SourceLeftFenced | Dragonfly could not be synced or promoted under `onSyncTimeout: Fail`. `DragonflyPromotionFailed` includes a `PromotingDragonfly` phase that passed its deadline without a takeover. |
| `TargetChanged` | RolledBack, SourceLeftFenced | The target is not the server, or not in the state, the promotion intent recorded, and nothing was written to it. Also: a new operator process found the target pod replaced before the run's own failover record was durable, with the source still holding the whole fenced set under the run's fence and every other promotable site read-only; anything only the replaced pod could hold was written after the fence (the asynchronous-replication RPO), so the run rolls back instead of holding. |
| `PromotionAborted` | RolledBack, SourceLeftFenced | The promotion statements kept failing for 2 minutes with the target reachable, before anything was written. A re-run in a new operator process whose target still has its replication channel does not count a failed `STOP REPLICA` or `RESET REPLICA ALL` as a possible write, so it also ends here. |
| `PromotionUnconfirmed` | PromotedUnconfirmed | A write may have been sent but the promotion could not be confirmed within 2 minutes. |
| `ManagerUnavailable` | SourceLeftFenced, PromotedUnconfirmed | No topology manager ran for the group for 5 minutes while the run held the claim. A promotion this process had already confirmed ends `Succeeded` instead: the terminal write applies the failover record and DNS is left to the next manager. |
| `StatusStalled` | NotStarted, RolledBack, SourceLeftFenced, PromotedUnconfirmed | Status writes failed for 2 minutes; the run ended with a terminal marker. |
| `ExecuteFailed` | ManualRecoveryRequired | The promotion was executed and failed in a way the run cannot explain (for example transactions on the target outside the fenced set). |
| `InternalError` | any | An inconsistency in the run's own records. |

`result.warnings` qualify an outcome:

| Warning | Meaning |
| --- | --- |
| `DNSUpdateFailed` | The promotion succeeded but the DNS update failed (`dns.state: Failed`, `dns.lastError`). The `-primary` Service label swap already carries writes; the topology manager's DNS reconcile repairs the record after the release. |
| `DragonflySessionsLost` | The Dragonfly takeover succeeded but the MySQL run did not: Dragonfly now leads on the target while MySQL stayed on the source. |
| `TargetReplicationNotRestored` | A rollback left the target without a running replication channel: it could not restore the channel after `STOP REPLICA` or `RESET REPLICA ALL`, would not point it at an unverified source, or the run ended `SourceLeftFenced` with the channel gone. See playbook 23 in the doctor skill. |
| `UnreachablePeers` | A peer did not answer at some step where that is allowed: a reader at any point, any peer in the probe right after the fence (the pre-write gate still requires every `primary-candidate` and `dr-only` peer to answer), or a peer that answered read-only at the gate and not at the confirm. |
| `FenceNotAttributable` | The source is read-only, but the fence cannot be proven to be this run's; the run does not clear it. |
| `StatusStalled` | The run ended with a terminal marker. |
| `SourceReplaced` | The source's `@@server_uuid` changed during the run (a clone or restore replaced it). A rollback does not re-point the target at such a source; it leaves the target for a reclone. |
| `TargetSuperReadOnlyNotRestored` | A rollback that found the source already writable could not put the target back to `super_read_only=ON` before its deadline. The target still reads `read_only=ON`, `super_read_only=OFF`, so sessions with `SUPER` or `CONNECTION_ADMIN` can write to it beside the source; its channel was not restored (`TargetReplicationNotRestored` too). Set `super_read_only=ON` on the target by hand, then restore its replication or reclone it. |

## Deadlines and worst-case write outage

"Write outage" is the time during which no site accepts application writes, from the run's fence until a writable primary exists again. The figures assume the default settings and a topology-manager emergency debounce of about 6 seconds.

| Phase / condition | Window or deadline | Outcome | Worst-case write outage |
| --- | --- | --- | --- |
| `Admitting` | 2 minutes from entering `Admitting` | `NotStarted{AdmissionTimeout}` | 0: nothing is fenced |
| `Deferred` | until `admission.retryTime`, then `Admitting` | — | 0 |
| `Fencing`: the fence fails or a peer stays unreadable while the source is reachable | 30 seconds from `fence.intentTime` | `RollingBack{FenceFailed}` | ≤ 60 seconds |
| Any phase from `Fencing` up to the promotion, including the pre-write gate: the source does not answer | 10 seconds of consecutive failed probes, counted from the first failed source observation | `RollingBack{SourceLost}`, then `SourceLeftFenced` at once (no unfence retries) and emergency failover. A caught-up target is **not** promoted on its own: the pre-write gate needs source evidence | about 16 seconds plus the emergency path |
| `Draining` | `settings.drainTimeout` (30 seconds) | advance | 30 seconds (planned pause) |
| `WaitingForLag` | `settings.maxLagWait` (5 minutes) | `RollingBack{LagTimeout}` | 5 minutes + ≤ 30 seconds (the documented cost of a lagging target) |
| `WaitingForLag`, the Dragonfly phases, or `Promoting` before a write: the target does not answer | 10 seconds | `RollingBack{TargetLost}`: nothing was written, so the source is unfenced | about 10 seconds + ≤ 30 seconds |
| `WaitingForDragonflySync` | `maxSyncWait` (30 seconds) | `Proceed` or `Fail` | `maxSyncWait` |
| `PromotingDragonfly` | 40 seconds (gate waits) + `maxSyncWait` + 12 seconds from `takeover.intentTime` (82 seconds by default); one pass is bounded at the gate wait + `maxSyncWait` + 12 seconds + 15 seconds | `onSyncTimeout` as for a failed takeover: `Proceed` promotes MySQL anyway, `Fail` rolls back. A target an earlier attempt already promoted is finished instead | about 82 seconds |
| `Promoting` before a write: statements fail with the target reachable | 2 minutes from `promotion.intentTime` | `RollingBack{PromotionAborted}` | 2 minutes + ≤ 30 seconds |
| `Promoting` after a possible write: the target does not answer | 10 seconds | `PromotedUnconfirmed{TargetLost}` | about 16 seconds |
| `Promoting` after the target holds the run's own writes: the source does not answer at the pre-write gate | at once | `PromotedUnconfirmed{SourceLost}`, naming the target | the target is already writable; applications reach it once the topology manager adopts it and publishes DNS |
| `Promoting` after a possible write: the target answers but cannot be confirmed | 2 minutes | `PromotedUnconfirmed{PromotionUnconfirmed}` | up to 2 minutes (the target may already be serving) |
| `RollingBack` | 30 seconds from `rollback.intentTime` | `SourceLeftFenced{<rollback reason>}` | ≤ 30 seconds, then the named re-assert or manual (see below) |
| `Publishing` | none | the claim is already released; the status write keeps retrying | 0 |
| Status writes stall (including writes that conflict on every attempt of a pass) | 2 minutes from the durable stall-since time | terminal marker; a confirmed promotion only once its failover record is durable | 2 minutes + the named re-assert |
| No topology manager while holding the claim | 5 minutes from the durable absent-since time | `SourceLeftFenced` or `PromotedUnconfirmed`, reason `ManagerUnavailable`; `Succeeded` for a promotion this process already confirmed | ≤ 5 minutes (with no manager nothing could fail over anyway), then the named re-assert once a manager starts |
| `ManualRecoveryRequired` | until acknowledged | hold | the hold blocks automation, not writes: a writable site keeps serving |

## Rollback

`RollingBack` decides every step live, on each attempt, until it finishes or its 30-second deadline passes:

1. If a promotion intent exists and the run cannot prove that nothing was written to the target, the target must answer and hold nothing outside the fenced set. If it does not answer within the 10-second target-loss window (never past the rollback deadline; the source stays fenced meanwhile), the run ends `PromotedUnconfirmed`; if it holds other transactions, `ManualRecoveryRequired{ExecuteFailed}`.
2. A source that already answers writable ends `RolledBack` with no unfence sent, once a read-only target found at `super_read_only=OFF` is set back to `super_read_only=ON` and read back (while that fails the rollback retries; at its deadline it ends `RolledBack` with `TargetSuperReadOnlyNotRestored` and `TargetReplicationNotRestored`, the target's channel untouched), unless the target is writable too and the run may have written to it (a promotion intent was recorded): that is two writers, and the run ends `ManualRecoveryRequired{ForeignWritable}` with the [automation hold](#the-automation-hold) (message `the rollback found another writable site beside the writable source`). Another writable site the run never touched is logged (`planned failover: rollback found another writable site beside the source`) and left to split-brain handling; the run stays `RolledBack`.
3. If any other site answers writable, the source is **left fenced** (`SourceLeftFenced`): unfencing it would make two writable primaries. A site that merely does not answer does not stop the unfence.
4. A source lost for 10 seconds (`SourceLost`) is left fenced with no unfence retries; emergency failover takes over.
5. A fence that cannot be attributed to the run is not cleared (`SourceLeftFenced` with `FenceNotAttributable`). The fence is the run's when this process recorded sending it to that server, or when the durable intent names the server's current `@@server_uuid`.
6. Otherwise a read-only target found at `super_read_only=OFF` is first set back to `super_read_only=ON` and read back; while that fails the rollback retries with the source fenced (WARN `planned failover: could not restore the target's super_read_only`) and ends `SourceLeftFenced` at its deadline. The target's replication channel is then restored if the promotion had stopped or reset it, but re-created only toward a verified source (its pinned `@@server_uuid` matches, or it is the run's own writable source), and the source is unfenced on a pinned session to the same server (`super_read_only=OFF`, `read_only=OFF`) and read back. A confirmed unfence ends `RolledBack`.

A writable source whose `@@server_uuid` differs from the one the fence recorded adds the warning `SourceReplaced` and leaves the target for a reclone (`TargetReplicationNotRestored`). Every `SourceLeftFenced` rollback end reports `TargetReplicationNotRestored` when the target has no running channel.

The rollback never touches a site other than the source and the target.

## Healing a fenced source

A `SourceLeftFenced` run leaves the source read-only. Whether that heals on its own depends on why:

| Cause | How it ends |
| --- | --- |
| `SourceLost` | The source is unreachable: emergency failover runs after the release. |
| A writable peer (`ForeignWritable`, or a rollback that found another writable site) | A writable site exists, so there is no write outage. The fenced source is a read-only non-active site under the normal topology paths; the other writer is the existing split-brain path's, or a human's. |
| An attributable fence (`StatusStalled`, `ManagerUnavailable`, an unconfirmed unfence at the rollback deadline, other rollbacks that could not unfence), every site reachable, `status.lastFailoverTarget` empty or naming the source | **Automatic.** Once the terminal record (or the terminal marker) has committed, and before the claim is released, the run names the source for the topology manager's re-assert (`planned failover: named fenced source for re-assert`); after a restart the naming is re-derived from the terminal record. The re-assert restores writability only with every other site reachable and read-only and the source GTID-complete, rate-limited by `failoverCooldown` (WARN `re-asserting fenced promoted primary`). |
| An attributable fence with a peer unreachable | The normal unreachable-plus-read-only promotion path of emergency failover decides. |
| An attributable fence with `status.lastFailoverTarget` naming another site | **Manual**: the re-assert targets that site, not the source. |
| `FenceNotAttributable` (also on a run that sent its fence and then ended because authority moved), `AuthorityChanged` before the run's fence was applied, `LegacyRunRefused` | **Manual**: the fence is not the run's to clear, and the source is never named for the re-assert, including after a restart. |

The messages of the `FenceNotAttributable` and `LegacyRunRefused` ends carry this advice: `check which site is writable; if none is, unfence the site with the most complete GTID set by hand (confirm no other site is writable first); re-annotate only once a site is writable`. For the manual cases, check which site is writable first. If one is, leave the source fenced: old-primary recovery repoints it as a replica. If none is, confirm on every site that `@@GLOBAL.read_only=1`, pick the site with the most complete GTID set, and unfence it by hand (`SET GLOBAL super_read_only=OFF; SET GLOBAL read_only=OFF;`). Nothing else clears a fence the run could not attribute. Re-annotating a planned failover does not help here: admission needs exactly one writable primary, so with every site read-only the request waits with `waitReason: AuthorityUnsettled` and ends `NotStarted{AdmissionTimeout}` after 2 minutes while writes stay refused. Once one site is writable again, a planned failover can move the primary wherever you want it.

## Promoted but unconfirmed

`PromotedUnconfirmed` means `super_read_only=OFF` may have reached the target, but the run lost the target or could not confirm the promotion. Once the terminal record (or marker) has committed, and before the claim is released, the run names the target as the topology manager's last failover target (it reaches `status.lastFailoverTarget` through the next status write), so split-brain judgement keeps it. It names the target only while the durable failover record is still the run's baseline (or its own); if a failover was recorded during the run it names nothing and logs `planned failover: a failover was recorded during the run; the unconfirmed target is not named`. It does **not** stamp `status.lastFailover` or a pending promotion, so the cooldown does not block emergency failover. When the run ended because no topology manager ran (`ManagerUnavailable`), nothing is named.

Emergency failover may then promote the fenced source. That is the same RPO trade as emergency failover of any unreachable primary: DNS never pointed at the target, so it took essentially no application writes, and the sidecar lease rule fences a target cut off from its peers. To recover:

1. Read `@@GLOBAL.read_only`, `@@GLOBAL.super_read_only` and `@@GLOBAL.gtid_executed` on the source and the target.
2. If the target is writable and the source still fenced, the target is the primary in all but name; the topology manager adopts it on its next polls (it is the named last failover target). Verify DNS and application writes.
3. If both are read-only, the re-assert or emergency failover decides on the next polls. If the group stays without a writable site, follow the `NoPrimary` row of the doctor skill's alert matrix.
4. If both are writable, it is a split brain: follow the split-brain runbook.

## The automation hold

A run that may have written to the target and cannot explain the result ends `ManualRecoveryRequired`. In the same conditioned status write it records the hold and sets the condition that summarises it:

```yaml
status:
  plannedFailoverHold:
    runID: 6f1c2a4e-4b7d-4a1f-9a0e-2d5b8c3f7e10
    reason: ForeignWritable
    sourceSite: iad
    targetSite: pdx
    ambiguousSites: [iad, pdx]
    holdTime: "2026-04-20T14:32:09Z"
  conditions:
  - type: AutomaticFailoverHeld
    status: "True"
    reason: PlannedFailoverManualRecoveryRequired
    observedGeneration: 7
    message: >-
      planned failover run 6f1c2a4e-4b7d-4a1f-9a0e-2d5b8c3f7e10 ended ManualRecoveryRequired (ForeignWritable);
      writable or ambiguous sites: iad, pdx. Automatic failover is held: resolve the split brain by hand, then annotate
      bloodraven.shipstream.io/acknowledge-planned-failover-hold=6f1c2a4e-4b7d-4a1f-9a0e-2d5b8c3f7e10
```

`status.plannedFailoverHold` is the record: read the run from `plannedFailoverHold.runID`, not from the message. It outlives the run's `plannedFailover` block, which a refused request can replace. `ambiguousSites` lists the run's target and source plus every site the failing step classified (a writable or unreadable peer found by the pre-write gate, say). A hold rebuilt from the terminal marker by a process that did not see the run lists every site in `spec.sites`, target and source first.

and the claim becomes a hold: emergency failover, split-brain resolution, the re-assert, ordered updates, rotations, recovery and convergence, bootstraps and DNS reconciliation stay held for the group, exactly as while a run holds the claim. Writes on whichever site is writable continue, and the rest of the group's reconcile keeps running: pod labels, backup and verification schedules, backup status and keyring work are not held. A new planned-failover request is refused with `NotStarted{ManualRecoveryPending}` (Event only, keeping the hold run's block, while that block is the latest), also when only a terminal marker carries the hold; a request submitted during the hold does not run after the acknowledgement. Dragonfly is held too, because the hold owns the active Dragonfly the way a running planned failover does: if the Dragonfly master fails, no replica is promoted until the hold is acknowledged; replicas that lose their master are not re-attached; the active site's Dragonfly rollout is not promoted through; and a `dragonfly-snapshot-upgrade` request is rejected with the Warning Event `DragonflyUpgradeRejected` (`a planned failover run or automation hold owns the sites`). Applications that depend on the cache for availability see a Dragonfly failure as an outage for as long as the hold stands: resolve and acknowledge the hold promptly. Once it is acknowledged the Dragonfly manager resumes and repairs and promotes as usual. The hold survives operator restarts: it is rebuilt from `status.plannedFailoverHold` (or from a terminal marker that carries `ManualRecoveryRequired`) before the topology manager starts. A `True` condition without `plannedFailoverHold` (a hand-edited status, or a CRD rolled back across this release) holds too, at runtime as well as after a restart, but names no run, so no acknowledgement can clear it: remove the condition by hand once the sites are resolved. The operator then releases the hold without a restart: a hold that no `status.plannedFailoverHold`, `True` condition, `ManualRecoveryRequired` terminal marker or acknowledgement backs is released (`planned failover: released an automation hold no durable record backs`, then `planned failover: claim released` with `why=orphanHold`).

**Why a hold, and not let split-brain resolution pick.** The existing split-brain path keeps the history-named site, which can be the old source, and fences the other, which may be the only holder of acknowledged writes. An optional operation that ends unexplained must not discard data automatically.

The hold is visible as the Warning Event `PlannedFailoverManualRecoveryRequired` when it is set, the Warning Event `PlannedFailoverHoldPersisted` every 10 minutes while it stands, the condition in `kubectl bloodraven status` (the summary shows `+held`), and the doctor triage. To clear it, resolve the split brain by hand and then acknowledge it with the run's id, `kubectl bloodraven ack-planned-failover-hold <group>` (which writes `bloodraven.shipstream.io/acknowledge-planned-failover-hold=<runID>`); see the [hold runbook](/docs/operations/runbooks#planned-failover-automation-hold). The operator then removes `status.plannedFailoverHold` and sets the condition `False` with reason `PlannedFailoverHoldAcknowledged` (and writes the terminal record if only the marker carried the hold), deletes the marker, releases the hold, deletes the acknowledgement and emits the Normal Event `PlannedFailoverHoldAcknowledged`. An acknowledgement that names another run is ignored with the Warning Event `PlannedFailoverHoldAcknowledgementIgnored`. So is one that finds no standing hold (`no automation hold is standing for planned failover <runID>; nothing was resumed`) or a claim held for another run; the annotation is removed either way.

## Status stalls and the terminal marker

If the run's status writes fail for 2 minutes in a row while it holds the claim (an RBAC 403 on `status`, a 422, a failing admission webhook, or a write that conflicts on all three attempts of a pass; leader election does not bound these), the run ends outside `/status`:

1. The first failed write records the annotation `bloodraven.shipstream.io/planned-failover-stall-since: <runID>:since=<YYYYMMDDThhmmssZ>` with a conditioned metadata patch. It is never moved forward for the same run, so operator restarts do not restart the 2 minutes; the first committed status write for the run removes it.
2. After 2 minutes (10 seconds for a run that already released its claim after its promotion was confirmed, recorded and published, where only the `Publishing` write is left) the run finishes in memory only, with no MySQL rollback: a confirmed promotion is still recorded and published (`Succeeded` with the warning `StatusStalled`), but only once its failover record (time, target and the fenced set as the watermark) reads back from the out-of-band annotations or `status` (until then the operator keeps retrying and logs `planned failover: status stalled, but the promotion's failover record is not durable yet; retrying`, because a restart restores the watermark only from a durable record); a possible write becomes `PromotedUnconfirmed`; a run that never sent a `SET super_read_only=ON` (by this process's own record of the statement, not merely an attempt) becomes `NotStarted` or `RolledBack`; otherwise the source stays fenced (`SourceLeftFenced{StatusStalled}`) and is named for the re-assert.
3. It writes the annotation `bloodraven.shipstream.io/planned-failover-terminal: {"schemaVersion":1,"runID":"<runID>","outcome":"<outcome>","reason":"<reason>","warnings":[...]}`, conditioned on metadata. `warnings` is optional; the terminal record rebuilt from the marker keeps those warnings plus `StatusStalled`, and a marker carrying `FenceNotAttributable` never names the source for the re-assert. One run's marker never replaces another run's `ManualRecoveryRequired` marker (that run's hold evidence); the stalled run then keeps retrying, and keeps its claim, as when metadata writes fail. A marker that is not this payload, or carries another `schemaVersion`, proves nothing: it is ignored and logged. The marker also fences every late status write of the run. Every planned-failover predicate treats the run it names as terminal.
4. It releases the claim (or keeps it as a hold for `ManualRecoveryRequired`), logs ERROR `planned failover: status stalled; ended the run with a terminal marker` and emits the Warning Event `PlannedFailoverStatusStalled`.
5. It keeps retrying the terminal status record every 10 seconds and deletes a non-hold marker once that record lands. If the marker is removed by hand first, the operator still writes the run's terminal record (every 10 seconds until it commits), releases any claim hydrated back for the run, and never touches MySQL for the run again. The run's per-run annotations (`planned-failover-stall-since`, `planned-failover-manager-absent-since`, `planned-failover-confirmed`) are removed by the next pass once the run has ended. A `Succeeded` record rebuilt from a marker (by a restarted operator) carries the run's confirmation time, so it still writes `status.lastFailover`, `status.lastFailoverTarget` and `status.promotionGtidExecuted`.

`kubectl bloodraven promote --wait` and `kubectl bloodraven status` honour a marker that names the current run: `--wait` returns the marker's outcome (success, or an error naming `<outcome>:<reason>`) even while `status.plannedFailover.phase` still reads a non-terminal phase, and `status` prints `Ended by terminal marker: <outcome>:<reason>`. A successful `--wait` also prints the run's `result.warnings`.

Residuals: if even metadata writes fail, the claim stays held, the Warning Event says `the operator cannot write MysqlFailoverGroup <ns>/<name>`, and leader election is the only bound (the operator could not record an emergency failover either). A run whose fenced set exceeds 64 KiB cannot use the marker release, because the out-of-band watermark annotation cannot hold it; it keeps its claim until a status write lands.

An ambiguous status write (a timeout, a reset connection, a 5xx) is settled before anything else happens: the operator re-reads the object, and if the write did not land it bumps the `bloodraven.shipstream.io/planned-failover-status-fence` annotation conditioned on the same `resourceVersion`, which proves the write can never commit (`planned failover: status write ambiguous; settling`). The new fence value always moves past the stored one (by 1ns when the clock has not moved), and the fence counts as proof only if it moved the object's `resourceVersion`; otherwise settlement retries, and the write stays unknown after its attempts.

## Operator restarts, manager restarts, leader changes

- **No topology manager.** A run that holds the claim waits for one (with no manager, no other topology actor exists). After 30 seconds it emits the Warning Event `PlannedFailoverStalledManagerAbsent`; after 5 minutes, measured from the annotation `bloodraven.shipstream.io/planned-failover-manager-absent-since: <runID>:since=<YYYYMMDDThhmmssZ>`, it ends without MySQL access: `SourceLeftFenced{ManagerUnavailable}` (or the rollback's reason), or `PromotedUnconfirmed{ManagerUnavailable}` from `Promoting`. A promotion this process had already confirmed ends `Succeeded` instead (`promoted "<site>"; no topology manager for 5m0s, so the failover record is applied by this terminal write and DNS is left to the next manager`), with the failover record applied to status; if a failover was recorded during the run, it ends `ManualRecoveryRequired{AuthorityChanged}`.
- **A replaced topology manager.** The claim lives in a per-group slot shared by the old and new manager, so a configuration or credential change that restarts the manager does not drop it. A new request waits in admission (`PredecessorBusy`) while the old manager's ordered update is still exiting. A failover the old manager recorded (an ordered-update handoff that finished after it was replaced, whose status write the operator drops) is carried into the new manager, newest record wins, so its cooldown and last failover target still apply (`carried a retired topology manager's failover record`); a record whose target is no longer a site is not carried. The predecessor's named active site (a source named for the re-assert, say) is carried too (`carried the replaced topology manager's named active site`). A group deleted and recreated under the same name (another UID) does not inherit the old object's claim slot, hold included, or the retired manager's failover record (`group recreated, restarting topology manager`; WARN `planned failover: the group was recreated; its claim slot starts empty` when the old slot was held).
- **Deployment leases.** A deployment-lease refusal at admission (`TopologyPersistencePending`, `ConcurrentOperation`) is an admission wait (`admission.waitReason` `AuthorityUnsettled`, `UpdateInFlight`, `RestoreInFlight` or `ClaimHeld`), bounded by the admission deadline, not a reconcile error.
- **A reconcile that returns early.** When an earlier reconcile step returns an error or a requeue (credentials, encryption, ConfigMaps, Deployments, Services, the PDB, a Dragonfly snapshot upgrade, a restore Job or an in-place restore), the reconcile still runs one planned-failover pass for a run already in flight, a hold or acknowledgement, a terminal marker or a deadline annotation; a new request waits for a reconcile that reaches the regular step (`planned failover: pass on an early-returning reconcile failed` if that pass fails). While a run owns the sites, is `Publishing`, or a run's claim is held, the earlier step's error is logged (`reconcile failed while a planned failover is in flight; retrying on the planned-failover cadence`, key `requeueAfter`) and the reconcile requeues on the run's cadence instead of returning the error, whose exponential backoff would starve the run's deadlines. Only such a run (or a held run claim) skips the rest of the reconcile; an `Admitting` or `Deferred` run without a claim does not hold up label sync, Dragonfly labels or backups.
- **Pass bounds.** One reconcile pass, measured from before its uncached read of the group, is bounded at 15 seconds, 30 seconds for the promotion statements (each statement at 5 seconds), 45 seconds for the confirmed tail and the `PromotingDragonfly` bound above, plus up to 5 seconds for each durable write that needs its reserve and 30 seconds of settlement for each ambiguous write. Every durable write of a run (status records including the terminal one, deadline and marker annotations, request removal) and the stall bookkeeping keep a reserved 5-second budget even when MySQL work used up the pass's bound. The controller runs one reconcile at a time across groups, so a planned failover can delay another group's reconcile (label sync) by up to that long. Emergency failover runs in the topology manager and is not delayed.
- **Leader changes.** Exclusion holds within one operator leader, and across a handover only as far as controller-runtime's lease handover goes. See [Operator availability](/docs/architecture/operator-availability#leader-handover-and-planned-failover).

## Upgrading across this release

Do not upgrade the operator across this release with a planned failover in flight. A non-terminal block written by an older operator (no `runID`, or a removed phase such as `Pending`, `Validating` or `Resuming`) is refused, not resumed: no claim is hydrated, nothing is sent to MySQL, and the Warning Event `PlannedFailoverLegacyRunRefused` is emitted.

- A block in `Pending`, `Validating` or `Deferred` ends `NotStarted{LegacyRunRefused}`. A legacy `Deferred` request's annotation is left in place, so it re-runs as a new, strict request.
- A block in `Draining` or `WaitingForLag` ends `SourceLeftFenced{LegacyRunRefused}` with the message `planned failover in phase "<phase>" was written by an older operator and is refused: check which site is writable; if none is, unfence the site with the most complete GTID set by hand (confirm no other site is writable first); re-annotate only once a site is writable`.
- A block in `Promoting` or `Resuming` ends `PromotedUnconfirmed{LegacyRunRefused}`, because the older operator may already have made the target writable. Its message reads `... is refused: its promotion may have made the target writable; check which site is writable; ...` with the same advice.
- In both cases re-annotating only works once a site is writable; with every site read-only, unfence one by hand first. The old `sourcePrimary` field is pruned on read, so the record no longer names the source. These cases are manual (see [Healing a fenced source](#healing-a-fenced-source)).

See [Upgrade policy](/docs/operations/upgrade-policy#operator-upgrade-across-the-planned-failover-claim-release) for the CRD changes and for rolling back across this release.

## Follower convergence after success

Once the target is confirmed writable and planned-failover mutation is no
longer in flight, Bloodraven converges every other candidate, `dr-only`, and
`read-only` follower directly to the new primary. A chained or stale source is
not considered healthy merely because its replication threads are running.

Before `STOP REPLICA`, the new primary's `GTID_EXECUTED` must contain the
follower's executed set. Bloodraven repeats this check after STOP to close the
SQL-applier race, then changes the source and starts replication without
resetting replication metadata. A failure is retried boundedly on subsequent
polls. GTID non-containment is reported per site as
`sourceConvergenceState: Blocked` and
`sourceConvergenceReason: GTIDDiverged`; the operator does not discard the
follower's extra transactions or silently repoint it.

Reader client endpoints remain absent until MySQL is read-only, both threads
are healthy, direct-source convergence is `Converged`, and known lag is within
the effective reader threshold. A blocked or lagging reader does not change
the successful planned-failover result or the group's shared Ready/Degraded
conditions.

## Anti-flap cooldown

The planned path records `status.lastFailover` (the promotion's `confirmationTime`), `status.lastFailoverTarget` and `status.promotionGtidExecuted` (the fenced set) on success, exactly like the emergency path, and in the same status write as the `Succeeded` record. The record never moves to an older `lastFailover`. This means:

- A planned failover within `spec.failoverCooldown` of any prior failover is **rejected** at admission (or deferred with `onCooldown: Defer`).
- An emergency failover within `spec.failoverCooldown` of a planned failover is **blocked** by the same cooldown check in the topology manager.
- A `PromotedUnconfirmed` run does not stamp `lastFailover`, so it does not start a cooldown.

The default cooldown is 5 minutes; production deployments should keep this, not lower it.

## RPO

Planned failover is the **one** Bloodraven operation with an RPO of zero by construction. The pre-write gate promotes only a target that holds exactly the fenced source's GTID set, immediately before its `super_read_only` is cleared, with the source still fenced and every other promotable site read-only. Any scenario that would produce loss (the target falls behind, the source is lost mid-run, catch-up times out, a peer cannot be read) routes to a rollback or an outcome that leaves the decision to emergency failover or a human, instead of promoting a lagging replica. See [Durability and RPO](/docs/architecture/durability-and-rpo).
