![planned failover infographic](/img/infographics/planned-failover.webp)

Planned failover is the admin-triggered graceful switchover path. It is the operational-hygiene counterpart to [emergency failover](/docs/operations/failover): use it for maintenance windows, rolling kernel upgrades on the active site's nodes, or any time you want to move the primary role to a specific replica **without** relying on the operator's automatic detection.

## TL;DR

```bash
kubectl annotate mysqlfailovergroup orders \
  bloodraven.shipstream.io/planned-failover=pdx
```

The operator claims the group's sites, fences the current primary, waits for `pdx` to apply the fenced source's whole GTID set, promotes it, publishes DNS, and records the failover. When `spec.dragonfly.enabled=true`, the same request also waits for the target Dragonfly replica to catch up and promotes it before the MySQL promotion. A successful run ends with `.status.plannedFailover.phase: Succeeded` and `.status.plannedFailover.result.outcome: Succeeded`.

Only `primary-candidate` sites are valid targets. `dr-only` and `read-only`
followers are never promoted, used for active DNS, or involved in node-taint
handoff. Readers remain direct followers and application read pools after the
switchover.

## Why not `kubectl exec`?

Manual promotion via three `kubectl exec ... SET GLOBAL ...` commands (see [Operations](/docs/operations/operations#manual-promotion-fallback-operator-unreachable)) works but has four real problems:

1. **No atomicity** — a dropped connection or typo mid-sequence leaves the cluster fenced-on-both-sides or promoting a replica that has not drained its relay logs.
2. **No lag gate** — nothing mechanical checks that the target is caught up before you flip `read_only=0`.
3. **No audit trail** — `bloodraven_failovers_total` does not increment, no Event fires, no CR status reflects what you did.
4. **Bypasses the anti-flap cooldown** — a switchover immediately before a real emergency exposes the cluster to a window where the operator refuses to take automatic action.

The annotation API closes all four.

## Strict by design

A planned failover is optional, so it is strict. It moves the primary role only when it can prove that doing so is safe. Otherwise it waits (before anything is fenced) or stops, and it never writes to the target on a guess:

- **Positive read-only evidence.** When the claim is granted, when the source is fenced, and again immediately before the target's `super_read_only` is cleared, every other `primary-candidate` and every `dr-only` site must answer, and answer read-only. A site that does not answer is treated as a site that might be writable: the sidecar does not self-fence on lease expiry while it can still reach a peer, so a site the operator cannot reach may still be accepting writes. An unreadable `read-only` reader does not block the run; it is recorded as the warning `UnreachablePeers`. A writable reader blocks it like any other writable site.
- **A down DR site blocks planned failovers.** This follows from the rule above and is the deliberate availability cost. While a `primary-candidate` or `dr-only` site is down, a request waits in admission with `waitReason: PeerUnreadable` and ends `NotStarted` with `reason: AdmissionTimeout` after 2 minutes. Bring the site back, or remove it from `spec.sites`, then re-annotate. Emergency failover is not affected.
- **No guessing after a possible write.** Once `super_read_only=OFF` may have reached the target, a run that cannot explain what it finds does not let automatic split-brain resolution pick a winner. It ends `ManualRecoveryRequired` and holds automation until a human acknowledges it (see [The automation hold](#the-automation-hold)).
- **A run never ends `Succeeded` while a foreign writable site exists.**

## Lifecycle

```
            ┌──── Deferred (owns nothing; annotation kept) ────┐
 annotate ──┤                                                  ▼
            └──► Admitting (owns nothing) ──claim granted──► Fencing ──► Draining ──► WaitingForLag
                     │                                         │                         │
                     ▼ reject / deadline                       │            ┌────────────┴─────────────┐
               Failed{NotStarted}                              │            ▼ Dragonfly enabled        │
                                                               │   WaitingForDragonflySync             │
                                                               │            ▼                          │
                                                               │   PromotingDragonfly ─────────────────┤
                                                               │                                       ▼
                                                               │                                   Promoting
                                                               │                                       │ confirmed
                                                               ▼ nothing written to the target         ▼
                                                          RollingBack ──► Failed{RolledBack |      Publishing ──► Succeeded
                                                                          SourceLeftFenced}        (claim released)
              Promoting ── a write may have been sent; target lost or unconfirmable ──► Failed{PromotedUnconfirmed}
              Promoting ── a foreign writer, foreign transactions, or a writable target with a channel ──► Failed{ManualRecoveryRequired} + hold
```

`WaitingForDragonflySync` and `PromotingDragonfly` are skipped when Dragonfly was not enabled when the request was accepted.

| Phase | What the operator is doing |
| --- | --- |
| `Admitting` | The request was accepted and given a `runId`, and the annotation was removed. The run owns nothing yet. Each pass re-validates the request against an uncached read and asks the topology manager for the claim. While the claim is not granted, `admission.waitReason` says why (see [Admission](#admission)). The run ends `Failed{NotStarted, AdmissionTimeout}` at `admission.deadline`, 2 minutes after it entered `Admitting`. |
| `Deferred` | Cooldown with `onCooldown: defer`, or an unexpired deployment `failover-hold` (`admission.deferReason: DeploymentHold`). The run owns nothing and the annotation is kept; admission is retried at `admission.retryAfter`, and the run enters `Admitting` with a fresh 2-minute deadline. |
| `Fencing` | The claim is granted. `source`, `claimedAt`, `claimBaseline` and the fence intent (`fence.state: Intended` with the source's `sourceServerUUID`) are durable before anything is sent. On one pinned session the operator re-checks that the source is the same server and writable, sets `super_read_only=ON`, reads it back, snapshots `GTID_EXECUTED`, and re-probes every peer. The source's `role=primary` pod label is stripped, so the `-primary` Service sheds it. |
| `Draining` | The fence is proven (`fence.state: Applied`, `fence.gtidSet` is the fenced set; an empty set is valid for a source that never binlogged a transaction). `KillAppConnections` runs on the source every second until no application session is left or `settings.drainTimeout` (measured from `drain.startTime`) passes. |
| `WaitingForLag` | Polling the target until its `GTID_EXECUTED` contains `fence.gtidSet`, bounded by `settings.maxLagWait` from `lagWait.startTime`. A target holding any transaction outside that set rolls the run back with `DivergentTarget`: the source is fenced, so such a transaction is history the source never had. |
| `WaitingForDragonflySync` | Captures the source Dragonfly replication offset and polls the target replica until it reaches it, bounded by `settings.dragonfly.maxSyncWait`. |
| `PromotingDragonfly` | Strips the source Dragonfly traffic label, then promotes the target with `REPLTAKEOVER` (recorded first as `dragonfly.takeover.state: Intended`). If the target already reports `role:master` on a re-run, no second `REPLTAKEOVER` is sent. |
| `Promoting` | The promotion intent (`promotion.state: Intended` with the target's `targetServerUUID`) is durable. On one pinned target session the operator runs `STOP REPLICA` and `RESET REPLICA ALL`, then the pre-write gate, then clears `super_read_only` and `read_only`, then confirms with live reads. The gate requires the target to be the recorded server, read-only, without a channel and holding exactly the fenced set; the source to be the fenced server, still read-only; and every other `primary-candidate` and `dr-only` site to answer read-only. A re-run classifies how far an interrupted promotion got from MySQL state and `@@server_uuid` before it sends anything. |
| `Publishing` | The promotion is confirmed (`promotion.state: Confirmed`), recorded in the topology manager, and published to DNS (`dns.state`). The claim is released once this record is durable. Only status bookkeeping remains. |
| `RollingBack` | A failure while nothing was written to the target. The rollback intent (`rollback.reason`) is durable, then every step is decided live (see [Rollback](#rollback)). |
| `Succeeded` | Terminal success, written together with `status.lastFailover`, `status.lastFailoverTarget` and `status.promotionGtidExecuted`. |
| `Failed` | Terminal failure. `result.outcome` says what the cluster was left in and `result.reason` says why (see [Outcomes](#outcomes-and-reasons)). |

Every transition is one durable status write, conditioned on the `resourceVersion` of an uncached read, and every side effect runs only after the record that announces it has committed. An operator restart therefore always lands on a record whose side effect is either done or provably not started, and the next pass confirms it live before going on: it logs `planned failover: confirming recorded side effect`. The block is retained until a new annotation replaces it; a new annotation replaces only a terminal block.

## The claim

The claim is what a planned failover owns while it runs. It is held in one slot per group in the operator process, shared by every topology-manager generation, and granted by the topology manager against the other actors that can change the sites. While a run holds the claim (from `Fencing` until `Publishing` or a terminal record is durable), the topology manager defers:

- emergency failover, split-brain resolution and the primary re-assert (`cross-site action deferred: planned failover in progress`);
- ordered updates, keyring rotations and bootstraps;
- old-primary recovery, its connection drain and replication-source convergence;
- DNS reconciliation (the run publishes DNS itself before it releases);
- Dragonfly emergency and rollout promotions.

Application writes on whichever site is writable continue, and writable `dr-only` or `read-only` sites are still fenced. A request that is only waiting (`Admitting` without a grant, or `Deferred`) owns nothing and defers nothing.

The claim is released only by the run that owns it, and only after one of: a durable `Publishing` or terminal record, a status write proven not to have committed, or a durable [terminal marker](#status-stalls-and-the-terminal-marker). A `ManualRecoveryRequired` run does not release it: the claim becomes an [automation hold](#the-automation-hold). The release is logged as `planned failover: claim released` with a `why` field.

After an operator restart the claim is hydrated from an uncached read when the topology manager starts, and the run re-proves its authority before its next side effect: the durable failover record still matches `claimBaseline`, the fence is still the run's own, and no other site is writable.

### Admission

An `Admitting` pass first re-validates the request (a failure ends it `NotStarted` with that reason): the target is a known `primary-candidate`, is not already active, is not mid-keyring-rotation (`KeyringRotation`), is a healthy read-only replica without a divergence report (`DivergentTarget`, `TargetUnhealthy`), is not awaiting its post-restore reclone (`TargetUnhealthy`), no in-place restore or ordered update is in progress (`ConcurrentOperation`), the cooldown has passed (`CooldownActive`) and the durable failover record is readable (`InvalidFailoverState`). A cooldown that only appears during `Admitting` ends the run `CooldownActive`; a run does not go back to `Deferred`.

Then it asks for the claim. The grant probes every site live: the source must answer writable with a readable `@@server_uuid`; the target must answer read-only with both replication threads running, no applier error, and replicating from the source; every other `primary-candidate` and `dr-only` site must answer read-only, and no site may be writable beside the source. Transient conditions wait; the latest is `admission.waitReason`, written (with a `PlannedFailoverWaiting` Event) only when it changes:

| `waitReason` | Waiting for |
| --- | --- |
| `ManagerAbsent`, `ManagerNotReady`, `ManagerRetiring` | No topology manager is running for the group, it has not completed a poll, or it is being replaced. |
| `PredecessorBusy` | A replaced topology manager is still changing the sites (its ordered update has not exited). |
| `AuthorityUnsettled` | The topology manager names no unique writable primary, the source reads read-only, the target or another site reads writable, or authority moved while the claim was being decided. |
| `PeerUnreadable` | The source, or a `primary-candidate` or `dr-only` peer, did not answer (see [Strict by design](#strict-by-design)). |
| `TargetNotReady` | The target did not answer, has no channel, its threads are not both running, its applier reports an error, or it replicates from a site other than the source. |
| `PromotionInFlight`, `UpdateInFlight`, `RestoreInFlight`, `BootstrapInFlight` | Another topology change holds the sites. |
| `RecoveryInFlight` | A recovery, connection-drain or source-convergence step is still running on the sites. Each such step is bounded (about 40s at most). |
| `KeyringRotation` | A keyring rotation of the target is being admitted. |
| `DragonflyUpgradeInFlight` | A Dragonfly snapshot upgrade is in flight. |
| `ClaimHeld` | Another run holds the claim. |
| `StatusUnsettled` | Reserved; not written by this release. |

A reason that cannot pass by waiting rejects the run at once instead: `UnknownSite`, `TargetNotPromotable`, `AlreadyActive`, `KeyringRotation` (the target is mid-rotation), `DivergentTarget`, `TargetUnhealthy` (a reclone-pending target), and `ManualRecoveryPending` (an [automation hold](#the-automation-hold) stands). A planned failover is not an override for a site awaiting its post-restore reclone.

## Spec-level defaults

A [deployment hold](/docs/configuration/deployment-api#durability-and-fencing) defers admission regardless of `onCooldown`. `admission.deferReason: DeploymentHold` names the operation and instance in the message, and `admission.retryAfter` is the earliest hold expiry. Renewal can extend the wait. A hold found while a run is already `Admitting` (normally impossible: a hold lease is refused while a run is active) ends it `NotStarted` with `ConcurrentOperation`. Ordered update and restore-in-place honor the same holds, while emergency failover and fencing never consult them. A hold does not relax any normal admission requirement when it expires. Use the [explicit revocation procedure](/docs/operations/operations#deployment-coordination), not Lease deletion, when approved maintenance must interrupt a deployment.

Cluster-wide knobs live on the CR so common overrides don't have to be spelled into every `kubectl annotate`:

```yaml
spec:
  plannedFailover:
    maxLagWait: 5m     # max time to wait for the target to catch up before rolling back
    drainTimeout: 30s  # upper bound on KillAppConnections polling after super_read_only=ON
    onCooldown: reject # one of: "reject" (default) or "defer"
  dragonfly:
    plannedFailover:
      maxSyncWait: 30s      # Dragonfly target sync / REPLTAKEOVER budget
      onSyncTimeout: proceed # one of: "proceed" (default) or "fail"
```

All fields are optional; omitting `plannedFailover` is equivalent to `{maxLagWait: 5m, drainTimeout: 30s, onCooldown: reject}`. Omitting `dragonfly.plannedFailover` is equivalent to `{maxSyncWait: 30s, onSyncTimeout: proceed}` when Dragonfly is enabled. The effective values are snapshotted into `status.plannedFailover.settings` when the request is accepted (again when a `Deferred` run resumes), so a spec edit does not change a running switchover.

- **`maxLagWait`** — how long `WaitingForLag` polls the target before rolling back. Set shorter than the default when you know the cluster is caught up and want to fail fast.
- **`drainTimeout`** — upper bound on the `Draining` phase's `KillAppConnections` loop. After `super_read_only=ON`, the operator kills stragglers every second until the count reaches zero or the budget expires; advancing to `WaitingForLag` happens either way (`drain.remainingConnections` records what was left) so a stuck client cannot block the switchover. Surviving clients cannot write: they get `ER_OPTION_PREVENTS_STATEMENT`.
- **`onCooldown`** — what happens when admission finds the anti-flap cooldown active:
  - `reject` (default): stamp `Failed{NotStarted, CooldownActive}` and clear the annotation. The admin must re-annotate after the cooldown expires.
  - `defer`: stamp `Deferred`, keep the annotation in place, and retry admission automatically at `admission.retryAfter`. Useful when you want to queue a switchover immediately after an emergency event without manually waiting out the cooldown. Removing the annotation while `Deferred` ends the run `NotStarted` with `Cancelled`.
- **`dragonfly.plannedFailover.maxSyncWait`** — how long `WaitingForDragonflySync` waits for the target Dragonfly replica to reach the source offset. The same duration is used as the `REPLTAKEOVER` timeout. Dragonfly takes that timeout in whole seconds, so it is rounded up to the next second (minimum 1s). The operator waits up to 12s beyond it for the reply, because the target Dragonfly allows its master 10s past the budget.
- **`dragonfly.plannedFailover.onSyncTimeout`** — what happens when Dragonfly sync or promotion cannot prove session preservation (including a source offset that could not be captured, `dragonfly.sourceOffsetState: Unavailable`):
  - `proceed` (default): continue to the MySQL promotion and record `status.plannedFailover.dragonfly.sessions: Lost` with `dragonfly.reason` `DragonflySyncTimeout` or `DragonflyPromotionFailed`.
  - `fail`: roll back before the MySQL promotion (`rollback.reason` `DragonflySyncTimeout` or `DragonflyPromotionFailed`), release the MySQL fence, and leave `status.activeSite` unchanged.

### Per-request override

The annotation value may carry a `maxLagWait` override, mirroring the reclone-annotation key=value grammar:

```bash
kubectl annotate mysqlfailovergroup orders \
  bloodraven.shipstream.io/planned-failover=pdx:maxLagWait=30s
```

Useful when you know the target is caught up and want to fail fast rather than wait five minutes for the default timeout. An unparseable value is rejected with a `PlannedFailoverRejected` Event and removed; no status block is written for it. An annotation for the already-active site is removed with a `PlannedFailoverSkipped` Event. An annotation added while another run is past admission is removed with a `PlannedFailoverRejected` Event.

## Outcomes and reasons

`result.outcome` says what the cluster was left in:

| Outcome | Meaning | What to do |
| --- | --- | --- |
| `Succeeded` | The promotion completed, was confirmed with positive evidence, recorded and published. | Nothing; check `result.warnings`. |
| `NotStarted` | No fence intent was ever durable: nothing was sent to any site. | Fix the reason and re-annotate. |
| `RolledBack` | A fence intent was durable, nothing was written to the target, and the source is writable at the end. | Fix the reason and re-annotate. |
| `SourceLeftFenced` | Nothing was written to the target, and the source stays read-only: a writable peer, an unattributable fence, an unconfirmed unfence, a lost source, a status stall, or no manager. | See [Healing a fenced source](#healing-a-fenced-source): most cases heal on their own, some are manual. |
| `PromotedUnconfirmed` | `super_read_only=OFF` may have been sent to the target, and the target could not be confirmed or was lost. | See [Promoted but unconfirmed](#promoted-but-unconfirmed). |
| `ManualRecoveryRequired` | The run may have written to the target and the result cannot be explained: a foreign writable site, transactions on the target outside the fenced set, a writable target with a replication channel, a replaced server after a possible write. **Automation is held.** | Follow the [hold runbook](/docs/operations/runbooks#planned-failover-automation-hold). |

`result.reason` says why:

| Reason | Outcome(s) | Meaning |
| --- | --- | --- |
| `InvalidAnnotation`, `UnknownSite`, `TargetNotPromotable`, `AlreadyActive`, `TargetUnhealthy`, `KeyringRotation`, `CooldownActive`, `ConcurrentOperation`, `InvalidFailoverState`, `Cancelled` | NotStarted | Admission refused the request (see [Admission](#admission)). |
| `DivergentTarget` | NotStarted; RolledBack or SourceLeftFenced | The target has a divergence report (refused before fencing), or held transactions outside the fenced set during the lag wait (rolled back). Reclone the target or make the primary contain the set, then re-annotate. See [Divergent replicas](/docs/operations/failover#divergent-replicas). |
| `ManualRecoveryPending` | NotStarted | A new request was refused because an [automation hold](#the-automation-hold) stands. |
| `AdmissionTimeout` | NotStarted | The claim was not granted within 2 minutes; the message names the last wait reason. |
| `AuthorityChanged` | NotStarted, RolledBack, SourceLeftFenced, ManualRecoveryRequired | Authority moved: the source was replaced or turned read-only before the fence was sent, the source's `super_read_only=ON` is not this run's, the claim could not be re-established, or the failover record changed after a possible write. |
| `LegacyRunRefused` | NotStarted, SourceLeftFenced | The block was written by an older operator (see [Upgrading across this release](#upgrading-across-this-release)). |
| `FenceFailed` | RolledBack, SourceLeftFenced | The fence could not be applied and proven within 30 seconds (this includes a peer that stayed unreadable). |
| `SourceLost` | SourceLeftFenced (RolledBack if the source answers writable again) | The source did not answer for 10 seconds; emergency failover takes over after the release. |
| `SourceUnfenced` | RolledBack, SourceLeftFenced | The source's fence disappeared (for example mysqld restarted to its boot state) before the promotion. |
| `TargetLost` | RolledBack, SourceLeftFenced, PromotedUnconfirmed | The target did not answer for 10 seconds. |
| `ForeignWritable` | SourceLeftFenced (before a write), ManualRecoveryRequired (after a possible write) | Another site answered writable. |
| `PeerUnreadable` | RolledBack or SourceLeftFenced; PromotedUnconfirmed | A `primary-candidate` or `dr-only` peer did not answer at the pre-write gate. |
| `LagTimeout` | RolledBack, SourceLeftFenced | The target did not apply the fenced set within `maxLagWait`. |
| `InvalidGTID` | RolledBack, SourceLeftFenced | The fenced set could not be parsed. |
| `DragonflySyncTimeout`, `DragonflyPromotionFailed` | RolledBack, SourceLeftFenced | Dragonfly could not be synced or promoted under `onSyncTimeout: fail`. |
| `TargetChanged` | RolledBack, SourceLeftFenced | The target is not the server, or not in the state, the promotion intent recorded, and nothing was written to it. |
| `PromotionAborted` | RolledBack, SourceLeftFenced | The promotion statements kept failing for 2 minutes with the target reachable, before anything was written. |
| `PromotionUnconfirmed` | PromotedUnconfirmed | A write may have been sent but the promotion could not be confirmed within 2 minutes. |
| `ManagerUnavailable` | SourceLeftFenced, PromotedUnconfirmed | No topology manager ran for the group for 5 minutes while the run held the claim. |
| `StatusStalled` | NotStarted, RolledBack, SourceLeftFenced, PromotedUnconfirmed | Status writes failed for 2 minutes; the run ended with a terminal marker. |
| `ExecuteFailed` | ManualRecoveryRequired | The promotion was executed and failed in a way the run cannot explain (for example transactions on the target outside the fenced set). |
| `InternalError` | any | An inconsistency in the run's own records. |

`result.warnings` qualify an outcome:

| Warning | Meaning |
| --- | --- |
| `DNSUpdateFailed` | The promotion succeeded but the DNS update failed (`dns.state: Failed`, `dns.lastError`). The `-primary` Service label swap already carries writes; the topology manager's DNS reconcile repairs the record after the release. |
| `DragonflySessionsLost` | The Dragonfly takeover succeeded but the MySQL run did not: Dragonfly now leads on the target while MySQL stayed on the source. |
| `TargetReplicationNotRestored` | A rollback after `STOP REPLICA` or `RESET REPLICA ALL` could not restore the target's replication channel. See playbook 23 in the doctor skill. |
| `UnreachablePeers` | A peer did not answer at some step where that is allowed: a reader at any point, any peer in the probe right after the fence (the pre-write gate still requires every `primary-candidate` and `dr-only` peer to answer), or a peer that answered read-only at the gate and not at the confirm. |
| `FenceNotAttributable` | The source is read-only, but the fence cannot be proven to be this run's; the run does not clear it. |
| `StatusStalled` | The run ended with a terminal marker. |
| `SourceReplaced` | The source's `@@server_uuid` changed during the run (a clone or restore replaced it). |

## Deadlines and worst-case write outage

"Write outage" is the time during which no site accepts application writes, from the run's fence until a writable primary exists again. The figures assume the default settings and a topology-manager emergency debounce of about 6 seconds.

| Phase / condition | Window or deadline | Outcome | Worst-case write outage |
| --- | --- | --- | --- |
| `Admitting` | 2 minutes from entering `Admitting` | `NotStarted{AdmissionTimeout}` | 0: nothing is fenced |
| `Deferred` | until `admission.retryAfter`, then `Admitting` | — | 0 |
| `Fencing`: the fence fails or a peer stays unreadable while the source is reachable | 30 seconds from `fence.intendedAt` | `RollingBack{FenceFailed}` | ≤ 60 seconds |
| Any phase from `Fencing` up to the promotion: the source does not answer | 10 seconds of consecutive failed probes | `RollingBack{SourceLost}`, then `SourceLeftFenced` at once (no unfence retries) and emergency failover. A caught-up target is **not** promoted on its own: the pre-write gate needs source evidence | about 16 seconds plus the emergency path |
| `Draining` | `settings.drainTimeout` (30 seconds) | advance | 30 seconds (planned pause) |
| `WaitingForLag` | `settings.maxLagWait` (5 minutes) | `RollingBack{LagTimeout}` | 5 minutes + ≤ 30 seconds (the documented cost of a lagging target) |
| `WaitingForLag`, the Dragonfly phases, or `Promoting` before a write: the target does not answer | 10 seconds | `RollingBack{TargetLost}`: nothing was written, so the source is unfenced | about 10 seconds + ≤ 30 seconds |
| `WaitingForDragonflySync`, `PromotingDragonfly` | `maxSyncWait` (30 seconds); the takeover waits up to `maxSyncWait` + 12 seconds, plus about 40 seconds if an emergency Dragonfly promotion holds the gate | `proceed` or `fail` | about 112 seconds |
| `Promoting` before a write: statements fail with the target reachable | 2 minutes from `promotion.intendedAt` | `RollingBack{PromotionAborted}` | 2 minutes + ≤ 30 seconds |
| `Promoting` after a possible write: the target does not answer | 10 seconds | `PromotedUnconfirmed{TargetLost}` | about 16 seconds |
| `Promoting` after a possible write: the target answers but cannot be confirmed | 2 minutes | `PromotedUnconfirmed{PromotionUnconfirmed}` | up to 2 minutes (the target may already be serving) |
| `RollingBack` | 30 seconds from `rollback.intendedAt` | `SourceLeftFenced{<rollback reason>}` | ≤ 30 seconds, then the named re-assert or manual (see below) |
| `Publishing` | none | the claim is already released; the status write keeps retrying | 0 |
| Status writes stall | 2 minutes from the durable stall-since time | terminal marker | 2 minutes + the named re-assert |
| No topology manager while holding the claim | 5 minutes from the durable absent-since time | `SourceLeftFenced` or `PromotedUnconfirmed`, reason `ManagerUnavailable` | ≤ 5 minutes (with no manager nothing could fail over anyway), then the named re-assert once a manager starts |
| `ManualRecoveryRequired` | until acknowledged | hold | the hold blocks automation, not writes: a writable site keeps serving |

## Rollback

`RollingBack` decides every step live, on each attempt, until it finishes or its 30-second deadline passes:

1. If a promotion intent exists and the run cannot prove that nothing was written to the target, the target must answer and hold nothing outside the fenced set. If it does not answer, the run ends `PromotedUnconfirmed`; if it holds other transactions, `ManualRecoveryRequired{ExecuteFailed}`.
2. A source that already answers writable ends `RolledBack` with no unfence sent.
3. If any other site answers writable, the source is **left fenced** (`SourceLeftFenced`): unfencing it would make two writable primaries. A site that merely does not answer does not stop the unfence.
4. A source lost for 10 seconds (`SourceLost`) is left fenced with no unfence retries; emergency failover takes over.
5. A fence that cannot be attributed to the run is not cleared (`SourceLeftFenced` with `FenceNotAttributable`). The fence is the run's when this process recorded sending it to that server, or when the durable intent names the server's current `@@server_uuid`.
6. Otherwise the target's replication channel is restored if the promotion had stopped or reset it, and the source is unfenced on a pinned session to the same server (`super_read_only=OFF`, `read_only=OFF`) and read back. A confirmed unfence ends `RolledBack`.

The rollback never touches a site other than the source and the target.

## Healing a fenced source

A `SourceLeftFenced` run leaves the source read-only. Whether that heals on its own depends on why:

| Cause | How it ends |
| --- | --- |
| `SourceLost` | The source is unreachable: emergency failover runs after the release. |
| A writable peer (`ForeignWritable`, or a rollback that found another writable site) | A writable site exists, so there is no write outage. The fenced source is a read-only non-active site under the normal topology paths; the other writer is the existing split-brain path's, or a human's. |
| An attributable fence (`StatusStalled`, `ManagerUnavailable`, an unconfirmed unfence at the rollback deadline, other rollbacks that could not unfence), every site reachable, `status.lastFailoverTarget` empty or naming the source | **Automatic.** Before releasing, the run names the source for the topology manager's re-assert (`planned failover: named fenced source for re-assert`); after a restart the naming is re-derived from the terminal record. The re-assert restores writability only with every other site reachable and read-only and the source GTID-complete, rate-limited by `failoverCooldown` (WARN `re-asserting fenced promoted primary`). |
| An attributable fence with a peer unreachable | The normal unreachable-plus-read-only promotion path of emergency failover decides. |
| An attributable fence with `status.lastFailoverTarget` naming another site | **Manual**: the re-assert targets that site, not the source. |
| `FenceNotAttributable`, `AuthorityChanged` before the run's fence was applied, `LegacyRunRefused` | **Manual**: the fence is not the run's to clear. |

For the manual cases, check which site is writable first. If one is, leave the source fenced: old-primary recovery repoints it as a replica. If none is, confirm on every site that `@@GLOBAL.read_only=1`, pick the site with the most complete GTID set, and either unfence it by hand (`SET GLOBAL super_read_only=OFF; SET GLOBAL read_only=OFF;`) or re-annotate a planned failover. Nothing else clears a fence the run could not attribute.

## Promoted but unconfirmed

`PromotedUnconfirmed` means `super_read_only=OFF` may have reached the target, but the run lost the target or could not confirm the promotion. The run names the target as the topology manager's last failover target (it reaches `status.lastFailoverTarget` through the next status write), so split-brain judgement keeps it. It does **not** stamp `status.lastFailover` or a pending promotion, so the cooldown does not block emergency failover. When the run ended because no topology manager ran (`ManagerUnavailable`), nothing is named.

Emergency failover may then promote the fenced source. That is the same RPO trade as emergency failover of any unreachable primary: DNS never pointed at the target, so it took essentially no application writes, and the sidecar lease rule fences a target cut off from its peers. To recover:

1. Read `@@GLOBAL.read_only`, `@@GLOBAL.super_read_only` and `@@GLOBAL.gtid_executed` on the source and the target.
2. If the target is writable and the source still fenced, the target is the primary in all but name; the topology manager adopts it on its next polls (it is the named last failover target). Verify DNS and application writes.
3. If both are read-only, the re-assert or emergency failover decides on the next polls. If the group stays without a writable site, follow the `NoPrimary` row of the doctor skill's alert matrix.
4. If both are writable, it is a split brain: follow the split-brain runbook.

## The automation hold

A run that may have written to the target and cannot explain the result ends `ManualRecoveryRequired`. In the same conditioned status write it sets the condition:

```yaml
- type: AutomaticFailoverHeld
  status: "True"
  reason: PlannedFailoverManualRecovery
  message: >-
    planned failover run <runId> ended ManualRecoveryRequired (<reason>); writable or ambiguous sites: <sites>.
    Automatic failover is held: resolve the split brain by hand, then annotate
    bloodraven.shipstream.io/ack-planned-failover-hold=<runId>
```

and the claim becomes a hold: emergency failover, split-brain resolution, the re-assert, ordered updates, rotations, recovery and convergence, bootstraps and DNS reconciliation stay held for the group, exactly as while a run holds the claim. Writes on whichever site is writable continue. A new planned-failover request is refused with `NotStarted{ManualRecoveryPending}`. The hold survives operator restarts: it is rebuilt from the condition (or from a terminal marker that carries `ManualRecoveryRequired`) before the topology manager starts.

**Why a hold, and not let split-brain resolution pick.** The existing split-brain path keeps the history-named site, which can be the old source, and fences the other, which may be the only holder of acknowledged writes. An optional operation that ends unexplained must not discard data automatically.

The hold is visible as the Warning Event `PlannedFailoverManualRecoveryRequired` when it is set, the Warning Event `PlannedFailoverHoldPending` every 10 minutes while it stands, the condition in `kubectl bloodraven status` (the summary shows `+held`), and the doctor triage. To clear it, resolve the split brain by hand and then acknowledge it with the run's id; see the [hold runbook](/docs/operations/runbooks#planned-failover-automation-hold). The operator then removes the condition (and writes the terminal record if only the marker carried the hold), deletes the marker, releases the hold, deletes the acknowledgement and emits the Normal Event `PlannedFailoverHoldCleared`. An acknowledgement that names another run is ignored with the Warning Event `PlannedFailoverHoldAckIgnored`.

## Status stalls and the terminal marker

If the run's status writes fail for 2 minutes in a row while it holds the claim (an RBAC 403 on `status`, a 422, or a failing admission webhook; leader election does not bound these), the run ends outside `/status`:

1. The first failed write records the annotation `bloodraven.shipstream.io/planned-failover-stall-since: <runId>/<RFC3339>` with a conditioned metadata patch. It is never moved forward for the same run, so operator restarts do not restart the 2 minutes; the first committed status write for the run removes it.
2. After 2 minutes the run finishes in memory only, with no MySQL rollback: a confirmed promotion is still recorded and published (`Succeeded` with the warning `StatusStalled`); a possible write becomes `PromotedUnconfirmed`; a run that sent no fence becomes `NotStarted` or `RolledBack`; otherwise the source stays fenced (`SourceLeftFenced{StatusStalled}`) and is named for the re-assert.
3. It writes the annotation `bloodraven.shipstream.io/planned-failover-terminal: <runId>/<outcome>/<reason>`, conditioned on metadata. The marker also fences every late status write of the run. Every planned-failover predicate treats the run it names as terminal.
4. It releases the claim (or keeps it as a hold for `ManualRecoveryRequired`), logs ERROR `planned failover: status stalled; ended the run with a terminal marker` and emits the Warning Event `PlannedFailoverStatusStalled`.
5. It keeps retrying the terminal status record every 10 seconds and deletes a non-hold marker once that record lands.

Residuals: if even metadata writes fail, the claim stays held, the Warning Event says `the operator cannot write MysqlFailoverGroup <ns>/<name>`, and leader election is the only bound (the operator could not record an emergency failover either). A run whose fenced set exceeds 64 KiB cannot use the marker release, because the out-of-band watermark annotation cannot hold it; it keeps its claim until a status write lands.

An ambiguous status write (a timeout, a reset connection, a 5xx) is settled before anything else happens: the operator re-reads the object, and if the write did not land it bumps the `bloodraven.shipstream.io/planned-failover-status-fence` annotation conditioned on the same `resourceVersion`, which proves the write can never commit (`planned failover: status write ambiguous; settling`).

## Operator restarts, manager restarts, leader changes

- **No topology manager.** A run that holds the claim waits for one (with no manager, no other topology actor exists). After 30 seconds it emits the Warning Event `PlannedFailoverStalled`; after 5 minutes, measured from the annotation `bloodraven.shipstream.io/planned-failover-manager-absent-since: <runId>/<RFC3339>`, it ends without MySQL access: `SourceLeftFenced{ManagerUnavailable}` (or the rollback's reason), or `PromotedUnconfirmed{ManagerUnavailable}` from `Promoting`.
- **A replaced topology manager.** The claim lives in a per-group slot shared by the old and new manager, so a configuration or credential change that restarts the manager does not drop it. A new request waits in admission (`PredecessorBusy`) while the old manager's ordered update is still exiting.
- **Pass bounds.** One reconcile pass is bounded at 15 seconds, 30 seconds for the promotion statements, and 45 seconds for the confirmed tail, plus up to 30 seconds of settlement. The controller runs one reconcile at a time across groups, so a planned failover can delay another group's reconcile (label sync) by up to that long. Emergency failover runs in the topology manager and is not delayed.
- **Leader changes.** Exclusion holds within one operator leader, and across a handover only as far as controller-runtime's lease handover goes. See [Operator availability](/docs/architecture/operator-availability#leader-handover-and-planned-failover).

## Upgrading across this release

Do not upgrade the operator across this release with a planned failover in flight. A non-terminal block written by an older operator (no `runId`, or a removed phase such as `Pending`, `Validating` or `Resuming`) is refused, not resumed: no claim is hydrated, nothing is sent to MySQL, and the Warning Event `PlannedFailoverLegacyRefused` is emitted.

- A block in `Pending`, `Validating` or `Deferred` ends `NotStarted{LegacyRunRefused}`. A legacy `Deferred` request's annotation is left in place, so it re-runs as a new, strict request.
- A block in `Draining` through `Resuming` ends `SourceLeftFenced{LegacyRunRefused}` with the message `check which site is writable, then unfence the source or re-annotate`. The old `sourcePrimary` field is pruned on read, so the record no longer names the source. This case is manual (see [Healing a fenced source](#healing-a-fenced-source)).

See [Upgrade policy](/docs/operations/upgrade-policy#operator-upgrade-across-the-planned-failover-claim-release) for the CRD requirement.

## Follower convergence after success

Once the target is confirmed writable and planned-failover mutation is no
longer in flight, Bloodraven converges every other candidate, `dr-only`, and
`read-only` follower directly to the new primary. A chained or stale source is
not considered healthy merely because its replication threads are running.

Before `STOP REPLICA`, the new primary's `GTID_EXECUTED` must contain the
follower's executed set. Bloodraven repeats this check after STOP to close the
SQL-applier race, then changes the source and starts replication without
resetting replication metadata. A failure is retried boundedly on subsequent
polls. GTID non-containment is reported per site as
`sourceConvergenceState: Blocked` and
`sourceConvergenceReason: GTIDDiverged`; the operator does not discard the
follower's extra transactions or silently repoint it.

Reader client endpoints remain absent until MySQL is read-only, both threads
are healthy, direct-source convergence is `Converged`, and known lag is within
the effective reader threshold. A blocked or lagging reader does not change
the successful planned-failover result or the group's shared Ready/Degraded
conditions.

## Anti-flap cooldown

The planned path records `status.lastFailover` (the promotion's `confirmedAt`), `status.lastFailoverTarget` and `status.promotionGtidExecuted` (the fenced set) on success, exactly like the emergency path, and in the same status write as the `Succeeded` record. The record never moves to an older `lastFailover`. This means:

- A planned failover within `spec.failoverCooldown` of any prior failover is **rejected** at admission (or deferred with `onCooldown: defer`).
- An emergency failover within `spec.failoverCooldown` of a planned failover is **blocked** by the same cooldown check in the topology manager.
- A `PromotedUnconfirmed` run does not stamp `lastFailover`, so it does not start a cooldown.

The default cooldown is 5 minutes; production deployments should keep this, not lower it.

## RPO

Planned failover is the **one** Bloodraven operation with an RPO of zero by construction. The pre-write gate promotes only a target that holds exactly the fenced source's GTID set, immediately before its `super_read_only` is cleared, with the source still fenced and every other promotable site read-only. Any scenario that would produce loss (the target falls behind, the source is lost mid-run, catch-up times out, a peer cannot be read) routes to a rollback or an outcome that leaves the decision to emergency failover or a human, instead of promoting a lagging replica. See [Durability and RPO](/docs/architecture/durability-and-rpo).
