---
title: Upgrade and version-skew policy
---

What MySQL and sidecar versions Bloodraven supports, how to move
between them, and what mismatches the operator tolerates during a
rollout.

This page is deliberately narrow. It covers the MySQL image
(`spec.image`) and the sidecar image (`spec.sidecarImage`). Operator
(Helm chart) upgrades and CRD-version migrations are separate topics.

## Supported MySQL versions

Bloodraven supports a single steady-state MySQL baseline at a time,
pinned to the default `spec.image` tag:

- **Current baseline**: `mysql:9.7`. This is the default for new
  deployments and the version exercised in CI, the playground, and
  backup / restore paths.

The following are **not supported**:

- MySQL 8.0 and 8.4. If you run these today, upgrade MySQL to 9.7
  outside of Bloodraven before adopting the operator, or bootstrap a
  fresh failover group from a `mysqlsh`-produced dump using
  `initFromBackup`.
- MySQL 9.8 and later Innovation releases. Bloodraven does not track
  Innovation releases unless and until the project explicitly adopts a
  later LTS baseline.
- MySQL 5.7 and earlier (no GTID, no clone plugin).

::warning
**Pin, don't float**


Always pin `spec.image` to an immutable tag (e.g. `mysql:9.7`, not
`mysql:9`). A floating tag can drift you onto an unsupported version
between pod restarts. See the
[Production hardening checklist](/docs/configuration/production-hardening#image-supply-chain).
::
### Implementation prerequisites

These are satisfied by the supported tags and only matter if you
point Bloodraven at something else: GTID-only replication
(`SOURCE_AUTO_POSITION=1`), the MySQL clone plugin (`CLONE INSTANCE
FROM`), and the `REPLICA`/`SOURCE` SQL vocabulary. The operator does
not validate these at startup — an unsupported image surfaces as
MySQL pod failures, not an operator admission error.

## Rolling image upgrades

To roll a MySQL image change (e.g. patch-version bump):

1. Confirm `spec.updateStrategy.type: OrderedUpdate` is set (it is the
   default).
2. Bump `spec.image` to the new pinned tag.
3. `kubectl apply`.
4. Watch `status.updatePhase` and the `Updating` / `Bootstrapping`
   conditions on `status.conditions`, and confirm replication catches
   up before the second site rolls. `Updating=True` with reason
   `OrderedUpdateStalled` means a rolled pod did not become `Ready` and
   stay `Ready` for 30s (for example a new sidecar image that cannot
   start or crash-loops): the rollout stopped there, with the active site
   still serving, until that pod has been `Ready` for 30s. Each rolled
   site takes at least those 30s.
5. Take a new full backup, then run a backup-verification drill against
   it on the new version (see
   [Backup verification](/docs/backup-and-restore/backup-verification)).

With `OrderedUpdate`, Bloodraven upgrades the **standby first**, then
hands the primary role to it, then upgrades the old active. The handoff
fences the old active and promotes the standby only once it holds every
transaction the old active committed, so it loses none and pauses writes
for at most about 30s (plus the promotion itself, or up to 10s to unfence on
abort); if the standby cannot catch up, the old active is unfenced
and the rollout retries later. This is the direction
MySQL's rolling-upgrade contract requires: the replica's MySQL version
must be ≥ the primary's during the rollout. See
[Failover → Ordered updates](/docs/operations/failover#ordered-updates) for the
full sequence.

The handoff also refuses a standby that holds transactions the active site
lacks, and the operator audits every replica for such transactions (see
[Divergent replicas](/docs/operations/failover#divergent-replicas)). An
upgrade can therefore stall on purpose: if a replica already carries errant
GTIDs, `Degraded` turns `True` with reason `DivergentTransactions` on the
first polls after the new operator starts, followers are still rolled, and
the active site's update waits, unfenced and serving, until the replica is
recloned or the primary is made to contain the set. This applies to the
operator upgrade itself whenever it changes the MySQL pod template (a sidecar
image bump does). Installations that ran ordered updates on v1.5.0 or earlier
can carry such GTIDs from issue #202. The stall does not stop application deployments: the deployment API keeps granting leases for a replica's divergence report.

Apply the v1.6.0 `MysqlFailoverGroup` CRD with server-side apply before upgrading the chart (Helm does not upgrade `crds/`). It adds `status.sites[].divergenceDetectedBy` and `divergenceComparedTo` and the `mfg` short name. Without it the API server drops the two fields, and after an operator restart a replica's report reads as an old primary's: the messages say "old primary" and the deployment API treats the group as unstable until the report clears.

To find out before upgrading, audit each follower against the primary. Read
the follower first, then compute the difference on the primary:

```sql
-- On the follower:
SELECT @@GLOBAL.gtid_executed;
-- On the primary, with the follower's set from the line above:
SELECT GTID_SUBTRACT('<follower gtid_executed>', @@GLOBAL.gtid_executed) AS extra;
```

An empty `extra` means the follower holds nothing the primary lacks (it says
nothing about rows or lag). A non-empty one is the set to discard by
reclone or to make the primary contain (see [Divergent replicas](/docs/operations/failover#divergent-replicas) for what each choice does to the replica's rows). Repeat the check if the primary
changed or a server was replaced between the two reads. The
`bloodraven-doctor` skill's `gtid-audit.sh` runs the same comparison for every
follower.

::caution
**Do not use `updateStrategy.type: Recreate` for a major bump**


`Recreate` restarts both sites simultaneously. If one pod's in-place
MySQL upgrade stalls or fails, you lose write availability with no
healthy primary and no rollback path. Use `OrderedUpdate` for any
MySQL image change.
::
For MySQL-level upgrade semantics — data-dictionary migrations,
deprecated-feature removals, schema changes — defer to Oracle's own
release notes. Bloodraven drives the rollout; it does not duplicate
the MySQL upgrade matrix.

## Cross-site version skew

**Transient (during a rollout): allowed.** The `OrderedUpdate`
sequence keeps the newer MySQL on the replica side of replication
throughout the bump, which is MySQL-supported. The skew window lasts
from the moment the standby finishes upgrading until the old active
has been restarted on the new image — roughly pod-ready time plus
the failover drain. No user action is required.

**Steady-state (intentional per-site version split): not supported.**
`spec.image` is a single field per `MysqlFailoverGroup`; `SiteSpec`
has no per-site image override. The operator reconciles both site
Deployments to the same image tag. If you edit a site's Deployment
manifest out of band to pin a different tag, the next reconcile
reverts it.

## Sidecar ↔ operator skew

The sidecar binary and the operator binary are released together.
The supported configuration is matching versions:
`spec.sidecarImage` built from the same release as the running
operator Deployment.

Bloodraven tolerates a **one-minor** transient skew in either
direction during a rolling upgrade. Both sides of the HTTP surface
between the two are additive-only:

- **Operator endpoints** (polled by sidecars): `/healthz`, `/status`,
  `/active-site`, `/pitr-cutoff`.
- **Sidecar endpoints** (polled by the operator and peer sidecars):
  `/health`, `/status`, `/peer/ping`, `/peer/active-site`,
  `/archiver/status`, `/keyring/status`, `/livez`.

PITR retention uses the additive `coverage=gtid-v1` capability and backup
GTID bounds. During skew, older sidecars receive no timestamp cutoff
from the updated operator, and updated sidecars reject time-only replies
from older operators. New archive retirements pause until both sides can
prove content-bound coverage; persisted pending deletes can still finish.
Previously complete proofs without matching proof content IDs are
re-inspected in bounded batches before new retirement. Pending or Running
group backups pause new retirements across all profiles. Upgrade the
operator first to suppress unsafe time-only
retention replies from the older protocol.

An older sidecar rewriting an ID-aware PITR manifest drops IDs, coverage, purged-base bridges, quarantine/reset evidence, divergence/acknowledgement records,
and pending deletions; its pruning may drop all rows sharing one basename.
Re-upgrading recovers surviving stripped IDs only from exact confined
`remotePath` keys. It cannot recover lost rows, purged-base provenance, quarantine/reset evidence, divergence/acknowledgement records or pending deletes. Preserve a compatible recovery image for each archive generation; Use a new prefix and full backup after RESET. Obsolete upload-order guards have a verified canonical-backup acknowledgement procedure; verified namespace reuse still requires a new generation. See [PITR history repair](/docs/backup-and-restore/pitr-history-repair). Preserve
archive objects, manifests, encryption material, and compatible recovery
images before rollback. See [PITR upgrade and downgrade](/docs/backup-and-restore/backup-restore#point-in-time-recovery-pitr) for recovery steps.

`/archiver/status` gained additive `storeReady` and
`consecutiveFailedScans` fields. A sidecar
whose PITR archive store cannot be built (unreadable passphrase or
credentials file, invalid endpoint, empty PVC mount path) now keeps serving
readiness and fencing, reports `enabled:true`, `storeReady:false` and
the init error, and retries the store in the background. The fix lives
in the sidecar image, which the operator rolls through the ordered
update: until a pod runs the new image it still exits on that error,
crash-loops, and drops out of every Service. The updated operator
reports such a pod as `PITRArchiveReady=False` with reason
`SidecarUnreachable` once it has not answered for 5 minutes since the
operator started (3 failed polls over 60 s for a sidecar that answered
before), and reads a missing `storeReady` from an older sidecar as "not
reported", never as an init failure. Without `consecutiveFailedScans`
it debounces errors on the older sidecar's `lastScanAt`. An older operator ignores the field and still shows
the init error in `status.pitr.message`.

The PVC archive store now refuses to start unless its mount path is a
mount point, and writers also probe write access. A site whose
`pitr-archive` volume was missing from the pod, or not writable, used
to show `PITRArchiveReady=True` (writes landed in the container
filesystem) or a later `ArchiverError`. After the sidecar rollout it
shows `False` / `ArchiveStoreInitFailed`. `pitr-download`,
`pitr-quarantine` and the encrypted-backup `encrypt-upload` /
`decrypt-download` steps now fail at start when their PVC is not mounted
at the configured path. Writers also refuse a write prefix that leaves
the mounted volume through a symlink (for example `binlogs` linked to
another volume), which used to work: the store reports
`ArchiveStoreInitFailed` with `outside the archive volume`; replace the
symlink with a directory on the archive volume. Unencrypted PVC backups
are unchanged.

The kubelet probes the sidecar too, and the operator renders those
probes. That makes the probe paths part of the same contract, so they
only use endpoints every supported sidecar serves. Liveness probes
`/peer/ping`, which answers without touching MySQL. Readiness probes
`/health`. The newer `/livez` also detects a wedged fencing loop, but a
sidecar that predates it answers 404, and a liveness probe on it would
restart that sidecar in a loop. It becomes the liveness target once
every supported sidecar serves it.

A briefly older-or-newer sidecar stays compatible with the operator
while pods roll. Skew beyond one minor is not tested and not
guaranteed.

When a release bumps both `spec.image` and `spec.sidecarImage`
together, `OrderedUpdate` restarts the sidecar as part of the pod
restart it already performs — the replica-first ordering applies
automatically, no separate sidecar sequencing is required.

## v1.7.0: PITR archive identity

v1.7.0 supports Kubernetes 1.31 and newer (the chart's `kubeVersion` is
`>=1.31.0-0`); upgrade older clusters before the operator.

v1.7.0 changes the PITR archive format and refuses archives written before
it. Plan the upgrade as a new archive generation:

1. Let in-flight PITR restores and verifications finish.
2. Record every PITR target (`initFromBackup.pointInTime.stopDatetime`,
   verification and profile verification `pointInTime.timestamp`) before
   applying the v1.7.0 CRDs. v1.7.0 renames both to `stopTime`, which takes
   RFC 3339 with an explicit zone and whole seconds only: a
   `YYYY-MM-DD HH:MM:SS` or zone-less value (read as UTC before) needs a `Z`,
   and a fractional second is refused. The CRDs prune the old names, and a
   group whose `initFromBackup.pointInTime` has no `stopTime` fails every
   write, finalizer removal included, until step 5 sets it. List them with:

   ```bash
   kubectl get mysqlfailovergroups,mysqlbackupverifications -A -o json | jq -r '.items[] | [.kind,.metadata.namespace,.metadata.name, (.spec.initFromBackup.pointInTime.stopDatetime // .spec.pointInTime.timestamp // ""), ([.spec.backup.profiles[]?.verification.pointInTime.timestamp // empty] | join(","))] | select((.[3]+.[4]) != "") | @tsv'
   ```

   Also bring every timer inside its v1.7.0 bound (see
   [Timers](/docs/configuration/crd-reference#timers)): for example
   `pollInterval: 0s`, a `failoverCooldown` under `30s`, or a
   `plannedFailover.maxLagWait` over `1h` is refused, and so is a
   `planned-failover` annotation whose `maxLagWait=` is outside `1s` to `1h`.
   Set `dragonfly.maxMemory`, if any, to a positive quantity, and omit a
   `proactorThreads: 0`.

   Also change any S3 `prefix` (profiles, `initFromBackup`/`restoreInPlace`
   S3 sources, standby sources) longer than 512 characters or with an empty
   (`a//b`), `.` or `..` segment, any profile `name` longer than 63
   characters, and replace any `MysqlBackup` whose name ends in
   `.bloodraven-backup.json`: the v1.7.0 CRDs refuse them. The v1.7.0 CRDs
   also make `spec.backup.profiles` a list-map keyed by `name` (duplicate
   names are refused; at most 32 profiles) and bound `pitr.profileName` (a
   DNS label of at most 63 characters), `s3.bucket` (63), `s3.endpointURL`
   (512), `pvc.claimName` (253), `pvc.subPath` (512), and every passphrase
   Secret reference's `name` and `key` (253 each, also on `initFromBackup`,
   `restoreInPlace` and standby `decryption`). Every Secret name (the
   credential roles, `tls.secretName`, S3 credentials, passphrase and
   Dragonfly references, `MysqlDatabase` `owner`/`users[]` `secretName`)
   and every `failoverGroupRef.name` and `backupRef.name` must be a DNS
   subdomain (lowercase, at most 253 characters), and every Secret key at
   most 253 characters of `[-._a-zA-Z0-9]`; an optional Secret name set to
   `""` is refused (omit it instead). `MysqlBackup` and
   `MysqlBackupVerification` `profileName` and schedule `profileName` must
   be DNS labels of at most 63 characters, `MysqlBackup` `sourceSite` must
   match the site-name pattern, and `spec.sidecar.operatorEndpoint` must be
   `host:port`. The v1.7.0 CRDs also refuse
   duplicate entries in `splitBrainPolicy.sitePriorities`; more than one
   `restoreInPlace.loadOptions.includeSchemas` entry; duplicate names, or
   more than 16 entries, in `extraContainers`, `extraInitContainers` and
   `backup.imagePullSecrets`; duplicate `backup.schedules` names, more than
   32 schedules, or a schedule name longer than 63 characters; duplicate,
   more than 256, or longer than 64 character names in the `dump` and
   `loadOptions` `includeSchemas`/`excludeSchemas` lists; and more than 16
   `MysqlDatabase` `deploymentClients` (which are now keyed by the
   namespace and ServiceAccount pair, so one namespace may list several).
   Fix offending objects first.
3. Remove `pointInTime.sites` and `pointInTime.allowUnverifiedCrossSite`
   from `initFromBackup`, and `pointInTime.sites` from verifications and
   profile verification schedules. Add `pointInTime.archiveProfileName` to
   any `initFromBackup.pointInTime`. Remove any
   `replica-preserve-commit-order` override from `spec.mysqlConf`
   (it is now operator-owned and forced `ON`). v1.7.0 also removes these
   fields, which earlier releases accepted and ignored or refused:
   - `spec.secretName` (the DSN credential mode). `spec.credentials` is
     required: create an operator Secret with `username`, `password` and
     `MYSQL_ROOT_PASSWORD` (plus `MYSQL_REPLICATION_USER` and
     `MYSQL_REPLICATION_PASSWORD` if replication uses its own account) and
     set `credentials.operatorSecretName`. Express DSN `tls=` options through
     `spec.tls`.
   - `spec.tls.issuerRef`: `spec.tls` is `secretName` only.
   - `spec.restoreInPlace.pointInTime`, which the operator refused; use
     `initFromBackup.pointInTime` on a new group.
   - `loadOptions.resetProgress`, profile `storage.s3.storageClass`, profile
     `verification.storage` and `MysqlBackupVerification` `spec.storage`.
     Bound a verification's disk with `spec.resources.limits.ephemeral-storage`.
   - `spec.triggeredBy` on `MysqlBackup` and `MysqlBackupVerification`: the
     value moves to the annotation `bloodraven.shipstream.io/triggered-by`.
   - `MysqlBackupVerification` `status.podName`, `status.pvcName` and
     `status.serviceName` (never written), and the `Checking` and `Cleaning`
     phases (never entered).
4. Grant the sidecar's PITR credentials `s3:ListBucket`, `s3:GetObject`,
   `s3:PutObject` and `s3:DeleteObject` (the sidecar reads the descriptor and
   manifests back), and confirm the store enforces conditional writes
   ([PITR archive requirements](/docs/backup-and-restore/backup-s3#pitr-archive-requirements)).
   Grant every backup profile's credentials `s3:GetObject` and `s3:PutObject`
   on `<prefix>/*`: each backup Job reads its backup stamp before writing it
   and reads it back after, so a role with put and list but no get now fails
   every backup with `backup stamp: read …: AccessDenied`. Every backup Job
   also needs `s3:ListBucket`, to check that its dump location is empty
   before creating the stamp. Artifact cleanup still needs `s3:ListBucket`
   and `s3:DeleteObject`, and deleting a failed
   backup now reads its stamp too
   ([Backup credential permissions](/docs/backup-and-restore/backup-s3#backup-credential-permissions)).
5. Apply the v1.7.0 CRDs, then, before upgrading the operator, give every
   site its `serverID` (required by the v1.7.0 CRDs; the older CRDs drop
   the field, so it cannot be set in advance). Use the `server_id` the site
   runs today, 101 plus its index in `spec.sites` (`101` for the first
   site, `102` for the second, ...), so no data directory changes identity:
   ```bash
   kubectl patch mysqlfailovergroup <name> --type=json -p '[{"op":"add","path":"/spec/sites/0/serverID","value":101},{"op":"add","path":"/spec/sites/1/serverID","value":102}]'
   ```
   The id is immutable from then on and no longer follows the site's
   position. Until it is set, every write of the object that does not add
   it fails (the uniqueness rule cannot evaluate), the operator's status
   writes included, so the operator would lose its failover record.

   In the same pass, re-apply every manifest with the fields v1.7.0
   renames. The v1.7.0 CRDs drop the old names, so a stored object loses
   them; where the new field is required (`credentials.operatorSecretName`,
   `MysqlDatabase` `failoverGroupRef`) every write fails until it is set:

   | Kind | Old field | New field |
   |---|---|---|
   | `MysqlFailoverGroup` | `spec.credentials.{operator,app,readOnly,monitor,backup}Secret` | `spec.credentials.{operator,app,readOnly,monitor,backup}SecretName` |
   | `MysqlFailoverGroup` | `s3.credentialsSecret` (profiles, `initFromBackup` and `restoreInPlace` sources) | `s3.credentialsSecretName` |
   | `MysqlStandbyCluster` | `spec.source.s3.credentialsSecret` | `spec.source.s3.credentialsSecretName` |
   | `MysqlFailoverGroup`, `MysqlStandbyCluster` | `encryption.passphraseSecret`, `decryption.passphraseSecret` | `…passphraseSecretKeyRef` (same `{name, key}` body) |
   | `MysqlFailoverGroup` | `spec.dragonfly.auth.{secretName, passwordKey}` | `spec.dragonfly.auth.passwordSecretKeyRef{name, key}` |
   | `MysqlFailoverGroup` | `spec.dragonfly.snapshot.{s3Endpoint, s3UseHTTPS}` | `spec.dragonfly.snapshot.s3EndpointURL`: `s3Endpoint: rustfs:9000` with `s3UseHTTPS: false` becomes `http://rustfs:9000`; an unset `s3UseHTTPS` means `https://` |
   | `MysqlFailoverGroup` | `spec.sidecar.bloodravenAddress` | `spec.sidecar.operatorEndpoint` |
   | `MysqlFailoverGroup` | `initFromBackup.source.mysqlBackupRef`, `restoreInPlace.source.mysqlBackupRef` | `…source.backupRef` |
   | `MysqlDatabase` | `spec.groupRef` | `spec.failoverGroupRef` |
   | `MysqlBackup` | `spec.sourceSiteOverride` | `spec.sourceSite` |
   | `MysqlFailoverGroup` | `spec.cloneTimeout: 3600` (integer seconds; the old CRD stored the default in every group) | `spec.cloneTimeout: 1h` (a duration, `1m` to `24h`). The stored integer fails every write until it is rewritten or removed |
   | `MysqlFailoverGroup` | `spec.dns.ttl` | `spec.dns.ttlSeconds` |
   | `MysqlFailoverGroup` | `encryptionAtRest.keyring.escrowTimeoutSeconds: 600` | `encryptionAtRest.keyring.escrowTimeout: 10m` |
   | `MysqlFailoverGroup` | `backup.retry.{initialBackoffSeconds: 60, maxBackoffSeconds: 1800}` | `backup.retry.{initialBackoff: 1m, maxBackoff: 30m}` |
   | `MysqlFailoverGroup` | `spec.dragonfly.maxMemoryMb: 512` | `spec.dragonfly.maxMemory: 512Mi` |
   | `MysqlFailoverGroup` | `initFromBackup.pointInTime.stopDatetime` | `initFromBackup.pointInTime.stopTime` (step 2) |
   | `MysqlBackupVerification`, profile `verification` | `pointInTime.timestamp` | `pointInTime.stopTime`, required for `Timestamp` and forbidden for `Latest` |
   | `MysqlBackupVerification`, profile `verification` | `sanityCheck.expect.{minRows, maxDurationSeconds: 60}` | `sanityCheck.{minResult, timeout: 60s}` |

   Two defaults change meaning. `ttlSecondsAfterFinished` on a
   `MysqlBackupVerification` and on a profile's `verification` no longer
   defaults to `0`: an omitted value now keeps a successful verification's
   Pod (and its restored datadir) until retention deletes the verification,
   so set `ttlSecondsAfterFinished: 0` to keep the immediate cleanup. And an
   explicit `0` is now kept as `0` instead of being replaced by the default:
   `replication.maxLagSeconds: 0` requires a caught-up replica (it meant
   `300`), and `backup.backoffLimit: 0` and `backup.maxLagSecondsForSource: 0`
   are honored. `status.sanityCheck` is now `{outcome, result,
   durationMilliseconds, error}` (it was `{ran, resultRow, durationMs,
   error}`).

   A `MysqlBackupVerification` `backupRef: {}` (which meant "latest") is
   refused: omit `backupRef` instead. The chart's operator environment
   variable `BLOODRAVEN_DEFAULT_AUXILIARY_ADDRESS` is now
   `BLOODRAVEN_DEFAULT_OPERATOR_ENDPOINT`; an `extraEnv` entry that
   overrides it by name must be renamed. Then upgrade the operator. Every MySQL pod of a
   group without PITR rolls once through the ordered update (new sidecar
   identity env, PITR render v6). A group **with** PITR enabled is
   different: its site Deployments carry no `bloodraven.shipstream.io/pitr-render`
   annotation yet, so the operator does not update them at all (nor their
   ConfigMaps) until a `pitr-archive-check` Job authenticates the archive key
   (log `pitr render deferred`). The deferral holds while **any** site
   Deployment lacks a decodable annotation, so deleting and re-creating one
   site Deployment does not lift it; a site created meanwhile renders the held
   render, and a pre-v1.7.0 writer next to an annotated site counts as a
   running writer, so the write target is authenticated by a check Job. On a pre-v1.7.0 prefix the check refuses
   `ArchiveLegacy` (`PITRArchiveBindingReady=False`, Warning
   `PITRArchiveBindingRefused` naming the Deployments), and the Deployments
   stay as they are, still archiving to the old prefix, until step 6.
   Backups do not wait for it (`PITRArchiveRolloutPending` is not used while
   deferred): until the roll, every backup proceeds with no archive stamp (Normal Event `PITRArchiveNotStamped`), so none is a
   point-in-time baseline. While deferred, the pods keep their pre-v1.7.0
   sidecars, which report no archive identity, so `PITRArchiveReady` is
   `False` / `SidecarOutdated` even when `spec.sidecarImage` is not set:
   that is expected, clearing or changing `spec.sidecarImage` does not
   help, and it ends with step 6, when the Deployments roll. Separately, if
   `spec.sidecarImage` pins a sidecar older than v1.7.0, set it to the
   v1.7.0 release or clear it first, or the pods stay `SidecarOutdated`
   after step 6 too; their manifests are unusable for restores.
6. Point `spec.backup.pitr` at a new prefix (a profile with a new prefix,
   or a new prefix on the active profile), because the old one is refused as
   `ArchiveLegacy`. Leading `/` in S3 prefixes are now ignored, so `/prod`
   and `prod` are the same prefix. A check Job finds the new prefix empty, the
   deferred Deployments roll once onto it, and the new archive's binding
   becomes `Bound` when a sidecar creates and verifies its descriptor. Binlogs
   sealed between the operator upgrade and this roll are archived only if
   MySQL still has them once the new prefix is in place; keep the window
   short. (Disabling PITR on the profile also ends the deferral.)
7. Once the new binding is `Bound` (`PITRArchiveBindingReady=True`), take
   and verify a full backup. It carries a backup stamp and
   `status.pitrArchiveID` tying it to the new archive.

During the roll, sidecars still on the old render query retention with
`profile=` and get HTTP 400 from `/pitr-cutoff`, which now takes `archive=`;
retention defers (nothing is deleted) until they roll.

From v1.7.0 on, the archive key is pinned by the group's archive encryption
binding: pods mount an operator-made key snapshot, and in-place passphrase or
encryption changes on an archive in use are refused. Key snapshot Secrets
(`mysql-pitr-key`, and one `mysql-dump-key` per encrypted backup) have no
owner reference and survive group deletion. See
[Archive encryption bindings](/docs/backup-and-restore/backup-encryption#archive-encryption-bindings).

Keep the old prefix, its backups, its passphrase and a pre-v1.7.0 operator
image if you may need a target from before the upgrade: v1.7.0 cannot read
the old archive. Do not run a pre-v1.7.0 sidecar against the new archive; it
rewrites its manifest as version 1 and the archive is then refused as
`PITRArchiveLegacy`. Backups taken before the upgrade have no backup stamp,
so PITR from them refuses `PITRBackupIdentityUnknown`; dump-only restores from
them still work. An **encrypted** backup taken before the upgrade also
recorded no dump key (`status.artifactStorage.passphraseSecretKeyRef`), and the
operator never decrypts a dump with the profile's live Secret, so:

- a `MysqlBackupVerification` of it, including a scheduled profile
  verification that picks it, fails `PITRBackupDumpKeyMissing`. Verification
  has no `decryption` override, so this is permanent. Verify the full backup
  taken in step 7 instead;
- a restore of it (`initFromBackup` or `restoreInPlace`) needs an explicit
  `decryption` naming a Secret that holds the passphrase the backup was
  written with. To check such a backup, restore it into a scratch group with
  `decryption` set.

Keep the passphrase of every pre-upgrade encrypted backup you may restore,
even after you rotate the profile's Secret. Restore and verification status moves from the flat
`status.restore.pitr*` fields to `status.restore.pointInTime` (now
`status.restore.provenance.pointInTime`); update any
tooling that reads them. Stop targets are whole seconds; a fractional second
is rejected. See
[Upgrading to archive identity](/docs/backup-and-restore/backup-restore#upgrading-to-archive-identity).

v1.7.0 also changes condition reasons, polarity and printer columns. Update
alert rules, scripts and deployment tooling that match on them, and re-apply
the chart's Argo CD health script (`charts/bloodraven/argocd/`) if you copied
it into `argocd-cm`: the old script reads `Ready.observedGeneration` and the
old `Bootstrapping` and `Updating` polarity.

| Kind | Before v1.7.0 | From v1.7.0 |
|---|---|---|
| `MysqlFailoverGroup` `Ready` | reason `TopologyPolled`, `True` or `False` | `True/Healthy`; `False/NoWritablePrimary` (no site writable) or `False/ReplicationUnhealthy` |
| `MysqlFailoverGroup` `Degraded` | `True/Degraded`, `True/Alert` | `True/SiteUnhealthy`, `True/CrossSiteAlert`; new `True/BootstrapFailed` while a failed clone's target does not replicate |
| `MysqlFailoverGroup` `Bootstrapping` | `False/Done` after a clone; `True/Failed` after a failed one | `True` only while a clone runs. `False/NotBootstrapping` after a clone (also before any clone); `False/BootstrapFailed` after a failed one, together with `Degraded=True/BootstrapFailed` |
| `MysqlFailoverGroup` `Updating` | `False/OrderedUpdateStalled` | `True/OrderedUpdateStalled` (the update is still in progress) |
| `MysqlFailoverGroup` status | condition `observedGeneration` was the generation of the object written | new `status.observedGeneration`, the generation the topology manager applied, carried by the topology conditions; the Argo CD health script reads it |
| `MysqlBackup` `Ready` | `False/NoHealthySource` while waiting for a source; a wait past 30 minutes failed with its pending reason | `False` from creation (`Pending`, the pending reason, `Running`); `False/WaitingForHealthySource` while waiting for a source; past 30 minutes `NoHealthySource` (a source wait) or `PendingTimedOut` (any other wait). `NoHealthySource` is terminal only |
| `MysqlBackupVerification` `Ready` | absent | mirrors `Verified`; `False/InProgress` before |
| `MysqlStandbyCluster` `Ready` | absent | `True/SourceDiscovered` when `BucketReadable` and `SourceConfigKnown` are both `True`, otherwise the first one's `False` reason |
| `MysqlDatabase` `Ready` | `False/GroupNotFound` while the group does not exist | `False/GroupNotYetCreated` (`GroupNotFound` stays a terminal reason on backups and verifications) |
| Printer columns | `kubectl get msc` showed `BucketReadable` and `SourceKnown` | `kubectl get msc` shows `Ready` instead; `kubectl get mysqlbackup` and `kubectl get mbv` gain `Ready` |

## Operator upgrade across the planned-failover claim release

The release that introduced the durable planned-failover claim (issue
#235) replaced the shape of `status.plannedFailover` (see the
[CRD reference](/docs/configuration/crd-reference#plannedfailoverstatus)
for the removed fields). It is not resumable across the upgrade:

1. **Do not upgrade with a planned failover in flight.** Wait for
   `status.plannedFailover.phase` to be `Succeeded` or `Failed` (or
   remove the annotation of a `Deferred` request) before you roll the
   operator. A non-terminal block written by the older operator is
   refused, not resumed: `Pending`, `Validating` and `Deferred` end
   `NotStarted` with reason `LegacyRunRefused`; `Draining` and
   `WaitingForLag` end `SourceLeftFenced` with `LegacyRunRefused`; and
   `Promoting` and `Resuming` end `PromotedUnconfirmed` with
   `LegacyRunRefused`, because the older operator may already have made the
   target writable. In both of those cases follow the run's message:
   check which site is writable; if none is, unfence the site with the most
   complete GTID set by hand (confirm no other site is writable first);
   re-annotate only once a site is writable (a planned failover is not
   admitted while no site is writable; see [Planned failover](/docs/operations/planned-failover#upgrading-across-this-release)).
2. **A block the older operator wrote stays valid.** After the CRD
   upgrade, such a block is read back with its removed fields pruned, so
   it has no `runID`, `targetSite`, `settings` and so on. The CRD does not
   mark `runID`, `revision`, `phase`, `targetSite`, `settings` or
   `startTime` `required`: the operator always sets them on a block it
   writes, and enforces their presence itself (a non-terminal block
   without a `runID` is refused as a legacy run). A terminal legacy block
   (`Succeeded` or `Failed`) therefore validates, and status writes beside
   it keep working. A non-terminal legacy block in a removed phase
   (`Pending`, `Validating`, `Resuming`) is outside the new phase enum:
   CRD validation ratcheting of status writes (Kubernetes 1.33 and newer)
   accepts it unchanged, and the operator replaces it when it refuses the
   run. Kubernetes 1.31 and 1.32 validate status writes without
   ratcheting, so there status writes that keep such a block fail until
   the operator's refusal replaces it on its next pass, which item 1
   avoids.
3. **Rewrite lower-case policy values as part of the upgrade, not later.**
   `spec.plannedFailover.onCooldown` now accepts `Reject` or `Defer` and
   `spec.dragonfly.plannedFailover.onSyncTimeout` accepts `Proceed` or
   `Fail`; the released lower-case `reject`, `defer`, `proceed` and `fail`
   fail validation. The older CRD accepts only the lower-case spellings,
   so the values cannot be rewritten in advance. Do it in this order:
   1. Find every stored lower-case value, in failover groups and in the
      group templates of standby clusters
      (`spec.template.spec.plannedFailover.onCooldown` and
      `spec.template.spec.dragonfly.plannedFailover.onSyncTimeout`):
      ```bash
      kubectl get mysqlfailovergroups,mysqlstandbyclusters -A -o json | jq -r '.items[] |
        [.kind, .metadata.namespace, .metadata.name,
         ((.spec.template.spec // .spec).plannedFailover.onCooldown // "-"),
         ((.spec.template.spec // .spec).dragonfly.plannedFailover.onSyncTimeout // "-")] | @tsv'
      ```
   2. Apply the new CRDs.
   3. Immediately rewrite each lower-case value in CamelCase (`reject` →
      `Reject`, `defer` → `Defer`, `proceed` → `Proceed`, `fail` → `Fail`),
      or remove the field where it holds the default (`Reject`, `Proceed`).
      Update the manifests in Git too, or the next sync writes the
      lower-case value back and is refused.
   4. Roll the operator.

   This is mandatory, not cosmetic. On a cluster without CRD validation
   ratcheting, every write to the object's main resource validates the
   whole spec, so a stored lower-case value makes all of them fail: the
   operator's failover-record annotation after an emergency or planned
   failover, the planned-failover terminal marker and stall annotations,
   removing a consumed request annotation, deleting a hold
   acknowledgement, and your own `kubectl annotate` of a planned-failover
   request or an acknowledgement. Ratcheting accepts an unchanged
   lower-case value, but the first edit that touches the field must
   rewrite it anyway, so migrate there too. The new operator reads only
   the CamelCase values: a stored lower-case `fail` or `defer` is read as
   the default (`Proceed`, `Reject`), so a group that still holds one does
   not roll back on a sync timeout or defer. Between steps 3 and 4 the
   older operator compares the values literally and treats `Defer` and
   `Fail` as the defaults (`reject`, `proceed`): do not request a planned
   failover in that window.
4. **Dashboards, alerts and Event consumers.**
   `bloodraven_planned_failovers_total{result}` is now the kebab-case of
   the run's outcome (`succeeded`, `not-started`, `rolled-back`,
   `source-left-fenced`, `promoted-unconfirmed`,
   `manual-recovery-required`) instead of `success`, `rejected`,
   `failed_timeout` and `failed_other`. `failed_timeout` has no single
   successor: a lag timeout ends `rolled-back`, an admission timeout
   `not-started`; select on `status.plannedFailover.result.reason` for the
   cause. Queries on the removed status fields (for example `transactionsLost` or
   `durationSeconds`) must move to `result` and the duration histogram.
   Three planned-failover Event reasons were renamed, with the same type
   (`Normal`) and meaning:

   | Released reason | Reason now |
   | --- | --- |
   | `PlannedFailoverDraining` | `PlannedFailoverDrainStarted` |
   | `PlannedFailoverLagOK` | `PlannedFailoverTargetCaughtUp` |
   | `PlannedFailoverCompleted` | `PlannedFailoverSucceeded` |

   `PlannedFailoverStarted`, `PlannedFailoverSkipped`,
   `PlannedFailoverRejected`, `PlannedFailoverDeferred` and
   `PlannedFailoverFailed` keep their names. The new reasons are listed in
   [Planned failover](/docs/operations/planned-failover).
5. **Deployment API companions.** `operations.plannedFailover` in
   `/deploy/v1` carries the new vocabulary
   ([Deployment API](/docs/configuration/deployment-api)). `phase` is
   `status.plannedFailover.phase`: `Pending` and `Validating` became
   `Admitting`, `Resuming` became `Publishing`, and `Fencing` and
   `RollingBack` are new; the empty phase is reported only when there is no
   block. A `planned-failover-terminal` marker that names the run wins over
   a stale live phase: `phase` is then `Succeeded` or `Failed` with the
   marker's outcome and reason. `reason` is no longer a free-form string,
   and it belongs to the current phase only: `admission.waitReason` while
   `Admitting`, `admission.deferReason` while `Deferred`, `result.reason`
   (empty when the result has none) for `Succeeded` and `Failed`, and
   empty in any other phase; all are enums. The new key `outcome` carries
   `result.outcome` (empty until the run ends). A companion that switches on phase
   or reason strings must be updated before the upgrade. Coordination
   decisions should use `stable` and `unstableReason`, which kept their
   meaning.
6. **Do not roll the operator or the CRDs back across this release while a
   run or a hold stands.** The older operator does not know the claim, the
   terminal marker or the hold: it ignores `status.plannedFailoverHold`
   and a `ManualRecoveryRequired` terminal marker, and resumes emergency
   failover, split-brain resolution, the re-assert and DNS reconcile on a
   group a human was meant to resolve first. It also cannot resume or
   refuse a new-format run. Before rolling back, wait for
   `status.plannedFailover.phase` to be `Succeeded` or `Failed`, and resolve
   and acknowledge any hold (`AutomaticFailoverHeld=True`,
   `status.plannedFailoverHold`, or a
   `bloodraven.shipstream.io/planned-failover-terminal` annotation with
   outcome `ManualRecoveryRequired`): see the
   [hold runbook](/docs/operations/runbooks#planned-failover-automation-hold).
   Rolling the CRDs back as well prunes `status.plannedFailoverHold` and
   the new `status.plannedFailover` fields but keeps the generic
   `AutomaticFailoverHeld` condition. When you upgrade again, that `True`
   condition names no run, so no acknowledgement can clear it: resolve the
   sites, then remove the condition by hand as the hold runbook describes.

### Rolling back across this release

A Helm rollback of the operator image leaves the new CRDs in place. The
CRD does not require the fields the older operator drops, so its status
writes keep working beside a new-format block. Still:

1. **Acknowledge any standing hold first**
   (`kubectl bloodraven ack-planned-failover-hold <group>`). The older
   operator drops `status.plannedFailoverHold` on its first status write.
2. **Do not request a planned failover while the older operator runs on the
   new CRD.** Its first phase (`Pending`) is outside the new phase enum, so
   its run cannot start. If you need planned failovers during the
   rollback, re-apply the previous CRDs as well (see item 6 above for what
   that prunes).
3. **Expect the last planned-failover block to lose fields.** The older
   operator rewrites it without `runID`, `targetSite`, `settings` or
   `result`. Rolling forward again treats such a terminal block as history
   and a non-terminal one as a legacy run (`LegacyRunRefused`, item 1).

## Restoring across versions

`MysqlBackup.status.mysqlImage` records the image tag that produced
each dump. The safe path is to restore onto the same major version
that produced the backup. **Do not** restore a dump onto an older
MySQL version — MySQL does not support version downgrade of data.

Backup-restore throughput and sizing guidance live under a separate
performance guide (WISHLIST #27).

## What Bloodraven does not do

- **No version admission check.** Setting `spec.image` to an
  unsupported tag will not produce a CRD validation error. MySQL
  itself rejects unsupported upgrades at pod start.
- **No skip-a-major guardrail.** There is no enforcement that blocks
  an `8.0 → 9.7` jump or a `9.7 → 9.8+` jump at the operator layer.
- **No downgrade path.** MySQL does not support version downgrade,
  and Bloodraven inherits that limitation.
- **No per-site MySQL version.** The CRD does not expose a per-site
  image, so mixed-version steady state is not expressible.
