---
title: Upgrade and version-skew policy
---

What MySQL and sidecar versions Bloodraven supports, how to move
between them, and what mismatches the operator tolerates during a
rollout.

This page is deliberately narrow. It covers the MySQL image
(`spec.image`) and the sidecar image (`spec.sidecar.image`, or the
operator's default when it is unset). Operator
(Helm chart) upgrades and CRD-version migrations are separate topics.

## Supported MySQL versions

Bloodraven supports a single steady-state MySQL baseline at a time,
pinned to the default `spec.image` tag:

- **Current baseline**: `mysql:9.7`. This is the default for new
  deployments and the version exercised in CI, the playground, and
  backup / restore paths.

The following are **not supported**:

- MySQL 8.0 and 8.4. If you run these today, upgrade MySQL to 9.7
  outside of Bloodraven before adopting the operator, or bootstrap a
  fresh failover group from a `mysqlsh`-produced dump using
  `initFromBackup`.
- MySQL 9.8 and later Innovation releases. Bloodraven does not track
  Innovation releases unless and until the project explicitly adopts a
  later LTS baseline.
- MySQL 5.7 and earlier (no GTID, no clone plugin).

::warning
**Pin, don't float**


Always pin `spec.image` to an immutable tag (e.g. `mysql:9.7`, not
`mysql:9`). A floating tag can drift you onto an unsupported version
between pod restarts. See the
[Production hardening checklist](/docs/configuration/production-hardening#image-supply-chain).
::
### Implementation prerequisites

These are satisfied by the supported tags and only matter if you
point Bloodraven at something else: GTID-only replication
(`SOURCE_AUTO_POSITION=1`), the MySQL clone plugin (`CLONE INSTANCE
FROM`), and the `REPLICA`/`SOURCE` SQL vocabulary. The operator does
not validate these at startup — an unsupported image surfaces as
MySQL pod failures, not an operator admission error.

The image must also ship `/bin/bash` and its entrypoint at
`/usr/local/bin/docker-entrypoint.sh` (the Docker Official Image),
`/entrypoint.sh` (Oracle's `community-server` image), or as
`docker-entrypoint.sh` on `PATH`. The operator sets the mysql
container's `command` to its launcher, which replaces the image's
`ENTRYPOINT` and ends by running that entrypoint with `mysqld` and the
operator's flags (see
[Server identity after a clone](/docs/operations/operations#server-identity-after-a-clone)).
An image with its entrypoint elsewhere does not start: the mysql
container exits with code 127 and the line `bloodraven-launcher: no
MySQL image entrypoint found (…); spec.image must provide one. …`,
which goes on to name the remedy. An image without `/bin/bash` cannot
start the container at all (`StartError`). Before the launcher, a group
without encryption at rest ran the image's `ENTRYPOINT` whatever its
path. Bash itself is not a new requirement: the operator's first-boot
script in `/docker-entrypoint-initdb.d` has always been a bash script
that the image's entrypoint runs.

Check a custom image before you point a group at it, and before an
operator upgrade that introduces the launcher (see the warning under
"Sidecar ↔ operator skew" below). This prints `ok` for an image the
launcher can start:

```bash
docker run --rm --entrypoint /bin/bash <image> -c 'test -x /usr/local/bin/docker-entrypoint.sh || test -x /entrypoint.sh || command -v docker-entrypoint.sh >/dev/null' && echo ok
```

Anything else (no output, or `exec: "/bin/bash": … no such file or
directory`) means the mysql container will not start with that image.
The supported tags pass.

## Rolling image upgrades

To roll a MySQL image change (e.g. patch-version bump):

1. Confirm `spec.updateStrategy.type: OrderedUpdate` is set (it is the
   default).
2. Bump `spec.image` to the new pinned tag.
3. `kubectl apply`.
4. Watch `status.updatePhase` and the `Updating` / `Bootstrapping`
   conditions on `status.conditions`, and confirm replication catches
   up before the second site rolls. `Updating=True` with reason
   `OrderedUpdateStalled` means a rolled pod did not become `Ready` and
   stay `Ready` for 30s (for example a new sidecar image that cannot
   start or crash-loops): the rollout stopped there, with the active site
   still serving, until that pod has been `Ready` for 30s. Each rolled
   site takes at least those 30s.
5. Take a new full backup, then run a backup-verification drill against
   it on the new version (see
   [Backup verification](/docs/backup-and-restore/backup-verification)).

With `OrderedUpdate`, Bloodraven upgrades the **standby first**, then
hands the primary role to it, then upgrades the old active. The handoff
fences the old active and promotes the standby only once it holds every
transaction the old active committed, so it loses none and pauses writes
for at most about 30s (plus the promotion itself, or up to 10s to unfence on
abort); if the standby cannot catch up, the old active is unfenced
and the rollout retries later. This is the direction
MySQL's rolling-upgrade contract requires: the replica's MySQL version
must be ≥ the primary's during the rollout. See
[Failover → Ordered updates](/docs/operations/failover#ordered-updates) for the
full sequence.

The handoff also refuses a standby that holds transactions the active site
lacks, and the operator audits every replica for such transactions (see
[Divergent replicas](/docs/operations/failover#divergent-replicas)). An
upgrade can therefore stall on purpose: if a replica already carries errant
GTIDs, `Degraded` turns `True` with reason `DivergentTransactions` on the
first polls after the new operator starts, followers are still rolled, and
the active site's update waits, unfenced and serving, until the replica is
recloned or the primary is made to contain the set. This applies to the
operator upgrade itself whenever it changes the MySQL pod template (a sidecar
image bump does). Installations that ran ordered updates on v1.5.0 or earlier
can carry such GTIDs from issue #202. The stall does not stop application deployments: the deployment API keeps granting leases for a replica's divergence report.

When upgrading to v1.6.0, apply the v1.6.0 `MysqlFailoverGroup` CRD with server-side apply before upgrading the chart (Helm does not upgrade `crds/`); this routine is not for v1.6.0 → v1.7.0 (see [Upgrading from v1.6.0 to v1.7.0](#upgrading-from-v160-to-v170)). It adds `status.sites[].divergenceDetectedBy` and `divergenceComparedTo` and the `mfg` short name. Without it the API server drops the two fields, and after an operator restart a replica's report reads as an old primary's: the messages say "old primary" and the deployment API treats the group as unstable until the report clears.

To find out before upgrading, audit each follower against the primary. Read
the follower first, then compute the difference on the primary:

```sql
-- On the follower:
SELECT @@GLOBAL.gtid_executed;
-- On the primary, with the follower's set from the line above:
SELECT GTID_SUBTRACT('<follower gtid_executed>', @@GLOBAL.gtid_executed) AS extra;
```

An empty `extra` means the follower holds nothing the primary lacks (it says
nothing about rows or lag). A non-empty one is the set to discard by
reclone or to make the primary contain (see [Divergent replicas](/docs/operations/failover#divergent-replicas) for what each choice does to the replica's rows). Repeat the check if the primary
changed or a server was replaced between the two reads. The
`bloodraven-doctor` skill's `gtid-audit.sh` runs the same comparison for every
follower.

::caution
**Do not use `updateStrategy.type: Recreate` for a major bump**


`Recreate` restarts both sites simultaneously. If one pod's in-place
MySQL upgrade stalls or fails, you lose write availability with no
healthy primary and no rollback path. Use `OrderedUpdate` for any
MySQL image change.
::
For MySQL-level upgrade semantics — data-dictionary migrations,
deprecated-feature removals, schema changes — defer to Oracle's own
release notes. Bloodraven drives the rollout; it does not duplicate
the MySQL upgrade matrix.

## Cross-site version skew

**Transient (during a rollout): allowed.** The `OrderedUpdate`
sequence keeps the newer MySQL on the replica side of replication
throughout the bump, which is MySQL-supported. The skew window lasts
from the moment the standby finishes upgrading until the old active
has been restarted on the new image — roughly pod-ready time plus
the failover drain. No user action is required.

**Steady-state (intentional per-site version split): not supported.**
`spec.image` is a single field per `MysqlFailoverGroup`; `SiteSpec`
has no per-site image override. The operator reconciles both site
Deployments to the same image tag. If you edit a site's Deployment
manifest out of band to pin a different tag, the next reconcile
reverts it.

## Sidecar ↔ operator skew

The sidecar binary and the operator binary are released together.
The supported configuration is matching versions. A group that leaves
`spec.sidecar.image` unset gets that by construction: it runs the
sidecar image the operator release ships with (the chart's
`sidecar.image.repository` and `sidecar.image.tag`, passed to the
operator as `BLOODRAVEN_SIDECAR_IMAGE`; the tag defaults to the chart's
`appVersion`). A group that pins `spec.sidecar.image` should pin the
release of the running operator Deployment; a pin with another release
tag gets a `SidecarVersionSkew` Warning.

Because an unpinned group follows the operator, an operator upgrade
that ships a new sidecar image changes that group's pod spec, and the
group rolls: an ordered update (followers first, a handoff of the
primary role, then the old primary; see
[Ordered updates](/docs/operations/failover#ordered-updates)) under
`OrderedUpdate`, both sites at once under `Recreate`. Each such group starts its roll on its own after the
upgrade. A pinned group does not move its sidecar until the pin
changes, though a release that changes the rendered pod spec in other
ways rolls it too.

Bloodraven tolerates a **one-minor** transient skew in either
direction during a rolling upgrade. Both sides of the HTTP surface
between the two are additive-only:

- **Operator endpoints** (polled by sidecars): `/healthz`, `/status`,
  `/active-site`, `/pitr-cutoff`.
- **Sidecar endpoints** (polled by the operator and peer sidecars):
  `/health`, `/status`, `/peer/ping`, `/peer/active-site`,
  `/archiver/status`, `/keyring/status`, `/livez`.

PITR retention uses the additive `coverage=gtid-v1` capability and backup
GTID bounds. During skew, older sidecars receive no timestamp cutoff
from the updated operator, and updated sidecars reject time-only replies
from older operators. New archive retirements pause until both sides can
prove content-bound coverage; persisted pending deletes can still finish.
Previously complete proofs without matching proof content IDs are
re-inspected in bounded batches before new retirement. Pending or Running
group backups pause new retirements across all profiles. Upgrade the
operator first to suppress unsafe time-only
retention replies from the older protocol.

An older sidecar rewriting an ID-aware PITR manifest drops IDs, coverage, purged-base bridges, quarantine/reset evidence, divergence/acknowledgement records,
and pending deletions; its pruning may drop all rows sharing one basename.
Re-upgrading recovers none of it: a manifest an older sidecar rewrote is
refused (`PITRArchiveLegacy`, or `PITRArchiveObjectInvalid` for a row left
without an `id`). It cannot recover lost rows, purged-base provenance, quarantine/reset evidence, divergence/acknowledgement records or pending deletes. Preserve a compatible recovery image for each archive generation; Use a new prefix and full backup after RESET. Obsolete upload-order guards have a verified canonical-backup acknowledgement procedure; verified namespace reuse still requires a new generation. See [PITR history repair](/docs/backup-and-restore/pitr-history-repair). Preserve
archive objects, manifests, encryption material, and compatible recovery
images before rollback. See [PITR upgrade and downgrade](/docs/backup-and-restore/backup-restore#point-in-time-recovery-pitr) for recovery steps.

`/archiver/status` gained additive `storeReady` and
`consecutiveFailedScans` fields. A sidecar
whose PITR archive store cannot be built (unreadable passphrase or
credentials file, invalid endpoint, empty PVC mount path) now keeps serving
readiness and fencing, reports `enabled:true`, `storeReady:false` and
the init error, and retries the store in the background. The fix lives
in the sidecar image, which the operator rolls through the ordered
update: until a pod runs the new image it still exits on that error,
crash-loops, and drops out of every Service. The updated operator
reports such a pod as `PITRArchiveReady=False` with reason
`SidecarUnreachable` once it has not answered for 5 minutes since the
operator started (3 failed polls over 60 s for a sidecar that answered
before), and reads a missing `storeReady` from an older sidecar as "not
reported", never as an init failure. Without `consecutiveFailedScans`
it debounces errors on the older sidecar's `lastScanAt`. An older operator ignores the field and still shows
the init error in `status.pitr.message`.

`/archiver/status` also gained an additive `tail` block (`state`,
`activeFile`, `newestSealedFile`, `pendingFiles`, `reason`), and a sidecar
that reports it archives the
[tail of its last writable era](/docs/backup-and-restore/backup-restore#archiving-the-tail-of-an-outgoing-primary)
while its server is read-only. An older sidecar reports no `tail` and
uploads nothing while read-only. Before a reclone the updated operator
waits for that block, so a reclone of a site whose pod still runs an older
sidecar starts after the full 2 minutes, with a Warning
`PITRArchiveTailNotArchived` that says the sidecar reports no archive tail.
An older operator ignores the block and neither rotates binary logs nor
waits.

The PVC archive store now refuses to start unless its mount path is a
mount point, and writers also probe write access. A site whose
`pitr-archive` volume was missing from the pod, or not writable, used
to show `PITRArchiveReady=True` (writes landed in the container
filesystem) or a later `ArchiverError`. After the sidecar rollout it
shows `False` / `ArchiveStoreInitFailed`. `pitr-download`,
`pitr-quarantine` and the encrypted-backup `encrypt-upload` /
`decrypt-download` steps now fail at start when their PVC is not mounted
at the configured path. Writers also refuse a write prefix that leaves
the mounted volume through a symlink (for example `binlogs` linked to
another volume), which used to work: the store reports
`ArchiveStoreInitFailed` with `outside the archive volume`; replace the
symlink with a directory on the archive volume. Unencrypted PVC backups
are unchanged.

The mysql container starts through the operator's launcher, which
gives every `CLONE INSTANCE` recipient a new `server_uuid`
([Server identity after a clone](/docs/operations/operations#server-identity-after-a-clone)).
The release that introduces it changes the mysql container's `command`
in every group's pod template, so every group rolls once after the
operator upgrade, including a group that pins `spec.sidecar.image`: an
ordered update under `OrderedUpdate` (followers first, a handoff of the
primary role, then the old primary), both sites at once under
`Recreate`. A group that follows the operator's sidecar image rolls
once for both changes. There is nothing to configure for the supported
images.

::warning
**Custom `spec.image`: check it before this upgrade**


The roll starts the mysql container through the launcher, so a custom
image must meet the
[implementation prerequisites](#implementation-prerequisites): run the
one-line check there against every custom image before you upgrade the
operator. An image that fails it crash-loops as soon as its pod rolls.

- With `updateStrategy.type: OrderedUpdate` (the default) the damage
  stops at one site. The first follower that is rolled never becomes
  `Ready`, the update stalls there (`Updating=True` /
  `OrderedUpdateStalled`, naming `mysql not ready: crash looping, last
  exit code 127`), no other site is rolled and the primary is neither
  handed off nor restarted. Fix `spec.image`; the stalled site rolls
  again and the update continues.
- With `updateStrategy.type: Recreate` every site's Deployment is
  patched at once, so every site crash-loops together: a full outage of
  the group, caused by the operator upgrade. Do not upgrade the operator
  over a `Recreate` group with a custom image until the check passes;
  if in doubt, switch the group to `OrderedUpdate` first.
::

Apply this release's CRDs before the operator, as for every upgrade (Helm
does not upgrade `crds/`). They add `status.restore.backupRef` and
`status.restoreInPlace.backupRef`, where a restore records the
`MysqlBackup` it holds
([A backup is held while a restore reads it](/docs/backup-and-restore/backup-restore#a-backup-is-held-while-a-restore-reads-it)).
With an older `MysqlFailoverGroup` CRD the API server drops those fields
without an error, and the hold is weaker than documented until the CRD is
applied: an in-place restore waiting in `Preflight` stamps a new hold on
its backup on every pass and each one is removed again within a minute,
a backup is then protected by its name only between the hold and the
restore Job, and a backup deleted by hand in that window ends the restore
instead of waiting for it. A restore whose Job runs is protected either
way.

What to expect around that roll:

- A pod that has not rolled yet has no launcher. A clone into it keeps
  the recipient's `server_uuid`, and the updated operator says so with
  a Warning Event `CloneServerUUIDNotRotated`. Reclone the site after
  its pod has rolled if it matters (next item).
- Rolling a pod does not change its server's `server_uuid`; only a
  clone does. A server cloned by an earlier release keeps the identity
  it has until its next clone. That matters for one kind of site: a
  former primary that lost transactions at a failover and was recloned
  before the upgrade. Its sidecar lists the GTIDs it could reissue in
  `reissuableGtids` and reports an archiver error until the site is
  recloned
  ([Reissue risk](/docs/backup-and-restore/pitr-history-repair#reissue-risk)).
- The operator now reclones a site that lacks transactions it issued
  itself
  ([A returning site that lost its own transactions](/docs/operations/failover#a-returning-site-that-lost-its-own-transactions)).
  A group that already has such a site, replicating and looking healthy,
  gets it reported (`recoveryState: RecloneRequired`, Warning
  `OwnTransactionsLost`) and recloned within the first minute after the
  upgrade: expect one clone of that site from the primary. Apply the
  CRDs before the operator: `recoveryState: RecloneRequired`,
  `sourceConvergenceReason: OwnTransactionsLost` and
  `status.sites[].lostGtid` are new. An older CRD rejects the first two
  for the whole status update. The operator then writes the status with
  the nearest values that CRD knows, `RecoveryBlocked` and
  `GTIDDiverged`, and logs `status written with the values an older CRD
  accepts; the installed CRD is older than the operator` once; the older
  CRD also drops `lostGtid` and `lostTransactionCount` without an error.
  The `RecoveryPending` and `Degraded` conditions and the Events still say
  `OwnTransactionsLost`, and the operator keeps the site out of
  replication and promotion and reclones it as with the current CRD.
  What is lost until the CRD is applied: the lost set in status (it is in
  the Event and the log line), and after an operator restart the report
  is announced once more, because it cannot be read back. The current
  values are tried again every 10 minutes, so the status corrects itself
  after the CRD is applied.
- With encryption at rest and `binlog_encryption=ON`, a clone now ends
  with a new escrow version: the recipient stores a binary log
  encryption key for its new `server_uuid`
  ([Clones and the keyring](/docs/configuration/encryption-at-rest#clones-and-the-keyring)).
- While a clone has no outcome yet, the group carries the annotation
  `bloodraven.shipstream.io/clone-server-uuid` (the recipient's
  `server_uuid` before the clone) and, with encryption at rest, the
  recipient stays unsealed. Both end when an operator sees the clone
  completed or failed, also after an operator restart. Do not remove the
  annotation by hand; GitOps tooling that prunes unknown annotations on
  `MysqlFailoverGroup` must leave `bloodraven.shipstream.io/*` alone, as
  for the operator's other annotations.
- An older operator renders the pod without the launcher, so a
  downgrade rolls every group again. Servers keep the `server_uuid`
  they have.

The sidecar archives binary logs that MySQL encrypted
(`binlog_encryption=ON`, the default with `spec.encryptionAtRest`): it
decrypts each file with the binary log encryption key in the site's
keyring file and archives the plaintext
([Encryption at rest and PITR](/docs/backup-and-restore/backup-restore#encryption-at-rest-and-pitr)).
The change is in the sidecar image only. There is no new mount, Secret,
RBAC rule, CRD field or MySQL setting, and the mysql launcher is
unchanged, so the release rolls the pods once for the image, as every
release does. What to expect on a group that already ran with encryption
at rest and `spec.backup.pitr`:

- Until a site's pod runs the new sidecar it archives nothing, as before
  (`PITRArchiveReady=False` / `ArchiverError`, `invalid binlog magic`). A
  group that pins `spec.sidecar.image` stays in that state until the pin
  moves.
- Once the pod has rolled, the sidecar archives the encrypted binlogs
  that are still on the data volume. MySQL keeps them for
  `binlog-expire-logs-seconds` (14 days unless overridden). Older ones
  were purged and are never archived, and promotion records written
  before the upgrade have no promotion set. A point-in-time restore that
  needs a purged binlog refuses `PITRArchiveGap`.
- Wait for `PITRArchiveReady=True`, then take a full backup.
  Point-in-time restores are possible from that backup on.
- The archive holds the plaintext of the binary logs. If the PITR
  profile has no `encryption`, the operator raises a Warning Event
  `PITRArchiveNotEncrypted` once and the `EncryptionAtRestReady`
  condition's message says the archive "has no encryption of its own".
  Nothing is refused. `encryption` cannot be added to the profile in
  place: use a new profile with a new prefix
  ([Rotation](/docs/backup-and-restore/backup-encryption#rotation)), or
  rely on the store's encryption.
- A reclone of a read-only site no longer waits its 2 minutes for a tail
  that could not be read, and promotion records carry
  `promotionGtidExecuted` again.
- `coverage.binaryLog: false` still works and is no longer needed for
  PITR.
- An older sidecar cannot read the encrypted files, so a downgrade of
  the sidecar image returns the group to archiving nothing.

The kubelet probes the sidecar too, and the operator renders those
probes. That makes the probe paths part of the same contract, so they
only use endpoints every supported sidecar serves. Liveness probes
`/peer/ping`, which answers without touching MySQL. Readiness probes
`/health`. The newer `/livez` also detects a wedged fencing loop, but a
sidecar that predates it answers 404, and a liveness probe on it would
restart that sidecar in a loop. It becomes the liveness target once
every supported sidecar serves it.

A briefly older-or-newer sidecar stays compatible with the operator
while pods roll. Skew beyond one minor is not tested and not
guaranteed.

When a change moves both `spec.image` and the sidecar image
together, `OrderedUpdate` restarts the sidecar as part of the pod
restart it already performs — the replica-first ordering applies
automatically, no separate sidecar sequencing is required.

## Upgrading from v1.6.0 to v1.7.0

::warning
**There is no in-place upgrade from v1.6.0 to v1.7.0.**


Never apply the v1.7.0 CRDs to a cluster that runs v1.6.0, by any route:
the "CRDs first, then the chart" routine of a normal upgrade (including the
[GitOps safe upgrade workflow](/docs/operations/gitops#safe-upgrade-workflow)),
a platform CRD application or an Argo CD Helm release that renders the
chart's `crds/`, the Argo CD layout in
[Production install examples](/docs/get-started/production-install-examples),
or the "CRDs managed separately" loop in
[Production install](/docs/get-started/install-production) pointed at a
newer release. On a v1.6.0 cluster, pin both the chart version and the CRD
source in Git for as long as it runs.
::

Why an in-place upgrade cannot work:

- **Stored defaults change type.** Every v1.6.0 `MysqlFailoverGroup` stores
  `cloneTimeout: 3600` (a duration in v1.7.0) and
  `updateStrategy: OrderedUpdate` (an object in v1.7.0), and every backup
  profile stores `retention: 7` (an object in v1.7.0). The API server prunes
  unknown fields but does not convert types, so the v1.7.0 operator cannot
  decode a stored v1.6.0 group, and one undecodable object fails its whole
  list of groups: it then manages none of them.
- **CRDs are cluster-scoped.** Applying the v1.7.0 CRDs changes the schema
  for every namespace at once. From then on every read of an old object has
  the old field names pruned, and the still-running v1.6.0 operator persists
  the pruned object on its next write.
- **Stored objects can break the new name and size rules.** A group stored
  before v1.7.0 can have a name that is not a DNS-1035 label, a group name
  plus site name longer than 41 characters, or an integer
  `spec.sites[].storage.size`. On Kubernetes 1.31 the API server validates
  status writes without ratcheting, so it refuses the operator's own status
  writes to such a group. An integer size cannot be decoded at all: v1.7.0
  stores a size as a string.
- **Re-applying the manifests does not help.** Every bootstrapped group's
  `initFromBackup` block is renamed, and v1.7.0 refuses any change to it. A
  manifest re-apply cannot rewrite status, and several status records cannot
  be rebuilt from observation.

If the v1.7.0 CRDs were applied to a v1.6.0 cluster by mistake, scale every
Bloodraven operator to 0 first and write no Bloodraven object. Do not
re-apply the v1.6.0 CRDs as a fix; recovery depends on whether any object
was written since, and is part of the procedure below.

### The supported path: a new group in a new cluster

The supported path bootstraps a new group, in a cluster that has never had
the Bloodraven CRDs, from a v1.6.0 backup. The step-by-step procedure, its
recovery steps and its end-to-end test are tracked in
[issue #243](https://github.com/ShipStream/bloodraven/issues/243). Until it
is published, this outline is its scope, not a tested procedure:

1. Stop application writes and take a full backup on v1.6.0, on an **S3**
   profile that the new cluster can reach.
2. Install v1.7.0 in a cluster with no Bloodraven CRDs.
3. Write the new manifests with the changes listed in
   [What changes in v1.7.0](#what-changes-in-v170). Give every backup and
   PITR profile a prefix that no v1.6.0 group has used; reference the old
   backup only as a restore source. Apply with
   `kubectl apply --server-side --validate=strict`, so a leftover old field
   name is refused instead of pruned.
4. Bootstrap the group from the backup (`initFromBackup`, with `decryption`
   for an encrypted backup), excluding the schemas that `MysqlDatabase`
   objects manage. Then apply the `MysqlDatabase` objects and load each of
   their schemas with a per-schema `restoreInPlace`.
5. Recreate the MySQL accounts that neither the operator's credentials nor a
   `MysqlDatabase` create: restores do not load users.
6. Take a new full backup as the new group's baseline, wait for
   `PITRArchiveReady=True` when PITR is on, verify the baseline with a
   `MysqlBackupVerification`, and compare the application's data with the
   frozen source.
7. Cut over, and only then retire the old group. Keep the old cluster, its
   backups, its passphrases and its keyring escrow Secrets for as long as
   you may need them.

The new group does not carry over failover history, operation records
(restores, planned failovers, recoveries), `MysqlBackup` and
`MysqlBackupVerification` objects, verification holds, keyrings (it mints
its own) or PITR across the old archive.

There is no in-place rollback either: the v1.6.0 operator cannot decode a
v1.7.0 object. Until cut-over is verified, the old group in the old cluster
is the way back.

### What changes in v1.7.0

Use this list to write the new group's manifests and to update alert rules,
scripts and dashboards. v1.7.0 supports Kubernetes 1.31 and newer (the
chart's `kubeVersion` is `>=1.31.0-0`). On 1.31 and 1.32, keep the

v1.7.0 removes these fields, which earlier releases accepted and ignored or
refused:

- `spec.secretName` (the DSN credential mode). `spec.credentials` is
  required: create an operator Secret with `username`, `password` and
  `MYSQL_ROOT_PASSWORD` (plus `MYSQL_REPLICATION_USER` and
  `MYSQL_REPLICATION_PASSWORD` if replication uses its own account) and set
  `credentials.operatorSecretName`. As the DSN mode did, the first-boot init
  script of the new group creates that replication account with
  `REPLICATION SLAVE, REPLICATION CLIENT, BACKUP_ADMIN, CLONE_ADMIN`. Express
  DSN `tls=` options through `spec.tls`.
- `spec.tls.issuerRef`: `spec.tls` is `secretName` only.
- `spec.restoreInPlace.pointInTime`, which the operator refused; use
  `initFromBackup.pointInTime` on a new group.
- `loadOptions.resetProgress`, profile `storage.s3.storageClass`, profile
  `verification.storage` and `MysqlBackupVerification` `spec.storage`. Bound
  a verification's disk with `spec.resources.limits.ephemeral-storage`.
- `spec.triggeredBy` on `MysqlBackup` and `MysqlBackupVerification`: the
  value moves to the annotation `bloodraven.shipstream.io/triggered-by`.
- A `replica-preserve-commit-order` override in `spec.mysqlConf`: it is
  operator-owned and forced `ON`.

Some values that v1.6.0 accepted are refused, and some defaults change
meaning:

- **Timers** must be inside their bounds (see
  [Timers](/docs/configuration/crd-reference#timers)): for example
  `pollInterval: 0s`, a `failoverCooldown` under `30s`, or a
  `plannedFailover.maxLagWait` over `1h` is refused, and so is a
  `planned-failover` annotation whose `maxLagWait=` is outside `1s` to `1h`.
  `dragonfly.maxMemory`, if set, must be a positive quantity.
- **Names and lists.** S3 `prefix` values (profiles, restore and standby
  sources) are at most 512 characters with no empty (`a//b`), `.` or `..`
  segment, and a leading `/` is ignored, so `/prod` and `prod` are the same
  prefix. Profile names are DNS labels of at most 63 characters, and
  `spec.backup.profiles` is a list-map keyed by `name` (at most 32). Every
  Secret name and every `failoverGroupRef.name` and `backupRef.name` is a DNS
  subdomain (lowercase, at most 253 characters), and every Secret key is at
  most 253 characters of `[-._a-zA-Z0-9]`; set an optional Secret name to
  nothing rather than `""`. `MysqlBackup` and `MysqlBackupVerification`
  `profileName` and schedule `profileName` are DNS labels, `MysqlBackup`
  `sourceSite` matches the site-name pattern, and
  `spec.sidecar.operatorEndpoint` is `host:port`. The CRDs also refuse
  duplicate entries in `splitBrainPolicy.sitePriorities`; more than one
  `restoreInPlace.loadOptions.includeSchemas` entry; duplicate names, or
  more than 16 entries, in `extraContainers`, `extraInitContainers` and
  `backup.imagePullSecrets`; duplicate `backup.schedules` names, more than
  32 schedules, or a schedule name longer than 63 characters; duplicate,
  more than 256, or longer than 64 character names in the `dump` and
  `loadOptions` `includeSchemas`/`excludeSchemas` lists; more than 16
  `MysqlDatabase` `deploymentClients` (now keyed by the namespace and
  ServiceAccount pair); and a `MysqlBackup` whose name ends in
  `.bloodraven-backup.json`.
- **Names that become object names.** A `MysqlFailoverGroup` name is a
  DNS-1035 label (`a.b` and `1orders` are refused: the name starts the
  group's Service names). A site name is a DNS label of at most 20
  characters (no leading or trailing `-`), and the group name plus each
  site name is at most 41 characters. `splitBrainPolicy.sitePriorities`
  entries and `MysqlBackup` `sourceSite` follow the site rule. A
  `MysqlBackup` or `MysqlBackupVerification` name is at most 63 characters.
  A site name is part of the site's PVC and Service names, so a name that
  needs to change means a new group.
- **Sizes** (`spec.sites[].storage.size`, `pvc.provisioned.size`) are
  positive quantity strings; a bare number of bytes must be quoted.
- **`restoreInPlace.confirm`** must be an RFC 3339 timestamp with an
  upper-case `T` and `Z`, an offset within `-23:59`..`+23:59` and a
  digits-only fraction.
- **Edits that are refused.** A site cannot be removed or renamed (see
  [Replacing a site](/docs/operations/operations#replacing-a-site)); a
  site's `zone`, `storage.storageClassName` and `storage.size` are
  immutable (a size is compared by value); `spec.initFromBackup` cannot be
  added, changed or removed (a bootstrap that failed on its own block is
  retried by recreating the never-bootstrapped group, see
  [A failed bootstrap restore](/docs/backup-and-restore/backup-restore#a-failed-bootstrap-restore));
  `spec.encryptionAtRest.enabled` cannot go back to `false`, and the
  keyring paths cannot change while it is `true`; a profile's
  `pvc.provisioned` cannot change, be added or be removed; and a
  `MysqlBackup`'s `failoverGroupRef`, `profileName` and `sourceSite`, and a
  `MysqlBackupVerification`'s `failoverGroupRef`, `profileName`,
  `backupRef`, `pointInTime` and `sanityCheck`, are immutable.
- **`ttlSecondsAfterFinished`** on a `MysqlBackupVerification` and on a
  profile's `verification` no longer defaults to `0`: an omitted value keeps
  a successful verification's Pod (and its restored datadir) until
  retention deletes the verification. Set `ttlSecondsAfterFinished: 0` to
  keep the immediate cleanup.
- **An explicit `0` is kept as `0`** instead of being replaced by the
  default: `replication.maxLagSeconds: 0` requires a caught-up replica (it
  meant `300`), and `backup.backoffLimit: 0` and
  `backup.maxLagSecondsForSource: 0` are honored.
- **`MysqlBackupVerification` `backupRef: {}`** (which meant "latest") is
  refused: omit `backupRef` instead.
- **`MysqlBackup` `spec.deletionPolicy`** is new. The default `Delete`
  keeps the v1.6.0 behaviour (deleting the object deletes its artifact);
  `Retain` keeps the artifact, unless it is on a claim the group
  provisioned, which is deleted with the group
  ([Keeping an artifact](/docs/backup-and-restore/backup-restore#keeping-an-artifact)).
- The chart's operator environment variable
  `BLOODRAVEN_DEFAULT_AUXILIARY_ADDRESS` is now
  `BLOODRAVEN_DEFAULT_OPERATOR_ENDPOINT`; rename an `extraEnv` entry that
  overrides it.

#### PITR archive identity

v1.7.0 changes the PITR archive format and refuses archives written before
it. The new group's PITR profile must use a new prefix (a v1.6.0 prefix is
refused as `ArchiveLegacy`), and its first full backup after the archive is
`Bound` (`PITRArchiveBindingReady=True`) is its first point-in-time
baseline: it carries a backup stamp and `status.pitrArchiveID`.

- Grant the sidecar's PITR credentials `s3:ListBucket`, `s3:GetObject`,
  `s3:PutObject` and `s3:DeleteObject`, and confirm the store enforces
  conditional writes
  ([PITR archive requirements](/docs/backup-and-restore/backup-s3#pitr-archive-requirements)).
  Grant every backup profile's credentials `s3:ListBucket`, `s3:GetObject`
  and `s3:PutObject` on `<prefix>/*`: each backup Job checks that its dump
  location is empty, then reads its backup stamp before writing it and
  reads it back after. Artifact cleanup still needs `s3:ListBucket` and
  `s3:DeleteObject`, and deleting a failed backup reads its stamp too
  ([Backup credential permissions](/docs/backup-and-restore/backup-s3#backup-credential-permissions)).
- v1.7.0 cannot read a v1.6.0 archive. Keep the old prefix, its backups, its
  passphrase and the v1.6.0 cluster if you may need a target from before the
  move. Do not run a pre-v1.7.0 sidecar against a v1.7.0 archive: it
  rewrites its manifest as version 1 and the archive is then refused as
  `PITRArchiveLegacy`.
- A v1.6.0 backup has no backup stamp, so PITR from it refuses
  `PITRBackupIdentityUnknown`; a dump-only restore from it works. An
  **encrypted** v1.6.0 backup also recorded no dump key, and the operator
  never decrypts a dump with a profile's live Secret, so restoring it
  (`initFromBackup` or `restoreInPlace`) needs an explicit `decryption`
  naming a Secret that holds the passphrase it was written with. Keep that
  passphrase even after you rotate the profile's Secret.
- The archive key is pinned by the group's archive encryption binding: pods
  mount an operator-made key snapshot, and in-place passphrase or encryption
  changes on an archive in use are refused. Key snapshot Secrets
  (`mysql-pitr-key`, and one `mysql-dump-key` per encrypted backup) have no
  owner reference and survive group deletion. See
  [Archive encryption bindings](/docs/backup-and-restore/backup-encryption#archive-encryption-bindings).

See also
[Upgrading to archive identity](/docs/backup-and-restore/backup-restore#upgrading-to-archive-identity).

  `bloodraven_deploy_lease_revocations_total{reason}` label, the
  `/deploy/v1` `409 revoked` body's `reason`, and the
  `DeploymentLeaseRevoked` Event message. Other `reason` labels carry the
  renamed condition and Event reasons.
- The operator's `/status` and `/ws/status` carry the CR values for site
  `state` and `role` (`Writable`, `ReadOnly`, `PrimaryCandidate`, ...).
  Both carry `lastFailover{time, target, promotionGtidExecuted}` in the
  shape of `status.lastFailover`; the flat `/status`
  `promotionGtidExecuted` field is gone. `/ws/status` also carries
  `sites[].replication`, and its `updatePhase` is now populated (it was
  always empty).
- Structured logs: the `state transition` record's `from` and `to` values
  and the `role` field of the fencing and planned-failover records carry the
  same CamelCase values. The INFO record `dragonfly snapshot-upgrade
  deferred: the Dragonfly master differs from the MySQL active site`
  (fields `fg`, `dragonflyMaster`, `activeSite`) is now
  `dragonfly snapshot-upgrade deferred` with fields `fg` and `reason`, and
  covers every cause a run waits for. See the
  [log schema](/docs/observability/log-schema).
- `/deploy/v1` `operations.plannedFailover` carries the planned-failover
  vocabulary below ([Deployment API](/docs/configuration/deployment-api)).

### Planned failover in v1.7.0

The durable planned-failover claim (issue #235) is part of v1.7.0. It
replaced the shape of `status.plannedFailover` (see the
[CRD reference](/docs/configuration/crd-reference#plannedfailoverstatus)) and
its vocabulary:

- `spec.plannedFailover.onCooldown` accepts `Reject` or `Defer`, and
  `spec.dragonfly.plannedFailover.onSyncTimeout` accepts `Proceed` or
  `Fail`; the lower-case spellings are refused.
- Queries on the removed status fields (for example `transactionsLost` or
  `durationSeconds`) must move to `status.plannedFailover.result` and the
  duration histogram. The renamed Event reasons are in [Events](#events);
  `PlannedFailoverStarted`, `PlannedFailoverSkipped`,
  `PlannedFailoverRejected`, `PlannedFailoverDeferred` and
  `PlannedFailoverFailed` keep their names. The new reasons are listed in
  [Planned failover](/docs/operations/planned-failover).
- **Deployment API companions.** `operations.plannedFailover` in
  `/deploy/v1` carries the new vocabulary. `phase` is
  `status.plannedFailover.phase`: `Pending` and `Validating` became
  `Admitting`, `Resuming` became `Publishing`, and `Fencing` and
  `RollingBack` are new; the empty phase is reported only when there is no
  block. A `planned-failover-terminal` marker that names the run wins over a
  stale live phase: `phase` is then `Succeeded` or `Failed` with the
  marker's outcome and reason. `reason` is no longer a free-form string, and
  it belongs to the current phase only: `admission.waitReason` while
  `Admitting`, `admission.deferReason` while `Deferred`, `result.reason`
  (empty when the result has none) for `Succeeded` and `Failed`, and empty
  in any other phase; all are enums. The new key `outcome` carries
  `result.outcome` (empty until the run ends). A companion that switches on
  phase or reason strings must be updated before cut-over. Coordination
  decisions should use `stable` and `unstableReason`, which kept their
  meaning.

## Dragonfly behavior changes after v1.7.0

These apply to groups with `spec.dragonfly.enabled: true` when the operator
is upgraded past v1.7.0. None of them changes a CRD field or a pod template,
and nothing rolls. The mechanisms are described under
[Dragonfly during failover](/docs/operations/failover#dragonfly-during-failover).

| Was | Is | What to do |
|---|---|---|
| A Dragonfly-only promotion acted on the first missed poll of the master. | It waits for `spec.failureThreshold` consecutive missed polls (default 3, 4 to 17 s depending on how the master fails). | Nothing. Set `spec.failureThreshold` lower only if you accept acting on one missed observation; the field also governs MySQL. |
| A master that restarted empty emptied its replica (the operator re-attached it). | The replica that holds the cache is promoted, and the master is taken back to the MySQL active site when the restarted instance is in sync. | Expect `DragonflySessionsLost` for the promotion and `status.dragonfly.activeSite` on another site than `status.activeSite` for 30 s or longer (up to 15 minutes after repeated restarts of the same site). |
| The same replica was promoted even when the operator had seen it cut off from the running master for a long time. | It is not promoted (`DragonflyStaleReplicaNotPromoted`); it is re-attached and the cache starts with the restarted master's content. | Fix the path between the Dragonfly pods (NetworkPolicy, firewall, `masterauth`); alert on `status.dragonfly.sites[].linkStatus: down` beside a healthy master. |
| After a failed `REPLTAKEOVER`, the emergency promotion, the take-over to the MySQL active site and the rollout sent `REPLICAOF NO ONE`. | Not while the old master still answers as a master. The promotion fails (`DragonflyPromotionFailed`), the old master keeps the role, and the take-over is retried once the replica is proven in sync (`DragonflyFollowStalled` after two minutes). | Dashboards that assume the Dragonfly master is on the MySQL active site right after an emergency failover must allow for the old site keeping it while its Dragonfly is healthy and the new site's replica is not in sync. |
| The take-over to the MySQL active site was made for a replica that had ever received data. | It needs the sync proof of a planned failover: stable link, the master's `master_replid`, and its replication position on every flow. | Nothing. |
| The planned failover's sync wait and the rollout's readiness check compared `master_repl_offset`, which a Dragonfly master does not report, so they always passed. | They compare per-flow positions read with `DFLY REPLICAOFFSET` and `DEBUG REPLICA OFFSET`. | Make sure the operator's Dragonfly user may run both. The operator's own setup allows them; an ACL file or renamed commands in `spec.dragonfly.args` may not. |
| (New in this release.) | A site that refuses those commands does not stall a rollout or fail a planned failover: with the replica's link healthy, the operator goes on with `REPLTAKEOVER` alone and never falls back to `REPLICAOF NO ONE` (`DragonflySyncUnproven`, once per run or rollout). | Treat `DragonflySyncUnproven` as a configuration finding and grant the commands. |
| With three sites, a lost master was never replaced while two healthy replicas existed. | The replica that executed the most of the master's journal is promoted. | Nothing. |
| After a promotion the operator sent `CLIENT KILL TYPE NORMAL` to the old master, which Dragonfly refuses (`ERR syntax error`); the log line `client-kill: evicted clients from old master` was not written. | It lists the old master's connections and closes them by id, except its own and the replication links. The log lines carry the new field `killed`. | Nothing. The operator's Dragonfly user needs `CLIENT LIST` and `CLIENT KILL`. |

Log pipelines: the `msg` values added and removed are listed in the
[log schema](/docs/observability/log-schema#dragonfly); the rollout state
`Unprovable` and the line `dragonfly: replication position cannot be
compared; not waiting for maxSyncWait` existed only in unreleased builds.

## Restoring across versions

`MysqlBackup.status.mysqlImage` records the image tag that produced
each dump. The safe path is to restore onto the same major version
that produced the backup. **Do not** restore a dump onto an older
MySQL version — MySQL does not support version downgrade of data.

Backup-restore throughput and sizing guidance live under a separate
performance guide (WISHLIST #27).

## What Bloodraven does not do

- **No version admission check.** Setting `spec.image` to an
  unsupported tag will not produce a CRD validation error. MySQL
  itself rejects unsupported upgrades at pod start.
- **No skip-a-major guardrail.** There is no enforcement that blocks
  an `8.0 → 9.7` jump or a `9.7 → 9.8+` jump at the operator layer.
- **No downgrade path.** MySQL does not support version downgrade,
  and Bloodraven inherits that limitation.
- **No per-site MySQL version.** The CRD does not expose a per-site
  image, so mixed-version steady state is not expressible.
