---
title: Repair PITR history safely
description: Resolve missing or divergent archived files without deleting recovery evidence.
---

Use this procedure when the archiver or downloader reports a missing object,
an issuance it cannot verify, a server that could reissue archived GTIDs, or
GTID namespace reuse. A zero backlog means local uploads caught up; it does
not prove that historical recovery is complete.

Divergent rows on their own need no repair. A row whose transactions the
site's server no longer has is evidence the planner uses, not an archiver
failure: see
[Divergent rows](#distinguish-divergence-re-logging-and-gtid-reuse).

Some archive states cannot be repaired in place. A reset epoch
(`PITRArchiveHistoryReset`), a [history-integrity marker](#unsafe-history-marker)
(`PITRArchiveUnsafeHistory`), a [reissue of archived GTIDs](#reissue-risk),
a legacy prefix (`PITRArchiveLegacy`), a manifest row without an `id`
(`PITRArchiveObjectInvalid`) and a descriptor owned by another group
(`PITRArchiveForeign`, `PITRArchiveCopy`) all need a new prefix and a full
backup.

None of the records below is an acknowledgement. A `divergent` record, a
quarantine and a canonical-backup acknowledgement change what the archiver
reports and what the planner may read, but a restore whose window holds lost,
errant or quarantined transactions still refuses
`PITRArchiveDivergentHistory` until those transactions are in
`excludeGtids`, or until you use a backup taken after them. See
[Target history and excludeGtids](/docs/backup-and-restore/backup-restore#target-history-and-excludegtids).

### Preserve the evidence and choose a baseline

1. Preserve the site's manifest, all archive objects, the original passphrase,
   and any surviving local binlogs. Record the error's site, name, ID,
   predecessor set and missing transaction set. `/archiver/status.lastError`
   and increases in `bloodraven_archiver_upload_failures` expose history
   problems before restore. Do not clear the manifest or overwrite objects.
2. Choose the canonical live dataset with your incident owner. Take and verify
   a new full backup of that dataset. Record its pre-dump `status.gtidExecuted`.
   Quarantine cannot reconstruct lost transactions. Restores whose target
   history does not need the row stay available; restores that need it use
   a backup taken after the quarantine (see the waiver below).
3. Pause PITR writers through your maintenance rollout and wait for the old
   sidecar processes to stop. Keep MySQL data and archive volumes intact.
   This prevents a concurrent manifest write from undoing the maintenance edit.

### Restore bytes or quarantine one row

If an original object can be recovered, restore those exact bytes at its
original key (`<prefix>/binlogs/<site>/<name>.<id>`), using the original
encryption settings. Every row is content-addressed: its `id` is the
identity of its bytes, so equal names, sizes and headers do not prove a
replacement. While the same bytes are still a sealed local binlog on the
site, the archiver uploads them again by itself.

For an unrecoverable file, run the matching operator image's
`pitr-quarantine` command in a maintenance Pod with the same archive
environment, writable archive PVC/S3 credentials and mounted key snapshot as
the writer. Use the exact storage prefix. A divergent row whose object is
intact needs no quarantine: quarantining it does not change what a restore
must exclude, and it does not remove a [reissue risk](#reissue-risk). For
example, this plaintext PVC maintenance Pod moves one manifest row and
preserves its object; replace all example values before applying it:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pitr-quarantine
spec:
  restartPolicy: Never
  securityContext:
    fsGroup: 65532 # reuse the archive writer's actual fsGroup
  containers:
    - name: quarantine
      image: your-registry/bloodraven:matching-version
      args:
        - pitr-quarantine
        - --site=iad
        - --name=mysql-bin.000004
        - --id=0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
        - --reason=Object lost; canonical backup verified
        - --resume-gtids=aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee:1-200
        - --confirm
      env:
        - {name: BLOODRAVEN_PITR_STORAGE_TYPE, value: PVC}
        - {name: BLOODRAVEN_PITR_MANIFEST_PREFIX, value: orders/binlogs}
        - {name: BLOODRAVEN_PITR_PVC_MOUNT_PATH, value: /archive}
        # Writer identity: copy these from the site's sidecar container.
        - {name: POD_NAMESPACE, value: orders}
        - {name: FAILOVER_GROUP, value: orders}
        - {name: BLOODRAVEN_FAILOVER_GROUP_UID, value: 11111111-2222-3333-4444-555555555555}
        - {name: BLOODRAVEN_PITR_DESTINATION, value: pvc://orders/your-existing-backup-pvc/orders/binlogs}
        - {name: BLOODRAVEN_PITR_ENCRYPTION_MODE, value: None}
      volumeMounts:
        - {name: archive, mountPath: /archive}
  volumes:
    - name: archive
      persistentVolumeClaim:
        claimName: your-existing-backup-pvc
```

Mount the archive PVC exactly at `BLOODRAVEN_PITR_PVC_MOUNT_PATH`, not
at a parent directory: the command refuses a path that is not a mount
point, and checks that it can write there.

`pitr-quarantine` is a writer, so it needs the same archive identity as the
site's sidecar: copy `BLOODRAVEN_FAILOVER_GROUP_UID`,
`BLOODRAVEN_PITR_DESTINATION` and `BLOODRAVEN_PITR_ENCRYPTION_MODE` from the
sidecar container of the site's MySQL Deployment (`kubectl get deploy
mysql-<group>-<site> -o yaml`), with the group's namespace and name. It checks
the descriptor exactly as the sidecar does and refuses an archive this group
does not own (`PITRArchiveForeign`, `PITRArchiveCopy`), a legacy prefix
(`PITRArchiveLegacy`), or a prefix with no archive (`PITRArchiveNotFound`).
It never creates a descriptor.

`--id` is the row's complete 64-character `id` from the site manifest. There
are no rows without one: a manifest that holds a row, a quarantined row or a
retirement record with no `id` was written before archive identity or edited
by hand, and the sidecar, the restore and this command all refuse it
(`PITRArchiveObjectInvalid`) instead of repairing it. `--id=legacy` is
refused. For encrypted archives, also mount the archive's accepted key
snapshot read-only (key `passphrase`) and set
`BLOODRAVEN_PITR_PASSPHRASE_FILE` to its mounted file. That is the Secret the
writers mount, which may differ from the profile's current Secret after a
refused edit. Read its name from the group's `Bound` binding for the
destination:

```bash
kubectl get mfg <group> -o json | jq -r --arg d '<destination>' \
  '.status.pitrArchiveBindings[] | select(.destination == $d and .state == "Bound") | .encryption.keySecretName'
```

(kubectl's JSONPath filters accept one comparison, not `&&`, hence `jq`.)
An empty result means the destination has no `Bound` binding: the key cannot
be read from status, so stop and resolve the binding first.

Copy `<destination>` exactly as `status.pitrArchiveBindings[].destination`
shows it (the normalized form, for example
`s3://<bucket>/<prefix>?endpoint=<escaped endpoint>`). S3
uses the existing `BLOODRAVEN_PITR_S3_*` and `BLOODRAVEN_PITR_AWS_CREDS_DIR`
configuration. Never pass Secret bytes as command arguments.

A maintenance Pod that references a key snapshot (a mounted or projected
volume, an env `secretKeyRef` or `envFrom`) blocks
[releasing that binding](/docs/backup-and-restore/backup-encryption#releasing-a-binding)
for as long as it has not finished, whatever its owner; delete it when the
repair is done.

The command writes a `quarantined` record containing the original row, reason,
time and resume GTIDs. It never calls object deletion. The replay planner
treats a quarantined row as follows:

- **Never data.** A quarantined row is never replayed. A restore whose target
  history needs its transactions refuses `PITRArchiveGap` ("it is in
  quarantined row `<site/name>`; un-quarantine it, or use a backup taken
  after it").
- **Never an acknowledgement.** Its transactions committed between the
  backup's newest transaction and the target still count toward the
  divergent set D, so they must be in `excludeGtids` unless they are on the
  target history. An unreadable quarantined row counts its hinted GTIDs, to
  fail closed.
- **Identity-checked.** A readable quarantined row that overlaps the backup,
  the target history or the replay is downloaded and compared like any other
  copy (`PITRArchiveNamespaceReuse` on a mismatch, or when it cannot be read).
  The comparison covers commit time, origin server, emptiness and
  [row changes](/docs/backup-and-restore/backup-restore#copies-of-one-transaction),
  so quarantining a row does not hide a copy whose rows differ.
- **The waiver.** An unreadable quarantined row needs no identity download
  when all three hold: every GTID it holds is in the backup, the backup's
  stamp was created more than δ (the fixed 5 s clock-skew margin) after the
  quarantine, and none of its GTIDs is replayed. The dump
  was then taken from the live dataset after you declared the row lost, so
  the row's bytes cannot change the result. **Take a full backup after
  quarantining** and restore from it.

`--resume-gtids` is still required: the command checks it against prior
quarantine and acknowledgement bounds, and records it, but the planner no
longer uses it to scope windows.
After recovering an original object, the same command with the exact site,
name and ID plus `--undo --confirm` restores the row. Preserve the manifest
copy as your incident record. Resume PITR writers, inspect status, and verify
an isolated restore with application markers across the repaired boundary.

### Distinguish divergence, re-logging and GTID reuse

**Divergent rows are evidence, not a failure.** Every scan, each site's
sidecar audits its own manifest against its server: a row that holds, or
builds on, transactions the server's `gtid_executed` no longer contains is
recorded in the manifest's `divergent` list with those transactions
(`missingGtids`). The usual cause is a lossy failover. An old primary that
comes back read-only archives the
[tail of its last writable era](/docs/backup-and-restore/backup-restore#archiving-the-tail-of-an-outgoing-primary),
including the transactions the new primary never received. Once that site is
recloned, its server no longer holds them, and its audit records the tail
row.

That row is correct archive content and needs no action on the archive:

- `divergentRows` in the site's `/archiver/status` rises, and the sidecar
  logs `archive divergence evidence recorded` once.
- `lastError` stays empty, `uploadFailures` does not move, and
  `PITRArchiveReady` stays `True`. Its message names the sites that hold
  divergent rows (`...; iad: 1 divergent row (...)`).
- The site keeps uploading and retention keeps running. A divergent row is
  not retired by retention, because no retained backup contains its lost
  transactions.
- The planner reads the record. A restore whose window crosses those
  transactions refuses `PITRArchiveDivergentHistory` and prints them, until
  they are in `excludeGtids` or you restore from a backup taken after them.
  In latest mode the lost tail is a second head (`PITRArchiveSplitBrain`
  names both branches) until it is excluded. Promotion records give the same
  evidence without an audit: a transaction committed before a site was
  promoted without it was lost at that failover.

Empty execution, a running clone, and a read-only server without a
replication channel supply no evidence during bootstrap. Every eligible
audit recomputes the missing sets, so a record ends when the server holds
the transactions again.

**The one divergence that is an error** is a server that could issue the
missing GTIDs again: the transactions were issued under the `server_uuid`
the server still has. A clone gives its recipient a new `server_uuid`, so
this is a data directory that was restored or reset without a clone, or a
site cloned by a release that kept the recipient's `server_uuid`. The site
reports it in `reissuableGtids`, its `lastError` reads `site <s>: server_uuid
<uuid> no longer has archived transactions <set> that it issued ...`, and
`PITRArchiveReady` turns `False` with reason `ArchiverError`. See
[Reissue risk](#reissue-risk) for what to do. The same holds for a
quarantined row: a quarantine moves only metadata, and the server can
reissue a quarantined row's transactions too. For that source the record is
kept when the numbers return, because the replacement transactions may still
be in the active, unarchived binlog; rotation alone does not prove original
issuance.

A verified reuse guard requires overlapping GTIDs of the same source server UUID
with different archived content identities and different original commit or
transaction-query identities. Re-logging may change file framing and immediate
commit time while preserving original issuance. Smaller names, out-of-order
uploads, identical-byte retries and a transient GET are not reset evidence.
Unknown origins never create a reuse guard or authorize overlapping generations.
Rows whose coverage is not bound to their `id` are inspected in bounded
batches even when retention is disabled. One worker drains a large stream; foreground
rotations run first, failed inspections cool down for an hour, and restart
reconstructs pending work from the manifest. Retirement waits for unresolved
issuance checks. Downloads independently verify overlapping observed GTIDs
before applying numeric backup cuts; unavailable or incomplete issuance
proof fails loudly. Original commit/query evidence distinguishes actual
reuse from a recovered execution set.

Quarantine preserves conflict and divergence evidence; undo restores the
row and its divergence protection. A verified namespace-reuse guard remains
even after quarantine: GTID containment alone cannot identify the right backup
generation once numbers were reused. Start a new prefix/full backup for that
case; acknowledgement only recovers obsolete guards without verified reuse.

For a real `RESET BINARY LOGS AND GTIDS`, prefer a new archive generation and
full backup. A reset epoch, including one the archiver records after it
verifies GTID reuse, refuses the whole archive (`PITRArchiveHistoryReset`), not
only the affected site, whatever the backup and target. Set the selected profile's
`spec.backup.profiles[name].storage.s3.prefix` (S3), or
`spec.backup.profiles[name].storage.pvc.subPath` (PVC), to a new unused location;
these are paths inside the existing named profile, not literal map keys.
The archiver appends `binlogs/` there. Alternatively create a new profile and
select it with `spec.backup.pitr.profileName`. Wait for the rollout and take
and verify a full backup in that generation. Keep older backups paired with
their original generation; identical GTID numbers do not make a pre-reset
backup compatible with a post-reset dataset.

### Recover an obsolete guard behind a canonical full backup

Older versions could set `epoch.resetReason` from upload order alone. It is
recoverable without deleting objects or discarding valid earlier windows.
After preserving evidence, verifying a canonical full backup and stopping
writers as above, use the same maintenance Pod/storage configuration with:

```text
bloodraven pitr-quarantine --site=iad --acknowledge-history \
  --reason='Canonical full backup verified; obsolete upload-order guard' \
  --resume-gtids='aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee:1-200' --confirm
```

This streams and identity-verifies every active archived file and requires
its observed execution frontier to be covered by the canonical backup bound.
Any verified namespace-reuse evidence, or missing, corrupt or uncovered
history, refuses acknowledgement; first recover
those exact objects or explicitly quarantine the unresolved rows. No objects
are deleted or overwritten. The manifest records the reason, time, verification
bound and prior guard reason, then supersedes the obsolete guard and
divergence records. Verification also compares overlapping issuance, including
streams whose conflicting evidence has not yet been recorded.
Acknowledgement removes no rows and adds no global backup cutoff; older
backups still undergo normal replay, divergence and generation checks, and
the acknowledgement does not exclude anything from a restore.
Quarantined rows retain their own bounds. Verified reuse cannot be cleared
by acknowledgement or quarantine. Resume writers, inspect status and verify
an isolated application restore.

### Unsafe history marker

A site sets a permanent `historyIntegrity` marker in its own manifest when it
finds a replication or binlog filter, `binlog_format` other than `ROW`,
`binlog_row_image` other than `FULL`, or `replica_preserve_commit_order`
off. From then on it uploads nothing, its `lastError` starts
`PITRArchiveUnsafeHistory: <site> <violation> <detail>`, and the group shows
`PITRArchiveReady=False` / `ArchiveUnsafeHistory`. Binlogs written while the
setting was in force cannot certify history, so no repair command clears the
marker, and removing the setting does not either. The marker removes every
restore target that needs that site's bytes, including targets before the
violation; the new prefix restores only targets after it. The operator emits
a Warning `PITRArchiveUnsafeHistoryDetected` when a site reports the marker.

1. Undo the change. While PITR is enabled the operator refuses these
   options in `spec.mysqlConf` (condition `PITRMysqlConfAccepted=False`,
   Warning `PITRMysqlConfRefused`) and owns `replica-preserve-commit-order`,
   so a marker comes from an out-of-band change: `SET GLOBAL`, a hand-edited
   my.cnf. Remove any refused key from `spec.mysqlConf` too.
2. Point `spec.backup.pitr` at a new prefix (or a new profile) and wait for
   the rollout.
3. Take and verify a full backup in the new archive. Keep the old prefix with
   its backups and passphrase as evidence; do not delete the marked manifest.

### Reissue risk

A server reissues GTIDs when it lost transactions it had issued and still
has the `server_uuid` it issued them under: its next write takes the lowest
free number of that `server_uuid`, which the archive already holds for
another transaction. Once the reissued transactions are archived, the site's
archiver verifies the reuse and every restore from the archive refuses
`PITRArchiveHistoryReset`, and neither quarantine nor acknowledgement clears
it.

A clone gives its recipient a new `server_uuid`
([Server identity after a clone](/docs/operations/operations#server-identity-after-a-clone)),
so a site recloned after a lossy failover cannot reissue what it lost: its
divergent rows are [evidence only](#distinguish-divergence-re-logging-and-gtid-reuse).
The risk remains for:

- a data directory restored from a snapshot or reset in place
  (`RESET BINARY LOGS AND GTIDS`), which keeps `auto.cnf`;
- a site cloned by a release that kept the recipient's `server_uuid`, or
  whose clone reported Warning `CloneServerUUIDNotRotated`.

The sidecar reports it before anything is reissued. `reissuableGtids` in the
site's `/archiver/status` lists the archived transactions (of divergent and
quarantined rows) that its server no longer has and could issue again,
`lastError` carries them with the row, and `PITRArchiveReady` is `False` /
`ArchiverError`:

```text
site iad: server_uuid <uuid> no longer has archived transactions <uuid>:9-10
that it issued (row mysql-bin.000002 id <id>) and reuses their GTIDs when it
writes; once the reused GTIDs are archived, every restore from this archive
refuses PITRArchiveHistoryReset. Reclone this site before it is promoted (a
clone starts with a new server_uuid); if it is already the primary, start a
new archive prefix and take a full backup
```

**While the site is a replica**, reclone it
(`kubectl bloodraven reclone <group> <site>`). The clone starts with a new
`server_uuid`, the next audit reports `reissuableGtids` empty, and the error
clears; the divergent row stays as evidence. If the reclone reports
`CloneServerUUIDNotRotated`, fix what that Event names and reclone again.
Quarantining the row does not help: the server can still reissue its
transactions.

**When such a site is promoted**, the active site changes (failover, planned
failover or re-promotion, also after a `NoPrimary` interval on a group that
has failed over before) and the operator emits:

```text
Warning PITRArchiveReissueRiskDetected  site <s> was promoted while its archive holds
transactions its server no longer has and issued under the server_uuid it still has:
<set>. Its new writes reuse those GTIDs, and once they are archived every restore
from this archive refuses PITRArchiveHistoryReset. Start a new archive prefix and
take a full backup.
```

The Warning fires only for a site whose last archiver status reports a
non-empty `reissuableGtids`. Divergent or quarantined rows of a server with
another `server_uuid` do not fire it. When the site's sidecar has reported
no verdict (a sidecar image that predates the field, or one whose audit has
not evaluated its server yet), the operator falls back to the row counts and
says so: `... holds N divergent/quarantined rows, and its sidecar has not
reported whether its server can reissue their GTIDs ...`. Then read
`reissuableGtids` from the site (`sidecar-probe.sh <group> archiver`) and act
only if it is not empty.

After the Warning, act at once:

1. Point `spec.backup.pitr` at a new prefix and wait for the rollout.
2. Take and verify a full backup in the new archive.
3. Keep the old prefix and its backups.

The old prefix stays usable for targets before the reissue only if no
reissued GTID reached it. Once the promoted site archives one there, its
archiver verifies the reuse and persists a reset epoch (`resetReason`), and
from then on every restore from that prefix refuses `PITRArchiveHistoryReset`,
targets before the reissue included. The rollout to the new prefix is
therefore urgent: the promoted site keeps uploading into the old prefix
until its pod rolls. If the old prefix was reset, point-in-time restores from
it need a copy of the archive's manifests from before the reset (bucket
versioning, or a copy of the prefix taken earlier); the retained dumps still
restore without `pointInTime`.
