---
title: Repair PITR history safely
description: Resolve missing or divergent archived files without deleting recovery evidence.
---

Use this procedure when the archiver or downloader reports a missing object,
a divergent boundary, or GTID namespace reuse. A zero backlog means local
uploads caught up; it does not prove that historical recovery is complete.

### Preserve the evidence and choose a baseline

1. Preserve the site's manifest, all archive objects, the original passphrase,
   and any surviving local binlogs. Record the error's site, name, ID,
   predecessor set and missing transaction set. `/archiver/status.lastError`
   and increases in `bloodraven_archiver_upload_failures` expose history
   problems before restore. Do not clear the manifest or overwrite objects.
2. Choose the canonical live dataset with your incident owner. Take and verify
   a new full backup of that dataset. Record its pre-dump `status.gtidExecuted`.
   Quarantine cannot reconstruct lost transactions. Only windows that need
   the excluded row require its canonical backup bound; earlier windows
   proven to stop before that row remain available.
3. Pause PITR writers through your maintenance rollout and wait for the old
   sidecar processes to stop. Keep MySQL data and archive volumes intact.
   This prevents a concurrent manifest write from undoing the maintenance edit.

### Restore bytes or quarantine one row

If an original object can be recovered, restore those exact bytes at its
original key, using the original encryption settings. When a missing legacy
row has a verified `contentId` matching surviving local bytes, the archiver
can publish the ID-aware object and atomically replace the dead legacy row.
Without that digest, equal names, sizes and headers do not prove replacement.

For an unrecoverable file or an abandoned divergent tail, run the matching
operator image's `pitr-quarantine` command in a maintenance Pod with the same
archive environment, writable archive PVC/S3 credentials and mounted
passphrase Secret as the writer. Use the exact storage prefix. For example,
this plaintext PVC maintenance Pod moves one legacy manifest row and preserves
its object; replace all example values before applying it:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pitr-quarantine
spec:
  restartPolicy: Never
  securityContext:
    fsGroup: 65532 # reuse the archive writer's actual fsGroup
  containers:
    - name: quarantine
      image: your-registry/bloodraven:matching-version
      args:
        - pitr-quarantine
        - --site=iad
        - --name=mysql-bin.000004
        - --id=legacy
        - --reason=Object lost before identity verification; canonical backup verified
        - --resume-gtids=aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee:1-200
        - --confirm
      env:
        - {name: BLOODRAVEN_PITR_STORAGE_TYPE, value: PVC}
        - {name: BLOODRAVEN_PITR_MANIFEST_PREFIX, value: orders/binlogs}
        - {name: BLOODRAVEN_PITR_PVC_MOUNT_PATH, value: /archive}
      volumeMounts:
        - {name: archive, mountPath: /archive}
  volumes:
    - name: archive
      persistentVolumeClaim:
        claimName: your-existing-backup-pvc
```

For ID-aware rows, pass the complete 64-character archive ID instead of
`legacy`. For encrypted archives, also mount the existing passphrase Secret
read-only and set `BLOODRAVEN_PITR_PASSPHRASE_FILE` to its mounted file. S3
uses the existing `BLOODRAVEN_PITR_S3_*` and `BLOODRAVEN_PITR_AWS_CREDS_DIR`
configuration. Never pass Secret bytes as command arguments.

The command writes a `quarantined` record containing the original row, reason,
time and required resume GTIDs. It never calls object deletion. The downloader
logs `quarantined binlog excluded` at Warn when
`BLOODRAVEN_PITR_START_GTIDS` covers the recorded resume bound. This exclusion
works even if the quarantined object is missing or corrupt. Restore and
verification Jobs supply the source backup's known pre-dump bound; unknown/raw
sources require an explicitly trustworthy bound. A backup below that bound
can still restore a window proven to end before the row, or whose verified
transactions are already in the backup. A window that needs the excluded
row fails instead of silently skipping the gap. Ambiguous placement also fails.

After recovering an original object, the same command with the exact site,
name and ID plus `--undo --confirm` restores the row. Preserve the manifest
copy as your incident record. Resume PITR writers, inspect status, and verify
an isolated restore with application markers across the repaired boundary.

### Distinguish divergence, re-logging and GTID reuse

The auditor records `divergent` identities when archived GTIDs are absent
from a server that has established its history. Empty execution, a running
clone, and a read-only server without a replication channel supply no
negative evidence during bootstrap. Every eligible audit recomputes the
missing sets; a recovered foreign-source set can clear contradicted flags
and their status error. Known loss from the current server UUID remains
unresolved when its numbers return: replacement transactions may still be
in the active, unarchived binlog. Preserve the flag until recovery is verified
or a canonical recovery is explicitly acknowledged; quarantine an abandoned
tail promptly. Rotation alone does not prove original issuance. A restore refuses a window containing transactions from a flagged
row, including the last row and aliases discovered during download. A flag
does not block an unrelated earlier window or verified lower-cut rows.

A verified reuse guard requires overlapping GTIDs of the same source server UUID
with different archived content identities and different original commit or
transaction-query identities. Re-logging may change file framing and immediate
commit time while preserving original issuance. Smaller names, out-of-order
uploads, identical-byte retries and a transient GET are not reset evidence.
Unknown origins never create a reuse guard or authorize overlapping generations.
Legacy rows without bound coverage are inspected in bounded batches even
when retention is disabled. One worker drains a large stream; foreground
rotations run first, failed inspections cool down for an hour, and restart
reconstructs pending work from the manifest. Retirement waits for unresolved
issuance checks. Downloads independently verify overlapping observed GTIDs
before applying numeric backup cuts; unavailable or incomplete issuance
proof fails loudly. Original commit/query evidence distinguishes actual
reuse from a recovered execution set.

Quarantine preserves conflict and divergence evidence; undo restores the
row and its divergence protection. A verified namespace-reuse guard remains
even after quarantine: GTID containment alone cannot identify the right backup
generation once numbers were reused. Start a new prefix/full backup for that
case; acknowledgement only recovers obsolete guards without verified reuse.

For a real `RESET BINARY LOGS AND GTIDS`, prefer a new archive generation and
full backup. Set the selected profile's
`spec.backup.profiles[name].storage.s3.prefix` (S3), or
`spec.backup.profiles[name].storage.pvc.subPath` (PVC), to a new unused location;
these are paths inside the existing named profile, not literal map keys.
The archiver appends `binlogs/` there. Alternatively create a new profile and
select it with `spec.backup.pitr.profileName`. Wait for the rollout and take
and verify a full backup in that generation. Keep older backups paired with
their original generation; identical GTID numbers do not make a pre-reset
backup compatible with a post-reset dataset.

### Recover an obsolete guard behind a canonical full backup

Older versions could set `epoch.resetReason` from upload order alone. It is
recoverable without deleting objects or discarding valid earlier windows.
After preserving evidence, verifying a canonical full backup and stopping
writers as above, use the same maintenance Pod/storage configuration with:

```text
bloodraven pitr-quarantine --site=iad --acknowledge-history \
  --reason='Canonical full backup verified; obsolete upload-order guard' \
  --resume-gtids='aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee:1-200' --confirm
```

This streams and identity-verifies every active archived file and requires
its observed execution frontier to be covered by the canonical backup bound.
Any verified namespace-reuse evidence, or missing, corrupt or uncovered
history, refuses acknowledgement; first recover
those exact objects or explicitly quarantine the unresolved rows. No objects
are deleted or overwritten. The manifest records the reason, time, verification
bound and prior guard reason, then supersedes the obsolete guard and
divergence markers. Verification also compares overlapping issuance, including
legacy streams whose conflicting evidence has not yet been recorded.
Acknowledgement removes no rows and adds no global backup cutoff; older
backups still undergo normal replay, divergence and generation checks.
Quarantined rows retain their own bounds. Verified reuse cannot be cleared
by acknowledgement or quarantine. Resume writers, inspect status and verify
an isolated application restore.
