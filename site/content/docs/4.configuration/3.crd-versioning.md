title: CRD versioning and migration
---

![crd versioning infographic](/img/infographics/crd-versioning.webp)

Bloodraven's API is `shipstream.io/v1beta1` from v1.8.0 on. This page is
the contract for that version: what can change, how the two served
versions relate, how stored objects move to a new storage version, and
what must be true before `v1`.

## Served versions

Every Bloodraven CRD serves two versions with **one schema**:

| Version | Served | Stored | Status |
|---|---|---|---|
| `shipstream.io/v1beta1` | yes | yes | The version the operator, the kubectl plugin and the docs use. |
| `shipstream.io/v1alpha1` | yes | no | Deprecated. The API server answers requests through it with a deprecation warning. It is removed in the next minor release. |

The five kinds are `MysqlFailoverGroup`, `MysqlDatabase`, `MysqlBackup`,
`MysqlBackupVerification` and `MysqlStandbyCluster`.

Because the two schemas are identical, an object written through one
version reads the same through the other: spec, status, defaults and
validation. Manifests written for v1.7.0 keep working when you change
their `apiVersion` line to `shipstream.io/v1beta1`, and keep working
unchanged until `v1alpha1` is removed.

The breaking changes of the alpha API all landed in v1.7.0, before the
promotion. They are listed in
[Upgrading from v1.6.0](/docs/operations/upgrade-policy#upgrading-from-v160-to-v170).

## What v1beta1 promises

| Change type | Policy |
|---|---|
| Add an optional spec field | Allowed in any minor release. It is added to every served version. |
| Add a status field | Allowed in any minor release. |
| Rename or remove a spec field | Add the replacement first and support both through at least one minor release. Remove the old field only in a new API version. |
| Remove an enum value | Deprecate it in the docs and with an Event first. Reject new usage only after one minor release. |
| Tighten a validation rule | Stored objects that break the new rule keep working: the API server does not apply a tightened rule to a field an update leaves alone. The release notes name the rule. |
| Change a default | Treated as breaking unless the old behavior is unsafe. Requires a release-note callout and migration guidance. |
| Change a condition reason, an Event reason, a well-known key, a metric label or a documented log message | Treated like a field: additions are allowed, and a change or removal needs a deprecation window. Update [Log schema](/docs/observability/log-schema) and the release notes in the same change. |

Status fields are observations and records the operator owns. Do not
write them by hand, except where a runbook says so.

## Destructive operations need a confirmation

An operation that destroys data is never triggered by a field that a
re-applied manifest could set again by accident. Bloodraven uses two
patterns, and a new destructive operation must use one of them:

- **A one-shot action annotation.** The value names the target and
  carries a confirmation, for example the group's name and UID for a
  reclone. The operator consumes the annotation. See
  [Well-known metadata](/docs/configuration/well-known-metadata).
- **A monotonic token in the spec.** `spec.restoreInPlace.confirm` is an
  RFC 3339 timestamp. A restore runs only when the token is newer than
  the last one used (`status.restoreInPlace.confirmTokenUsed`), so
  applying the same manifest again does nothing.

Both are enforced the same way through every served version.

## Conversion strategy: none

The CRDs use conversion strategy `None`. The API server converts between
`v1alpha1` and `v1beta1` by rewriting the `apiVersion` field and nothing
else. There is no conversion webhook, so there is no webhook Service,
certificate or extra component on the path of every API read.

This works only while the served versions have identical schemas. A test
in the repository fails on the first difference between them. From that
point a conversion webhook is required before the change can ship, with
its chart Service, CA injection and tests. A field added after the
promotion is therefore added to every served version at once.

## Storage-version migration

Kubernetes stores each object at one version, the storage version. After
an upgrade that changes it, the objects created before the upgrade are
still encoded at the old version until something writes them again. Each
CRD records the versions that may still be in storage in
`status.storedVersions`:

```bash
kubectl get crd mysqlfailovergroups.shipstream.io \
  -o jsonpath='{.status.storedVersions}{"\n"}'
```

After the upgrade to v1.8.0 this prints `["v1alpha1","v1beta1"]`. The
API server refuses a CRD that drops a version listed there, so
`v1alpha1` cannot be removed until every object is rewritten and the
list is `["v1beta1"]`. `kubectl bloodraven migrate-storage` does both.

### Run the migration

Run it once, after the CRDs of the new release are applied and the new
operator is running. It works on every namespace.

1. Back up the objects. This is a copy of the Kubernetes objects, not a
   MySQL backup:

   ```bash
   for kind in mysqlfailovergroups mysqldatabases mysqlbackups \
       mysqlbackupverifications mysqlstandbyclusters; do
     kubectl get "$kind.shipstream.io" -A -o yaml > "bloodraven-$kind.yaml"
   done
   ```

2. Give the account that runs the command the permissions it needs. The
   operator does not hold them. The repository ships a ClusterRole with
   exactly these permissions,
   [`examples/storage-migrator-clusterrole.yaml`](https://github.com/ShipStream/bloodraven/blob/main/examples/storage-migrator-clusterrole.yaml):

   ```bash
   kubectl apply -f examples/storage-migrator-clusterrole.yaml
   kubectl create clusterrolebinding bloodraven-storage-migrator \
     --clusterrole=bloodraven-storage-migrator --user=ACCOUNT
   ```

3. Check what the migration would do:

   ```bash
   kubectl bloodraven migrate-storage --dry-run
   ```

4. Run it:

   ```bash
   kubectl bloodraven migrate-storage
   ```

   The last line of the report is
   `Done. Every Bloodraven object is stored as shipstream.io/v1beta1.`

5. Confirm that every CRD lists one stored version, then remove the
   binding:

   ```bash
   kubectl get crd -o custom-columns=NAME:.metadata.name,STORED:.status.storedVersions \
     | grep shipstream.io
   kubectl delete clusterrolebinding bloodraven-storage-migrator
   ```

### What the command does

| Step | What it checks or does | If it fails |
|---|---|---|
| 1. Permissions | Asks the API server whether the account may `get`, `list` and `patch` the five kinds, `get` their CRDs and `update` `customresourcedefinitions/status`. | Lists the missing permissions and stops. Nothing is read in bulk or written. |
| 2. CRDs | Every CRD is installed and stores `v1beta1`. | Stops: apply the release's CRDs first, and use the plugin of that release. |
| 3. Objects | Validates every object of the five kinds against the installed schema, as a new object would be validated. | Lists each object that does not conform and stops. Nothing is written. |
| 4. Rewrite | Writes each object back unchanged, as an empty patch the API server applies to the object it holds. The API server stores it at `v1beta1`. | The operator's status updates do not make the write fail: the patch carries no `resourceVersion`, so the API server applies it to the current object. A write that still conflicts is retried; an object that keeps changing is reported as such; run the command again. |
| 5. Stored versions | Sets `status.storedVersions` to `["v1beta1"]` for each kind whose objects were all rewritten. | The kind keeps its old list. Run the command again. |

The command never deletes or recreates an object, never changes a spec,
and does not touch MySQL. The operator keeps running during it. Running
it again is safe: a kind that is already migrated is skipped.

### Objects that do not conform

Step 3 exists because the API server does not validate what it already
stores. An object stored by a release with a different schema (v1.6.0 or
earlier) is read with its old field names dropped, and a plain update of
it succeeds: the API server accepts schema errors on fields an update
does not change. Rewriting such an object would make the loss permanent.

If the command lists objects that do not conform, do not edit them into
shape and do not delete them. An object from v1.6.0 cannot be upgraded
in place; follow
[Upgrading from v1.6.0](/docs/operations/upgrade-policy#upgrading-from-v160-to-v170).
The operator makes the same check when it starts and refuses to run
against such objects; see
[The operator's check at start](/docs/operations/upgrade-policy#the-operators-check-at-start).

### There is no way back to older CRDs

`status.storedVersions` gains `v1beta1` the moment the v1.8.0 CRDs are
applied, before any object is written. The API server then refuses a CRD
that does not list `v1beta1`, so the v1.7.0 CRDs cannot be re-applied.
Rolling back the operator alone is possible, because v1.7.0 talks
`v1alpha1`, which stays served. See
[Rolling back](/docs/operations/upgrade-policy#rolling-back-after-the-v180-upgrade).

Never remove a version from `status.storedVersions` by hand.

## Before v1alpha1 is removed

The release that removes `v1alpha1` from the CRDs requires, on every
cluster:

- `status.storedVersions` is `["v1beta1"]` for all five CRDs. Otherwise
  the API server refuses the new CRDs.
- Every manifest, pipeline, script and client uses
  `shipstream.io/v1beta1`. The API server's deprecation warnings on
  `v1alpha1` requests show what still does not: `kubectl` prints them,
  and the API server counts them in
  `apiserver_requested_deprecated_apis`.

## Promotion criteria for v1

Move to `v1` only after `v1beta1` has survived real upgrades and the
following contract is acceptable:

- No breaking spec-field removals within `v1`.
- Additive spec fields are allowed.
- Status fields may grow additively; existing documented status fields
  keep their meaning.
- Enum values are not removed without a deprecation window.
- Defaults do not change in a way that causes existing manifests to
  reconcile into different data-plane behavior.
- Destructive operations remain gated by one of the two confirmation
  patterns above.

## Release-note requirements

Every release that changes the CRD schema must include:

- A list of added, changed, deprecated, and removed fields.
- Whether the storage version changes and `migrate-storage` must be run.
- Any validation rule that was tightened.
- A `kubectl apply --server-side --dry-run=server` command users can run
  against representative manifests.
- Any data-plane behavior change caused by new defaults.

## How the contract is tested

| What is tested | Where |
|---|---|
| Both served versions have the same schema, printer columns and subresources, and each CRD stays under 900 KB with both. | `internal/crdcompat` (`TestServedVersionsShareOneSchema`, `TestCRDsFitTheRequestLimit`) |
| One real object per kind, as v1.7.0 stored it with its status, decodes into the current types and conforms to the current schema. | `test/fixtures/v1alpha1`, `TestV170FixturesFitThisBuild` |
| Spec and status written through one version read the same through the other, and confirmations and immutability rules hold through both. | `test/envtest/served_versions_test.go` |
| Every example passes a server-side dry run with strict field validation at both versions. | `TestExamplesPassServerSideDryRun` |
| `migrate-storage` on v1.7.0's objects, with only the example ClusterRole, beside a concurrent status writer; and its refusal of v1.6.0's objects. | `test/envtest/storage_migration_test.go` |
| The operator's check at start refuses older CRDs and objects that do not fit, and only warns on newer CRDs. | `test/envtest/storage_migration_test.go` |
| The published v1.7.0 is installed with one object of every kind, upgraded to the build, migrated, and failed over. | The `upgrade` E2E job (scenarios 74, 78 and 01) |

## What not to do

- Do not silently change field meaning while keeping the same name.
- Do not install a CRD version that the running operator cannot
  reconcile.
- Do not add a field to one served version only.
- Do not remove a served version while `status.storedVersions` lists it.
- Do not rely on Helm for either step: Helm does not upgrade a chart's
  `crds/`, and it does not rewrite existing objects.
