## `MysqlFailoverGroup`

Complete reference for the `MysqlFailoverGroup` custom resource (`shipstream.io/v1alpha1`).

| Field | Use most often for | Guide |
|---|---|---|
| `spec.sites` | Site topology, placement, storage, LB IPs | [Placement Contract](/docs/configuration/placement-contract) |
| `spec.credentials` | Per-role MySQL users | [Credentials And TLS](/docs/configuration/credentials-and-tls) |

| `spec.backup` | Backup profiles, schedules, PITR | [Backup Overview](/docs/backup-and-restore/backup-overview) |
| `spec.initFromBackup` | Bootstrap restore into a new group | [Backup And Restore](/docs/backup-and-restore/backup-restore) |

| `spec.dragonfly` | Optional Dragonfly cache/session co-management | [App Integration](/docs/configuration/app-integration#connection-endpoints) |

::caution
**Destructive and high-risk fields**


Review runbooks before changing `spec.restoreInPlace`, restore-related `confirm` tokens, reclone controls, and any field that changes `spec.sites`, `spec.credentials`, `spec.tls`, or MySQL images. Restore and reclone operations can replace data; image and credential changes can trigger restarts or failed reconnects.
::
## Spec

Set it only to pin a specific image; a pin tagged with another release than the operator gets a `SidecarVersionSkew` Warning. No value is persisted when it is omitted. |

### Timers

Every timer in the spec is a duration string (`30s`, `5m`, `1h`) with a lower
and an upper bound checked at admission (`must be between <min> and <max>`),
so a zero or a value Go's `time.Duration` cannot hold is refused instead of
being rewritten to a default. Integer `...Seconds` fields remain only where the
value is passed verbatim to a Kubernetes field (`activeDeadlineSeconds`,
`startingDeadlineSeconds`, `terminationGracePeriodSeconds`,
`ttlSecondsAfterFinished`) or compared with a MySQL or DNS value in seconds
(`maxLagSeconds`, `readOnlyMaxLagSeconds`, `maxLagSecondsForSource`,
`dns.ttlSeconds`).

| Field | Default | Bounds |
|---|---|---|
| `pollInterval` | `2s` | `1s`..`5m` |
| `connectionDrainTimeout` | `30s` | `1s`..`10m` |
| `failoverCooldown` | `5m` | `30s`..`24h` |
| `cloneTimeout` | `1h` | `1m`..`24h` |
| `sidecar.peerCheckInterval` | `5s` | `1s`..`1m` |
| `sidecar.leaseTimeout` | `20s` | `3s`..`10m`, and at least 3× `peerCheckInterval` |
| `backup.pitr.archivePollInterval` | `60s` | `5s`..`1h` |
| `backup.retry.initialBackoff` | `1m` | `1s`..`1h` |
| `backup.retry.maxBackoff` | `30m` | `1s`..`24h`, and at least `initialBackoff` |
| `encryptionAtRest.keyring.escrowTimeout` | `10m` | `30s`..`1h` |
| `plannedFailover.maxLagWait` (and the `planned-failover` annotation's `maxLagWait=`) | `5m` | `1s`..`1h` |
| `plannedFailover.drainTimeout` | `30s` | `1s`..`10m` |
| `dragonfly.plannedFailover.maxSyncWait` | `30s` | `1s`..`10m` |
| `MysqlBackupVerification.spec.sanityCheck.timeout` (and a profile's `verification.sanityCheck.timeout`) | `60s` | `1s`..`1h` |
| `MysqlStandbyCluster.spec.freshness.discoveryInterval` | `5m` | `30s`..`24h` |

The CRDs store each default in Go's spelling (`5m0s`, `1h0m0s`), the form the
operator writes back, so a stored object does not change on the operator's
first update. `status.plannedFailover.settings` holds the effective timers a
run was accepted with; the operator writes it from these bounded inputs and it
carries no bounds of its own.

### SiteSpec

Each entry in `spec.sites` defines one site in the failover group.

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `name` | string | Yes | -- | Unique site identifier (e.g. `iad`, `pdx`), the key of `spec.sites`. Used in Service names, labels, and PITR archive keys. Lowercase letters, digits, and `-` only (`^[a-z0-9-]+$`). MaxLength=253. |
| `serverID` | integer | Yes | -- | The site's MySQL `server_id`, 1 to 4294967295. Unique within the group and immutable: it identifies the server in binary logs, the PITR archive's promotion records and backup stamps, so it does not follow the site's position in `spec.sites`. The examples use `101`, `102`, ... in declaration order. |
| `role` | string | No | `PrimaryCandidate` | `PrimaryCandidate` can be promoted; `DisasterRecovery` and `ReadOnly` are never promoted. A reader provides a health-gated site-specific read pool. At least two `PrimaryCandidate` sites are required. |
| `zone` | string | Yes | -- | Availability zone or region for pod scheduling |
| `taintNodeSelector` | map[string]string | Conditional | -- | Required and non-empty for `PrimaryCandidate` and `DisasterRecovery`; optional for `ReadOnly`. Selects nodes that receive this group's `db-readonly` taint. Accepted but ignored on readers, which never cause taint operations. |
| `lbIP` | string | Conditional | -- | Required and non-empty for `PrimaryCandidate` and `DisasterRecovery`; optional for `ReadOnly`. Used for active-primary DNS steering. Accepted but ignored on readers, which are never DNS targets. |
| `storage` | StorageSpec | Yes | -- | Persistent storage configuration for this site |
| `resources` | ResourceRequirements | No | -- | Compute resources (requests/limits) for the MySQL container at this site |
| `mysqlConf` | map[string]string | No | -- | Site-specific MySQL options applied after normalized group overrides, with the same key and value rules. Changing this map rolls only affected sites unless other drift is pending. |
| `serviceTemplate` | SiteServiceTemplate | No | -- | Scalar and annotation overrides for this site's client-facing MySQL Service. Does not affect sibling, primary, replicas, or internal Services. |

Reader manifests may retain legacy `lbIP` and `taintNodeSelector` values for
compatibility, but Bloodraven ignores them. Changing a reader to
`PrimaryCandidate` or `DisasterRecovery` is rejected until both fields are present.
A reader does not satisfy the two-candidate minimum and cannot appear in
`splitBrainPolicy.sitePriorities`.

### Admission combinations

| Combination | Admitted? |
|---|---|
| Two `PrimaryCandidate` sites, each with non-empty `lbIP` and `taintNodeSelector` | Yes |
| Two candidates plus a reader with both placement fields omitted | Yes |
| Reader with either or both legacy placement fields supplied | Yes; supplied values are ignored |
| Omitted/default role, explicit candidate, or `DisasterRecovery` with either placement field omitted | No |
| Fewer than two candidates, or a reader/DR site in `sitePriorities` | No |
| `externalTrafficPolicy` on an effective `ClusterIP` Service | No |
| Site `nodePort` on an effective `ClusterIP` Service | No |
| ETP on `NodePort`/`LoadBalancer`, or site NodePort in 1-65535 on those types | Yes; Kubernetes then applies its cluster-specific NodePort range |

### SplitBrainPolicySpec

Opt-in configuration for how the operator should behave when more than
one site is simultaneously writable and the operator cannot infer a
winner from prior failover history. See
[Split-brain resolution](/docs/operations/failover#split-brain-resolution) for a
full description of semantics and tradeoffs.

| Field | Type | Required | Description |
|---|---|---|---|
| `sitePriorities` | []string | No | Ordered list of `PrimaryCandidate` site names. The operator walks the list and promotes the first entry that is currently writable; every other writable site is fenced. Empty or unset falls back to manual resolution (alert only). MaxItems=16. Entries must be unique and must reference sites with role `PrimaryCandidate`. |

### SiteServiceTemplate (`spec.sites[].serviceTemplate`)

| Field | Type | Required | Description |
|---|---|---|---|
| `type` | string | No | Site Service override: `ClusterIP`, `LoadBalancer`, or `NodePort`. Omitted inherits the group type. |
| `externalTrafficPolicy` | string | No | Site override: `Cluster` or `Local`. Legal only when the effective site type is `NodePort` or `LoadBalancer`. |

never exposed through a client Service or assigned a NodePort.

### CredentialsSpec

`credentials` is required. The operator manages MySQL users on the primary — creating them during first boot via an init script and updating passwords via `ALTER USER` when the referenced Secrets change.

| Field | Type | Required | Description |
|---|---|---|---|
| `operatorSecretName` | string | Yes | Secret for operator and sidecar connections. Required keys: `username`, `password`, `MYSQL_ROOT_PASSWORD`. Optional: `MYSQL_REPLICATION_USER`, `MYSQL_REPLICATION_PASSWORD` (default to operator credentials). Grants: `ALL PRIVILEGES WITH GRANT OPTION`. |
| `appSecretName` | string | No | Secret for application read-write connections. Keys: `username`, `password`. Grants on `*.*`: data and schema privileges (DML, DDL, views, routines, triggers, events, temporary tables, `LOCK TABLES`, `SHOW DATABASES`). No `GRANT OPTION`, `SUPER`, `CREATE USER`, or other administrative privileges. |
| `readOnlySecretName` | string | No | Secret for application read-only connections. Keys: `username`, `password`. Grants: `SELECT`, `SHOW VIEW`, `SHOW DATABASES`, `PROCESS`. |
| `monitorSecretName` | string | No | Secret for Prometheus exporter connections. Keys: `username`, `password`. Grants: `PROCESS`, `REPLICATION CLIENT`, `SELECT` on `performance_schema`. |
| `backupSecretName` | string | No | Secret for backup connections (restore Jobs run as the operator account). Keys: `username`, `password`. Grants: `SELECT`, `LOCK TABLES`, `SHOW VIEW`, `EVENT`, `TRIGGER`, `RELOAD`, `BACKUP_ADMIN`, `REPLICATION CLIENT`. |

Secret references follow one convention across the five kinds: a field
that names a whole Secret ends in `SecretName` and is a string; a field
that selects one key of a Secret ends in `SecretKeyRef` and is a
`{name, key}` object. Every Secret name is a DNS subdomain of at most 253
characters, and every key is at most 253 characters of `[-._a-zA-Z0-9]`.

the field disables backups for this failover group.

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `image` | string | No | `container-registry.oracle.com/mysql/community-server:9.7` | Image containing `mysqlsh` used for dump / load. |
| `imagePullSecrets` | []LocalObjectReference | No | -- | Pull secrets for the backup image. A list-map keyed by `name`, at most 16 entries. |
| `profiles` | []BackupProfile | No | -- | Reusable named backup configurations referenced by schedules and `MysqlBackup` CRs. A list-map keyed by `name` (`x-kubernetes-list-type: map`): names must be unique, and server-side apply merges entries by name, so two field managers can each own a profile. At most 32 entries. |
| `schedules` | []BackupSchedule | No | -- | Cron-driven recurring backups; each references a profile by name. Each entry becomes a Kubernetes CronJob owned by this failover group. A list-map keyed by `name` (names at most 63 characters), at most 32 entries. |
| `maxLagSecondsForSource` | int | No | `300` | Threshold above which the backup reconciler falls back from replica-first source selection to the primary. `0` uses a replica only when it reports zero lag. |
| `resources` | ResourceRequirements | No | -- | Resources for the backup Job's mysqlsh container. |
| `activeDeadlineSeconds` | int | No | `7200` | Wall-clock cap on a single backup Job. |
| `backoffLimit` | int | No | `2` | Job-level backoffLimit applied to backup Jobs. `0` runs each Job's pod once. |
| `retry` | BackupRetrySpec | No | -- | Operator-level retries for Failed scheduled MysqlBackup CRs: `maxAttempts` (default `1`, 1 to 10, including the original), `initialBackoff` (default `1m`, `1s` to `1h`) and `maxBackoff` (default `30m`, `1s` to `24h`, at least `initialBackoff`). Independent of Job `backoffLimit`. |
| `pitr` | PITRSpec | No | -- | Continuous binlog archival for point-in-time recovery. |
| `podSecurityContext` | PodSecurityContext | No | -- | Overrides default hardened pod security context merged onto the defaults. |
| `containerSecurityContext` | SecurityContext | No | -- | Overrides default hardened container security context. |
| `stagingVolumeSizeLimit` | Quantity | No | -- | Cap on the plaintext-staging `emptyDir` used by backup / restore / verify Jobs. Unset falls through to the node's ephemeral-storage limit; set on shared clusters to keep a large dump from triggering `DiskPressure` (AUDIT H6). |

### BackupProfile (`spec.backup.profiles[]`)

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `name` | string | Yes | -- | Profile identifier, `[a-z0-9]([-a-z0-9]*[a-z0-9])?`, at most 63 characters. |
| `storage` | BackupStorage | Yes | -- | Tagged union: `type: S3` + `s3` block, or `type: PVC` + `pvc` block. `s3.prefix` (here, in `initFromBackup`/`restoreInPlace` S3 sources and in a standby's source) is at most 512 characters; empty segments (`a//b`) and `.` or `..` segments are refused at admission, and a leading or trailing `/` is allowed and ignored. Backups land under `<prefix>/<mysqlbackup-name>/` and the PITR archive under `<prefix>/binlogs/`. |
| `dump` | DumpOptions | No | -- | `util.dumpInstance()` tuning (threads, chunk size, compression, schema filters, consistent locking, OCIMDS checks). |
| `retention` | BackupRetention | No | `{}` | Which of this profile's MysqlBackup CRs are kept: `keepLast`, `keepWithinDays`, `keepFailed`. See [BackupRetention](#backupretention). |
| `verification` | VerificationSpec | No | -- | Opt-in periodic restore-of-this-profile's-latest-backup into a throwaway MySQL instance; renders a CronJob when `enabled: true`. Its `retention` (`keepLast`, default `30`; `keepFailed`, default `10`; `0` keeps none) caps the profile's Succeeded and Failed MysqlBackupVerification CRs. |
| `encryption` | BackupEncryptionSpec | No | -- | Enables client-side envelope encryption (AES-256-GCM + HKDF-SHA256) for every dump file and, when this profile is also used for PITR, every archived binlog. The passphrase is yours: the operator never generates it. It snapshots the bytes into immutable operator-made Secrets (one per accepted PITR archive key, one per backup), so pods never read your Secret directly. Changing the encryption or the bytes of a profile whose archive is in use is refused (at admission while PITR is enabled, otherwise on the `PITRArchiveBindingReady` condition); each backup's dumps use that backup's own snapshot. See [Backup encryption](/docs/backup-and-restore/backup-encryption). |

**Bounds.** `s3.bucket` is at most 63 characters, `s3.endpointURL` and
`s3.prefix` at most 512, `pvc.claimName` at most 253 and `pvc.subPath` at
most 512. They are bounded in UTF-8 bytes as well as characters (CEL
`bytes(self).size()`), at 63, 512, 512, 253 and 512 bytes, with messages such
as "bucket must be at most 63 bytes (UTF-8)" and "prefix must be at most 512
bytes (UTF-8)". They keep the admission rule on the `MysqlFailoverGroup` root
within the API server's CEL cost budget.

### PassphraseSecretKeyRef

Reused by `BackupEncryptionSpec`, `BackupDecryptionSpec`,
`spec.initFromBackup.decryption`, `spec.restoreInPlace.decryption`, and the
`MysqlStandbyCluster` `source.decryption`; the bounds below apply to all of
them.

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `name` | string | Yes | -- | Name of the Secret, a DNS subdomain of at most 253 characters. |
| `key` | string | No | `passphrase` | Key within the Secret that holds the passphrase bytes, at most 253 characters of `[-._a-zA-Z0-9]`. Leading and trailing `\n`, `\r`, space and tab are stripped when the passphrase is read; other whitespace is part of the key. |

For a backup profile, the operator snapshots the passphrase (see
[Key snapshots](/docs/backup-and-restore/backup-encryption#key-snapshots));
a byte change on a profile whose PITR archive is in use is refused, and each
backup's dumps use that backup's own dump-key snapshot.

### BackupDecryptionSpec

Used on `spec.initFromBackup.decryption` and
`spec.restoreInPlace.decryption` to supply the passphrase that decrypts
an encrypted backup. When the source is a `backupRef` and the field is
omitted, the operator uses the backup's own dump-key snapshot recorded in
`status.artifactStorage.passphraseSecretKeyRef`; it never falls back to the
profile's live Secret (`PITRBackupDumpKeyMissing` when neither exists).

| Field | Type | Required | Description |
|---|---|---|---|
| `passphraseSecretKeyRef` | PassphraseSecretKeyRef | Yes | Secret holding the passphrase used at backup time. Rotating to a new value does not re-wrap existing ciphertext — it will simply fail to decrypt. |

### BackupRetention

A successful MysqlBackup is kept when **any** rule keeps it: it is one of
the newest `keepLast`, or it completed within `keepWithinDays`. It is
deleted only when it is outside both. Failed CRs are counted separately.
A backup that a verification may be reading is kept until the run stops.
See [Backup and restore → Retention](/docs/backup-and-restore/backup-restore#retention),
which also maps the released `retention: N` and `retentionPolicy` fields.

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `keepLast` | int | No | `7` | The newest this-many successful CRs are always kept. At least `1`, so retention never deletes the last good backup. |
| `keepWithinDays` | int | No | -- | Also keep every successful CR that completed within this many days. At least `1`; unset keeps by count only. |
| `keepFailed` | int | No | `10` | The newest this-many Failed CRs are kept. `0` keeps none. A Failed CR that is still its schedule's latest is kept until a newer CR of that schedule exists, whatever this says: `spec.backup.retry` retries it and `status.backupSchedules` reports it. |

### PITRSpec (`spec.backup.pitr`)

Enables continuous binary-log archival so restores can target an
arbitrary `stopTime` on top of any retained full dump. See
[Backup and restore → Point-in-time recovery](/docs/backup-and-restore/backup-restore#point-in-time-recovery-pitr)
for the end-to-end story.

| Field | Type | Required | Description |
|---|---|---|---|
| `enabled` | bool | No | Turns archival on. Omitting the whole block is equivalent to `false`. |
| `profileName` | string | Yes when enabled | Name of a `spec.backup.profiles[]` entry, a DNS label of at most 63 characters (`[a-z0-9]([-a-z0-9]*[a-z0-9])?`). Binlog objects and per-site manifests live under a `binlogs/` subprefix inside that profile's storage. |
| `maxBinlogSize` | string | No | Passed to MySQL as `max_binlog_size`. Controls rotation cadence (and therefore the RPO gap). Default `"100M"`. |
| `archivePollInterval` | duration | No | Belt-and-suspenders scan cadence alongside inotify. Default `"60s"`, `5s` to `1h`. |

The archive under `<prefix>/binlogs/` carries a write-once descriptor
(`archive.json`) naming this group's UID, an archive ID derived from that UID
and the normalized destination, and the encryption mode. Manifests are
version 2 and name the archive ID. Writers need a store that enforces atomic
create. Prefixes written before v1.7.0 are refused (`ArchiveLegacy`): use a
new prefix and take a full backup. See
[Archive identity](/docs/backup-and-restore/backup-restore#archive-identity).
The operator always owns `replica-preserve-commit-order` (`ON`, for every
group, whether or not PITR is enabled). While PITR is enabled, replication or
binlog filters, `binlog_format` other than `ROW`
or `binlog_row_image` other than `FULL` in `spec.mysqlConf` are refused: they
are left out of the rendered my.cnf and reported by the condition
`PITRMysqlConfAccepted=False` / `PITRUnsafeSettingRefused` and a Warning
`PITRMysqlConfRefused`. `PITRArchiveReady=False` / `ArchiveUnsafeHistory`
comes only from a sidecar's history-integrity marker, that is, from a change
made outside the spec.

**Encryption change rule.** A validation rule on the `MysqlFailoverGroup` root
refuses an update that, with `pitr.enabled` true in both the old and new object
and the same `pitr.profileName`, changes that profile's `encryption` (its
presence, `algorithm`, `passphraseSecretKeyRef.name` or `key`) while its storage
destination (type, bucket, prefix, endpoint, claim, sub-path) stays the same:

```
spec.backup.profiles[pitr.profileName].encryption (presence, algorithm, passphraseSecretKeyRef) cannot change while that profile archives PITR binlogs to the same storage; create a new profile with a new storage prefix and its own passphrase, switch spec.backup.pitr.profileName to it, wait until its archive binding is Bound, then take a full backup (see Backup encryption > Rotation)
```

An omitted `algorithm` equals `AES-256-GCM` and an omitted `key` equals
`passphrase`. The rule compares references, so renaming the Secret to a copy
with the same bytes is refused too. Edits with PITR disabled, across a
`pitr.profileName` change, or together with a destination change pass
admission and are judged by the group's
[archive encryption binding](/docs/backup-and-restore/backup-encryption#archive-encryption-bindings).

### InitFromBackupSpec (`spec.initFromBackup`)

One-shot restore-on-first-boot. The operator runs a restore Job against
the initial primary site before normal bootstrap is considered
complete. Once `status.restore.phase == Succeeded`, subsequent
reconciles skip the restore even if this field is still set.

| Field | Type | Required | Description |
|---|---|---|---|
| `source` | RestoreSource | Yes | Tagged reference: exactly one of `backupRef`, `s3`, or `pvc`. |
| `loadOptions` | LoadOptions | No | `util.loadDump()` tuning (threads, skipBinlog, loadIndexes, schema filters). Restore Jobs disable load-progress tracking, so every load starts clean. |
| `pointInTime` | PointInTimeSpec | No | Post-load binlog replay to a specific target timestamp. Requires the source group to have had `spec.backup.pitr.enabled=true` at backup time. A validation rule requires `pointInTime.archiveProfileName` whenever `pointInTime` is set. |
| `decryption` | BackupDecryptionSpec | No | Passphrase to decrypt the source backup's dump. When omitted for a `backupRef`, the operator uses the backup's recorded dump-key snapshot (`status.artifactStorage.passphraseSecretKeyRef`), never the profile's live Secret. Replayed binlogs are decrypted with the archive's read-binding key snapshot, not with this Secret. |

### RestoreInPlaceSpec (`spec.restoreInPlace`)

Re-triggerable destructive restore against the currently-active
primary. Unlike `initFromBackup` (one-shot, greenfield), this field is
meant to be edited repeatedly: bumping `confirm` to a newer RFC 3339
timestamp re-arms another restore. See `RestoreInPlaceSpec` in the
source for full semantics (full-instance vs. per-schema restores).

| Field | Type | Required | Description |
|---|---|---|---|
| `confirm` | string | Yes | Anti-fat-finger token. Must be an RFC 3339 timestamp strictly greater than `status.restoreInPlace.confirmTokenUsed`. |
| `source` | RestoreSource | Yes | Tagged reference: one of `backupRef`, `s3`, or `pvc`. |
| `loadOptions` | LoadOptions | No | `util.loadDump()` tuning. For per-schema restores, `skipBinlog` is force-set to `false` so the DROP+load replicates. |
| `decryption` | BackupDecryptionSpec | No | Same semantics as `InitFromBackupSpec.Decryption`. |

### PointInTimeSpec (`spec.initFromBackup.pointInTime`)

Requests binlog replay on top of the loaded dump. Requires the source
failover group to have had `spec.backup.pitr.enabled=true` at the
time of the full dump — otherwise there is no archive to replay.

| Field | Type | Required | Description |
|---|---|---|---|
| `stopTime` | timestamp | Yes | The target instant: RFC 3339 with an explicit zone and whole seconds (`2026-04-15T09:30:00Z`, `2026-04-15T09:30:00+02:00`). Pattern `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}(Z\|[+-]([01][0-9]\|2[0-3]):[0-5][0-9])$`: a missing zone, a space instead of `T`, a lowercase `t` or `z`, a fractional second, or an offset outside `-23:59`..`+23:59` is rejected at admission, so every stored value is one the operator's typed client can read. Commit times are compared to the microsecond. Replay restores the history of the first archived transaction committed at or after it, cut just before that transaction. |
| `archiveProfileName` | string | Yes under `initFromBackup` | `spec.backup.profiles` entry whose archive the restore reads. DNS label, 1–63 characters (`^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`). Required by a validation rule on `initFromBackup` ("pointInTime.archiveProfileName is required: name the backup profile whose PITR archive the restore reads"). It may not resolve to this group's own active PITR destination; destinations are compared normalized, so aliases are refused too, with `RestoreBuildFailed` / `PITRArchiveDestinationShared` before any Job is created. Replay considers every site manifest under that archive. |
| `allowPartial` | bool | No | Default `false`. Accept an archive with no transaction at or after `stopTime`: the restore then replays to the archive head (`status.restore.provenance.pointInTime.outcome: Partial`, with a Warning Event `PITRReplayTruncated`). It relaxes nothing else; archive identity, lineage and continuity checks still apply. |
| `excludeGtids` | string | No | GTIDs that are never replayed, at most 131072 characters, in MySQL's GTID set syntax (tags, line breaks and upper-case UUIDs are accepted; the Job receives the set normalized). Every entry must start with a server UUID, and the canonical set (tags spelled out per tag) must fit 64 KiB, since it reaches the Job as one environment string; a set that does not parse, an entry without a UUID, or a longer canonical set fails at reconcile with `PITRTargetInvalid`. They must not intersect the backup (`PITRExcludeIntersectsBackup`). Every archived transaction committed between the backup's newest transaction and the target that is outside the target history must be listed (`PITRArchiveDivergentHistory` prints that set). Excluding a transaction on the target history skips its GTID, but later row images may still carry its effects; it is reported as `onHistoryExclusions`. See [Target history and excludeGtids](/docs/backup-and-restore/backup-restore#target-history-and-excludegtids). |

`sites` and `allowUnverifiedCrossSite` were removed in v1.7.0; replay
considers every manifest in the archive. See
[Restore to a target timestamp](/docs/backup-and-restore/backup-restore#restore-to-a-target-timestamp).

Reconcile-time refusals set `status.restore.reason` and emit
`RestoreBuildFailed` before any Job is created:

| Token | When |
|---|---|
| `PITRTargetInvalid` | `stopTime` is missing or has a fractional second (an object built outside admission), `archiveProfileName` is empty or names no profile in `spec.backup.profiles`, or `excludeGtids` does not parse, has an entry that does not start with a server UUID, or exceeds 64 KiB canonical. |
| `PITRBackupIdentityUnknown` | The referenced `MysqlBackup` records no source failover group UID (`status.failoverGroupUID` is empty: a backup from before v1.7.0, which has no backup stamp), or a direct S3 or PVC source sits at the root of its store (no `prefix` or `subPath`), where no stamp can identify it. Take a new backup, or name the dump's directory in the source. |
| `PITRBackupFiltered` | `loadOptions.includeSchemas` or `excludeSchemas` is combined with `pointInTime`. |
| `PITRArchiveDestinationShared` | `archiveProfileName` resolves to this group's own active PITR destination. |

`PITRBackupAfterTarget` is not checked at reconcile: `status.completionTime`
includes the upload and would refuse valid targets. `dump-meta` and the
planner check the target against the dump's own end and the dumped server's
clock. A logged load (`loadOptions.skipBinlog: false`) is also refused. The
refusals `dump-meta`, `pitr-download` and `restore.py` can report are listed
in [Restore refusals](/docs/backup-and-restore/backup-restore#restore-refusals).

### PITR completion status (`status.restore`)

| Field | Type | Description |
|---|---|---|
| `jobUID` | string | Producing Job identity; a recreated Job with the same name never inherits the previous outcome. |

### PointInTimeResult

One shape for `MysqlFailoverGroup.status.restore.provenance.pointInTime`,
`status.restoreInPlace.provenance.pointInTime` and `MysqlBackupVerification.status.pointInTime`.
It is filled only

| Field | Type | Description |

| `onHistoryExclusionCount` | int64 | Number of GTIDs in `onHistoryExclusions`. |
| `gtidExecuted` | string | The target's `@@global.gtid_executed` after replay, which the replay proved equal to the target history minus `excludeGtids`. Empty when longer than 2048 characters. |

### PointInTimeVerificationSpec (`MysqlBackupVerification.spec.pointInTime`)

### KeyringSpec

`mysqldDir` and `pluginDir` are image-specific. The defaults match the
official `mysql:9.x` images — MySQL only reads its global component
manifest from the directory holding `mysqld`, and its global component
config from `plugin_dir`, so a wrong value shows up as InnoDB refusing to
start. The three directory fields must be absolute paths made of
`A-Z a-z 0-9 . _ / -` (no trailing `/`), because the operator embeds them in
the `mysqld` launcher script.

| Field | Type | Default | Description |
|---|---|---|---|
| `dataFileDir` | string | `/run/mysql-keyring` | Keyring mount point. It must be outside the actual MySQL datadir. Admission rejects `/var/lib/mysql` and descendants; custom-image datadirs require manual verification. |
| `mysqldDir` | string | `/usr/sbin` | Directory containing the `mysqld` binary; `mysqld.my` is subPath-mounted here. |
| `pluginDir` | string | `/usr/lib64/mysql/plugin` | MySQL `plugin_dir`; `component_keyring_file.cnf` is subPath-mounted here. |
| `retainVersions` | int | `5` | Superseded escrow Secret versions kept per site (2--50). The version a site is currently sealed against is never pruned. |
| `escrowTimeout` | duration | `10m` | How long before a site that has not escrowed its keyring is reported `Failed`. `30s` to `1h`. The site stays unsealed and the operator keeps retrying either way. |

## Full example

```yaml
apiVersion: shipstream.io/v1alpha1
kind: MysqlFailoverGroup
metadata:
  name: orders
spec:
  image: mysql:9.7
  sites:
    - name: iad
      serverID: 101
      zone: us-east-1a
      taintNodeSelector:
        bloodraven.shipstream.io/failover-group.orders: "true"
        bloodraven.shipstream.io/site.orders: iad
      lbIP: 10.0.1.1
      storage:
        storageClassName: fast-ssd
        size: 100Gi
      resources:
        requests:
          cpu: "2"
          memory: "16Gi"
        limits:
          cpu: "4"
          memory: "16Gi"
    - name: pdx
      serverID: 102
      zone: us-west-2a
      taintNodeSelector:
        bloodraven.shipstream.io/failover-group.orders: "true"
```

### PlannedFailoverStatus

Every field belongs to the run named by `runID`. The operator writes the block with a status update conditioned on the object's `resourceVersion`, one write per transition, and refuses a non-terminal block without a `runID` (a block an older operator wrote). The CRD schema marks no field of the block `required` (an older operator rolled back onto this CRD must still be able to write its own block); the fields described as "always set by the operator" are set on every block this operator writes, and their minimum length or value still applies when present. See [Planned failover](/docs/operations/planned-failover) for the lifecycle.

| Field | Type | Description |
|---|---|---|
| `runID` | string | Always set by the operator. Identifies the run; minted when a request is first stamped (`Admitting` or `Deferred`). It is the token of the run's claim and the value the hold acknowledgement must name. |
| `revision` | int64 | Always set by the operator, ≥ 1. Increments on every write the run makes; settlement of an ambiguous write identifies a committed write by `(runID, revision)`. |
| `phase` | string | Always set by the operator. `Admitting`, `Deferred`, `Fencing`, `Draining`, `WaitingForLag`, `WaitingForDragonflySync`, `PromotingDragonfly`, `Promoting`, `Publishing`, `RollingBack`, `Succeeded` or `Failed`. |

| `startTime` | timestamp | Always set by the operator. When the request was first accepted. |
| `sourceSite` | string | The site the topology manager named the unique writable primary when it granted the claim. Empty until `Fencing`. |
| `claimTime` | timestamp | When the claim was granted. |
| `claimBaseline` | FailoverRecordRef | The durable failover record at the grant (the newer of status and the out-of-band record) as `{time, target}`, `time` at second precision. A re-proof after a restart compares both by value. |

### Conditions

The topology conditions (`Ready`, `Degraded`, `Bootstrapping`, `Updating`,
`RecoveryPending`, `DivergentPromotion`) carry the generation the topology
manager applied, the same value as `status.observedGeneration`, so a spec edit
the manager has not taken up yet does not read as observed. A condition
another writer owns (`S3CredentialsReady`, `PITRMysqlConfAccepted`,
`PITRArchiveReady`, `PITRArchiveBindingReady`, the encryption conditions)
carries the generation that writer evaluated.

| Type | Meaning |
|---|---|
| `Ready` | `True` with reason `Healthy` when there is exactly one confirmed writable `PrimaryCandidate` and every non-reader follower has healthy direct replication. Reader reachability, lag, threads, and source state do not change this group condition. `False` with reason `NoWritablePrimary` when no site is writable, or `ReplicationUnhealthy` when a site is writable but replication is not healthy. `False` with reason `InitFromBackupInProgress`, or `InitFromBackupFailed` after a failure, while a `spec.initFromBackup` restore has not succeeded. `Unknown` with reason `Initializing` right after an operator start, while no site is confirmed writable and a `PrimaryCandidate` has not been classified yet (see [Initializing after an operator start](/docs/operations/failover#initializing-after-an-operator-start)). |
| `Degraded` | `False` with reason `Healthy` when nothing is wrong. `True` with the most important problem, in this order: a cross-site alert (`SplitBrain`, `NoPrimary`, `TotalLoss`, or `CrossSiteAlert` for any other cross-site alert), `BootstrapFailed`, `SiteUnhealthy` (a non-reader site is unreachable, or a writable site that cannot be promoted needs fencing), then the per-site replication reasons: `ReplicationBroken`, `ReplicationError`, `ReplicationLagging` (lag exceeds `maxLagSeconds`) and `ReplicationSourceMismatch`. Reader failures are excluded and remain visible per site and in metrics. `BootstrapFailed` is recomputed on every poll: it holds while the target of the failed clone neither replicates (`replication` `Healthy` or `Lagging`) nor is the writable primary, and clears when a new clone starts or the site replicates by another path; the deployment API refuses leases while it holds. Also `True` with reason `DivergentTransactions` whenever any site, readers included, is `RecoveryBlocked`; that reason outranks the replication reasons, and does not by itself make the deployment API refuse leases. `True` with reason `RestoreReclonePending` while `status.restoreReclones.pending` lists sites and nothing else is wrong: their replication is stopped until their post-restore reclone, and the deployment API refuses leases with the same reason. `True` with reason `WorkloadSelectorMismatch` when a site's Deployment or Dragonfly StatefulSet has a selector other than the one the operator renders (for example an object left by an earlier release with other label keys): the selector is immutable, so the operator does not update that workload and does not retry in a loop; a `WorkloadSelectorMismatch` Warning Event names the object, and deleting it lets the operator re-create it (a MySQL site keeps its PVC). `True` with reason `MetadataVersionUnsupported` when an internal annotation payload, the planned-failover terminal marker or a deployment lease record, has a `schemaVersion` this operator does not know, with a `MetadataVersionUnsupported` Warning Event: the payload proves nothing (lease requests are refused while a lease record is unreadable), except that a terminal marker naming a run with outcome `ManualRecoveryRequired` still holds automatic failover. Both outrank the per-site replication reasons and `RestoreReclonePending`, but not the cross-site alerts, `BootstrapFailed`, `SiteUnhealthy` or `DivergentTransactions`, and the deployment API reports the group unstable with that reason. `Unknown` with reason `Initializing`, alongside `Ready`, until the operator has classified the topology after a start; `ReplicationBroken`, `ReplicationError`, `ReplicationLagging`, `DivergentTransactions`, `WorkloadSelectorMismatch`, `MetadataVersionUnsupported` and `RestoreReclonePending` still set it `True` (the last comes from the persisted `status.restoreReclones`, not from a topology observation, so it is known during `Initializing` and keeps the deployment API refusing leases). |
| `DivergentPromotion` | Set `True` (reason `DivergentSitePromoted`) when a site carrying a divergence report became the confirmed primary, so its extra transactions are now authoritative. A later divergent promotion is appended to the message (newest last, five newest kept). The operator never clears it; remove it from status after reviewing the transactions. |
| `AutomaticFailoverHeld` | Summarises `status.plannedFailoverHold`. `True` (reason `PlannedFailoverManualRecoveryRequired`) after a planned failover that may have written to its target ended `ManualRecoveryRequired`; the message names the run, the writable or ambiguous sites and the acknowledgement, for people only (read the run from `status.plannedFailoverHold.runID`). `False` (reason `PlannedFailoverHoldAcknowledged`) once the hold was acknowledged; absent on a group that was never held. Its `observedGeneration` is the generation of the object the hold was read from and written to (the planned failover's terminal write, or the acknowledgement), not `status.observedGeneration`: the hold comes from durable run evidence, not from the configuration the topology manager applied. While it is `True`, emergency failover, split-brain resolution, the primary re-assert, ordered updates, keyring rotations, recovery and source convergence, bootstraps and DNS reconciliation stay held for the group. Cleared by the operator after the `bloodraven.shipstream.io/acknowledge-planned-failover-hold=<runID>` annotation (`kubectl bloodraven ack-planned-failover-hold <group>`); see the [hold runbook](/docs/operations/runbooks#planned-failover-automation-hold). |
| `RecoveryPending` | `True` while old-primary recovery is running (`RecoveryInProgress`) or when an old primary has divergent transactions (`DivergentTransactions`). Use the reclone annotation only for `DivergentTransactions`. |
| `Bootstrapping` | `True` only while a clone runs (fresh-deploy, auto-clone, or reclone), with the phase as its reason: `Cloning`, `WaitingForRestart`, `SetupReplication`. A finished clone is `False` with reason `NotBootstrapping` and the message `<Bootstrap\|Reclone\|Auto-clone> completed successfully`; `NotBootstrapping` is also the state before any clone. A failed clone is `False` with reason `BootstrapFailed`, which also sets `Degraded=True` with reason `BootstrapFailed` while the failure stands; `Bootstrapping` keeps reporting the last clone's outcome until the next clone starts. To wait for a clone you requested, wait for `False`/`NotBootstrapping` with a `lastTransitionTime` after the request and the target site's `replication` `Healthy` (or `Lagging`). |
| `Updating` | `True` while an ordered update runs; the reason is the phase (`UpdateReplica`, `WaitReplica`, `Failover`, `UpdateOldPrimary`, `WaitOldPrimary`), also in `status.updatePhase`. | `PITRArchiveReady` | Present only while `spec.backup.pitr.enabled=true`; removed when PITR is disabled. Derived from the operator's 30 s polls of every site's `/archiver/status`. `True` / `Archiving`: every site answered with an enabled archiver, a ready store and no error. `False` / `ArchiveStoreInitFailed`: a sidecar cannot build its archive store (for example an unreadable passphrase or credentials file, an invalid S3 endpoint, an empty PVC mount path, or a PVC mount path that is not a mount point or not writable); immediate. `False` / `ArchiverError`: a site with a ready store reported an error from 2 consecutive archiver scans (`consecutiveFailedScans` ≥ 2; from an older sidecar, an error from a later `lastScanAt`), or the same error for 10 minutes or three scan intervals (the current `archivePollInterval`), whichever is longer, without a scan completing. One failed scan never sets it, even though the default 60 s scan interval leaves it visible to two polls. `False` / `ArchiverDisabled`: a sidecar reports archiving disabled on 2 consecutive polls while the spec enables it and no ordered update is pending for that site; usually `spec.backup.pitr.profileName` names no existing profile (see the `BackupPITRInvalid` Event). `Unknown` / `AwaitingRollout`: a sidecar reports archiving disabled while that site's ordered update is still pending (or, right after the topology manager starts, before it has computed which sites drift), the normal state right after enabling PITR; no Event. It applies only when the PITR spec renders an archiver (an empty or unknown `profileName` does not) and for at most 30 minutes per site; a rollout still pending after that is `False` / `ArchiverDisabled` with the message `ordered update still pending after 30m`. `False` / `SidecarOutdated`: an enabled archiver reports no archive-identity block, so it predates archive identity and its manifests are unusable for restores: a `spec.sidecar.image` pin older than v1.7.0, or, right after an upgrade to v1.7.0, old pods whose Deployment update is deferred until the archive is switched to a new prefix (see [Upgrade policy](/docs/operations/upgrade-policy#pitr-archive-identity); changing `spec.sidecar.image` does not end that); `Unknown` / `AwaitingRollout` while that site's ordered update is pending (at most 30 minutes), otherwise `False` on the second poll. Set `spec.sidecar.image` to this operator's release, or clear it, before archiving to a new prefix. `False` / `SidecarUnreachable`: a site's poll failed 3 times in a row over at least 60 s, or over at least 5 minutes for a site whose sidecar has not answered since this operator process started (new groups, bootstraps, a crash-looping older sidecar after an operator upgrade). `Unknown` / `AwaitingFirstPoll`: this operator process has not observed every site yet; a `True` from before an operator restart is not kept without a fresh observation, a `False` is, and a replacement topology manager continues its predecessor's observations. If the operator cannot read the group uncached when a manager starts, the condition is left as persisted until it can. A single missed poll or a single failed scan keeps the current status; returning from `False` to `True` needs 2 consecutive clean poll rounds. `False` / `ArchiveForeign`, `ArchiveCopy`, `ArchiveLegacy`, `ArchiveDescriptorMissing`, `ArchiveEncryptionMismatch`, `ArchiveKeyMismatch`, `ArchiveVersionUnsupported`, `ArchiveStoreUnsupported` or `ArchiveUnsafeHistory`: a sidecar refused the archive's identity, or set its permanent history-integrity marker (see [Archive identity](/docs/backup-and-restore/backup-restore#archive-identity)); immediate. `ArchiveVersionUnsupported` also covers a damaged `archive.json` (undecodable, trailing data, wrong kind, a malformed field, source names outside Kubernetes bounds, or larger than 64 KiB); its message then gives the repair (restore the original object, or point the profile at a new prefix) instead of an upgrade. `ArchiveUnsafeHistory` comes only from a sidecar's marker, with an edge-triggered Warning `PITRArchiveUnsafeHistoryDetected` in addition to `PITRArchiveNotReady`; the condition does not preview `spec.mysqlConf`, whose unsafe options are refused instead (see `PITRMysqlConfAccepted`). When sites disagree the reason is the first of `ArchiveStoreInitFailed`, the archive refusals in the order above, `ArchiverError`, `SidecarOutdated`, `ArchiverDisabled`, `SidecarUnreachable` that applies, and the message lists every affected site, sorted, as `site: detail`. A change in status, reason or the set of affected sites is written at once; a change confined to message text (for example a new S3 request ID) at most every 5 minutes. A Warning `PITRArchiveNotReady` Event ("PITRArchiveReady is False (<reason>): <message>") fires when the condition enters `False`, and a Normal `PITRArchiveRecovered` Event ("PITRArchiveReady is True again: every site reports a running archiver with a ready store and no error") when it returns to `True`; reason or message changes while `False` fire none. Archiving state never affects pod readiness. |
| `PITRArchiveBindingReady` | Present while the group has archive bindings or binding targets; owned by the reconciler, `observedGeneration` set. The first that applies: `False` / `BindingLimitReached` (a destination in use has no binding, and 16 entries that stay exist: `Bound`, or used by a target); `False` / a refused binding reason of an entry in use, or `ArchiveForeign` / `ArchiveCopy` when a `Bound` read binding is made the write target; `False` / `EncryptionChangeRefused` or `KeyChangeRefused` (a profile in archive use differs from its `Bound` binding; pods keep the binding); `False` / `KeyMaterialLost` (a `Bound` binding's key snapshot is missing, or is present but no longer passes the check of the accepted key; the message says which, and never advises deleting a snapshot that is present); `Unknown` / `Authenticating` or `Establishing`; `True` / `Bound`, with a note while no full backup is stamped with the write binding's archive ID. Refusal messages name the profiles (up to 8), the destination and the procedure. See [Archive encryption bindings](/docs/backup-and-restore/backup-encryption#condition-events-and-log-lines). |
| `PITRMysqlConfAccepted` | Present only while `spec.backup.pitr.enabled=true`; removed when PITR is disabled. Owned by the reconciler. `True` / `Accepted`: no `spec.mysqlConf` option breaks PITR replay. `False` / `PITRUnsafeSettingRefused`: group or site `mysqlConf` sets a replication or binlog filter (`replicate-do-*`, `replicate-ignore-*`, `replicate-wild-*`, `replicate-rewrite-db`, `binlog-do-db`, `binlog-ignore-db`), `binlog_format` other than `ROW` or `binlog_row_image` other than `FULL`; the effective group-plus-site value is judged per site, so a group value every site overrides safely is not refused. Refused options are left out of the rendered my.cnf (MySQL's safe default applies). The message lists each as `<site>: <field> sets <key>[=<value>] (<why>)`, and a Warning `PITRMysqlConfRefused` fires once per refused set. `replica-preserve-commit-order` is operator-owned and never reaches this check. |
| `S3CredentialsReady` | Present only when the group references S3 storage (a backup profile, `initFromBackup`, or `restoreInPlace`). `True` when every referenced `credentialsSecretName` exists and has non-empty `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`. `False` with reason `CredentialsIncomplete` otherwise, together with an `S3CredentialsIncomplete` warning event; backup, restore, and cleanup Jobs fail in that state because they do not fall back to IRSA, Workload Identity, or instance-profile credentials. |

### Annotations

[Well-known metadata](/docs/configuration/well-known-metadata) is the complete list of the labels, annotations, finalizers and the taint Bloodraven reads or writes, with each key's writer, value grammar and stability level. Action annotations share one value grammar, `<subject>(:<key>=<value>)*`; a destructive action on a site carries `confirm=<metadata.name>:uid=<metadata.uid>`, where the uid is `kubectl get mfg <group> -o jsonpath='{.metadata.uid}'`, so a request left over for an earlier group of the same name does not apply.

| Annotation | Description |
|---|---|
| `bloodraven.shipstream.io/last-failover` | Operator-owned out-of-band copy of `status.lastFailover.time`, formatted as an RFC3339 UTC timestamp at second precision. Do not edit manually. Reset tooling clears it together with status history. |
| `bloodraven.shipstream.io/last-failover-target` | Operator-owned out-of-band copy of `status.lastFailover.target`. It is always written and cleared as a pair with `last-failover`. Do not edit manually. |
| `bloodraven.shipstream.io/reclone-site` | Triggers a `CLONE INSTANCE` from the current primary to the named site. CLONE INSTANCE wipes the site's datadir, so both forms carry the group's name and uid: `<site>:confirm=<group-name>:uid=<group-uid>` for a cold reclone (no divergent GTID recorded), and `<site>:confirm=<group-name>:uid=<group-uid>:gtidPrefix=<prefix>` when `status.sites[].divergentGtid` is non-empty. The prefix is at least 8 hex digits or `-` of the source UUID of the set's first entry (never its `:interval` part, since a value cannot contain `:`); it proves the requester read the divergence and does not replace `confirm=`. `kubectl bloodraven reclone <group> <site>` builds the value. Any other form, including a bare site or the positional `<site>:<prefix>` of earlier releases, is rejected with a message that prints the full form. Invalid annotations are rejected with a `RecloneRejected` Warning Event and cleared. Valid ones emit `RecloneRequested` and report progress via the `Bootstrapping` condition. The operator also writes this annotation itself to drain `status.restoreReclones` after a full-instance in-place restore; it never overwrites a value someone else set. |
| `bloodraven.shipstream.io/planned-failover` | Starts a planned failover to the named site: `<site>[:maxLagWait=<duration>]`; the override takes the same `1s` to `1h` bound as `spec.plannedFailover.maxLagWait`. The grammar is `<subject>(:<key>=<value>)*`: values use only `A-Za-z0-9._/+-`, each key appears once, and an empty or unknown pair is rejected. The operator removes it once the run is accepted (or kept while `Deferred`). When Dragonfly is enabled, the planned-failover status includes a `dragonfly` substatus with session-preservation details. |
| `bloodraven.shipstream.io/acknowledge-planned-failover-hold` | Set by an administrator to the held run's `runID` (`status.plannedFailoverHold.runID`), or with `kubectl bloodraven ack-planned-failover-hold <group>`, to acknowledge an automation hold (`AutomaticFailoverHeld=True`) after resolving the split brain. The operator clears the hold and then removes the annotation. A value naming another run, a value given when no hold stands, or one beside a claim held for another run resumes nothing and gets a `PlannedFailoverHoldAcknowledgmentIgnored` Warning Event; when no hold stands the annotation is removed anyway. |
| `bloodraven.shipstream.io/planned-failover-terminal` | Operator-owned: a versioned JSON payload, `{"schemaVersion":1,"runID":"<runID>","outcome":"<outcome>","reason":"<reason>","warnings":["<warning>"]}` (`reason` and `warnings` may be omitted). `warnings` are the run's terminal warnings (API warning tokens); the terminal record a marker-ended run gets keeps them and adds `StatusStalled`, and a marker carrying `FenceNotAttributable` never names the source for re-assert, also after a restart. A value that is not this payload is ignored and logged; one with a `schemaVersion` this operator does not know is also reported as `Degraded=True/MetadataVersionUnsupported` with a `MetadataVersionUnsupported` Warning Event; a payload the strict parser rejects (an unknown field, a newer `schemaVersion`, an unfamiliar reason) that is still JSON naming a run with outcome `ManualRecoveryRequired` is treated as a hold, and the acknowledgement can delete it. Ends a run whose status writes stalled for 2 minutes; every planned-failover check treats the named run as terminal. Removed once the terminal status record lands, except that a `ManualRecoveryRequired` marker is a hold record and is removed only by the acknowledgement. Do not edit. |
| `bloodraven.shipstream.io/planned-failover-stall-since` | Operator-owned: `<runID>:since=<YYYYMMDDThhmmssZ>`. The durable start of the status-stall deadline. Do not edit. |
| `bloodraven.shipstream.io/planned-failover-manager-absent-since` | Operator-owned: `<runID>:since=<YYYYMMDDThhmmssZ>`. The durable start of the 5-minute manager-absence deadline. Do not edit. |
| `bloodraven.shipstream.io/planned-failover-confirmed` | Operator-owned: `<runID>:since=<YYYYMMDDThhmmssZ>`, the time the run's promotion was confirmed. Written after the run's promotion is confirmed, recorded and published, and before its claim is released (if the write fails the claim is kept and retried). A restart before the `Publishing` write commits treats the run as recorded from it: no claim is hydrated and the run publishes without one, even if a later emergency failover replaced the run's failover record. Removed when the run ends; one a finished run left behind is removed by the next pass, as are its `stall-since` and `manager-absent-since` annotations. Do not edit. |
| `bloodraven.shipstream.io/planned-failover-status-fence` | Operator-owned: an ISO 8601 basic UTC instant with nanoseconds (`20261104T100000.123456789Z`) bumped, conditioned on the `resourceVersion` an ambiguous status write was made against, to prove that write can never commit. Each bump moves the value past the stored one (1ns past it when the clock has not advanced), and it counts as proof only if it moved the object's `resourceVersion`. Do not edit. |
| `bloodraven.shipstream.io/promotion-gtid-executed` | Operator-owned out-of-band copy of `status.lastFailover.promotionGtidExecuted`, written with `last-failover` and `last-failover-target` and conditioned on the object's `resourceVersion`. | `bloodraven.shipstream.io/promotion-gtid-executed-for` | Operator-owned: `<RFC3339 last-failover> <last-failover-target>`, binding `promotion-gtid-executed` to its failover event. Written and deleted in the same patch as `promotion-gtid-executed`. A watermark whose binding does not name the event that `last-failover` and `last-failover-target` record (a writer that knows only those two advanced them) is ignored. Do not edit. Reset tooling clears it together with status history. |
| `bloodraven.shipstream.io/rotate-keyring` | Rotates the named site's InnoDB master key. **Refused on the active primary** -- rotation is the one operation whose failure window would cost data rather than a re-clone, so the supported procedure is to rotate replicas, run a planned failover, then rotate the ex-primary. Also refused while an ordered update or planned failover is in flight (decided against the operator's live state too, not only status: also refused while a planned failover or promotion is in flight, on the site the operator currently observes as primary, and until it has observed a unique writable primary with the target read-only). Cleared automatically once the requested rotation completes and the site is `Sealed` again (an escrow repair back to `Sealed` keeps it). |
| `bloodraven.shipstream.io/release-pitr-archive-binding` | Releases one archive binding and deletes its key snapshots. Value `<id>:confirm=<group-name>:uid=<group-uid>`, one id per annotation. The id is derived from the destination, so it recurs in a re-created group of the same name; the uid keeps a stale request from releasing the new group's binding. Refused while the binding is in use (Warning `PITRArchiveBindingReleaseRefused`, annotation kept, retried every minute); a malformed value or a wrong `confirm` or `uid` is rejected (Warning `PITRArchiveBindingReleaseRejected`) and removed. Never commit it in GitOps. See [Releasing a binding](/docs/backup-and-restore/backup-encryption#releasing-a-binding). |

## `MysqlBackup`

One backup run. Created by hand or by a schedule CronJob. See
[Backup and restore](/docs/backup-and-restore/backup-restore). The spec names
the failover group (`spec.failoverGroupRef.name`), the profile
(`spec.profileName`, a DNS label of at most 63 characters) and
optionally `spec.sourceSite`, a site of that group to take the dump from.
`spec.deletionPolicy` (`Delete` by default, or `Retain`) decides what deleting
the CR, by hand or by retention, does to the artifact: `Delete` removes the
artifact from storage and then the backup's dump-key snapshot Secret; `Retain`
runs no cleanup, keeps both, and records a Normal `ArtifactRetained` Event
naming them (delete them by hand when no longer needed). It is read when the
deletion is processed. A backup re-created with the name of a retained one
fails at its backup stamp step while the retained dump is still at that
location.
`failoverGroupRef.name` is a DNS subdomain of at most 253 characters. A name ending
in `.bloodraven-backup.json` is refused at admission: that suffix is the
[backup stamp](/docs/backup-and-restore/backup-restore#backup-stamp)
object's.

### Status

| Field | Type | Description |
|---|---|---|
| `phase` | string | `Pending`, `Running`, `Succeeded` or `Failed`. |
| `startTime`, `completionTime` | timestamp | When the backup Job started and reached a terminal state. |
| `jobName` | string | The producing backup Job. |
| `sourceSite` | string | The site the dump was taken from. |
| `artifactStorage` | ArtifactStorage | Where the producing Job wrote the artifact: storage `type`, `location`, and the bucket, endpoint and region or the claim. Restores, verifications and artifact cleanup read the destination only from here. Immutable once `location` is set (see below). Replaces the former `status.location` and `status.storageType`. |
| `size`, `sizeBytes` | string, int | Reported artifact size. |
| `gtidExecuted` | string | `@@global.gtid_executed` at dump time. |
| `binlogPosition` | `{file, position}` | Binary-log position at dump time. Unset when the dump did not report one. Replaces `binlogFile` and `binlogPos`. |
| `encryption` | `{mode, algorithm}` | `mode` is `Passphrase` when the producing Job encrypted the artifact (the key is `artifactStorage.passphraseSecretKeyRef`) and `None` when it wrote plaintext; `algorithm` is the algorithm stamped on the artifact, empty for `None`. Written from the owned producing Job when the Job is created and derived again from it at completion; a correction emits a Warning `EncryptionAttributionCorrected`. Absent when no owned producing Job attributes it. Restores and verifications use it to decide whether to decrypt. Replaces `encrypted` and `encryptionAlgorithm`. |
| `failoverGroupUID` | string | `metadata.uid` of the source failover group. Pinned on the backup Job as annotation `bloodraven.shipstream.io/failover-group-uid` when the Job is created, and recovered from the Job if the status write is lost. The backup stamp records the same UID. |
| `pitrArchiveID` | string | The archive ID the group's rendered PITR writers used when the Job was created (`^(ar1-[a-z2-7]{26})?$`): the one every site Deployment's render agrees on. A backup of the active PITR profile waits `Pending` with reason `PITRArchiveRolloutPending` while a roll changes it (some renders decode and they disagree). Any other backup never waits: when the renders disagree or one is unreadable it proceeds with this field empty, as does a backup of the PITR profile while the render is deferred (any site Deployment lacks a decodable render while the write binding is not `Bound`/`Establishing`: the pre-v1.7.0 deferral, which does not wait for a roll); either way a Normal Event `PITRArchiveStampSkipped` says why, and the backup is no point-in-time baseline. Empty when PITR was off. Pinned as annotation `bloodraven.shipstream.io/pitr-archive-id` and recovered from the Job. |
| `attempt` | int | Retry attempt for scheduled retries. |
| `conditions` | []Condition | See below. |

`kubectl get mysqlbackup` shows `Group`, `Profile`, `Phase`, `Ready` (the
`Ready` condition's status), `Started`, `Completed` and `Age`; `-o wide` adds
the `Location` (`.status.artifactStorage.location`) and `Size` columns.

Reasons from archive encryption bindings: `Pending` with
`PITRArchiveRolloutPending` (a backup of the active PITR profile while the
sites render different archive IDs),
`PassphraseSecretMissing` (the encrypted profile's Secret or key is missing,
so no dump-key snapshot can be made) or `DumpKeySnapshotConflict` (the
dump-key snapshot name is held by another backup's Secret); `Failed` with
`ProfileReadOnly` (the profile is
[read-only](/docs/backup-and-restore/backup-encryption#read-only-profiles)).

### ArtifactStorage (`status.artifactStorage`)

Recorded from the producing Job when it is created, or recovered from that Job
for backups taken by older operators. Restores, verifications, PITR dump
metadata and cleanup read the bucket, endpoint, region and claim from here and
never follow later edits of the profile's bucket, endpoint, prefix, `subPath`
or claim. A PVC backup therefore needs no profile to be restored or verified.

| Field | Type | Description |
|---|---|---|
| `type` | string | `S3` or `PVC`, the storage backend the producing Job wrote to. Required. |
| `location` | string | The exact artifact location the producing Job wrote: a bucket-relative prefix for plain S3 (`<prefix>/<name>`), `s3://<bucket>/<prefix>/<name>/` for encrypted S3, or `/backups[/<subPath>]/<name>` for PVC. |
| `bucket` | string | S3 bucket. |
| `endpointURL` | string | S3 endpoint override in effect for the Job; empty for AWS. |
| `region` | string | S3 region in effect for the Job. Cleanup signs for `us-east-1` when no region is set anywhere, as mysqlsh does. |
| `claimName` | string | PersistentVolumeClaim (PVC storage). |
| `passphraseSecretKeyRef` | `{name, key}` | For an encrypted backup, the backup's own immutable dump-key snapshot (`mysqlbackup-<name>-dump-key-<uid prefix>`, key `passphrase`) that the producing Job mounted. Restore and verification decrypt the dump with it, and deleting a backup that never succeeded reads its backup stamp with it; the profile's live Secret is used only when no Secret was recorded. The snapshot is deleted after the backup's artifacts are confirmed deleted. |

Credentials are deliberately not part of it: restores, verifications and
cleanup read them from the profile's current `credentialsSecretName`, so
rotating keys needs no change on old backups. Cleanup also deletes the backup stamp,
`<location>.bloodraven-backup.json`; see
[Backup stamp](/docs/backup-and-restore/backup-restore#backup-stamp).

Once `artifactStorage.location` is recorded, a validation rule on the `MysqlBackup` resource
rejects any update that changes or removes `status.artifactStorage`, including
removing or nulling the whole `status` through the status subresource. The
rule is evaluated on the resource root, so it cannot be bypassed by dropping
the parent object first.

### Conditions

| Type | Meaning |
|---|---|
| `JobCreated` | The producing Job was created. |
| `Ready` | `False` from the first reconcile: reason `Pending` until a launch attempt names a specific reason, then the pending reason while the backup waits (`WaitingForHealthySource`, `BackupJobConflict`, `PITRArchiveRolloutPending`, `DumpKeySnapshotConflict`, `PassphraseSecretMissing`), and `Running` while the backup Job runs. `True` with reason `Succeeded` once the backup succeeded with a known artifact destination, or `False` with the failure reason. A wait longer than 30 minutes fails the backup: with reason `NoHealthySource` after waiting for a source, or `PendingTimedOut` after any other wait, with the message `pending for <duration> (<pending reason>): <message>`; a failed backup never carries a pending reason. A Warning Event named after the pending reason fires once on entering a wait (again if the reason changes), and a `NoHealthySource` or `PendingTimedOut` Event on the timeout. |
| `MetadataComplete` | Optional completion metadata (size, GTID, binlog coordinates) was collected; `DestinationUnavailable` means the artifact location is unknown. |
| `ArtifactCleanup` | Only on a Terminating backup: why its artifact has not been removed yet. See [Artifact cleanup](/docs/backup-and-restore/backup-restore#artifact-cleanup) for the reasons. Before releasing an abandoned backup (one that never succeeded, or whose group or profile is gone) the operator stops its producing backup Job and waits for the Job's pods; a lost status update after the Job was created is recovered from the Job, running or failed. `False` / `ProducerStopStuck`, with a Warning `ArtifactCleanupStalledProducerStop`, when a producer pod has not stopped 10 minutes after the deletion: the deletion stays held, because the pod may still write to the destination. Once its node is confirmed down, `kubectl delete pod <pod> --force --grace-period=0`. |

### Annotations

| Annotation | Meaning |
|---|---|
| `verification-hold.bloodraven.shipstream.io/<verification UID>` | Value is the verification name. A `MysqlBackupVerification` is reading this backup; retention and artifact cleanup wait while it is live. See [Backup verification](/docs/backup-and-restore/backup-verification#the-backup-is-held-while-it-is-read). |
| `bloodraven.shipstream.io/triggered-by` | What created the backup: `manual` (or the `--triggered-by` value of `kubectl bloodraven backup`), `schedule/<schedule>`, or `retry/<schedule>/attempt-<n>`. A `MysqlBackupVerification` carries it too (`manual`, or `schedule` for a scheduled run). Informational; the operator never reads it. Replaces `spec.triggeredBy`, removed in v1.7.0. |

## `MysqlStandbyCluster`

**Phase 1 of WISHLIST #7.** A passive DR relationship descriptor that
lives on the DR cluster and continuously monitors a source
`MysqlFailoverGroup`'s dumps and PITR archive in a shared object store. The
controller populates `status.discovered` and stamps readiness conditions
on a configurable cadence. **No mysqld is started, no dump is loaded and
nothing is written to the bucket.**

See [Multi-cluster DR](/docs/architecture/multi-cluster-dr) for the end-to-end
recovery runbook and a full explanation of what the standby does and does
not provide.

### Top-level spec fields

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `transport` | string | No | `ObjectStore` | Transport mode. `ObjectStore` is the only value. |
| `source` | StandbySource | Yes | -- | The source group's S3 destination and optional decryption. |
| `freshness` | StandbyFreshnessSpec | No | -- | Bucket-discovery cadence (`discoveryInterval` only). |

### StandbySource

| Field | Type | Required | Description |
|---|---|---|---|
| `s3` | StandbyS3Source | Yes | The S3-compatible destination the source group's backup profile writes to. The controller only reads it. |
| `decryption` | BackupDecryptionSpec | No | Passphrase Secret to decrypt source artifacts. Must exist in the DR namespace. |

The standby identifies its source by the prefix alone. The archive
descriptor under `<prefix>/binlogs/` names the source group (namespace, name
and UID), and the standby publishes it in `status.discovered.binlogArchive.identity`.
Use metadata labels for a display name.

### StandbyS3Source

The S3 fields of a backup profile's `storage.s3` that apply to a reader,
with `prefix` required. The bounds are the profile's (see
[BackupProfile](#backupprofile-specbackupprofiles)).

| Field | Type | Required | Description |
|---|---|---|---|
| `bucket` | string | Yes | S3 bucket name, 1-63 bytes. |
| `prefix` | string | Yes | The source profile's prefix, at most 512 bytes, with at least one segment. A leading or trailing `/` is ignored; empty, `.` and `..` segments are refused. The standby scans `<prefix>/<dump>/` and `<prefix>/binlogs/`. |
| `region` | string | No | AWS region. Optional for non-AWS S3 stores. |
| `endpointURL` | string | No | Absolute `http://` or `https://` endpoint override without credentials, a query or a fragment, at most 512 bytes. |
| `credentialsSecretName` | string | Yes | Secret in this namespace with `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` (and optionally `AWS_SESSION_TOKEN`, `AWS_REGION`) for read access. |

### StandbyFreshnessSpec

| Field | Type | Default | Description |
|---|---|---|---|
| `discoveryInterval` | duration | `5m` | How often the controller re-scans the bucket to refresh `status.discovered`. `30s` to `24h`. |

Restore verification and activation are not implemented, so the API has no
fields for them: no verification cadence or staleness knobs, no activation
request and no template of the group an activation would create. Unknown
fields have no effect: the API server prunes them (they are silently dropped
and never persisted), and clients using strict server-side field validation —
the default for `kubectl apply`/`create` since Kubernetes 1.25 — reject them
outright.

### Status

| Field | Type | Description |
|---|---|---|
| `discovered` | StandbyDiscovered | Result of the most recent complete bucket scan; a failed or cut-short scan leaves it unchanged. See below. |
| `conditions` | []Condition | Standard Kubernetes conditions. See below. |

`status.discovered`:

| Field | Type | Description |
|---|---|---|
| `lastScanTime` | time | When the most recent complete scan finished. |
| `latestDump` | object | The newest dump under the prefix, chosen by the completion time in its `@.json`: `name`, `location` (the dump directory's object key in the bucket, with a trailing `/`), and, when the metadata records them, `completionTime`, `gtidExecuted` and `sizeBytes`. Absent when the prefix holds no dump. |
| `binlogArchive` | object | The verified source PITR archive and the window its manifests cover, published together: `identity` (`archiveID`, `destination`, `source{namespace, name, uid}`, `encryptionMode`, `algorithm`, read from `archive.json` and checked against every manifest), `manifestCount`, `fileCount`, `sizeBytes`, `oldestEventTime` and `newestEventTime`. A site whose manifest carries a history-integrity marker counts in `manifestCount` but adds no files. Absent when the prefix holds no archive, or while the archive is refused (see `SourceConfigKnown`); `latestDump` is still published then. |

`kubectl get msc` shows `Dump` (the latest dump's name), `NewestBinlog` (the
newest archived event time), `Ready` (the `Ready` condition's status) and
`Age`.

### Conditions

| Type | Meaning |
|---|---|
| `Ready` | Summarises the two conditions below. `True` with reason `SourceDiscovered` when `BucketReadable` and `SourceConfigKnown` are both `True`; otherwise `False` with the reason and message of the first of the two that is not `True` (`BucketReadable` first). |
| `BucketReadable` | Bucket scan succeeded within the last discovery interval. Reason: `ListSucceeded` (True), `ListFailed` (False), `ScanIncomplete` (False — the `List` call did not complete before the scan deadline; a context deadline/cancel during `List`, distinct from a genuine `ListFailed`. The previous `status.discovered` is preserved), `AuthFailed` (False — store construction failed, e.g. bad credentials), or `ConfigError` (False — missing/invalid spec fields). |
| `SourceConfigKnown` | At least one full dump and one binlog manifest were found. Reason: `DumpFound` (True), `NoDumpFound` (False), `NoBinlogManifests` (False — **dump found, no PITR window yet**: a dump exists but no binlog manifests are under `<prefix>/binlogs/`, so recovery is limited to the dump. This is the expected state for a dump-only source or a brand-new source, **not** a misconfiguration), `MetadataUnreadable` (False — dump `@.json` present but genuinely malformed/cannot be parsed), `ScanIncomplete` (False — the scan was cut short by a context deadline/cancel before reading every dump `@.json` or all manifests, or a manifest was listed but is gone when read (message `manifest … was listed but is gone; rescanning`, for example after retention); the partial selection is **not** published, the previous `status.discovered` is preserved as last-known-good, and no `BucketScanned` event is emitted), `ConfigError` (False — propagated from storage backend error), or an archive refusal (False — the token without its `PITR` prefix: `ArchiveLegacy`, `ArchiveDescriptorMissing`, `ArchiveIdentityMismatch` (a manifest names another archive), `ArchiveEncryptionMismatch`, `ArchiveKeyMismatch`, `ArchiveVersionUnsupported` (also a damaged `archive.json`), `ArchiveObjectInvalid`, `ArchiveListFailed` (an S3 403: grant `s3:ListBucket`; other failures are retried), `ArchiveHistoryReset` (a site manifest records a reset epoch, so no replay from the archive is possible), `ArchiveUnsafeHistory` (every site's manifest carries a history-integrity marker), or `ArchiveUnreadable` (another error without a token; a manifest refusal keeps its own token, such as `ArchiveLegacy`, `ArchiveVersionUnsupported` or `ArchiveObjectInvalid`). A marked site among unmarked ones is left out of the published window. `latestDump` is still published without `binlogArchive`, and a Warning `PITRArchiveRefused` fires when the reason changes. The standby expects `Passphrase` / `AES-256-GCM` when `source.decryption` is set and `None` otherwise). |
