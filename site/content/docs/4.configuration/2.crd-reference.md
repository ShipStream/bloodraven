::caution
**Destructive and high-risk fields**


Review runbooks before changing `spec.restoreInPlace`, restore-related `confirm` tokens, reclone controls, and any field that changes `spec.sites`, `spec.credentials`, `spec.tls`, or MySQL images. Restore and reclone operations can replace data; image and credential changes can trigger restarts or failed reconnects.

### SiteSpec

Each entry in `spec.sites` defines one site in the failover group.

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `name` | string | Yes | -- | Unique site identifier (e.g. `iad`, `pdx`). Used in Service names, labels, and PITR archive keys. Lowercase letters, digits, and `-` only (`^[a-z0-9-]+$`). MaxLength=253. |
| `role` | string | No | `primary-candidate` | `primary-candidate` can be promoted; `dr-only` and `read-only` are never promoted. A reader provides a health-gated site-specific read pool. At least two `primary-candidate` sites are required. |
| `zone` | string | Yes | -- | Availability zone or region for pod scheduling |
| `taintNodeSelector` | map[string]string | Conditional | -- | Required and non-empty for `primary-candidate` and `dr-only`; optional for `read-only`. Selects nodes that receive this group's `db-readonly` taint. Accepted but ignored on readers, which never cause taint operations. |
| `lbIP` | string | Conditional | -- | Required and non-empty for `primary-candidate` and `dr-only`; optional for `read-only`. Used for active-primary DNS steering. Accepted but ignored on readers, which are never DNS targets. |
| `storage` | StorageSpec | Yes | -- | Persistent storage configuration for this site |
| `resources` | ResourceRequirements | No | -- | Compute resources (requests/limits) for the MySQL container at this site |
| `mysqlConf` | map[string]string | No | -- | Site-specific MySQL options applied after normalized group overrides, with the same key and value rules. Changing this map rolls only affected sites unless other drift is pending. |
| `serviceTemplate` | SiteServiceTemplate | No | -- | Scalar and annotation overrides for this site's client-facing MySQL Service. Does not affect sibling, primary, replicas, or internal Services. |

Reader manifests may retain legacy `lbIP` and `taintNodeSelector` values for
compatibility, but Bloodraven ignores them. Changing a reader to
`primary-candidate` or `dr-only` is rejected until both fields are present.
A reader does not satisfy the two-candidate minimum and cannot appear in
`splitBrainPolicy.sitePriorities`.

### Admission combinations

| Combination | Admitted? |
|---|---|
| Two `primary-candidate` sites, each with non-empty `lbIP` and `taintNodeSelector` | Yes |
| Two candidates plus a reader with both placement fields omitted | Yes |
| Reader with either or both legacy placement fields supplied | Yes; supplied values are ignored |
| Omitted/default role, explicit candidate, or `dr-only` with either placement field omitted | No |
| Fewer than two candidates, or a reader/DR site in `sitePriorities` | No |
| `externalTrafficPolicy` on an effective `ClusterIP` Service | No |
| Site `nodePort` on an effective `ClusterIP` Service | No |
| ETP on `NodePort`/`LoadBalancer`, or site NodePort in 1-65535 on those types | Yes; Kubernetes then applies its cluster-specific NodePort range |

### SplitBrainPolicySpec

Opt-in configuration for how the operator should behave when more than
one site is simultaneously writable and the operator cannot infer a
winner from prior failover history. See
[Split-brain resolution](/docs/operations/failover#split-brain-resolution) for a
full description of semantics and tradeoffs.

| Field | Type | Required | Description |
|---|---|---|---|
| `sitePriorities` | []string | No | Ordered list of `primary-candidate` site names. The operator walks the list and promotes the first entry that is currently writable; every other writable site is fenced. Empty or unset falls back to manual resolution (alert only). MaxItems=16. Entries must reference sites with role `primary-candidate`. |

| Field | Type | Required | Description |
|---|---|---|---|
| `operatorSecret` | string | Yes | Secret for operator and sidecar connections. Required keys: `username`, `password`, `MYSQL_ROOT_PASSWORD`. Optional: `MYSQL_REPLICATION_USER`, `MYSQL_REPLICATION_PASSWORD` (default to operator credentials). Grants: `ALL PRIVILEGES WITH GRANT OPTION`. |
| `appSecret` | string | No | Secret for application read-write connections. Keys: `username`, `password`. Grants on `*.*`: data and schema privileges (DML, DDL, views, routines, triggers, events, temporary tables, `LOCK TABLES`, `SHOW DATABASES`). No `GRANT OPTION`, `SUPER`, `CREATE USER`, or other administrative privileges. |
| `readOnlySecret` | string | No | Secret for application read-only connections. Keys: `username`, `password`. Grants: `SELECT`, `SHOW VIEW`, `SHOW DATABASES`, `PROCESS`. |
| `monitorSecret` | string | No | Secret for Prometheus exporter connections. Keys: `username`, `password`. Grants: `PROCESS`, `REPLICATION CLIENT`, `SELECT` on `performance_schema`. |
| `backupSecret` | string | No | Secret for backup connections (restore Jobs run as the operator account). Keys: `username`, `password`. Grants: `SELECT`, `LOCK TABLES`, `SHOW VIEW`, `EVENT`, `TRIGGER`, `RELOAD`, `BACKUP_ADMIN`, `REPLICATION CLIENT`. |

### BackupProfile (`spec.backup.profiles[]`)

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `name` | string | Yes | -- | Profile identifier, `[a-z0-9]([-a-z0-9]*[a-z0-9])?`, at most 63 characters. |
| `storage` | BackupStorage | Yes | -- | Tagged union: `type: S3` + `s3` block, or `type: PVC` + `pvc` block. `s3.prefix` (here, in `initFromBackup`/`restoreInPlace` S3 sources and in a standby's source) is at most 512 characters; empty segments (`a//b`) and `.` or `..` segments are refused at admission, and a leading or trailing `/` is allowed and ignored. Backups land under `<prefix>/<mysqlbackup-name>/` and the PITR archive under `<prefix>/binlogs/`. |
| `dump` | DumpOptions | No | -- | `util.dumpInstance()` tuning (threads, chunk size, compression, schema filters, consistent locking, OCIMDS checks). |
| `retention` | int | No | `7` | Legacy shorthand: max number of successful MysqlBackup CRs to keep. Ignored when `retentionPolicy` is set. |
| `retentionPolicy` | RetentionPolicy | No | -- | Structured retention: `count`, `maxAgeDays`, `minKeep` floor, `maxFailedKeep` cap. Replaces the `retention` shorthand. |
| `verification` | VerificationSpec | No | -- | Opt-in periodic restore-of-this-profile's-latest-backup into a throwaway MySQL instance; renders a CronJob when `enabled: true`. |
| `encryption` | BackupEncryptionSpec | No | -- | Enables client-side envelope encryption (AES-256-GCM + HKDF-SHA256) for every dump file and, when this profile is also used for PITR, every archived binlog. The passphrase is yours: the operator never generates it. It snapshots the bytes into immutable operator-made Secrets (one per accepted PITR archive key, one per backup), so pods never read your Secret directly. Changing the encryption or the bytes of a profile whose archive is in use is refused (at admission while PITR is enabled, otherwise on the `PITRArchiveBindingReady` condition); each backup's dumps use that backup's own snapshot. See [Backup encryption](/docs/backup-and-restore/backup-encryption). |

**Bounds.** `s3.bucket` is at most 63 characters, `s3.endpointURL` and
`s3.prefix` at most 512, `pvc.claimName` at most 253 and `pvc.subPath` at
most 512. They are bounded in UTF-8 bytes as well as characters (CEL
`bytes(self).size()`), at 63, 512, 512, 253 and 512 bytes, with messages such
as "bucket must be at most 63 bytes (UTF-8)" and "prefix must be at most 512
bytes (UTF-8)". They keep the admission rule on the `MysqlFailoverGroup` root
within the API server's CEL cost budget.

|---|---|---|---|---|
| `algorithm` | string | No | `AES-256-GCM` | Encryption algorithm. Only `AES-256-GCM` is currently supported. |
| `passphraseSecret` | PassphraseSecretRef | Yes | -- | Reference to a Secret in the same namespace holding the passphrase. See [PassphraseSecretRef](#passphrasesecretref). |

### PassphraseSecretRef

Reused by `BackupEncryptionSpec`, `BackupDecryptionSpec`,
`spec.initFromBackup.decryption`, `spec.restoreInPlace.decryption`, and the
`MysqlStandbyCluster` `source.decryption`; the bounds below apply to all of
them.

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `name` | string | Yes | -- | Name of the Secret, at most 253 characters. |
| `key` | string | No | `passphrase` | Key within the Secret that holds the passphrase bytes, at most 253 characters. Leading and trailing `\n`, `\r`, space and tab are stripped when the passphrase is read; other whitespace is part of the key. |

For a backup profile, the operator snapshots the passphrase (see
[Key snapshots](/docs/backup-and-restore/backup-encryption#key-snapshots));
a byte change on a profile whose PITR archive is in use is refused, and each
backup's dumps use that backup's own dump-key snapshot.

### BackupDecryptionSpec

Used on `spec.initFromBackup.decryption` and
`spec.restoreInPlace.decryption` to supply the passphrase that decrypts
an encrypted backup. When the source is a `mysqlBackupRef` and the field is
omitted, the operator uses the backup's own dump-key snapshot recorded in
`status.artifactStorage.passphraseSecret`; it never falls back to the
profile's live Secret (`PITRBackupDumpKeyMissing` when neither exists).

| Field | Type | Required | Description |
|---|---|---|---|
| `passphraseSecret` | PassphraseSecretRef | Yes | Secret holding the passphrase used at backup time. Rotating to a new value does not re-wrap existing ciphertext — it will simply fail to decrypt. |

### RetentionPolicy

Fields are independently optional; a successful MysqlBackup is kept iff
**any** enabled check says keep. `minKeep` is the safety floor that
prevents a retention sweep from wiping the last good backup after a
long outage of failing attempts.

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `count` | int | No | `0` | Max number of successful CRs to keep. 0 disables count-based pruning. |
| `maxAgeDays` | int | No | `0` | Max age in days of a successful CR before it becomes eligible for pruning. 0 disables age-based pruning. |
| `minKeep` | int | No | `1` | This many newest successful CRs are always kept, regardless of the other knobs. |
| `maxFailedKeep` | int | No | `10` | Cap on the Failed bucket, independent of the success retention policy. |

### PITRSpec (`spec.backup.pitr`)

Enables continuous binary-log archival so restores can target an
arbitrary `stopDatetime` on top of any retained full dump. See
[Backup and restore → Point-in-time recovery](/docs/backup-and-restore/backup-restore#point-in-time-recovery-pitr)
for the end-to-end story.

| Field | Type | Required | Description |
|---|---|---|---|
| `enabled` | bool | No | Turns archival on. Omitting the whole block is equivalent to `false`. |
| `profileName` | string | Yes when enabled | Name of a `spec.backup.profiles[]` entry, a DNS label of at most 63 characters (`[a-z0-9]([-a-z0-9]*[a-z0-9])?`). Binlog objects and per-site manifests live under a `binlogs/` subprefix inside that profile's storage. |
| `maxBinlogSize` | string | No | Passed to MySQL as `max_binlog_size`. Controls rotation cadence (and therefore the RPO gap). Default `"100M"`. |
| `archivePollInterval` | duration | No | Belt-and-suspenders scan cadence alongside inotify. Default `"60s"`. |

The archive under `<prefix>/binlogs/` carries a write-once descriptor
(`archive.json`) naming this group's UID, an archive ID derived from that UID
and the normalized destination, and the encryption mode. Manifests are
version 2 and name the archive ID. Writers need a store that enforces atomic
create. Prefixes written before v1.7.0 are refused (`ArchiveLegacy`): use a
new prefix and take a full backup. See
[Archive identity](/docs/backup-and-restore/backup-restore#archive-identity).
The operator always owns `replica-preserve-commit-order` (`ON`, for every
group, whether or not PITR is enabled). While PITR is enabled, replication or
binlog filters, `binlog_format` other than `ROW`
or `binlog_row_image` other than `FULL` in `spec.mysqlConf` are refused: they
are left out of the rendered my.cnf and reported by the condition
`PITRMysqlConfAccepted=False` / `PITRUnsafeSettingRefused` and a Warning
`PITRMysqlConfRefused`. `PITRArchiveReady=False` / `ArchiveUnsafeHistory`
comes only from a sidecar's history-integrity marker, that is, from a change
made outside the spec.

**Encryption change rule.** A validation rule on the `MysqlFailoverGroup` root
refuses an update that, with `pitr.enabled` true in both the old and new object
and the same `pitr.profileName`, changes that profile's `encryption` (its
presence, `algorithm`, `passphraseSecret.name` or `key`) while its storage
destination (type, bucket, prefix, endpoint, claim, sub-path) stays the same:

```
spec.backup.profiles[pitr.profileName].encryption (presence, algorithm, passphraseSecret) cannot change while that profile archives PITR binlogs to the same storage; create a new profile with a new storage prefix and its own passphrase, switch spec.backup.pitr.profileName to it, wait until its archive binding is Bound, then take a full backup (see Backup encryption > Rotation)
```

An omitted `algorithm` equals `AES-256-GCM` and an omitted `key` equals
`passphrase`. The rule compares references, so renaming the Secret to a copy
with the same bytes is refused too. Edits with PITR disabled, across a
`pitr.profileName` change, or together with a destination change pass
admission and are judged by the group's
[archive encryption binding](/docs/backup-and-restore/backup-encryption#archive-encryption-bindings).

### InitFromBackupSpec (`spec.initFromBackup`)

One-shot restore-on-first-boot. The operator runs a restore Job against
the initial primary site before normal bootstrap is considered
complete. Once `status.restore.phase == Succeeded`, subsequent
reconciles skip the restore even if this field is still set.

| Field | Type | Required | Description |
|---|---|---|---|
| `source` | InitFromBackupSource | Yes | Tagged reference: exactly one of `mysqlBackupRef`, `s3`, or `pvc`. |
| `loadOptions` | LoadOptions | No | `util.loadDump()` tuning (threads, skipBinlog, loadIndexes, schema filters). `resetProgress` is accepted but has no effect: restore Jobs disable load-progress tracking. |
| `pointInTime` | PointInTimeSpec | No | Post-load binlog replay to a specific target timestamp. Requires the source group to have had `spec.backup.pitr.enabled=true` at backup time. A validation rule requires `pointInTime.archiveProfileName` whenever `pointInTime` is set. |
| `decryption` | BackupDecryptionSpec | No | Passphrase to decrypt the source backup's dump. When omitted for a `mysqlBackupRef`, the operator uses the backup's recorded dump-key snapshot (`status.artifactStorage.passphraseSecret`), never the profile's live Secret. Replayed binlogs are decrypted with the archive's read-binding key snapshot, not with this Secret. |

### RestoreInPlaceSpec (`spec.restoreInPlace`)

Re-triggerable destructive restore against the currently-active
primary. Unlike `initFromBackup` (one-shot, greenfield), this field is
meant to be edited repeatedly: bumping `confirm` to a newer RFC 3339
timestamp re-arms another restore. See `RestoreInPlaceSpec` in the
source for full semantics (full-instance vs. per-schema restores).

| Field | Type | Required | Description |
|---|---|---|---|
| `confirm` | string | Yes | Anti-fat-finger token. Must be an RFC 3339 timestamp strictly greater than `status.restoreInPlace.confirmTokenUsed`. |
| `source` | InitFromBackupSource | Yes | Tagged reference: one of `mysqlBackupRef`, `s3`, or `pvc`. |
| `loadOptions` | LoadOptions | No | `util.loadDump()` tuning. For per-schema restores, `skipBinlog` is force-set to `false` so the DROP+load replicates. |
| `pointInTime` | PointInTimeSpec | No | Not supported: a restore that sets it is rejected (`RestoreInPlaceRejected`) before fencing, without consuming `confirm`. Use `initFromBackup.pointInTime` on a new group. See [Point-in-time recovery is not supported in place](/docs/backup-and-restore/backup-restore#point-in-time-recovery-is-not-supported-in-place). |
| `decryption` | BackupDecryptionSpec | No | Same semantics as `InitFromBackupSpec.Decryption`. |

### PointInTimeSpec (`spec.initFromBackup.pointInTime`)

Requests binlog replay on top of the loaded dump. Requires the source
failover group to have had `spec.backup.pitr.enabled=true` at the
time of the full dump — otherwise there is no archive to replay.

| Field | Type | Required | Description |
|---|---|---|---|
| `stopDatetime` | string | Yes | The target instant, a whole second. RFC 3339 (`2026-04-15T09:30:00Z`, `2026-04-15T09:30:00+02:00`) or `YYYY-MM-DD HH:MM:SS`, read as UTC. Pattern `^[0-9]{4}-[0-9]{2}-[0-9]{2}[T ][0-9]{2}:[0-9]{2}:[0-9]{2}(Z\|[+-]([01][0-9]\|2[0-3]):[0-5][0-9])?$`: a fractional second or an out-of-range offset is rejected at admission. An object admitted with a fractional second before v1.7.0 must be corrected before the v1.7.0 CRDs are applied: on Kubernetes older than 1.30 (no CRD validation ratcheting) every update of it fails, finalizer removal included, until an update also corrects the value (see the [v1.7.0 upgrade checklist](/docs/operations/upgrade-policy)). Commit times are compared to the microsecond. Replay restores the history of the first archived transaction committed at or after it, cut just before that transaction. |
| `archiveProfileName` | string | Yes under `initFromBackup` | `spec.backup.profiles` entry whose archive the restore reads. DNS label, 1–63 characters (`^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`). Required by a validation rule on `initFromBackup` ("pointInTime.archiveProfileName is required: name the backup profile whose PITR archive the restore reads"). It may not resolve to this group's own active PITR destination; destinations are compared normalized, so aliases are refused too, with `RestoreBuildFailed` / `PITRArchiveDestinationShared` before any Job is created. Replay considers every site manifest under that archive. |
| `allowPartial` | bool | No | Default `false`. Accept an archive with no transaction at or after `stopDatetime`: the restore then replays to the archive head (outcome `Partial`, reason `PointInTimePartial`). It relaxes nothing else; archive identity, lineage and continuity checks still apply. |
| `excludeGtids` | string | No | GTIDs that are never replayed, at most 131072 characters, in MySQL's GTID set syntax (tags, line breaks and upper-case UUIDs are accepted; the Job receives the set normalized). Every entry must start with a server UUID, and the canonical set (tags spelled out per tag) must fit 64 KiB, since it reaches the Job as one environment string; a set that does not parse, an entry without a UUID, or a longer canonical set fails at reconcile with `PITRTargetInvalid`. They must not intersect the backup (`PITRExcludeIntersectsBackup`). Every archived transaction committed between the backup's newest transaction and the target that is outside the target history must be listed (`PITRArchiveDivergentHistory` prints that set). Excluding a transaction on the target history skips its GTID, but later row images may still carry its effects; it is reported as `onHistoryExclusions`. See [Target history and excludeGtids](/docs/backup-and-restore/backup-restore#target-history-and-excludegtids). |

`sites` and `allowUnverifiedCrossSite` were removed in v1.7.0; replay
considers every manifest in the archive. See
[Restore to a target timestamp](/docs/backup-and-restore/backup-restore#restore-to-a-target-timestamp).

Reconcile-time refusals set `status.restore.reason` and emit
`RestoreBuildFailed` before any Job is created:

| Token | When |
|---|---|
| `PITRTargetInvalid` | `stopDatetime` cannot be parsed or has a fractional second (objects admitted before the pattern), `archiveProfileName` is empty or names no profile in `spec.backup.profiles`, or `excludeGtids` does not parse, has an entry that does not start with a server UUID, or exceeds 64 KiB canonical. |
| `PITRBackupIdentityUnknown` | The referenced `MysqlBackup` records no source failover group UID (`status.failoverGroupUID` is empty: a backup from before v1.7.0, which has no backup stamp), or a direct S3 or PVC source sits at the root of its store (no `prefix` or `subPath`), where no stamp can identify it. Take a new backup, or name the dump's directory in the source. |
| `PITRBackupFiltered` | `loadOptions.includeSchemas` or `excludeSchemas` is combined with `pointInTime`. |
| `PITRArchiveDestinationShared` | `archiveProfileName` resolves to this group's own active PITR destination. |

`PITRBackupAfterTarget` is not checked at reconcile: `status.completionTime`
includes the upload and would refuse valid targets. `dump-meta` and the
planner check the target against the dump's own end and the dumped server's
clock. A logged load (`loadOptions.skipBinlog: false`) is also refused. The
refusals `dump-meta`, `pitr-download` and `restore.py` can report are listed
in [Restore refusals](/docs/backup-and-restore/backup-restore#restore-refusals).

### PITR completion status (`status.restore`)

| Field | Type | Description |
|---|---|---|
| `jobUID` | string | Producing Job identity; a recreated Job with the same name never inherits the previous outcome. |
| `reason` | string | The failure token (the first word of the failing step's termination message, for example `PITRArchiveDivergentHistory`), or `PointInTimePartial` on a partial success. |
| `pointInTime` | [PointInTimeResult](#pointintimeresult) | The certified outcome of the replay, read from the replay's verdict. Unset without `pointInTime`. |

`status.restoreInPlace.pointInTime` has the same type; in-place restores
reject `pointInTime`, so it stays unset. The flat `pitrStopDatetime`,
`pitrReplayedBinlogFile`, `pitrReplayedBinlogCount`, `pitrNewestEventTime`,

### PointInTimeResult

One shape for `MysqlFailoverGroup.status.restore.pointInTime`,
`status.restoreInPlace.pointInTime` and `MysqlBackupVerification.status.pointInTime`.
It is filled only
from a verdict the operator accepted (see
[How the operator reads the outcome](/docs/backup-and-restore/backup-restore#how-the-operator-reads-the-outcome)).

| Field | Type | Description |
|---|---|---|
| `mode` | string | `Timestamp` or `Latest`. Required. |
| `stopTime` | MicroTime | The requested target, a whole second (commit times are compared against it to the microsecond). Unset in `Latest` mode. |
| `outcome` | string | `TargetCovered` (an archived transaction at or after the target exists; the restore is its history cut just before it), `Partial` (none exists and `allowPartial` accepted the archive head) or `ArchiveHead` (latest mode). Required. |
| `archive` | PITRArchiveIdentity | The archive the replay read: `archiveID`, `destination`, `source{namespace, name, uid}`, `encryptionMode` and `algorithm`. |
| `replaySites` | []string | Sites whose archived binlogs were staged, sorted. At most 16. |
| `replaySitesOmitted` | int32 | Further staged sites the verdict's bounded site list left out; `replaySites` is complete only when this is zero or unset. |
| `segmentCount` | int32 | Number of replay segments. |
| `replayedBinlogCount` | int32 | Number of distinct archived binlogs the segments read. |
| `lastReplayedBinlog` | `{site, name}` | The file of the last segment. |
| `replayedTransactionCount` | int64 | Transactions replayed on top of the backup. |
| `newestReplayedCommitTime` | MicroTime | Newest original commit time among the replayed transactions. Never the requested target. |
| `excludedDivergentTransactionCount` | int64 | \|D\|: transactions committed between the backup's newest transaction and the target, outside the target history, that `excludeGtids` excluded. |
| `onHistoryExclusions` | string | Excluded transactions on the target history that precede a replayed one. Their GTIDs were skipped, but later row images may carry their effects; the result is not certified for them. At most 2048 characters; empty when the set is longer (the count still counts it). |
| `onHistoryExclusionCount` | int64 | Number of GTIDs in `onHistoryExclusions`. |
| `gtidExecuted` | string | The target's `@@global.gtid_executed` after replay, which the replay proved equal to the target history minus `excludeGtids`. Empty when longer than 2048 characters. |
| `gtidExecutedSHA256` | string | Hex SHA-256 of `gtidExecuted` as the server printed it (newlines removed); set even when `gtidExecuted` is too long to record. |

### PointInTimeVerificationSpec (`MysqlBackupVerification.spec.pointInTime`)

Also used by `spec.backup.profiles[].verification.pointInTime` for schedules.
Verification has no partial override. `sites` was removed in v1.7.0;
verification reads every manifest in the selected PITR archive.

| Field | Type | Default | Description |
|---|---|---|---|
| `mode` | string | `none` | `none`, `latest`, or `timestamp`. `latest` replays to the unique archive head and requires archived transactions beyond the loaded dump (`PITRNoArchivedReplay` otherwise). |
| `timestamp` | string | -- | Required for `timestamp`. Same forms and pattern as `PointInTimeSpec.stopDatetime` (a whole second; fractional seconds are rejected; correct any older fractional value before applying the v1.7.0 CRDs). The archive must hold a transaction at or after it (`PITRTargetNotCovered` otherwise). |
| `archiveProfileName` | string | `spec.backup.pitr.profileName` | The backup profile whose PITR archive the replay reads, a DNS label of 1 to 63 characters. Use it to verify history in a retained archive after a prefix switch. The replay mounts that archive's binding key snapshot. |
| `excludeGtids` | string | -- | Same meaning and checks as `PointInTimeSpec.excludeGtids` (entries start with a server UUID; at most 64 KiB canonical), at most 131072 characters: list the archived transactions committed between the backup's newest transaction and the target (or the archive head) that are outside the target history. |

A Succeeded PITR verification records `status.pointInTime`
([PointInTimeResult](#pointintimeresult)) and
`status.replayedThroughBinlog` (`file` is the last segment's file name,
`timestamp` the newest replayed commit time; `position` is not set). A
latest-mode verdict that reports divergent transactions is refused
`PITRCoverageInvalid`. A verification without
`pointInTime.archiveProfileName` replays the group's own active archive, so it
needs `spec.backup.pitr.enabled` (`PITRTargetInvalid` otherwise: "... so group
`<g>` has no active PITR archive to replay; set `pointInTime.archiveProfileName`
to the profile of the archive to replay (a retained archive needs no writer),
enable spec.backup.pitr, or verify without pointInTime"); naming
`archiveProfileName` replays a retained archive and needs no writer. When building its Job is refused with a PITR token
(`PITRTargetInvalid`, `PITRBackupIdentityUnknown`, …), the token is the
`Verified` condition's reason, not `BuildJobFailed`.

### EncryptionAtRestSpec (`spec.encryptionAtRest`)

Requires `spec.tls`: MySQL mandates a secure connection to clone
encrypted data and Bloodraven bootstraps every replica with `CLONE
INSTANCE`. The CRD rejects `enabled: true` without it.

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `enabled` | bool | Yes | `false` | Turn on data-at-rest encryption for every site. Refused on a group that is already serving unless the `bloodraven.shipstream.io/encryption-adopt=confirm` annotation is set. |
| `coverage` | EncryptionCoverageSpec | No | all `true` | Which encryption settings the operator enforces. See [EncryptionCoverageSpec](#encryptioncoveragespec). |
| `keyring` | KeyringSpec | No | -- | Keyring component paths and escrow lifecycle. See [KeyringSpec](#keyringspec). |

### EncryptionCoverageSpec

Every field defaults to `true`. These are operator-owned once encryption
is enabled: a `spec.mysqlConf` entry naming the same option is ignored,
so a stray override cannot silently downgrade a site. Turning one off
narrows the security claim.

| Field | Type | Default | MySQL setting |
|---|---|---|---|
| `tables` | bool | `true` | `default_table_encryption`. Applies to schemas and tables created afterwards; does not rewrite existing data. |
| `privilegeCheck` | bool | `true` | `table_encryption_privilege_check`. Stops application users opting individual tables out of encryption. |
| `redoLog` | bool | `true` | `innodb_redo_log_encrypt` |
| `undoLog` | bool | `true` | `innodb_undo_log_encrypt` |
| `binaryLog` | bool | `true` | `binlog_encryption` (covers relay logs on replicas too) |
| `systemTablespace` | bool | `true` | `ALTER TABLESPACE mysql ENCRYPTION='Y'`, run once by the sidecar on the writable site. Not covered by `default_table_encryption`; without it the data dictionary (schema, table, and column names) stays readable on a stolen PVC. |

### KeyringSpec

`mysqldDir` and `pluginDir` are image-specific. The defaults match the
official `mysql:9.x` images — MySQL only reads its global component
manifest from the directory holding `mysqld`, and its global component
config from `plugin_dir`, so a wrong value shows up as InnoDB refusing to
start. The three directory fields must be absolute paths made of
`A-Z a-z 0-9 . _ / -` (no trailing `/`), because the operator embeds them in
the `mysqld` launcher script.

| Field | Type | Default | Description |
|---|---|---|---|
| `dataFileDir` | string | `/run/mysql-keyring` | Keyring mount point. It must be outside the actual MySQL datadir. Admission rejects `/var/lib/mysql` and descendants; custom-image datadirs require manual verification. |
| `mysqldDir` | string | `/usr/sbin` | Directory containing the `mysqld` binary; `mysqld.my` is subPath-mounted here. |
| `pluginDir` | string | `/usr/lib64/mysql/plugin` | MySQL `plugin_dir`; `component_keyring_file.cnf` is subPath-mounted here. |
| `retainVersions` | int | `5` | Superseded escrow Secret versions kept per site (2--50). The version a site is currently sealed against is never pruned. |
| `escrowTimeoutSeconds` | int | `600` | How long before a site that has not escrowed its keyring is reported `Failed`. Minimum 30. The site stays unsealed and the operator keeps retrying either way. |

### Annotations

[Well-known metadata](/docs/configuration/well-known-metadata) gives each planned-failover key's writer, value grammar and stability level.

| Annotation | Description |
|---|---|
| `bloodraven.shipstream.io/last-failover` | Operator-owned out-of-band copy of `status.lastFailover`, formatted as an RFC3339 UTC timestamp at second precision. Do not edit manually. Reset tooling clears it together with status history. |
| `bloodraven.shipstream.io/last-failover-target` | Operator-owned out-of-band copy of `status.lastFailoverTarget`. It is always written and cleared as a pair with `last-failover`. Do not edit manually. |
| `bloodraven.shipstream.io/reclone-site` | Triggers a `CLONE INSTANCE` from the current primary to the named site. Both forms act as a fat-finger interlock (cold path added by AUDIT L3 / WISHLIST #5). Invalid annotations are rejected with a `RecloneRejected` Warning Event and cleared. Valid ones emit `RecloneRequested` and report progress via the `Bootstrapping` condition. The operator also writes this annotation itself to drain `status.restoreReclones` after a full-instance in-place restore; it never overwrites a value someone else set. |
| `bloodraven.shipstream.io/planned-failover` | Starts a planned failover to the named site: `<site>[:maxLagWait=<duration>]`. The grammar is `<subject>(:<key>=<value>)*`: values use only `A-Za-z0-9._/+-`, each key appears once, and an empty or unknown pair is rejected. The operator removes it once the run is accepted (or kept while `Deferred`). When Dragonfly is enabled, the planned-failover status includes a `dragonfly` substatus with session-preservation details. |
| `bloodraven.shipstream.io/acknowledge-planned-failover-hold` | Set by an administrator to the held run's `runID` (`status.plannedFailoverHold.runID`), or with `kubectl bloodraven ack-planned-failover-hold <group>`, to acknowledge an automation hold (`AutomaticFailoverHeld=True`) after resolving the split brain. The operator clears the hold and then removes the annotation. A value naming another run, a value given when no hold stands, or one beside a claim held for another run resumes nothing and gets a `PlannedFailoverHoldAcknowledgementIgnored` Warning Event; when no hold stands the annotation is removed anyway. |
| `bloodraven.shipstream.io/planned-failover-terminal` | Operator-owned: a versioned JSON payload, `{"schemaVersion":1,"runID":"<runID>","outcome":"<outcome>","reason":"<reason>","warnings":["<warning>"]}` (`reason` and `warnings` may be omitted). `warnings` are the run's terminal warnings (API warning tokens); the terminal record a marker-ended run gets keeps them and adds `StatusStalled`, and a marker carrying `FenceNotAttributable` never names the source for re-assert, also after a restart. A value that is not this payload, or has another `schemaVersion`, is ignored and logged; a payload the strict parser rejects (an unknown field, a newer `schemaVersion`, an unfamiliar reason) that is still JSON naming a run with outcome `ManualRecoveryRequired` is treated as a hold, and the acknowledgement can delete it. Ends a run whose status writes stalled for 2 minutes; every planned-failover check treats the named run as terminal. Removed once the terminal status record lands, except that a `ManualRecoveryRequired` marker is a hold record and is removed only by the acknowledgement. Do not edit. |
| `bloodraven.shipstream.io/planned-failover-stall-since` | Operator-owned: `<runID>:since=<YYYYMMDDThhmmssZ>`. The durable start of the status-stall deadline. Do not edit. |
| `bloodraven.shipstream.io/planned-failover-manager-absent-since` | Operator-owned: `<runID>:since=<YYYYMMDDThhmmssZ>`. The durable start of the 5-minute manager-absence deadline. Do not edit. |
| `bloodraven.shipstream.io/planned-failover-confirmed` | Operator-owned: `<runID>:since=<YYYYMMDDThhmmssZ>`, the time the run's promotion was confirmed. Written after the run's promotion is confirmed, recorded and published, and before its claim is released (if the write fails the claim is kept and retried). A restart before the `Publishing` write commits treats the run as recorded from it: no claim is hydrated and the run publishes without one, even if a later emergency failover replaced the run's failover record. Removed when the run ends; one a finished run left behind is removed by the next pass, as are its `stall-since` and `manager-absent-since` annotations. Do not edit. |
| `bloodraven.shipstream.io/planned-failover-status-fence` | Operator-owned: an ISO 8601 basic UTC instant with nanoseconds (`20261104T100000.123456789Z`) bumped, conditioned on the `resourceVersion` an ambiguous status write was made against, to prove that write can never commit. | `bloodraven.shipstream.io/promotion-gtid-executed` | Operator-owned out-of-band copy of `status.promotionGtidExecuted`, written with `last-failover` and `last-failover-target` and conditioned on the object's `resourceVersion`. | `bloodraven.shipstream.io/promotion-gtid-executed-for` | Operator-owned: `<RFC3339 last-failover> <last-failover-target>`, binding `promotion-gtid-executed` to its failover event. | `bloodraven.shipstream.io/dragonfly-snapshot-upgrade` | Starts the Dragonfly snapshot-restore upgrade workflow to the target image. Requires `spec.dragonfly.snapshot` to be configured. |
| `bloodraven.shipstream.io/rotate-keyring` | Rotates the named site's InnoDB master key. **Refused on the active primary** -- rotation is the one operation whose failure window would cost data rather than a re-clone, so the supported procedure is to rotate replicas, run a planned failover, then rotate the ex-primary. ## `MysqlBackup`

One backup run. Created by hand or by a schedule CronJob. See
[Backup and restore](/docs/backup-and-restore/backup-restore). The spec names
the failover group (`spec.failoverGroupRef.name`), the profile
(`spec.profileName`) and optionally `spec.sourceSiteOverride`. A name ending
in `.bloodraven-backup.json` is refused at admission: that suffix is the
[backup stamp](/docs/backup-and-restore/backup-restore#backup-stamp)
object's.

### Status

| Field | Type | Description |
|---|---|---|
| `phase` | string | `Pending`, `Running`, `Succeeded` or `Failed`. |
| `startTime`, `completionTime` | timestamp | When the backup Job started and reached a terminal state. |
| `jobName` | string | The producing backup Job. |
| `sourceSite` | string | The site the dump was taken from. |
| `location` | string | Resolved artifact location: a bucket-relative prefix for plain S3 (`<prefix>/<name>`), `s3://<bucket>/<prefix>/<name>/` for encrypted S3, or `/backups[/<subPath>]/<name>` for PVC. |
| `storageType` | string | `S3` or `PVC`. |
| `artifactStorage` | ArtifactStorage | Where the producing Job wrote the artifact. Artifact cleanup deletes only from here. Immutable once `location` is set (see below). |
| `size`, `sizeBytes` | string, int | Reported artifact size. |
| `gtidExecuted`, `binlogFile`, `binlogPos` | string, string, int | Source coordinates at dump time. |
| `encrypted`, `encryptionAlgorithm` | bool, string | Whether the artifact is encrypted, and how. |
| `failoverGroupUID` | string | `metadata.uid` of the source failover group. Pinned on the backup Job as annotation `bloodraven.shipstream.io/failover-group-uid` when the Job is created, and recovered from the Job if the status write is lost. The backup stamp records the same UID. |
| `pitrArchiveID` | string | The archive ID the group's rendered PITR writers used when the Job was created (`^(ar1-[a-z2-7]{26})?$`): the one every site Deployment's render agrees on. A backup of the active PITR profile waits `Pending` with reason `PITRArchiveRolloutPending` while a roll changes it (some renders decode and they disagree). Any other backup never waits: when the renders disagree or one is unreadable it proceeds with this field empty, as does a backup of the PITR profile while the render is deferred (any site Deployment lacks a decodable render while the write binding is not `Bound`/`Establishing`: the pre-v1.7.0 deferral, which does not wait for a roll); either way a Normal Event `PITRArchiveNotStamped` says why, and the backup is no point-in-time baseline. Empty when PITR was off. Pinned as annotation `bloodraven.shipstream.io/pitr-archive-id` and recovered from the Job. |
| `attempt` | int | Retry attempt for scheduled retries. |
| `conditions` | []Condition | See below. |

Reasons from archive encryption bindings: `Pending` with
`PITRArchiveRolloutPending` (a backup of the active PITR profile while the
sites render different archive IDs),
`PassphraseSecretMissing` (the encrypted profile's Secret or key is missing,
so no dump-key snapshot can be made) or `DumpKeySnapshotConflict` (the
dump-key snapshot name is held by another backup's Secret); `Failed` with
`ProfileReadOnly` (the profile is
[read-only](/docs/backup-and-restore/backup-encryption#read-only-profiles)).

### ArtifactStorage (`status.artifactStorage`)

Recorded from the producing Job when it is created, or recovered from that Job
for backups taken by older operators. Cleanup never follows later edits of the
profile's bucket, endpoint, prefix, `subPath` or claim.

| Field | Type | Description |
|---|---|---|
| `location` | string | The exact artifact location the producing Job wrote. Cleanup runs only when `status.location` is identical. |
| `bucket` | string | S3 bucket. |
| `endpointURL` | string | S3 endpoint override in effect for the Job; empty for AWS. |
| `region` | string | S3 region in effect for the Job. Cleanup signs for `us-east-1` when no region is set anywhere, as mysqlsh does. |
| `claimName` | string | PersistentVolumeClaim (PVC storage). |
| `passphraseSecret` | `{name, key}` | For an encrypted backup, the backup's own immutable dump-key snapshot (`mysqlbackup-<name>-dump-key-<uid prefix>`, key `passphrase`) that the producing Job mounted. Restore and verification decrypt the dump with it, and deleting a backup that never succeeded reads its backup stamp with it; the profile's live Secret is used only when no Secret was recorded. The snapshot is deleted after the backup's artifacts are confirmed deleted. |

Credentials are deliberately not part of it: cleanup reads them from the
profile's current `credentialsSecret`, so rotating keys needs no change on old
backups. Cleanup also deletes the backup stamp,
`<location>.bloodraven-backup.json`; see
[Backup stamp](/docs/backup-and-restore/backup-restore#backup-stamp).

Once `location` is recorded, a validation rule on the `MysqlBackup` resource
rejects any update that changes or removes `status.artifactStorage`, including
removing or nulling the whole `status` through the status subresource. The
rule is evaluated on the resource root, so it cannot be bypassed by dropping
the parent object first.

### Conditions

| Type | Meaning |
|---|---|
| `JobCreated` | The producing Job was created. |
| `Ready` | `True` once the backup succeeded with a known artifact destination. |
| `MetadataComplete` | Optional completion metadata (size, GTID, binlog coordinates) was collected; `DestinationUnavailable` means the artifact location is unknown. |
| `ArtifactCleanup` | Only on a Terminating backup: why its artifact has not been removed yet. See [Artifact cleanup](/docs/backup-and-restore/backup-restore#artifact-cleanup) for the reasons. Before releasing an abandoned backup (one that never succeeded, or whose group or profile is gone) the operator stops its producing backup Job and waits for the Job's pods; a lost status update after the Job was created is recovered from the Job, running or failed. `False` / `ProducerStopStuck`, with a Warning `ArtifactCleanupProducerStuck`, when a producer pod has not stopped 10 minutes after the deletion: the deletion stays held, because the pod may still write to the destination. Once its node is confirmed down, `kubectl delete pod <pod> --force --grace-period=0`. |

### Annotations

| Annotation | Meaning |
|---|---|
| `hold.verification.shipstream.io/<verification UID>` | Value is the verification name. A `MysqlBackupVerification` is reading this backup; retention and artifact cleanup wait while it is live. ## `MysqlStandbyCluster`

**Phase 1 of WISHLIST #7.** A passive DR relationship descriptor that
lives on the DR cluster and continuously monitors a source
`MysqlFailoverGroup`'s dumps and PITR archive in a shared object store. The
controller populates `status.discovered` and stamps readiness conditions
on a configurable cadence. **No mysqld is started, no dump is loaded and
nothing is written to the bucket.**

See [Multi-cluster DR](/docs/architecture/multi-cluster-dr) for the end-to-end
recovery runbook and a full explanation of what the standby does and does
not provide.

### Top-level spec fields

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `transport` | string | No | `ObjectStore` | Transport mode. `ObjectStore` is the only value. |
| `source` | StandbySource | Yes | -- | The source group's S3 destination and optional decryption. |
| `freshness` | StandbyFreshnessSpec | No | -- | Bucket-discovery cadence (`discoveryInterval` only). |

### StandbySource

| Field | Type | Required | Description |
|---|---|---|---|
| `s3` | StandbyS3Source | Yes | The S3-compatible destination the source group's backup profile writes to. The controller only reads it. |
| `decryption` | BackupDecryptionSpec | No | Passphrase Secret to decrypt source artifacts. Must exist in the DR namespace. |

The standby identifies its source by the prefix alone. The archive
descriptor under `<prefix>/binlogs/` names the source group (namespace, name
and UID), and the standby publishes it in `status.discovered.binlogArchive.identity`.
Use metadata labels for a display name.

### StandbyS3Source

The S3 fields of a backup profile's `storage.s3` that apply to a reader,
with `prefix` required. The bounds are the profile's (see
[BackupProfile](#backupprofile-specbackupprofiles)).

| Field | Type | Required | Description |
|---|---|---|---|
| `bucket` | string | Yes | S3 bucket name, 1-63 bytes. |
| `prefix` | string | Yes | The source profile's prefix, at most 512 bytes, with at least one segment. A leading or trailing `/` is ignored; empty, `.` and `..` segments are refused. The standby scans `<prefix>/<dump>/` and `<prefix>/binlogs/`. |
| `region` | string | No | AWS region. Optional for non-AWS S3 stores. |
| `endpointURL` | string | No | Absolute `http://` or `https://` endpoint override without credentials, a query or a fragment, at most 512 bytes. |
| `credentialsSecret` | string | Yes | Secret in this namespace with `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` (and optionally `AWS_SESSION_TOKEN`, `AWS_REGION`) for read access. |

### StandbyFreshnessSpec

| Field | Type | Default | Description |
|---|---|---|---|
| `discoveryInterval` | duration | `5m` | How often the controller re-scans the bucket to refresh `status.discovered`. Minimum `30s`. |

Restore verification and activation are not implemented, so the API has no
fields for them: no verification cadence or staleness knobs, no activation
request and no template of the group an activation would create. Unknown
fields have no effect: the API server prunes them (they are silently dropped
and never persisted), and clients using strict server-side field validation —
the default for `kubectl apply`/`create` since Kubernetes 1.25 — reject them
outright.

### Status

| Field | Type | Description |
|---|---|---|
| `discovered` | StandbyDiscovered | Result of the most recent complete bucket scan; a failed or cut-short scan leaves it unchanged. See below. |
| `conditions` | []Condition | Standard Kubernetes conditions. See below. |

`status.discovered`:

| Field | Type | Description |
|---|---|---|
| `lastScanTime` | time | When the most recent complete scan finished. |
| `latestDump` | object | The newest dump under the prefix, chosen by the completion time in its `@.json`: `name`, `location` (the dump directory's object key in the bucket, with a trailing `/`), and, when the metadata records them, `completionTime`, `gtidExecuted` and `sizeBytes`. Absent when the prefix holds no dump. |
| `binlogArchive` | object | The verified source PITR archive and the window its manifests cover, published together: `identity` (`archiveID`, `destination`, `source{namespace, name, uid}`, `encryptionMode`, `algorithm`, read from `archive.json` and checked against every manifest), `manifestCount`, `fileCount`, `sizeBytes`, `oldestEventTime` and `newestEventTime`. A site whose manifest carries a history-integrity marker counts in `manifestCount` but adds no files. Absent when the prefix holds no archive, or while the archive is refused (see `SourceConfigKnown`); `latestDump` is still published then. |

`kubectl get msc` shows `Dump` (the latest dump's name), `NewestBinlog` (the
newest archived event time), `BucketReadable`, `SourceKnown` and `Age`.

### Conditions

| Type | Meaning |
|---|---|
| `BucketReadable` | Bucket scan succeeded within the last discovery interval. Reason: `ListSucceeded` (True), `ListFailed` (False), `ScanIncomplete` (False — the `List` call did not complete before the scan deadline; a context deadline/cancel during `List`, distinct from a genuine `ListFailed`. The previous `status.discovered` is preserved), `AuthFailed` (False — store construction failed, e.g. bad credentials), or `ConfigError` (False — missing/invalid spec fields). |
| `SourceConfigKnown` | At least one full dump and one binlog manifest were found. Reason: `DumpFound` (True), `NoDumpFound` (False), `NoBinlogManifests` (False — **dump found, no PITR window yet**: a dump exists but no binlog manifests are under `<prefix>/binlogs/`, so recovery is limited to the dump. This is the expected state for a dump-only source or a brand-new source, **not** a misconfiguration), `MetadataUnreadable` (False — dump `@.json` present but genuinely malformed/cannot be parsed), `ScanIncomplete` (False — the scan was cut short by a context deadline/cancel before reading every dump `@.json` or all manifests, or a manifest was listed but is gone when read (message `manifest … was listed but is gone; rescanning`, for example after retention); the partial selection is **not** published, the previous `status.discovered` is preserved as last-known-good, and no `BucketScanned` event is emitted), `ConfigError` (False — propagated from storage backend error), or an archive refusal (False — the token without its `PITR` prefix: `ArchiveLegacy`, `ArchiveDescriptorMissing`, `ArchiveIdentityMismatch` (a manifest names another archive), `ArchiveEncryptionMismatch`, `ArchiveKeyMismatch`, `ArchiveVersionUnsupported` (also a damaged `archive.json`), `ArchiveObjectInvalid`, `ArchiveListFailed` (an S3 403: grant `s3:ListBucket`; other failures are retried), `ArchiveHistoryReset` (a site manifest records a reset epoch, so no replay from the archive is possible), `ArchiveUnsafeHistory` (every site's manifest carries a history-integrity marker), or `ArchiveUnreadable` (another error without a token; a manifest refusal keeps its own token, such as `ArchiveLegacy`, `ArchiveVersionUnsupported` or `ArchiveObjectInvalid`). A marked site among unmarked ones is left out of the published window. `latestDump` is still published without `binlogArchive`, and a Warning `PITRArchiveRefused` fires when the reason changes. The standby expects `Passphrase` / `AES-256-GCM` when `source.decryption` is set and `None` otherwise). The default `kubectl get` printcolumn surfaces this as the neutral `SourceKnown`. |
