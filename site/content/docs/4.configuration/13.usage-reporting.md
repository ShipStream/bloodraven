---
title: Usage reporting
description: The anonymous daily report the operator sends, exactly what it contains and keeps, and how to turn it off.
---

The operator sends one small anonymous report a day. It tells us how many
installs are running and which versions they run, so we know which releases
still need fixes. In return the operator learns the latest release and tells
you when yours is behind. The report is on by default and one setting turns it
off.

## What is sent

One HTTPS `POST` to `https://telemetry.bloodraven.dev/v1/report` with this body,
and nothing else:

```json
{"installId":"5f0c1e9a-3b7d-4c2e-9a41-6d8f2b7e0c13","version":"1.9.0","groups":3,"sites":6,"nodes":7}
```

| Field | What it is |
|---|---|
| `installId` | A random UUID the operator generates the first time it reports. It is not derived from anything in your cluster. |
| `version` | The operator's release. |
| `groups` | The number of `MysqlFailoverGroup` objects. |
| `sites` | The total number of sites across those groups. |
| `nodes` | The number of nodes in the cluster. |

The report has no names, namespaces, hostnames, IP addresses, labels, license
details, or anything from your databases. The `User-Agent` header is
`bloodraven/<version>`. The code that builds the report is
[`internal/telemetry`](https://github.com/shipstream/bloodraven/tree/main/internal/telemetry),
and a test fails if the payload gains a field this page does not list.

## What is kept

The receiving service, whose source is in
[`telemetry-server/`](https://github.com/shipstream/bloodraven/tree/main/telemetry-server),
keeps at most one report per install per day (a later report that day replaces
the earlier one), with the time it arrived. It also stores the network operator
and country of the address the report came from (for example
`AS16509 Amazon.com, Inc.` and `US`).

**The service never writes the IP address to its database or its logs.** To
find the network operator and country it sends the address to
[ipinfo.io](https://ipinfo.io). Its in-memory lookup cache (up to a day) and
rate limiter (up to an hour) keep only a keyed hash of the address, under a key
that is made at start and never stored. The service runs on
[Railway](https://railway.com), whose edge records the address of each request
in its own request logs for that platform's log retention period.

Reports are deleted after 400 days. They are used only to count active installs,
versions and deployment sizes. They are not sold or shared, and they are never
matched with license purchases.

## When it is sent

- Only the operator replica that holds the leader lease reports, so a highly
  available operator counts once.
- The first report goes 2 to 10 minutes after that replica starts, so a pod in
  a crash loop does not report. After that it reports about every 24 hours,
  with up to an hour of random offset either way.
- The install ID is stored in the ConfigMap `bloodraven-telemetry` in the
  operator's namespace. Nothing owns that ConfigMap, so uninstalling and
  reinstalling the chart keeps the same ID. Delete the ConfigMap to start
  over with a new one.

A report that fails, because the cluster has no egress, a proxy refuses it, or
the service is down, changes nothing: the first failure in a process is logged
once at INFO as `usage report failed`, later ones at debug level. Reconciling and
failover never wait for the report and never depend on it. A setting the
operator cannot read (`BLOODRAVEN_TELEMETRY` that is not a boolean, or an
endpoint that is not an http(s) URL) turns the report off with a warning; it
never stops the operator. The chart refuses such values at `helm upgrade`.

## What you get back

The response names the latest release. When it is newer than the running
operator, the leader logs `newer bloodraven release available` once (see the
[log schema](/docs/observability/log-schema#usage-reporting)) and exports
`bloodraven_update_available{latest_version="…"} 1` (see
[monitoring](/docs/observability/monitoring)). With reporting turned off,
neither appears.

## Turning it off

Any of these turns the report off. The operator then makes no connection
to the service at all:

- The chart value `telemetry.enabled=false`:

  ```bash
  helm upgrade bloodraven bloodraven/bloodraven --namespace bloodraven \
    --version "$(helm get metadata bloodraven --namespace bloodraven -o json | jq -r .version)" \
    --reuse-values --set telemetry.enabled=false
  ```

  The `--version` keeps the chart you run; leave it out to upgrade at the same
  time. Use your release's name and namespace.

- The operator flag `--telemetry=false`, or the environment variable
  `BLOODRAVEN_TELEMETRY=false` (which the chart sets).
- The environment variable `DO_NOT_TRACK=1`, the cross-tool
  [convention](https://consoledonottrack.com), for example through the chart's
  `extraEnv`.

The operator logs whether the report is on at every start:
`anonymous usage reporting enabled` or `anonymous usage reporting disabled`,
with the reason. To remove the install ID too, delete the ConfigMap:

```bash
kubectl -n <operator-namespace> delete configmap bloodraven-telemetry
```

## Network access

The report needs outbound HTTPS from the operator pod to
`telemetry.bloodraven.dev` on port 443. The operator uses `HTTPS_PROXY` and
`NO_PROXY` from its environment (set them with the chart's `extraEnv`). To send
the report through your own forwarding endpoint, set `telemetry.endpoint` to
its URL. The operator follows no redirects, so the report reaches the configured
endpoint or nobody. An egress NetworkPolicy that blocks the connection is fine:
the report simply fails, as above.
