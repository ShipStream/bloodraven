# Connection pools that survive a promotion

**Unit:** 4 — Where failover meets your application
**Objectives (unit-numbered):**
4. Explain why an open pooled connection keeps serving stale reads after a correct failover   [obj 4]
5. Choose a failover strategy — taint-based, Service-based, or site-local warm standby — for a given application   [obj 5]
6. Fix a pool with bounded connection lifetime, error-class retry, and a read/write split   [obj 6]

## Topic generation prompt

**Open by naming the wall from Unit 3 and resolving it.** This is the payoff the course has been building towards since the learner held a site down and watched everything work. Restate it in the first paragraph in the learner's own terms: the operator promoted in about twelve seconds, the DNS record flipped, the `-primary` selector moved to the surviving site, every status field said what it should — and the counter application carried on serving successful reads from the demoted site, with no alert anywhere. Say directly: nothing in that list was broken. The failover was correct. The application was broken, and the mechanism is small enough to state in three sentences.

Teach the mechanism in this order and do not reorder it.

First: a Service selector flip changes routing for **new connections only**. kube-proxy picks a backend at connection establishment; an established flow is not re-evaluated and is not reset. Every pooled connection your application opened before the promotion still points at the same pod it always did.

Second: `super_read_only` blocks writes but **closes no sockets**. Fencing is a variable change, not a disconnection. A surviving session therefore keeps serving stale reads until the site is next promoted or demoted — the reads succeed, return plausible data, and are wrong by however far the demoted site has drifted.

Third: the operator has exactly one mitigation, `KillAppConnections`, and the learner must know its limits precisely. It is best-effort, single-pass, never retried, and it runs **only if the old primary is reachable** — it kills everything in `information_schema.processlist` except itself and the binlog dump threads. In the Unit 3 scenario the site was held down, so it could not run at all. In a partition it will not run either. **Pre-empt the objection explicitly**: the sharp learner will already be thinking "but the operator kills app connections". Say so, then answer it — the mitigation exists, it is one pass on a best-effort path, and it is precisely absent in the failure modes that produce this symptom. The answer makes the lesson stronger, not weaker.

Then be honest about the project's own position, without dating the reading. Point at the version appendix for the issue state — this is a live, acknowledged gap, not history the learner is reading for context. The project's own wording is that an autonomous sidecar self-fence has no operator-side connection drain, and that only planned failover actually drains. Nothing else does. Add the observability half: no alert in Bloodraven's alert-runbook map fires for this. `BloodravenFailoverOccurred` is informational and operator-scoped — it tells you a promotion happened, and its runbook column already lists "app writes" as something a human must go and check. Nothing is watching your pool.

Now widen it so this does not read as a Bloodraven quirk, because it is not one. HikariCP carries an open issue titled "got a read-only connection from the connection pool after the db failover". Pool validation queries **pass** against a demoted primary — the node is alive, it is merely read-only — which is exactly why drivers grew `rejectReadOnly` handling, and why the first thing that actually fails is a write, with ERROR 1290 or 1792, not a health check. The JVM's default DNS cache can be infinite for the process lifetime, which is why a short TTL alone does not save you and AWS documents forcing `networkaddress.cache.ttl` to 60 s or less. And a proxy in front does not move existing sessions either — with ProxySQL's `fast_forward=1`, connections keep talking to the old master and hit read-only errors. Four independent ecosystems, one shape.

Then the distractors, each stated as plausible before it is dismissed: raise the pool size (more stale connections, held longer); set `reconnect=true` (reconnects only after something already broke, and stale reads never break); shorten the DNS TTL (does nothing for an established socket, and may do nothing at all against a caching runtime). The fix is three parts together and none of them alone: a **bounded connection lifetime** so no connection outlives a promotion by much, **retry on the right error class** — the read-only write errors, not blanket retry-everything — and a **read/write split** so writes resolve through `-primary` and only reads go to `-replicas`. For obj 5, give the three strategies with an honest selection rule: taint-based, where the `NoExecute` taint from topic 1 evicts the app pod at the demoted site and the restart guarantees a fresh pool (best when the app is co-located with MySQL and restart is cheap); Service-based, where the app stays up and bounded lifetime plus retry carries it across (best when restarts are expensive or the app is not site-pinned); site-local warm standby, where an instance runs at each site and only the one co-located with the current primary takes writes (best when cross-site write latency is the binding constraint). These are architecture choices, not Bloodraven features — say that.

Close on measurement. State explicitly that **no wall-clock recovery number is quotable here**. It depends on pool configuration, driver behaviour and DNS caching, none of which Bloodraven controls, so any number this course gave you would be a number about someone else's application. You measure your own write-gap. That is the unit project, and this paragraph should point straight at it. Do NOT cover planned failover mechanics (topic 3) or Dragonfly (topic 4).

Then the three-step mechanism in the order given, the `KillAppConnections` limits with the objection pre-empted, the three drain behaviours (planned drains ahead of the switch; emergency retries inside `spec.connectionDrainTimeout` while the site answers; a sidecar self-fence does not retry), the version-appendix pointer for the issue state, the missing alert, the four external corroborations, the three distractors, the three-part fix, the three strategies with a selection rule, and the closing measurement argument pointing at the project. - FLASHCARDS: Selector flip affects new connections only; `super_read_only` closes no sockets; stale reads persist until next promotion or demotion; `KillAppConnections` is best-effort and bounded by `spec.connectionDrainTimeout`, and every pass needs a reachable old primary; which of the three paths actually drains; only planned failover drains ahead of the switch; `BloodravenFailoverOccurred` is informational and operator-scoped; validation query passes against a demoted primary; ERROR 1290/1792; `rejectReadOnly`; JVM DNS cache; the three-part fix. 12 cards.
- QUIZ: 5 questions on discriminations that matter on call — whether a successful `SELECT` proves you are talking to the primary; why a pool health check did not catch this; when `KillAppConnections` runs and when it cannot; which of raising pool size, `reconnect=true`, shortening TTL, or bounding connection lifetime actually shortens the stale-read window; and which failover strategy fits a described application (co-located and cheap to restart vs. long-running and site-independent).

## Handoff

**Inherits:** The learner knows every surface Bloodraven moves on a promotion — selector, A record, taint — and that the application was still reading from the demoted site.
**Leaves:** The learner can explain the stale-read mechanism from first principles, name Bloodraven's one mitigation and its limits, choose a strategy, and state the three-part pool fix. The Unit 3 wall is resolved.
**Do not cover:** Planned failover phases, the lag gate, or rollback (topic 3); Dragonfly, `REPLTAKEOVER`, or `sessionsPreserved` (topic 4); anything about backups (Unit 6).
