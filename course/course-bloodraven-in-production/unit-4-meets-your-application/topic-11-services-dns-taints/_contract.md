# Services, DNS steering, and taints

**Unit:** 4 — Where failover meets your application
**Objectives (unit-numbered):**
1. Choose which of the four Service kinds an application should use for writes, for reads, and never   [obj 1]
2. Follow a `DNSEndpoint` CR out to an external-dns record and say what TTL costs you   [obj 2]
3. Explain what the `db-readonly` NoExecute taint evicts and why that is part of failover   [obj 3]

## Topic generation prompt

Open exactly where Unit 3 left the learner: `orders` has failed over, the RPO has been audited, the promotion was correct — and the counter application is still quietly reading from the demoted site. Name that as the open question in one or two sentences, say that topic 2 answers it, and then move on. This topic is the inventory: everything Bloodraven moves on a promotion, and nothing more.

Start with Services. There are four *kinds* per group and the object count is `2 × len(sites) + 2`, so eight objects for the three-site `orders` — per-site, internal per-site, `-primary`, `-replicas`. Be precise about which an application may touch: `-primary` for writes, `-replicas` for reads, the internal per-site Service never (it exists for sidecar and peer traffic). Give the real selectors: `-primary` is two labels — instance plus `role=primary`, with no `healthy` key and `PublishNotReadyAddresses` false; `-replicas` is three — instance, `role=replica`, `healthy=yes`. Then the reader endpoint's five conjuncts, all of which must hold before a site appears behind `-replicas`: converged source, replicating, non-nil lag, canonical direct source host, and lag within `EffectiveReadOnlyMaxLagSeconds()`. Land two consequences the learner should be able to derive: a pod stamped `role = "fenced"` by in-place restore or planned failover matches *neither* selector, which is what fencing looks like at the Service layer; and invalid or incomplete authority deliberately leaves every site non-primary and every reader non-serving, shedding every endpoint rather than serving stale ones. Shedding endpoints is a design choice, not a bug — say so plainly.

Then DNS. The operator writes one object: kind `DNSEndpoint`, apiVersion `externaldns.k8s.io/v1alpha1`, named `bloodraven-<group>`, always an `A` record, with `recordTTL` from `spec.dns.ttl` (default 60). Teach the write model precisely, because it surprises people: there is **no** create/update split. It is an idempotent server-side apply on **every poll**, with field ownership forced, and the desired target is always re-derived from live topology — which means a write that a webhook or an RBAC denial rejects self-heals on the next poll without anyone intervening. Note that `v1alpha1` is still the current external-dns API, and that an approved proposal targets `v1beta1` with no date attached, so plan for the group version to move eventually. Then the hard boundary: propagation is external-dns's job and **the operator cannot accelerate DNS propagation**. A stuck external-dns is a write outage after the operator has already logged that it finished. Chaos scenario 38 demonstrates exactly that — the CR promotes correctly while DNS stays stale under an RBAC denial.

Finish with taints. Give the exact key format `shipstream.io/db-readonly-<group>` — so `shipstream.io/db-readonly-orders` for our group — value `"true"`, effect `NoExecute`. Recall from Unit 2 that the taint is a pure function of a per-site transition, not a step in the failover sequence, and that `read-only` role sites are never tainted at all. Then teach what `NoExecute` actually does upstream: pods that do not tolerate the taint are evicted immediately, and pods that tolerate it with a `tolerationSeconds` stay bound for that long before the node lifecycle controller evicts them. Say why that belongs to failover: an application pod pinned to the demoted site gets removed rather than left pointing at a read-only MySQL, and a restarted pod comes back with a fresh connection pool. Chaos scenario 21 verifies the whole chain end to end — a non-tolerating canary on the old primary's node is evicted, while a canary tolerating the same taint stays Running. Do NOT cover connection pools, pool lifetime, retry classes, or why an established session survives all three of these mechanisms — that is topic 2 and it is the point of the unit.
