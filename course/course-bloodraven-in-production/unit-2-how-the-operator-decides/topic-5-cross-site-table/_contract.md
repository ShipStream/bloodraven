# The six-row table that decides everything

**Unit:** 2 — How the operator decides
**Objectives (unit-numbered):**
4. Turn any set of site states into the operator's action using the cross-site evaluation table   [obj 4]
5. Say why all-read-only and all-unreachable get an alert and no automatic action   [obj 5]
6. Predict what happens when a non-promotable reader turns up writable   [obj 6]

## Topic generation prompt

This is the load-bearing topic of the unit: `EvalCrossSite` takes the per-site states from topic 1 and returns one action, and everything visible about `playground` — the condition reason, the alert, the promotion — falls out of it. Teach the rows **in evaluation order**, because order is the whole behaviour. First, the fence-first early return: if any site is writable but not `primary-candidate`, the function fills `FenceSites`, sets `Reason = "Degraded"` with the alert `writable non-promotable site requires fencing (…)`, and **returns immediately** — it preempts split brain, failover, everything below. Then `TotalLoss` when `len(unreachable) == coreCount`. Then `SplitBrain`, which is strictly `len(writable) > 1` among core sites. Then the failover row, which needs three conjuncts at once — zero writable **and** at least one unreachable **and** at least one read-only — because without an unreachable peer the operator refuses to auto-elect at all: all-read-only is a startup or recovery state that needs human input, by explicit design. Then `NoPrimary`, with its two-site-specific message `NO PRIMARY: both sites are read-only` versus the general `NO PRIMARY: no writable site available`. Then the row the published docs table omits entirely: **Degraded with the primary up and a peer down** — one writable, one or more unreachable, alert `<site> unreachable while <site> is primary`. Then `Healthy`. Make the two documentation defects the topic's sharpest teaching point: the docs' table is missing both the Degraded primary-up-peer-down row and the fence-first return, and the docs call one outcome "Failover" while the code emits `Reason = "Degraded"` — so an alerting rule matching on a `Failover` reason will never fire, ever. The five reason strings that actually reach `status.conditions` are `Healthy`, `Degraded`, `SplitBrain`, `NoPrimary`, `TotalLoss`. Add three structural facts: `EvalCrossSite` is pure — it never consults history or policy beyond the supplied priorities, so split-brain auto-resolution is layered on by the caller; the matrix is evaluated on **every** poll so status always carries the current condition, while mutating cross-site actions stay transition-driven; and `role: read-only` sites are excluded from `coreCount` and all three tallies, but `dr-only` sites are **not** excluded — a common and expensive misreading. Finally, when the table does select a failover, name the selector: `pickFreshestCandidate` makes GTID freshness the primary selector to minimise data loss, and `sitePriorities` is only the tiebreaker for ties or incomparable sets. Do NOT cover the anti-flap cooldown or failover history (topic 3), and do NOT teach split-brain resolution tiers or `ResolveSplitBrain` — Unit 5 owns those.

## Requested activities

- READ: 1000-1200 words. The rows in evaluation order with their exact conditions and reason strings, the fence-first preemption, the refusal to elect from all-read-only, the missing-row and wrong-reason documentation defects stated plainly, purity and every-poll evaluation, `coreCount` exclusion for readers but not `dr-only`, and GTID-freshness-first promotion selection. Work at least two examples against `playground` end to end. One `order` widget requiring the learner to place the rows in the sequence the code evaluates them (fence-first, TotalLoss, SplitBrain, Failover, NoPrimary, Degraded, Healthy). One `match` widget pairing site-state sets with the emitted `Reason` string.
- FLASHCARDS: 10-12 cards. Each row's trigger condition and its `Reason`; the three-conjunct failover condition; strictly-more-than-one-writable for split brain; the fence-first preemption; the five real reason strings; readers excluded from `coreCount` and `dr-only` not; GTID freshness before `sitePriorities`.
- QUIZ: 6 questions. Tested discriminations: two writable sites where one is a reader (fence-first, not split brain); zero writable with two read-only and no unreachable (refuses to elect, `NoPrimary`) versus zero writable with one read-only and one unreachable (failover); one writable plus one unreachable, and what `Reason` reaches the status — with `Failover` offered as a distractor; whether a `dr-only` site counts toward `coreCount`; whether `sitePriorities` overrides a fresher GTID set.

## Handoff

**Inherits:** The learner can turn probe results into per-site states and time the transitions.
**Leaves:** The learner can read a set of site states and name the action, the alert and the `Reason` string the operator will produce.
**Do not cover:** Cooldown, failover history, the re-assert exception (topic 3), split-brain resolution tiers and `sitePriorities` mechanics (Unit 5), the failover sequence itself (Unit 3).
