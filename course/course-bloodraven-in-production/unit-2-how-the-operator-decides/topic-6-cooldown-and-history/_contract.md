# Cooldown, history, and the one exception

**Unit:** 2 — How the operator decides
**Objectives (unit-numbered):**
7. Say what `failoverCooldown` suppresses and, more importantly, what it does not   [obj 7]
8. Find `lastFailover` in both places the operator writes it and say why there are two   [obj 8]
9. Name the conditions that let the operator re-assert a fenced promoted primary instead of alerting   [obj 9]

## Topic generation prompt

The table from topic 2 says what should happen; this topic covers the memory that decides whether it is allowed to happen again. Teach `spec.failoverCooldown`, default `5m`, and be exact about where it bites: one guard, immediately before promotion — if `lastFailover` is non-zero and `clock.Since(lastFailover) < failoverCooldown`, the operator logs `failover blocked by anti-flap cooldown` with fields `lastFailover` and `cooldown`, and returns. That is the *only* thing it gates. Then teach the list of what it does **not** suppress, because this is where operators build wrong mental models: split-brain fencing, non-promotable fencing, source convergence, old-primary recovery, reclone, and DNS reconcile all run on their own poll call sites and none of them consults the cooldown. Add the sharp edge: the **ordered-update handoff promotion is not cooldown-gated at all**, yet it still calls `recordFailover` and increments `bloodraven_failovers_total` — so a failover counter can move during a rolling update while the cooldown was never consulted. Then the history. `lastFailover` and `lastFailoverTarget` are written to two durable places: the CR **status subresource**, and object **annotations** `bloodraven.shipstream.io/last-failover` and `bloodraven.shipstream.io/last-failover-target`, at RFC3339 second precision, written as a pair by JSON merge patch. Teach why the duplication is deliberate rather than sloppy: status is a subresource, so writes travel a separate API path with their own RBAC rule (`mysqlfailovergroups/status`) and admission chain — one path can be denied or broken while the other still records the fact. On restart the operator rehydrates by taking the **later** of the two copies, guarded by `FailoverClockSkewGrace = 5 * time.Minute` against a future-dated clock, with ties going to status. Then the exception: the operator may **re-assert a fenced promoted primary** rather than sitting on a `NoPrimary` alert. Give the preconditions as a checklist — no subsystem gate active (bootstrap blocking cross-site, ordered update, topology frozen, planned failover in flight), the re-assert rate limit satisfied, every non-target peer read-only, the target read-only **and** promotable, and the target's GTID set containing both the recorded promotion GTID and every peer's GTID. Teach the refusal case explicitly: if the recorded promotion GTID fails to parse, the operator refuses rather than skipping the gate, warning `primary re-assert refused: recorded promotion GTID set failed to parse — status corrupted or manually edited?`. Quote the success log verbatim: `re-asserting fenced promoted primary: no site is writable and the last failover target is GTID-complete; restoring writability` with field `site`, and name its metric `bloodraven_primary_reassert_total{site}`. Close on the timing consequence that surprises people: the re-assert rate limit uses a **separate** timer (`lastReassert`) that is never compared against `lastFailover`, so a re-assert can fire inside the failover cooldown window. Also teach `spec.updateStrategy`: `OrderedUpdate` (the default) leaves existing site Deployments untouched so the runner observes drift and rolls one site at a time, while `Recreate` clears the drift list and patches every site Deployment in one pass. Do NOT cover split brain resolution or `sitePriorities` — Unit 5 owns those.

## Requested activities

- READ: 1000-1200 words. The single cooldown guard and its log line, the six things it does not suppress, the un-gated ordered-update handoff that still increments the counter, the two durable locations with the subresource-RBAC reasoning, rehydration by later-copy with the 5 m skew guard, the re-assert preconditions and the unparseable-GTID refusal, the verbatim re-assert log and metric, the separate timer, and `spec.updateStrategy`. One `compare` widget asking the same three questions of the status copy and the annotation copy: which API path writes it, what RBAC it needs, and which one wins on rehydration. One `anatomy` widget on `bloodraven.shipstream.io/last-failover-target` broken into domain prefix, record noun and target qualifier, with the sibling key named alongside.
- FLASHCARDS: 8-10 cards. `failoverCooldown` default 5m; the one guarded action; three things it does not suppress; the two annotation keys; why status and annotations both exist; `FailoverClockSkewGrace` 5m and the tie rule; the re-assert log msg; `bloodraven_primary_reassert_total`; the separate re-assert timer; `spec.updateStrategy` and what `Recreate` really opts into.
- QUIZ: 5 questions. Tested discriminations: whether split-brain fencing waits for the cooldown (no); whether a failover counter can move without the cooldown being consulted (yes, ordered-update handoff); which copy of `lastFailover` wins after a restart when the two disagree; what happens when the recorded promotion GTID cannot be parsed (refuse, not skip); whether a re-assert can occur two minutes after a failover with a 5 m cooldown (yes, separate timer).
