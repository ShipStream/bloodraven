# Reading the operator's mind from logs and metrics

**Unit:** 2 — How the operator decides
**Objectives (unit-numbered):**
10. Follow one poll cycle through the structured log using the documented `msg` strings   [obj 10]
11. Read `bloodraven_site_state`, `bloodraven_replication_lag_seconds` and `bloodraven_state_transitions_total` and say what the group is doing   [obj 11]
12. Tell a lagging replica apart from a lagging reader in the same metric   [obj 12]

## Topic generation prompt

The learner can now run the table in their head; this topic makes them read it back off a live `playground`. Teach the structured log as an interface, not as debug output: `msg` strings and field names are a stability contract that downstream log pipelines filter on, which is why they are versioned in `docs/docs/log-schema.mdx` and why changing one is a breaking change. Anchor on the transition event — INFO `state transition` with fields `site`, `from`, `to`, `fg` — paired one-for-one with the counter `bloodraven_state_transitions_total{site, from, to}`, and note that transitions are deliberately not turned into Kubernetes events because they are too noisy. Then teach the metrics, using only these real names: `bloodraven_site_state{site, state}` as a state-set where the current state is 1 and the others are 0, with the state label one of `writable`, `read-only`, `unreachable`, `unknown`; `bloodraven_replication_lag_seconds{site}`, set only for replicating sites and **-1 when lag is NULL, meaning not replicating** — a distinction that matters more than any threshold; `bloodraven_state_transitions_total`; `bloodraven_failovers_total`; `bloodraven_poll_latency_seconds`; `bloodraven_divergent_transactions`; and `bloodraven_primary_reassert_total`. For objective 12, be concrete: `bloodraven_replication_lag_seconds` carries only a `site` label, so telling a lagging replica from a lagging reader is a join against role — the reader is the `role: read-only` site, it is excluded from `coreCount` and can never be promoted, its lag is judged against `readOnlyMaxLagSeconds` (which has no default and inherits `maxLagSeconds` when nil, but where an explicit `0` genuinely means zero reported lag) rather than the group's `maxLagSeconds` (default 300), and reader lag degrades reader endpoint eligibility rather than the group's health. The centrepiece of this topic is a **forensics exercise** built from issue #93. Present it as a puzzle before the answer: under a deny-all NetworkPolicy the operator reported `activeSite=iad`, `state=writable` and `Ready=True` for two minutes, while the sidecar at `iad` had already self-fenced. Give the learner the dashboard reading and the `bloodraven_poll_latency_seconds` series and ask what broke. The answer: `Poll()` froze on a hung MySQL read, because `database/sql` context cancellation does not reliably abort a read parked on a blackholed socket, and `Poll` waits on every site — so a frozen probe freezes the whole loop, and a frozen loop reports the last state it knew, forever, with full confidence. Include the wrong first diagnosis as its own lesson: the maintainers initially blamed conntrack and reached for `SetConnMaxLifetime(10s)`, which could not help, because a connection parked in a blocked read is never returned to the pool and therefore never recycled. State clearly and up front that this is a **captured case study, not something to reproduce**: it needs Calico, and it is masked on k3d with kube-router, which flushes conntrack on policy change. Do NOT write alerting rules, thresholds, or PrometheusRule YAML — Unit 6 owns alerting.

## Requested activities

- READ: 1000-1200 words. Logs as a stability contract, one poll cycle traced through its `msg` strings, the seven named metrics with their labels and meanings, the -1 lag sentinel, the replica-versus-reader discrimination via role and `readOnlyMaxLagSeconds`, then the issue #93 forensics exercise presented puzzle-first with the wrong-diagnosis coda and the do-not-reproduce warning. One `terminal` widget on a poll-cycle log excerpt whose next line the learner predicts before revealing. Optionally one `anatomy` widget on the series `bloodraven_site_state{site="iad",state="writable"}` broken into metric name, site label and state label.
- FLASHCARDS: 8-10 cards. The `state transition` msg and its four fields; the seven metric names and what each measures; the state-set encoding of `bloodraven_site_state`; the -1 sentinel on `bloodraven_replication_lag_seconds`; `readOnlyMaxLagSeconds` inheriting `maxLagSeconds` when nil but meaningful at `0`; why log `msg` strings are a contract.
- QUIZ: 5 questions. Tested discriminations: reading a `bloodraven_site_state` state-set to name the current state; `-1` lag versus `0` lag; which site a lag series belongs to when only the `site` label is present and one site is a reader; what a flat `bloodraven_state_transitions_total` plus a rising `bloodraven_poll_latency_seconds` implies; and, from the #93 artefacts, why `SetConnMaxLifetime` was not the fix.

## Handoff

**Inherits:** The learner can predict the operator's decision from site states and say whether cooldown will let it run.
**Leaves:** The learner can watch `playground` decide in real time — the transition log, the state-set gauges, the transition counter — and can tell a genuine reading from a frozen one. Everything is now in place to stop predicting and start measuring: Unit 3 holds a site down for real and puts a clock on the result.
**Do not cover:** Alerting rules, thresholds or PrometheusRule YAML (Unit 6); the failover sequence and its measured timings (Unit 3); dashboards as a product surface.
